## The pass line (`make bench-passline`)

The goal: rivus analyses a real product with the default flags, in a realistic time and memory, with a meaningful result. One line per target (bench/deps_bench.py; the targets, the pinned commits and the limits are data in bench/deps-targets.json):

`PASS|PASS(余裕不足)|FAIL memos-4gib time=<s>/<limit> mem=<GiB>/<cap> converged=<yes|no> finish=<yes|no> detected=<yes|no|n/a> quiet_after_fix=<yes|no|n/a> located=<n>`

The pass line is two separate conditions, and PASS needs both (decided 2026-11-24). The default flags are used (no `-no-deps`, no `-body-replaced`).

1. **It finishes** (`finish`), for `memos-4gib` (usememos/memos 26.11.2, `00fcd170281a75fc0e95ec4f2f54f43d32fe81bd`, with `-max-memory 4GiB`): it ends by itself within 180 s; the peak memory of the whole process tree (the same-time sum of the footprint on macOS, sampled every 0.5 s; see "Peak memory") stays within 4 GiB (the watchdog stops a run above the cap); and it converges (`converged`; no function stopped on the clock).
2. **It detects** (`detected`): CVE-2025-65799 (path traversal; public, fixed in 0.25.3) is found at the pre-fix commit `1d7efb158045924ab87f58d567bd79cd92edf6af` by place: at least one `path_traversal` finding has its source and its sink at the labelled places of the truth file [bench/memos/truth-1d7efb15.json](memos/truth-1d7efb15.json) (builtin models; `located=<n>` is the number of such findings, information). The truth file is read from the public fix (one file, `server/router/api/v1/attachment_service.go`): 1 source place (the request of `CreateAttachment`, line 51) and 3 sink places (`os.MkdirAll` 416, `os.Create` 419, `os.WriteFile` 426 in `SaveAttachmentBlob`). The lines are those of the pre-fix commit; the same sinks at the fixed commit are 422, 425 and 432 (the fix adds two checks before them), kept in the same file as `fixed_line`. A finding of the same kind at other places does not count. The two conditions are judged apart: `finish` does not use the detection, and the detection is read only from a run that converged.

`-no-deps` also meets the detection (a measured fact, 2026-11-24: memos at the pre-fix commit, `-no-deps`, 3 `path_traversal` findings at the 3 sink places, 5.7 s, 653 MB), so the detection does not depend on the dependencies; "finishes with the dependencies" is the other condition and is the one that the default flags have to meet.

`quiet_after_fix` (no `path_traversal` finding at the fixed commit `5f57f48673e2054f404b2c5b497a8eaa3690591d`) is a separate indicator and is not part of PASS/FAIL: rivus does not yet treat a fix of the kind "validate, then return early" as removing the flow (the declared checks of #169 do not exist yet). The fixed commit is analysed only when the pre-fix commit is detected; otherwise it is `n/a`. For a target with a truth file of the other kind (`through_tp`, dart-pub), `detected` is per vulnerability as below and `quiet_after_fix` is `n/a`. The Dart line is cocoon `app_dart` (below); dart_services (dart-pad `pkgs/dart_services`, `ad668d137e631beeaef3e263054a45696e8d4499`) is a load target, printed as `INFO`.

In the ledger ([heavy-ledger.tsv](heavy-ledger.tsv); `python3 bench/heavy_ledger.py`) the two are separate: `finish` (time, memory, `conv`) and `det`; `result` is PASS when both are yes (or PASS-thin, below).

**The next form of the "after the fix" condition (decided 2026-11-23, changed 2026-11-24 by ADR-122; not in force yet).** The condition above counts findings of the category, which says nothing about whether the finding went away for the right reason. Once the declared checks of issue #169 exist (a rule file declares a check function with `guards:`, and a finding that passes it is stopped, with a record in `suppressions` that names the rule file and the declaration), the detection condition is run with a rule file that declares the check that the fix added, on both commits: before the fix, with that rule, a finding still appears (the check does not exist yet there); after the fix, with that rule, there is no finding, and `suppressions` names the declaration that stopped it. Without the declaration the finding at the fixed commit stays, which is the evidence that the fix is the check. Until that mechanism exists, the line above is the condition, and a result of "no finding after the fix" (`quiet_after_fix`, where the runner has it) is only recorded, not part of PASS or FAIL.

### The memory margin: three states (decided 2026-11-26)

The memory is judged in three states. The margin is the cap of the row (`mem_cap_gb` in `bench/deps-targets.json`, in GiB) minus the peak of the process tree (`peak_footprint_gb` on macOS, from 2026-11-26; `peak_tree_gb` when `mem_basis` is `rss`; GiB; see "Peak memory" below), taken before rounding: **PASS** when the margin is 0.15 GiB or more; **thin** when it is from 0 up to (not including) 0.15 GiB; **FAIL** when it is below 0. The line itself does not move (A is 4.00 GiB; C, D and cocoon are 8 GiB). A thin row still passes (the exit status is the same as for PASS), but the printed line says `PASS(余裕不足)` and the ledger `result` is `PASS-thin` (an ASCII value for tools; the older rows keep `PASS`). The table of `python3 bench/heavy_ledger.py` shows `result` as written, and `--kind` and `--target` are not affected. 0.15 GiB is about 1.5 times the spread of the ten-odd measurements of the same run (0.05 to 0.1 GiB). Two thin rows in a row for one target make the work of widening the margin come first (docs/WORKFLOW.md). The function is `margin_state` in `bench/deps_bench.py`.

### The two lines of the pass line: A and C (decided 2026-11-24)

The user decided that the pass line is two lines, A and C, for different reasons (each was heavy for a different reason). The memos 8 GB line is not part of the pass line any more (the user decided on 2026-11-25, a decision that reduces the pass line): A is the same target with a stricter memory limit (4 GiB against 8 GB), so the memory and the time of the 8 GB line are contained in A; the detection (`detect`, including `quiet_after_fix`) is the same in both rows of `bench/deps-targets.json`, so A carries it (it was already there; nothing was moved). The target `memos` itself stays (`graph-check`, `--cost-check`); only its row of the pass line is removed, and the past rows of the ledger are not rewritten. Where the text above says "memos" with 180 s and the places of the truth file, it is read as the `memos-4gib` row. The earlier decision "Gitea is not used for the pass line" (2026-11-21) is replaced by this one: Gitea is fetched and run as a target of the pass line. Periodic runs and exploration on it are a separate decision. The result of each is in the ledger (`python3 bench/heavy_ledger.py --kind passline --target <name>`); no number is copied here.

The rows of the pass line (the target, its commit, its flags, the time and the memory limit) are not copied here: `make docs-gen WHAT=passline` prints them from `bench/deps-targets.json` (the targets that have `pass_line`), and `TestDocsSync` (`cmd/rivus`) holds that every such target is named in this file. The conditions besides the limits: A is converged and detected (CVE-2025-65799, by place, in the verdict), with `-max-memory 4GiB`, the default limit of a machine with 16 GB of physical memory (ADR-121: the same conditions as that machine); C is converged, and `detected=<n>/3` is printed but is **not** part of PASS/FAIL (and will not be: it is for reference); the time limit of C has its own ground (the limit of the earlier runs), because the 180 s of memos has none for Gitea.

The detection of C is per published vulnerability of [gitea-cve-truth.json](gitea-cve-truth.json), judged by place (the form of `bench/score.py`). C was added for its size, so the detection is not in the verdict, now or later: it is printed for reference only. A regression of a memory change is checked by the sameness of the graph representation, not by the count. The line and the ledger row of C carry the count `n/3` only: no count of findings, no list, no path, no place. `bench/deps-targets.json` has both targets; the runner reads `detect.mode` `score` (the field `vuln` of the truth file groups the entries of one vulnerability). `gitea` is not in the default `TARGETS` of `make bench-passline` (it takes up to 10 minutes): `make bench-passline TARGETS=gitea`. The time limit is kept by the watchdog of the runner; rivus is not given `-timeout` (its default is no limit), so a run that is cut at the limit is `stopped_time` and not a run that did not converge. The fetch (`git clone`, `git worktree`, `go mod download` into `~/.cache/rivus-bench`) never runs a script or `go generate` of the fetched code. Run it with the heavy-work lock, not at the same time as another heavy run.

### The cocoon target

The Dart target of the pass line is flutter/cocoon `app_dart` (`ae9eb1beaf765d644cc85dde38def030c80b4b7d`). Launch: cwd = `app_dart`, `-allow-deps-under <cocoon>/packages`, `dart pub get` only, the Flutter member of the root workspace removed in the copy (all in `bench/deps_bench.py`; data in `bench/deps-targets.json`). The line is the same as for memos (default flags, within 180 s and 8 GB, converged). `detected=n/a`: the project has no public security advisory, so no pre-fix / fixed pair. dart_services is pass line D (below; also a target of the depth experiments).

Pass line D: dart_services (user decision, 2026-11-24; dart-lang/dart-pad `pkgs/dart_services` at `ad668d137e631beeaef3e263054a45696e8d4499`, default flags). Conditions: converged, tree-total peak within 8 GB, time within 600 s (the same reason as Gitea in C: the 180 s had no ground). `detected=n/a` (no public vulnerability; not part of PASS/FAIL). `decided` is true. It takes up to 10 minutes, so it is not in the default of `make bench-passline`; select it with `TARGETS=dart_services`. Its preparation stays inside the approved bounded run (a pinned commit; git clone and checkout only; `dart pub get` of the pinned tree, as for cocoon; the code of the target is never run; one run of up to 10 minutes). The versions of the dependencies are pinned in the repository: `bench/dart-services/pubspec.lock` is the `pubspec.lock` resolved on 2026-11-22 (dart-pad has no committed lock at that commit), and `prepare` copies it to the root of the tree before `dart pub get`, so a pub.dev update does not move the result of D. `dart pub get` is not `--offline` in `prepare` of `bench/deps_bench.py`: it fetches the packages named by the pinned tree from the package registry, or reads the existing cache. The result is the newest `dart_services` row of the ledger (`python3 bench/heavy_ledger.py --target dart_services --last 1`); it is not copied here. A one-time investigation run may use a larger cap (10 GB); that value is not the pass line. See `docs/ROADMAP.md` section 3.

### Pass line rustypaste: the Rust row (decided 2026-11-26, from INFO)

rustypaste (orhun/rustypaste `00292076e47b5f500906a97a1b5c17665270d907`, a real application with dependencies: actix; default flags besides `-timeout 600s`). Conditions: converged, the whole run (fetch, the build of the project under the sandbox, the extractor, the analysis) within 150 s, and the footprint of the process tree within 8 GiB (`margin_state`: three states, margin 0.15 GiB, unchanged). `detected` (CVE-2026-90774, by place) and `quiet_after_fix` are printed and recorded, not judged (`detect_in_verdict: false` in the data): the reference only, as for C. `scc_coarsened=1` is known (ADR-124: the component of 7,492 functions made by actix is over the safety net of 5,500) and is not a finding on the quality; `expect_coarsened` is 1 so that the row fails when this stops being so, as for D. `decided` is true, so the row is PASS/FAIL, and it is in the weekly run; it is not in the default `TARGETS` (name it: `make bench-passline TARGETS=rustypaste`).

The time limit (decided 2026-11-26) is 150 s, from three runs of that date, one after another, on the footprint basis (the ledger rows at that date, `python3 bench/heavy_ledger.py --target rustypaste --last 3`; no number is copied here). A run with `-v` gives the breakdown: the load phase, which holds the fetch (`cargo fetch --locked`) and the build and extraction under the sandbox, is about 90 % of the wall; sites, graph and taint together are about 10 %. The limit is about 1.55 times the largest wall of the three. For the other rows it is about 3.8 times (A, cocoon), 4.6 times (C) and 1.65 times (D); rustypaste is of the D kind, a limit near the measured value, because the part that moves most is the fetch and the build of one fixed project, and the analysis is stable (the three walls differ by about 2 s). The value is in the range of 120 to 150 s that was asked for, at its upper end, because the fetch is network I/O: a run with an empty data directory (the first one) takes longer and is not the number of this row. Memory: the margin to the 8 GiB is about 3 GiB in the three runs (state `pass`); the RSS sum (`peak_tree_gb`) is kept as a reference. A run with an empty data directory (a cold fetch; one run, 2026-11-26) fitted in the limit: the load phase was about 5 s longer than a warm one (an estimate from the difference of `load` in `-v`, which does not print the fetch alone; one measurement, and it moves with the speed of the network). 定期の実行で、時間の上限(150 秒)を超えたときは、一度だけ再実行して、`load` の内訳(`-v`)で、取得のネットワークの揺れか、rivus の処理の遅さかを見る。再実行でも超えたら、`FAIL` として扱う。 The build of the extractor (`rivus setup rust`, the toolchain, about 1 GB) is not in the time of the verdict: `bench/deps_bench.py` never runs `rivus setup rust` and only reads the toolchain and the extractor that were prepared before (`RIVUS_RUST_TOOLCHAIN_DIR`, `RIVUS_RUST_EXTRACTOR`, or the pinned nightly under `~/.rustup` and `extractor/rust/target/debug/rivus-rust`); it stops with an error when they are not there. So the extractor has to be built before the run. All three: converged, detected yes, quiet_after_fix no, `scc_coarsened=1`.

### Detection: the line is per vulnerability, the detail is per position

`detected` counts per vulnerability, as for memos (which labels the source and the sink places; dart-pub labels the call sites a finding passes through): `yes` when at least one finding passes through a labelled position of that vulnerability's truth (builtin models, default flags). The position-level count is printed beside it as information: `through_tp=<n>/<N>`. The Dart target `dart-pub` (dart-lang/pub `5e24336e71a05a96b558d496953ebed223f6e40a`; one public fixed vulnerability, the zip slip of `extractTarGz`, 9 labelled call sites; `bench/dart-pub`) is printed as INFO (its line is not decided). `bench/score.py --through` gives the same position count from a saved result.

### Peak memory: what is measured how

The memory has two records (`bench/deps_bench.py`). (a) the end-of-run peak of the main process (`ru_maxrss` of the child from `wait4`: the largest single process of its subtree; bytes on macOS). (b) the whole PROCESS TREE: the maximum over fine samples of the SAME-TIME SUM, over all its processes, of the memory; the biggest process of the tree at that moment and when are kept, so that a large (a)/(b) difference can be explained. The verdict (PASS/FAIL) uses (b): the burden the machine really receives. The watchdog (the same samples; it kills the group of the run only, above the cap or the time limit) only stops a run early, on the same number as the verdict, so the kill and the verdict cannot disagree (the protection of the machine is the 20 GiB cap of the dependency benches and the time limit).

What the memory of (b) is changed on 2026-11-26 (decided by the user): from the sum of the RSS to the **footprint** (macOS `footprint`). The reason: macOS keeps counting in the RSS the pages that Go gave back with `MADV_FREE_REUSABLE`, so the RSS peak of C (Gitea) moved by about 0.5 GiB between equal runs (6.59 to 7.09 GiB), while its footprint was 6.01 GiB every time. The tree is found with `ps` (the process, its descendants, the members of its group, so orphans are found), and `footprint -j` is called once per sample for those pids (every 0.5 s; `total footprint`, shared pages once). The RSS sum is taken in the same sample and kept as `peak_tree_gb` (reference). Only the way of measuring changed: the lines (4 GiB for A, 8 GiB for C, D and cocoon) and the three states with the margin of 0.15 GiB are the same. The column `mem_basis` says what a row is: `footprint`, or `rss` (Linux, which has no `footprint` and measures the sum of the RSS from `ps` every 0.25 s as before; or a run where `footprint` failed 3 times in a row: that run is RSS as a whole, never a mix; a call that fails only because a process ended is dropped). The rows before 2026-11-26 are RSS and are not rewritten, so margins across that date are not like for like (bench/heavy-ledger.md).

### Where the numbers are

Every run of `make bench-passline` and `make bench-deps` adds one row to [heavy-ledger.tsv](heavy-ledger.tsv) (the columns, the notes: [heavy-ledger.md](heavy-ledger.md); `python3 bench/heavy_ledger.py` prints it with the margins). A number in a PR or an ADR points to a row (date and commit); it is not copied. `NO_LEDGER=1` adds no row (a binary with a measurement patch, or a run that is not used as a number). `BENCH_OUT` (default `.claude/work/bench-out/`, git-ignored) holds the JSON of the results; the ledger holds numbers only.
