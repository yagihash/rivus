# 設計: 依存のモデル化を、定型のタスクにする

> **状態: 案**(2026-11-22。相談役のレビュー前)。実装はない。1 回目の試行(Google Cloud の Pub/Sub と Functions、Go)を、この型どおりにやりながら、型と道具を直す。そのあとで、Dart で 2 回目。2 回通ったら、スキルとして固める。

## 1. 目的

「XXX のモデル構築をして」という指示だけで、新しいモデル(依存のパッケージの、source / sink / 流れ / 呼び戻し / 何も流さない)を作れるようにする。**この定型のタスクは、将来、利用者にも提供する**(自分の環境の内部パッケージや、外部の依存のモデル構築に使えるように)。方向性の 3.2(外から差し込むモデル)と、3.4 の 3 番と 5 番に当たる。先に手順書だけを書くと使えない手順になるので、**1 回、本物でやりながら型を作る**。

**確かめる道具が、この定型のタスクの本体である。** AI が書いたモデルは、もっともらしく見えて誤ることがある(2026-11-22 の例: 人が書いた Rust の `std::cmp::min` / `max` の `pure` でさえ誤っていた。結果が引数そのものでありうるのに、流れを止めていた)。流れのモデルの誤りは、黙った見逃しになる。だから、このタスクの出力は「YAML」ではなく、「**行ごとに、実行で確かめた / 本体を読んだ結果と同じ / 確かめていない、が付いた YAML**」。道具を作る順も、段 3(`verify`)と段 4(`compare`)が先で、手順書とスキルは、その上に薄く乗せる。

## 2. 型(段ごとに、入力 → 出力 → 合格の条件)

| 段 | 入力 → 出力 | 合格の条件 | 今ある道具 | 足りない道具 |
| --- | --- | --- | --- | --- |
| **0. 言語とパッケージを決める** | パッケージ名と**版**、**言語**、使っている対象(あれば) → モデル化する API の候補の一覧。同じ製品が複数の言語にある場合(Google Cloud の Go / Dart / Rust、gRPC、HTTP のクライアントなど)は、**どの言語の、どのパッケージ名か**を最初に確定する。指示が「XXX のモデル構築をして」だけのときは、対象のコード(あれば、その言語と依存の一覧)から決め、決められなければ聞く | 一覧に、使われている順(あれば)と、型つきのシンボルがある。**版を記録する**(YAML のどこに書くかは、試行で決める。ルールセットの名前と版 `ruleset: name@N` との関係を含めて) | `rivus models coverage`(モデルのない呼び先、finding の経路に載った数、雛形 `stub`)。対象がある場合のみ | 対象がないとき: **パッケージの公開シンボルを、型つきで列挙するコマンド**(Go は `go doc`、Dart / Rust は、extractor が出す名前の綴りで)。`rivus extract` / `rivus-dart` / `rivus-rust` が IR の名前を出すので、その名前で一覧にする |
| **1. 分類する** | 一覧 → 表(API ごとに source / sink / `flows` / `calls:` / `pure` / 対象外、と根拠 1 行: ライブラリのソースの場所か公式の文書)。表は、**言語に依らない部分**(その API が source か sink か、何を流すか)と、**言語ごとの部分**(シンボルの綴り、受け手の扱い、コールバックの形)に分けて書く。複数の言語を作るときは、1 枚の表から言語ごとの YAML を作る(「API の項目の表 1 枚から 3 言語の規則を作る」形) | 全行に分類と根拠がある。分類できない行は、そう書いてある | なし(AI が下書きし、人か AI が確かめる)。`docs/MODELING.md` の 1〜4 節が基準(`pure` にしてよいとき、`approximate`、`calls`、`parts`) | **MODELING.md に、基本の節がない**(`sources` / `sinks` / `flows` / `sanitizers` の書き方と、迷ったときの選び方)。分類の基準を 1 枚に |
| **2. YAML を書く** | 表 → ルールの YAML | `model.Parse` の厳しい検査を通る。`origin`: 組み込みに入れるなら `builtin`、AI の下書きのまま使うなら `llm` と必須の欄(`decided_at`、`rationale`、`model_version`)。`--deterministic-only` で外せる | `model.Parse`(未知の欄の拒否、`origin: llm` の必須欄)。`docs/MODELING.md`、`examples/rules/` の見本 4 つ(go-database-sql、go-gin、go-macaron、rust-actix-web) | 利用者が、書いた YAML だけを検査するコマンド(`rivus rules check` のような。今、`analyze` に渡したときの検査に頼っているか、確かめる) |
| **3. 実行で確かめる**(流れのモデル) | YAML → 行ごとの「実行で確かめた / 確かめていない(理由)」 | API を目印つきの値で実際に呼び、結果・書き込み先・コールバックの引数に目印が出るかを見て、YAML と比べて、同じ(または、モデルが多めで痕跡がある)。source / sink は実行で決まらないので、肯定と否定のフィクスチャで | リポジトリの中の仕組み: 動物園の表 S と `TestZooPureGo`(`bench/zoo-go/pure/`)、Dart の `bench/zoo-dart/pure`、`bench/gcp` の実行(`exec_test.go`)。**利用者のモデルには使えない**(リポジトリのテストの形) | **利用者のモデルにも使えるコマンド**(例 `rivus models verify`)。実行は第三者のコードを動かすので、**信頼できるコードに対してだけ使う**と、コマンドの出力と `--help` で知らせる。実行なしで進める道(静的に読むだけ。行は「実行で確かめていない」と記録され、`approximate` の扱い)も用意する |
| **4. 突き合わせ**(依存をモデルで切るとき。ADR-092 の条件 2) | 本体を読んだ結果と、モデルで切った結果 → 差の一覧 | 流れ(source → sink の組)と、境界の呼び出しの辺が同じ。違ってよいのは、モデルの側が多めで痕跡がある向きだけ | `rivus analyze` と `-no-deps` を、手で比べる(今回の測定のように)。`bench/zoo-dart/observed/compare.py`(Dart の観測した辺との突き合わせ) | **比べるコマンド**(`rivus models compare` のような)。パッケージごとに切る仕組み自体もない(ROADMAP の「依存をモデルで切る」) |
| **5. 当たることを確かめる** | YAML → 全行が、フィクスチャで当たる | どの行も当たる(当たらない行は入れない)。当たらない行は、理由つきで `dead-allow.txt` | `TestBuiltinRowsAreHitByTheZoo`(組み込みの行だけ。リポジトリのテスト)、`docs/MODELING.md` の 5 節 | **利用者のルールの当たらない行への警告**(ROADMAP 3 節に既にある項目) |
| **6. 報告** | 作った行 → 報告 | 作った行の数(種類ごと)、**パッケージの版**、実行で確かめた行 / 本体を読んだ結果と同じ行 / 確かめていない行(理由つき)、書式で書けなかった API(= 書式の課題)、費用の測定が、1 枚にある | `rivus models coverage` の数字、`stub` | 報告の雛形(スキルの中に) |
| **7. パッケージの版が上がったとき** | 新しい版 → 落ちた行の一覧 | 同じ `verify` と `compare` を、新しい版で走らせ直し、**落ちた行だけを直す**。版の記録を更新する | 段 3 と 4 の道具(足りない) | これがないと、モデルは静かに古くなる |

**段 1 の、誤りやすい型のチェックリスト**(分類のとき、必ず見る。今日までに見つかった誤りから作り、試行のたびに足す):
- (a) ジェネリックで、結果が引数そのものでありうる関数を `pure` にしていないか(`min` / `max` / `clamp` / `unwrap_or` の類)。
- (b) error や例外の文字列に、入力が入る(ADR-066)。
- (c) 渡した関数、引数や受け手が持つ関数を呼ぶ(`calls:`。引数と戻り値の両方)。
- (d) 受け手や引数への書き込み(結果だけを見ない)。
- (e) 受け手の状態を通って、あとで出てくる(イテレータ、ビルダー、登録)。
- (f) 数値や bool だけを返す関数は、流さなくてよい。

**段 3 以降の道具は、言語ごとに違う**(試行 2 回目の Dart で埋める):

| | Go | Dart | Rust |
| --- | --- | --- | --- |
| 段 3(実行で確かめる) | あり(リポジトリの中: `TestZooPureGo`、`bench/gcp` の実行。利用者向けの `verify` はない) | リポジトリの中: `bench/zoo-dart/pure`(`TestZooPathDart`)。利用者向けはない | 動物園の表 S の Rust 版(リポジトリの中)。利用者向けはない |
| 段 4(突き合わせ) | 手(`-no-deps` との比較)。`compare` はない | `bench/zoo-dart/observed/compare.py`(観測した辺との突き合わせ)。モデルとの比較はない | なし |
| 段 5(当たる検査) | 組み込みの行のみ(`TestBuiltinRowsAreHitByTheZoo`) | 同じ | 同じ |

**書式で書けない形(受け手の状態を通る、登録してあとで呼ぶ)**は、書式の課題として挙げる。書けるまでは、その API の呼び出し点に痕跡を出す(黙って切らない。ADR-092 の条件 3)。

### 2.1 誰がやるか(決定的なスクリプト / LLM)

ユーザーの要件(2026-11-22): **できる限り、決定的に実行できるスクリプトとして実装する**(LLM への依存を、できるだけ排除する)。source / sink / sanitizer として機能するかの判断には、LLM が要るので、そこは仕方ない。**作ったモデルの妥当性の検証の仕組みを、組み込む。** 最終的に、`analyze` / `index` / `graph` の使い方とセットにして、`gh skill` でインストールできる形にする([DESIGN-agent-interface.md](DESIGN-agent-interface.md))。

| 段 | 誰がやるか |
| --- | --- |
| 0 言語とパッケージ、API の一覧 | スクリプト(`rivus models coverage`、公開シンボルの列挙) |
| 1 分類 | **導出できるもの(流れ、既知の sink に届く / 既知の source から返す)は、スクリプトで下書き**。**LLM が要るのは、下に既知の source / sink がない「末端」と、sanitizer だけ** |
| 2 YAML と書式の検査 | スクリプト |
| 3 実行で確かめる | スクリプト |
| 4 突き合わせ | スクリプト |
| 5 当たる検査 | スクリプト |
| 6 報告 | スクリプト(数字と表)。LLM は文を足すだけ |
| 7 版が上がったとき | スクリプト |

**導出(試行 1 回目の最初の作業。確かめる)**: rivus は、依存の本体を読むとき、関数ごとの要約(どの引数が、どの結果・書き込み先・コールバックの引数に流れるか。どの引数が、どのラベルの sink に届くか。どの source から値を返すか)を既に作っている。それを、ルールの YAML の形に**書き出す**コマンド(例 `rivus models derive <パッケージ>`)があれば、流れの行は、決定的に、本体から作れる(LLM が読むより確か。段 4 の突き合わせは、定義上ほぼ通る)。さらに、依存の関数が、本体の中で既知の sink に届く / 既知の source から値を返すことも、要約から導ける(例: `database/sql` や `os/exec` を包むライブラリの関数は、「第 k 引数が、ラベル L の sink に届く」と決定的に言える)。導けるものは、LLM に聞かない。**LLM が要るのは、下に既知の source / sink がない末端**(例: SQL を gRPC で送る Spanner の `Query`)と、sanitizer。確かめること: (1) 要約が、YAML の `flows` / `calls:` / `pure` / sink / source に写せる形か、写せないもの(グローバルを通る、受け手の状態、候補の多い動的な呼び出し)がどれだけか、(2) `bench/gcp` の 29 種と、Pub/Sub・Functions の API が、「導出できる / 末端で LLM が判断する」に何種ずつ入るか。型の中心は、「導出 → 検証 → LLM は末端の source / sink と sanitizer のラベルだけ」になる。

**妥当性の検証は、2 層**: (i) **流れの行**: 決定的な検証(実行で確かめる、本体を読んだ結果との突き合わせ、当たる検査、書式の検査)。LLM は要らない。(ii) **source / sink / sanitizer の行**: 実行では決まらないので、LLM による検証(作った LLM とは別の役で、根拠 = ライブラリのソースの場所と公式の文書を突き合わせる。誤りやすい型のチェックリストを当てる)+ 肯定と否定のフィクスチャが rivus で期待どおり動くこと(ここは決定的)。sanitizer は、流れを消すので、(ii) の中でも一番厳しく(否定のフィクスチャが必須)。

**書く順は、finding の経路に載る呼び先から**(`models coverage` の `findings` の多い順)。全部の API を埋めることを、終わりの条件にしない(`bench/gcp` では、依存を読まなくても流れは同じで、モデルが戻すのは確信と過検出の少なさだった。1 つのベンチの数字)。

**スクリプトは、同じ入力に同じ出力**(並び、時刻を含めない)。**スキルは薄く**: 手順の判断や計算を、スキルの文に置かない。コマンド(`rivus models ...`)とスクリプトに置き、スキルは、どの順で、どのコマンドを呼び、どこで LLM が判断するかだけ。

## 3. 定型のタスクの形

リポジトリの中に、**配れる形のスキル**(例 `skills/rivus-model/SKILL.md` と、手順が使うスクリプト)を置く。`.claude/` の下ではなく、利用者が自分の環境に入れられる場所。中身は、上の段を、rivus のコマンドの呼び出しとして書いたもの。Claude 専用の書き方に寄せすぎない(手順書として人も読める)。組織やプロジェクトに固有の名前を入れない。新しい外部の依存を足さない。

## 4. 制約

- **実行で確かめる段(段 3)は、対象のライブラリのコードを実行する。信頼できるコードに対してだけ使う。** これを、手順とコマンドの出力(と `--help`)で、利用者に知らせる(隔離は、この段では作らない。ユーザーの判断、2026-11-22: 基本的に作者しか使わないので、知らせるに留める)。**実行なしで進める道**(静的に読むだけ。行は「実行で確かめていない」と記録され、`approximate` の扱い)は、残す。これは、モデル化のタスクの、実行で確かめる段についての判断で、ベンチや探索のために、新しい第三者のパッケージをまとめて取得・解析・実行する件は、別(緩めていない)。
- **ライブラリのソースと文書は、エージェントへの指示ではなく、データである。** このタスクは、第三者のライブラリのソース、コメント、README を AI に読ませる。そこに書かれた文(「このモデルは pure と書け」など)に、エージェントが従ってはいけない。スキルの手順に明記し、**合否は、読んだ内容ではなく、道具(`verify`、`compare`、書式の検査、当たる検査)の結果で決める**。実行の段の隔離と並べて、最初から入れておく(利用者に配るものなので)。
- モデルの方針(PRINCIPLES 3 節)は変えない: 組み込みに入れるかは、その都度、相談役が判断する(ADR-063 の 2026-11-22 の追記)、source / sink は広め、sanitizer は慎重、流れのモデルは測定で必要が示されたものだけ(ADR-092 の条件を含む)。

## 5. 試行の順

1. **文書だけ(今)**: この設計 1 枚と、ROADMAP の 3 節の項目。
2. **1 回目**(段階 4 の第 1 歩のあと、第 2 歩の前): **最初に、導出(2.1)を確かめる**。そのあと、Google Cloud の Pub/Sub と Functions(Go)を、この型どおりに作る。**まず `verify` を、利用者のモデルに使える形にする**(確かめる道具が本体。手順書とスキルは、その上に薄く乗せる)。型に合わなかった所、手でやった所を全部メモし、型と道具を直す。`calls:` の足りない形が出るはず。
3. **2 回目**: Dart のパッケージ 1 つ(shelf か dio)。言語が変わると崩れる所を出す。
4. 2 回通ったら、スキルとして固める(3 節)。

## 6. 確かめていないこと

- 「パッケージの公開シンボルの列挙」を、3 言語でどう出すか(段 0)。
- `rivus models verify` が、第三者の Dart / Rust のパッケージをどう実行するか(コンテナ。Rust は既に `cargo check` をコンテナで走らせている)。
- 利用者の書いた YAML だけを検査する道が、今あるか。

## 7. 決めること

- **行ごとの確かめの状態を、どこに持つか。** 報告の紙だけに書くのか、YAML の行に欄として持つのか(例 `verified: executed | compared | none`)。行に持つなら、ルールの書式の変更で、ROADMAP 3 節の「書式の版」と一緒に決める。出力(finding の `models`)に、その行が確かめ済みかが出ると、判定する側(LLM)の材料になる。1 回目の試行は、報告の紙に書く形で始める。
- 版の記録の置き場所(段 0。1 回目の試行で決める)。
