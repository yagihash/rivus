# ADR-045: 関数値の呼び出しの候補に、sink / source / モデルを適用する（yagihash/rivus #54）

- 状態: 有効
- 関連: DESIGN-callouts
- 状態の詳細: 拡張: 050/068/070
- 要旨: 候補は IR 上で一元決定(`valuecalls`)

**背景:** サイトも、モデルを適用する呼び出しも、呼び出しの静的なシンボルだけで決まっていた。`hd := http.Head; hd(u)` や `var run = exec.Command` は、関数値の呼び出し（`CalleeValue`）で、シンボルがなく、sink にならなかった（不確実性は `unmodeled_library_call`、「no body and no model」）。

**決めたこと:**
1. **候補は IR の上で、1 か所で決める**（`internal/valuecalls`）。サイトの列挙（`rivus sites` / `analyze`）と、解析のグラフ（`sg`）が、同じ候補を見る。結果は `ir.Callee.ValueCands`（ストリームには出さない）。`sg` の中にあった関数値の解決（`resolveValueCalls`）は、これに置き換えた
   - 値がそのまま関数（またはその場で作ったクロージャ。コピーと、関数型から関数型への `convert`（Rust の関数アイテム → 関数ポインタ）を通る）なら、その 1 つ
   - extractor が候補を持つ（Go の VTA）なら、それ
   - それ以外は、コピー・φ・パラメータ（呼び出し側が渡す引数、3 段まで）を通って届く関数。8 個を超えたら解決しない。メモリ（フィールドやリスト）は通らない
   - 本体のない関数も候補に入れる（ルールが名前で適用する）。シンボルは、IR に関数があればそのシンボル、なければ ID
2. **コピー・φ 由来の候補（その関数の中で分岐して届く関数）には、全部の候補にルールとモデルを適用する。** 候補ごとに別のサイトを作る（シンボルが違うので、ID も別）。候補が複数のときは、不確実性 `dynamic_dispatch` を候補つきで残す。候補が 1 つなら、静的な呼び出しと同じ扱い（シンボルで sink / source / モデル。`hd := http.Head; hd(u)`、`var run = exec.Command`）
3. **パラメータ由来の候補は、呼び出し側ごとに解決する。** `func run(f func(string), x string) { f(x) }` の候補は、すべての呼び出し側が渡す関数の和集合（`run(a, x)` と `run(b, y)` なら a と b）で、呼び出し側を区別しない。そこで、ADR-031 の追記（インターフェース呼び出しの候補を、呼び出し元が渡した型で絞る）の `Guard`（`disp`）と同じ仕組みを、関数値に広げた
   - 候補が、その関数のパラメータ p だけを通って届くとき（`ValueCand.Param = p`）、その候補（本体の要約から出る流れ、本体のない候補の sink に届く流れ）に、「p の関数は、この候補」というガードを付ける
   - 呼び出し側は、p に渡す引数が、**その場で決まる関数**（関数、その場で作ったクロージャ、それらのコピーや φ。`sg.ExactFuncs`）で、その中に候補がないなら、この流れを除去する（`feasible`）。a の sink は、`run(a, x)` から入った流れにだけ付き、`run(b, y)` から入った流れには付かない
   - 安全側: 渡す値が分からない（別の関数の戻り値、フィールド、自分のパラメータ）ときは落とさない。見逃しは増えない
   - ガードは、コードの条件ではないので `conditional_nodes` には出さない（`dispatch` ガードと同じ）
   - 関数の中で選んでいる候補（コピー・φ）は、パラメータ由来と混ざっていても、ガードを付けない（常に届く）。複数のパラメータを通る候補も同じ
4. **不確実性の説明:** 候補が分かっている呼び出しでは、シンボルにその候補を載せる。ルールだけで決まる候補（sink / source）は、不確実性を出さない（静的な呼び出しと同じ）。複数の候補のとき、本体のない候補だけが `unmodeled_library_call` で、候補の ID は `dynamic_dispatch` の `candidates` に載る

**限界:**
- 絞れるのは、パラメータに渡す値が、呼び出しのすぐ前で決まっているときだけ。パラメータをさらに別の関数に渡す（`wrapper(g)` → `run(g, x)`）と、内側のガードは、外側の呼び出し元では評価されない（絞らない）。フィールドに入れた関数も同じ（点の解析の問題）
- パラメータ由来で複数の候補があるとき、ルールの **source とモデル**（結果の汚染、サニタイザ、プロパゲータ）には、ガードを付けない（汚染のラベルは要素の流れではなく、セルに直接入る）。候補のどれかに該当するなら、全部の呼び出し側に適用する（過大側）。sink は、ガードで絞る
- 関数値を、フィールドやリストに入れて後から呼ぶ場合は、解決しない（メモリは通らない）。Go は、VTA が持つ候補を使う
- メソッドを関数として取った値（`(*T).M`）は、最初の引数がレシーバとして扱われる（`ValueCand.Recv`）。メソッド値（`x.M`）は、extractor が作る束縛の関数（本体がある）を通る

**検証:** `testdata/go/cases/funcsink`（コピー、グローバル変数、φ、パラメータの a / b、本体のない sink、呼び出し側が分からないとき）、`extractor/dart` と `extractor/rust` のサンプル（変数に入れた sink、パラメータで渡した sink、sink でない関数を渡す経路で出ない）。結果が変わるのは、関数値の呼び出しが sink / source / モデルのある関数に届くとき、と、パラメータ由来の過検出（b の経路から a の sink）が消えるとき。Gogs（2 件）、Gitea の `./modules/...`（5 件）、Dart / Rust のサンプル（足したケースの 2 件ずつだけが増える）、Dart の serverpod / pub、Rust の parseable の IR は、前後の findings が同じ。Gitea の `modules` では、`unmodeled_library_call` が 8 件減った（関数値の呼び出しが、シンボルを持ち、モデルのある関数に達した）。Gitea 全体（`./...`）は、このマシンのメモリ（27 GB のピーク）で終わらず、前後の比較ができていない。
