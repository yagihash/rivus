# ADR-074: sink が、引数の値の「どのフィールドか」を指定できるようにする(`parts`)。細かさが残らないときは、検出して `field_imprecision` を付ける(設計: docs/DESIGN-field-sinks.md)

- 状態: 有効
- 関連: MODELING §4, DESIGN-field-sinks
- 状態の詳細: 084 がサイレントな見逃しを直す
- 要旨: `field_imprecision`

**背景:** sink の書式は、位置(引数 n、レシーバ)までしか指定できず、`checkSink` は、位置の値の下の汚染を、構造を無視して全部見た。要求を構造体で組み立てる API(Google Cloud のクライアントと、生成された API 全般)では、危険なのは 1 つのフィールド(`SQL`、`Url`)で、同じ値の中の別のフィールド(`Params`、`Body`)は危険でない。全部見ると、別のフィールドだけが汚染された呼び出しで偽陽性になり、sink にしなければ見逃しになる。

**決めたこと(案 B: 今ある呼び出しの sink に、アクセスパスを書けるようにする。案 A の「フィールドへの書き込みが sink」は、設計の 10 節の条件が揃うまで作らない):**
1. **書式:** `model.Sink.Parts`(`{arg|recv, field}` の列)と、糖衣(`args: [n]` か `recv: true` と `field`)。`field` は、位置の値から下るフィールド名の列(`.` 区切り、`[]` は要素)。`args` / `recv` に書いた位置は、`parts` があっても全部が勝つ。`parts` があって `args` がないときは、「全部の引数」とは読まない。`parts` のない sink は、今までどおり(既存のルールの結果は変わらない)。
2. **照合:** セルのアクセスパス(位置の値からの残り)から、名前でない段(`*`、`[]`)を飛ばして、`field` の名前の列が、**部分列**として先頭から一致するか(`matchParts`)。下(一致する、または、その下)は、確かな finding。上(値が丸ごと汚染されている、アクセスパスが切れている)は、検出して `field_imprecision`(`why`: `whole_value` / `path_limit` / `element`)。別のフィールドは、一致しない(検出されない)。名前の段は飛ばさない。
3. **モデルも本体もない呼び出し先に渡された値**(`unmodeled`): 渡した値の根を覚える(汚染は足さない。`parts` のない sink と、今の伝播は変わらない)。`parts` の sink が、その根の下の汚染を見つけたら、アクセスパスに一致しなくても、検出して `field_imprecision`(`why`: `opaque_callee`)。今の既定の伝播は、引数の中を混ぜない(結果にだけ流す)ことを、段階 0 で確かめた。
4. **綴りの誤り(永久にサイレントな見逃し):** `field` の名前が、解析した IR のどの命令のフィールド名にも出ないとき、その sink は、その site で `parts` なし(全部)として扱い、`field_unresolved`(プログラム全体の不確実性と、finding の経路)を出す。**型の鎖の検査は、IR に構造体の定義(フィールド名と型)がないのでできない**(3 言語とも。`ir.TypeInfo` は `supers` だけ)。IR に足すのは、3 つの抽出器と書式の変更なので、別の設計。かわりに、死んだ行のゲートを `parts` のアクセスパスの単位に広げた(`TestZooFieldSinkRowsAreHit`: zoo のルールの `parts` の各行は、アクセスパスが「下」で一致する finding を持たなければ失敗。アクセスパスが `K` を超える行は、理由つきの一覧)。
5. **要約(`SinkReach`):** 要約の中では、呼び出し元のアクセスパス(`*` の段)を知らないので、`parts` の照合は、呼び出し元の実引数のセルに対して行う。`SinkReach` に、まだ照合していない残りの名前(`Field`)と、不確実のマーク(`Unsure`)を足した。`expandParam` は、`parts` のある到達では、同じ要素を 1 つにまとめない(同じ要素が、フィールドの中と、別のフィールドにある形を区別するため)。**マークは、キー(`sinkKey`)に入れて、確かな到達と不確実な到達を別々に持つ**(OR で 1 つにすると、確かな到達があるのに不確実と報告する誤った uncertainty になる)。finding(`recordFinding`)は、**確かな経路があれば、確かが勝つ**(不確実性は、確かな経路がないときだけ)。`signature` と `joinSummaries` の比較に `Field` とマークを入れた。
6. **`literal_only`:** `parts` のある sink は、定数だけの引数とは見ない(過検出側)。

**実測(段階 0。何も変えずに測った):** セルのアクセスパスは、ポインタの値そのものには `*` が出ず、ポインタを持つフィールドの先とインターフェースに包んだポインタの先に出る。Cloud Tasks の形(`CreateTask.Task.MessageType.HTTPRequest.URL`)は、設計の見積りの 5 段ではなく **7 段**(`Task`、`*`、`MessageType`、`*`、`HTTPRequest`、`*`、`URL`)で、K = 3 で `/Task/*/MessageType` に切れ、`URL` と `Body` が混ざる。この形は、`field_imprecision`(`path_limit`)で検出され、デコイも検出される(zoo の `conv/struct-field-deep` の `@fp`)。段階 4(`max(K, 道の段数)`)は、測ってから。

**確かめたこと:** zoo の `conv/struct-field-shallow` / `boxed`: デコイ(`Params` だけ汚染される)が検出されなくなった(偽陽性の消える側)。`struct-field-opaque`: `Opaque` が実際に `Params["body"]` を `SQL` に写す(実行で裏付け)脆弱が、`opaque_callee` つきで検出される。`testdata/go/cases/fieldsink`: 1 関数、別の関数を挟む(2 段)、丸ごとのコピー、ラッパー、丸ごと汚染された値(`NewReq` の `flows`)、確かな到達が不確実な到達に勝つ(同じ関数内と、要約を通して)、綴りの誤り、プロジェクトのインターフェースの裏の実装(ADR-068)、レシーバ。**見逃しの形(丸ごと、k で切れた、要素、モデルのない関数)は、すべて検出される。**

**限界:** アクセスパスの名前の検査は、「プログラムのどこかで使われているか」まで(型の鎖ではない)。`flows` の `to:` にアクセスパスがまだ書けないので、フィールドを公開しない生成コード(Opaque API、ビルダー、セッター)では、`whole_value` で検出されるだけ(段階 5 が前提)。`K` を超える深いアクセスパスは、段階 4 まで `path_limit`。Dart と Rust の `Option` / variant の透過な段は、段階 6。
