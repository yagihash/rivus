# ADR-114: 「プロジェクト」は、パターンで挙げたパッケージだけでなく、同じ module と、-C や -allow-deps-under の下の path 依存を含む(ADR-099 の定義を直す。2026-11-23)

- 状態: 有効
- 関連: ADR-099、README、AGENT-GUIDE、ARCHITECTURE 5.5、課題 #147
- 状態の詳細: 相談役の決定(2026-11-23)。ADR-099 の「プロジェクトの関数」の定義を直す。Go と Dart は実装した。Rust は決めだけで、実装は課題 #147 のあと
- 要旨: 狭めた指定でも、同じ module と path 依存の中の sink と source が列挙される

**背景:** ADR-099 は、source と sink を「プロジェクトの関数」の中だけで列挙し、依存の関数の中では列挙しないと決めた。ところが、プロジェクトの範囲は、実装では「パターンで挙げたパッケージ」(Go)と「`-C` の下のファイル」(Dart)だった。このため、プロジェクトの範囲を狭めて解析したとき(Go で `./cmd/...` や `-C cmd/app`、Dart でモノレポの `-C app`)、同じ module や path 依存の中の自分のコードが、依存として扱われた。その sink と source は列挙されず、`summary.dependency_sites` の数に入っていた。狭める指定が決めるのは、解析の入口と、頼んだ範囲であって、どのコードが利用者のものかではない。

**決めたこと:**
1. **プロジェクトは、利用者が自分のものとして持つコードの全体**。パターン、`-C`、`-allow-deps-under` は、入口と、読んでよい場所を決めるだけで、プロジェクトの外側を作らない。列挙するのは、読み込んだプロジェクトのパッケージの全部。解析の入口(どの関数から追うか)は変えない。
2. **Go:** 次のパッケージがプロジェクト。(a) パターンで挙げたもの、(b) main module のパッケージ(`go.work` があれば、`use` に並ぶ module は、すべて main module で、全部がプロジェクト)、(c) `replace` が**ディレクトリ**を指す module(`replace => ../x`。`go.work` なしでモノレポの module をつなぐ形)。次は依存: module キャッシュの module、`replace` が**バージョン**を指す module(取得したもの)、標準ライブラリ(読まない)、`go.work` に並ばず `replace` もない入れ子の module(`go.mod` が別のもの。取り込まれていなければ、そもそも読み込まれない)。(c) をプロジェクトにする理由: 判定できないときは、見逃しより過剰な列挙を選ぶ。そのほうが軽い誤り(見逃しは出力に出ない。過剰な列挙は、利用者が finding を見て分かる)。取り込んだ第三者のコピーや骨組みが `replace` で置かれている場合は、`-dep-dir DIR`(繰り返せる。`-C` からの相対か絶対)で、その下のパッケージを依存として読ませる。利用者に出す理由: プロジェクトの外の定義は、解析の対象を決める利用者の判断で、製品の意味であり、テストの設定だけに置くと利用者が同じ誤りを直せない。**指定したディレクトリは `summary.dep_dirs` に出る**(指定がなければ項目なし)。パターンで挙げたパッケージは `-dep-dir` で外れない。Dart の `--dep-dir` は extractor の引数で、同じ考え。zoo のテストは、骨組み(`skel`、`bench/zoo-go/dep`、zoo-pkg では zoo 本体)をこれで依存にする(骨組みの置き場を変えない)。列挙の順は、読み込んだパッケージのパスの順に固定する(`go/ssa` は map で持つので、順は走るたびに変わりうる)。標準ライブラリは読まない。
3. **Dart:** `-C` の下のファイルに加えて、`-allow-deps-under` の下にあるパッケージのファイル(`path:` 依存と、`workspace:` のメンバー)がプロジェクト。`-allow-deps-under` は、これまで読むかどうかだけを決めていた(読まない依存は `dependency_not_allowed`)。今は、読んだうえで、その下のパッケージを列挙の対象にもする。ただし pub のキャッシュ、SDK、Flutter の下は、`-allow-deps-under` がそれを含んでいても依存のまま(ホームのディレクトリを許可しても、取得した依存がプロジェクトにならない)。ワークスペースのメンバーは、根が `-C` か `-allow-deps-under` の下にあるとき、プロジェクト。
4. **Rust(決めだけ。実装は課題 #147 のあと):** 解析する crate が属する Cargo ワークスペースのメンバー(`cargo metadata` の `workspace_members`)と、ワークスペースの根の下にある path 依存はプロジェクト。レジストリと git の依存は依存。Rust のワークスペースのメンバーは、今はサンドボックスの下で抽出できない(課題 #147)ので、コードは変えず、#147 の実装と一緒に入れる。
5. **時間とメモリ:** 狭めた実行で、列挙の対象と、解析に入る関数が増えることがある(同じ module の、読み込み済みの他のパッケージ)。読み込む量は変わらない(依存の本体は、これまでも読んでいた)。測定(狭めた `./cmd/rivus` で、このリポジトリ自身): CPU 時間(user)77.0 秒 → 79.6 秒(+3%。経過時間は、他の処理との重なりでぶれ、2 回の測定で 19.1 秒 → 17.7 秒と 45 秒 → 64 秒)、メモリの最大 2.74 GB → 2.62 GB、解析の関数 7232 → 7355(+1.7%)。増加は 2 倍に遠く及ばないので、**元の振る舞いに戻すフラグは足さない**(足すと、「プロジェクト」の意味が 2 つになり、見逃しを知らせずに選べる口ができる)。大きなモノレポで増加が実際に問題になったら、その実測を添えて見直す。
6. **出力:** `summary.dependency_sites` の意味は変えない(読んだ依存の関数の数。列挙していない)。同じ module や path 依存の関数は、数に入らなくなる。`schema_version` は変えない。
7. **`-no-deps` と狭めた指定:** 挙げたパッケージの外は読み込まないので、同じ module の読み込まれなかったパッケージは列挙されず、出力もそのことを言わない。ここでは直さない。F-2(読み込まれなかった同じ module のパッケージの数を `summary` に出す)と一緒に扱う。
8. **source の `param_type` の規則:** その型のメソッドのレシーバも、引数として規則に一致し、source になる(go/ssa ではレシーバは引数)。意図した振る舞いで、利用者のプロジェクトでも起きる。zoo の `mark.In.Value` は、同じ module なのでプロジェクトになり、レシーバが source になった。ポインタのレシーバにして避けた。

**ADR-099 との関係:** 「プロジェクトの関数の中だけで列挙し、依存の中では列挙しない」は変えない。変えるのは、「プロジェクト」の範囲(1 から 4)。ADR-099 の状態を「一部覆った」にし、本文は書き換えない。
