# ADR-117: アクセスパスを切った所を通った値の段に、access_path_truncated の注記を付ける(2026-11-23)

- 状態: 有効
- 関連: ADR-008(不確実性の種類)、ADR-014(アクセスパスの深さ)、docs/issues/184(閉じた)、`-dep-k`(実験、PR #302)
- 要旨: 注記は、値が切ったパスを通った**段**にだけ付ける。関数の単位では付けない。要素の同一性には入れない

**背景:** アクセスパスを深さの上限(`-k`、依存の関数は `-dep-k`)で切ると、切った所より下は「まるごと汚染」として扱う(過大近似。別のフィールドへの流れを出すことがある)。これまでは、プログラム全体に 1 件(`depth_limit` の `path_limit:`。関数の一覧つき)の記録しかなく、その関数を通る finding は、確かな流れと同じ `no_uncertainty_on_path` に見えた(課題 #184)。

**経緯(同じ失敗をくり返さないために):**
1. 最初の実装(de98b0e5): 経路の関数のどれかで、パスを切ったことがあれば、finding に注記を付けた(関数の単位)。測ると、実プロジェクト(Go)で 141 件中 139 件に付いた。`no_uncertainty_on_path` と `requires_review` の差が、ほとんどなくなる。
2. 取り消し(b4108c79): 上の理由。深さを下げる実験のフラグ `-dep-k` の PR(#302)には入れなかった。
3. 作り直し(この ADR): 値の単位、段の単位にした。

**決めたこと:**
1. **付ける所**: 切ったパスのセルに値を入れた段(`add` で、パスを切ったとき)と、切ったパスの下を読んだ段(読んだ要素の `found.Cut`)。その段(`why`)の注記として付く。`pointer_alias` と同じ形で、finding の経路にその段があるときだけ finding に出る。経路の関数に切った所があるだけでは付かない。
2. **要素の同一性に入れない**: 注記の有無を要素に入れると、同じ要素が「切った」「切らない」で 2 つに分かれて、要約の要素が倍になる。段に付けるので、要約の要素は増えない(Go の gcp、Dart の gcp、AWS SDK のサーバ、Go の実プロジェクトで、前後が同じ。差は、実行ごとのゆれの 1% 以内)。
3. **注記の内容**: どの関数の(プロジェクトか依存か)、どの根の、切ったあとのパス(最初の数段)、元のパスの深さ、使った深さ。1 つの finding に 10 件まで出し、超えた分は件数を 1 件で言う。この情報を使う仕組みは、まだない(出すだけ)。
4. **使った深さを、いつも出す**: `summary.access_path_depth: {project, dependency}`。
5. **付かない所(既知)**: ポインタの位置のパスを切る所(`locs.go`。ループで伸びるパスの打ち切り)。

**測定(`-dep-k 2` の Go の実プロジェクト):** 153 件中 122 件に付く。どれも、もとから `requires_review` で、`confidence` は変わらない(151 件が `requires_review`、2 件が `no_uncertainty_on_path` のまま。2 件には付かない)。付いた所を読むと、`grpc` の `status.New`(`&Status{s: &spb.Status{...}}`、`/s/*/Message` が深さ 2 で切れる)と `pkg/errors.Wrap` の入れ子の構造体など、エラーを作る関数で、ほぼ全部の経路が通る本物の切れ目。Go の gcp(既定)は 27 件中 3 件(spanner のデコーダの `p.row.vals[last]` など、深さ 4 以上)。
**結果として:** 実プロジェクトでは `confidence` の区別は増えない(ほかの不確実性が既に多い)。注記の価値は、`no_uncertainty_on_path` の finding が、切ったパスを通ったかどうかを読めることにある。

**しないこと:** 注記の情報を使って、深さを場所ごとに変えること(課題で別に扱う)。
