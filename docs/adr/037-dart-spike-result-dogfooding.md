# ADR-037: Dart 実現性スパイクの結果と、ドッグフーディング（ステップ 1.12）

- 状態: 有効
- 関連: ARCHITECTURE 10
- 要旨: 実現可能。例外エッジとブロック切り、`finally` は複製

### Dart スパイク（ADR-011）

詳細は `spike/dart-cfg/README.md`(#38 で削除した。git の履歴にある)。捨てコードで、IR を設計する前に 3 つを確かめた。

- **判断: 実現できる。** `package:analyzer`（14.7、Dart 3.13.6）の解決済み AST から、ブリーフが難所とした構文（`async` / `await`、`await for`、`try` / `catch` / `finally`、ラベル付き `break` / `continue`、パターンの `switch`）の CFG を、正しく組める（約 550 行のビルダーと 20 件のテスト）。
  モノレポの複数パッケージにまたがる呼び出しも、生成コード（`part` ファイル）への呼び出しも、宣言に解決できる。アーキテクチャを変える必要は見つからなかった
- **IR の設計に反映する難所（決定したもの）:**
  1. **例外のエッジとブロックの切り方。** 例外のエッジをブロック単位で持つと、ブロックに呼び出しが 2 つあるときや、ハンドラが覆わないコード（`try` 本体の最後の呼び出しの後ろに続く `finally` の複製）で誤る。
     スパイクは最初にこれを誤った。**保護された範囲（`try`）の中では、投げうる呼び出しをブロックの終端にして、例外のエッジと正常な継続のエッジを 1 本ずつ持たせる**（MIR の呼び出しと同じ）。ハンドラが関数内にないときは、例外のエッジを引かない（関数の外へ出る例外は、関数内の流れではない）。
     ARCHITECTURE.md 2.4/2.5 の「呼び出し点に例外エッジを付けられる」は、この形に読み替える
  2. **`finally` の表現（レビュー項目 4 の決定）:** **extractor が、出口ごとにブロックを複製する**。IR に `finally` の概念は不要。テスト関数で 1 つの `finally` が 4 つに複製された。
     複製されたコードは同じソース位置を持つので、**サイトの列挙は、複製を 1 つとして数えなければならない**（そうしないと、サイトの ID（出現順）と指紋（ADR-028）が、出口の数で変わる）。IR の命令は必ずソース位置を持ち、複製であることが分かる必要がある（extractor がマークを付けるか、コアが位置で重複を除く）
  3. 式の中の `&&`、`||`、`?:`、`??`、switch 式は、extractor がブロックに展開し、合流点の値を持つローカル変数を作る（ADR-003 の書き換え可能ローカル変数に合う）
  4. パターンは、型テスト、フィールドの読み出し、束縛に展開する（`type_assert` と `field_load` で足りる）。網羅性は推論せず、「どの case にも一致しない」エッジを残す
  5. `await` はエッジ（決定済み）。`yield` と `Stream` の要素は、関数内の流れではなく、モデルか、生産者と `await for` を結ぶコールグラフが必要
  6. クロージャとローカル関数は別のグラフ。コンストラクタ呼び出しは `InstanceCreationExpression` で、`MethodInvocation` ではない
- **注意:** `package:analyzer` はバージョンごとに API が変わる（14.7 では `ClassDeclaration.name` がなく、引数は封印された `Argument`、`ForPartsWithPattern` がある、要素モデルは v2）。extractor は analyzer のバージョンと SDK のバージョンを固定する
- **調べていないこと:** コールグラフ（`pkg/vm` の type flow analysis）、`dynamic` のレシーバの多さ、大きなプロジェクトの解決の時間とメモリ。Phase 4 の次のリスクはここ

### ドッグフーディング（ステップ 1.12）

rivus 自身を rivus で解析した（`dogfood/rules.yaml`、`cmd/rivus/dogfood_test.go`）。

- **入口の宣言:** 各コマンドの入口関数（`runSites` など）の `args` を、`kind: param` の source として宣言した。`flag` パッケージのモデル（`Parse`、`String`、`StringVar` など）を、組み込みに足した
- **結果:** 818 関数、0.14 秒、1 パスで収束。**30 件の検出**（6 つのコマンドから、`os.ReadFile`、`os.Create`、`os.WriteFile`、`os.MkdirAll` へ）。内容は、CLI として意図した挙動（`-rules`、`-bookmarks`、`-index` で読むファイル、`-o`、`-cpuprofile` で書くファイル）を、事実として捉えたもの。
  不確実性は 446 件（`rivus` 89%、`mixed` 11%）、`depth_limit` は 0.2%
- **ループを回した:** `rivus models coverage` で、検出結果の経路に載っているのに推測だった関数（`(*go/token.File).Name`、`(*go/token.FileSet).File`、`packages.Load`）を見つけ、モデルを書いた（`origin: human`）。
  検出が **36 件 → 30 件**になった。消えたのは、「ファイル名が、位置（数値）から決まる」かのような誤った流れ。残ったのは、パターンが読むファイルを決める、事実としての流れ
- **回帰テスト:** 6 つのコマンドすべてから検出があること、`os.ReadFile` / `os.Create` / `os.WriteFile` に届くこと、入口の宣言（`origin: human`）と `flag` の組み込みモデルが経路に載ること、`File.Name` を通る検出が残っていないこと、収束、`depth_limit` の比率が 5% 未満であること

### 全体の計測表（Phase 1 の最後。Apple Silicon の Mac、Go 1.27.3）

| 対象 | 規模 | 時間 | 収束 | 検出 | 不確実性（`rivus` / `mixed` / `target`） | `depth_limit` |
|---|---|---|---|---|---|---|
| ghmint | 2,783 行 | 約 0.04 秒（ロード別） | ○ | 15 | 170（80% / 20% / 0%） | 0% |
| rivus 自身（dogfood） | 818 関数 | 0.14 秒 | ○ | 30 | 446（89% / 11% / 0%） | 0.2% |
| golang.org/x/tools | 156,429 行、8,101 関数 | 約 107 秒 | ○（2 パス） | 4 | 10,639 | 約 0.02% |

`mixed` と `target` の割り当ての見直し（ステップ 1.12 の約束）は、上の分布から、いまのまま据え置く。`dynamic_dispatch` の候補 0 件を `rivus` にした結果（ADR-032）、`mixed` は約 1 割〜2 割で、中身は候補が 1 件以上の呼び出しと `concurrency`。
これ以上細かく分ける材料は、まだない（Dart のコードで、候補数の分布を取ってから）。

### レビュー結果（Phase 1 完了時、ユーザーの承認）

Phase 1 の最後に挙げた 4 つの判断を、ユーザーが承認した。

1. **定数による特殊化（ADR-035）:** 条件が引数と定数の比較だけでできているとき、起こりえない側の流れを捨てる。「入ることがありえない分岐は見る必要がない」ので、判定ではなく定数の評価として扱い、このまま維持する
2. **性能と引き換えの粗さ（widening、単調な結合、関数ごとの予算、タイムアウト）:** 維持する。粗くなった結果は、必ず `depth_limit` として出力に残す
3. **Dart の `finally` は出口ごとに複製する（ADR-037）:** 維持する。IR の命令にソース位置を必須にし、サイトの列挙では複製を 1 つと数える
4. **候補 0 件の `dynamic_dispatch` は `rivus`（ADR-032）:** 維持する
