# ADR-124: 大きい SCC は、依存の関数を最初から深さ 0 で解く(#187)(2026-11-24)

- 状態: 有効(入口の実装。N の既定は 0 = 無効。N の値と、既定で有効にするかは、測定のあとに決める)
- 関連: ADR-118(規模のための仕組みの 3 条件)、ADR-119(依存のアクセスパスの深さ)、ADR-099(source と sink はプロジェクトの中だけ)、ADR-121(既定の値の選び方の流儀)、課題 #187
- 要旨: エンジンが解く SCC(参照のエッジを含む構成)が、N 関数以上で、依存の関数を含むなら、その SCC の依存の関数だけを、最初から深さ 0(`-dep-k 0` と同じ)で解く。プロジェクトの関数は深さを変えない。判定は、解く前に、コールグラフの構造だけで決める

**背景:** 依存を読むと、大きい SCC(dart_services: 13,983 関数)が、深さ 2 の `param` 出力で、現実の時間で収束しない。測定では、依存の関数を深さ 0 にした実行は、`global` の出力を粗くしなくても収束した。`-dep-k` は全体に一律の調整で、大きい SCC だけを粗くする上限ではない。#187 は、止める上限が流れを落とす課題で、この ADR は最初の入口、「大きい SCC は、流れを落とさずに、粗い形で解く」安全網を足す。

**経緯:** 最初の案は、解いている途中で、要約の鍵の数が予算を超えたら、途中の要約に fold をかける形だった。次の案は、超えたら捨てて最初から解き直す形(1 パス目はその場で、2 パス目以降は解析全体のやり直し)だった。どちらも、判定が解いている途中の状態に依り、捨てる処理(`global` の置き場の後始末、`resetForRestart`)と、2 パス目以降の特別扱いが要った。外部の設計者の助言で、**判定を解く前に移した**。

## 決めたこと(実装済み。内部の切り替えだけ。利用者のフラグは付けない)

1. **判定**(`coarse.go` の `coarsenBySize`): SCC 分解(参照のエッジを含む構成。エンジンが実際に解く SCC)の直後、解く前に、各 SCC について、(a) SCC の関数の数、または (b) その中の依存の関数の数(`SCCCoarsenDeps`)が N 以上で、依存の関数が 1 つ以上あるなら、その SCC の依存の関数にマークを付ける。関数の数はコールグラフだけで決まる。
2. **解き方**: マークのある関数は、最初から、アクセスパスの深さ 0 で解く(`state.k()` が 0 を返す。依存の関数だけ。プロジェクトの関数は元の深さのまま)。何も捨てない。答えは、「その SCC の依存の関数だけ `-dep-k 0` にした解析」と同じ(テストで確認: 要約、`global` の置き場の中身と書いた関数と読む関数、findings、uncertainties、stats のうち作業量でないもの。`global` に書くプロジェクトの関数が SCC に入り、SCC の外の関数が読む形で)。
3. **記録**: SCC ごとに `depth_limit`、detail `scc_coarsened:` の uncertainty を 1 件(`attributable_to: rivus`、`candidates` に依存の関数の一覧。detail に、関数の数、依存の関数の数、パッケージの数、N と数えたもの)。深さ 0 の要約を適用したステップにも、同じ種類のステップの uncertainty(`out_widened` と同じ作り)。`stats.scc_coarsened` に SCC の数。
4. **値**: `Options.SCCCoarsenN`(0 = 無効。**既定は 0**。出力は今と同じ)と、`SCCCoarsenDeps`(数えるものの切り替え)。実行からは、環境変数 `RIVUS_INTERNAL_SCC_COARSEN_N=n`(関数の数)または `n:deps`(依存の関数の数)の 1 つだけ(N を測るための内部の口。`-h` に出さない。ADR-121 と PRINCIPLES の「内部の切り替え」の流儀)。

## 判定を解く前に移した理由

- **順序・マシン・時間切れに依らない**(ADR-118 の (ii))。解いている途中の量(鍵の数)で決めると、`-timeout` や反復の上限(`MaxPasses`)で止まるのが先か、予算に当たるのが先かで、粗くしたかが機械の負荷で変わる。関数の数は、入力だけで決まる。
- **捨てる処理が要らない**。解き直す形は、`global` の置き場、書いた関数、読む関数、記録、統計を、全部、元に戻す必要があり、2 パス目以降は解析全体のやり直しになった。最初から深さ 0 なら、戻すものがない。
- **答えの説明が 1 つで済む**: 「その SCC の依存の関数は、`-dep-k 0`」。

## uncertainty の種類: 新しく足さず、既存の `depth_limit` の detail で言う

`depth_limit` は「解析の上限で、流れの精度を落とした」の種類で、すでに `path_limit`(パスを切った)、`out_limit` と hop の `out_widened`(出力をまとめた)が、同じ形(関数の一覧の記録と、hop の uncertainty)で言う。`scc_coarsened` も同じ意味の延長で、利用者の扱い(その周辺は多めに出る側として読む)が変わらない。`recursion_approximation` は、不動点に届かなかった意味で合わない。新しい kind はスキーマの変更になるので、避けた。

## ADR-118 の 3 条件

- (i) 過大近似の向きだけ: 満たす。深さ 0 は、依存の関数の要素のパスを切るだけで、切った所より下は「まるごと」として扱う(ADR-117、ADR-119)。深さ 0 の答えは、深さ 2 の答えのパスを切ったものを含む(テストで確認: 要素の包含)。
- (ii) 順序・マシンに依らない: 満たす。判定は、コールグラフの SCC の構成と N だけ。時計も、メモリも、解いている途中の量も見ない。`-workers` 1、2、既定で、要約と記録が同じ(テスト)。
- (iii) 出力が言う: 満たす。上の 3。

## ユーザーの承認

- 「大きい SCC は、依存の関数を最初から深さ 0 で解く」形は、外部の設計者の助言で、相談役とユーザーに伝わっている。
- N の値、数えるもの(SCC の関数の数か、依存の関数の数か)、既定で有効にするかは、まだ決めていない(今は無効)。測定(全部の対象で、エンジンが解く SCC の関数の数と、その中の依存の関数の数)のあとに、PRINCIPLES の「既定の値や上限を選ぶとき」に従って決める。他の対象で当たった SCC の数が 0 であることを、合格基準の確認に入れる。dart_services の finding が、どれだけ変わるかは、そのあと、ユーザーに聞く。

## まだ届かないもの(未確認と限界)

- N 未満で、深さ 2 で収束しない SCC は、守られない(N の値の問題。測定で決める)。
- プロジェクトの関数だけの SCC、プロジェクトと依存が混ざる SCC のプロジェクトの関数は、粗くしない。深さ 0 の要素が、プロジェクトの関数の出力の数を増やすかは、測っていない。#187 の残りの項目。
- dart_services での収束と、finding の差は、この ADR では測っていない(別の測定)。
- Dart の zoo の再帰のセルでの確認は、していない(そのセルは、プロジェクトの関数だけで、依存の関数がない)。確認は、依存の関数のマークを付けた小さい対象(`testdata/scccoarse`)で行った。
