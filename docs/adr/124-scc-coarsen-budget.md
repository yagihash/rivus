# ADR-124: 大きい SCC は、依存の関数を最初から深さ 0 で解く(#187)(2026-11-24)

- 状態: 有効(既定は有効、N = 5,500 の依存の関数。2026-11-24 に、ユーザーが決定。最初は既定で無効の入口だった)
- 関連: ADR-118(規模のための仕組みの 3 条件)、ADR-119(依存のアクセスパスの深さ)、ADR-099(source と sink はプロジェクトの中だけ)、ADR-121(既定の値の選び方の流儀)、課題 #187
- 要旨: エンジンが解く SCC(参照のエッジを含む構成)の、依存の関数の数が N 以上なら、その SCC の依存の関数だけを、最初から深さ 0(`-dep-k 0` と同じ)で解く。N は `-scc-coarsen`(既定 5,500。0 で無効)。プロジェクトの関数は深さを変えない。判定は、解く前に、コールグラフの構造だけで決める

**背景:** 依存を読むと、大きい SCC(dart_services: 13,983 関数)が、深さ 2 の `param` 出力で、現実の時間で収束しない。測定では、依存の関数を深さ 0 にした実行は、`global` の出力を粗くしなくても収束した。`-dep-k` は全体に一律の調整で、大きい SCC だけを粗くする上限ではない。#187 は、止める上限が流れを落とす課題で、この ADR は最初の入口、「大きい SCC は、流れを落とさずに、粗い形で解く」安全網を足す。

**経緯:** 最初の案は、解いている途中で、要約の鍵の数が予算を超えたら、途中の要約に fold をかける形だった。次の案は、超えたら捨てて最初から解き直す形(1 パス目はその場で、2 パス目以降は解析全体のやり直し)だった。どちらも、判定が解いている途中の状態に依り、捨てる処理(`global` の置き場の後始末、`resetForRestart`)と、2 パス目以降の特別扱いが要った。外部の設計者の助言で、**判定を解く前に移した**。

## 決めたこと(実装済み。内部の切り替えだけ。利用者のフラグは付けない)

1. **判定**(`coarse.go` の `coarsenBySize`): SCC 分解(参照のエッジを含む構成。エンジンが実際に解く SCC)の直後、解く前に、各 SCC について、その中の**依存の関数の数**が N 以上なら、その SCC の依存の関数にマークを付ける。数はコールグラフだけで決まる。プロジェクトの関数は数えない(プロジェクトの関数だけの SCC は、この仕組みで粗くしない)。
2. **解き方**: マークのある関数は、最初から、アクセスパスの深さ 0 で解く(`state.k()` が 0 を返す。依存の関数だけ。プロジェクトの関数は元の深さのまま)。何も捨てない。答えは、「その SCC の依存の関数だけ `-dep-k 0` にした解析」と同じ(テストで確認: 要約、`global` の置き場の中身と書いた関数と読む関数、findings、uncertainties、stats のうち作業量でないもの。`global` に書くプロジェクトの関数が SCC に入り、SCC の外の関数が読む形で)。
3. **記録**: SCC ごとに `depth_limit`、detail `scc_coarsened:` の uncertainty を 1 件(`attributable_to: rivus`、`candidates` に依存の関数の一覧。detail に、関数の数、依存の関数の数、パッケージの数、N)。深さ 0 の要約を適用したステップにも、同じ種類のステップの uncertainty(`out_widened` と同じ作り)。`stats.scc_coarsened` に SCC の数、`stats.largest_scc_deps` に、1 つの SCC が持つ依存の関数の最大の数(N と比べる数。当てない対象でも出る)。
4. **値(利用者の調整の指定)**: `-scc-coarsen <n>`(`-dep-k` と同じ、調整の指定。`flagInfo` は `Not`、`diagnostic`)。**既定 5,500**。0 で無効。インデックスの鍵(`flags.scc-coarsen`)に入る。環境変数 `RIVUS_INTERNAL_SCC_COARSEN_N` と、関数の数で数える切り替えは、フラグに置き換えて消した(測定の口はフラグで足りる)。

## N の選び方(2026-11-24)

**ルール**(`docs/PRINCIPLES.md` の「既定の値や上限を選ぶとき」): 深さ 2 で収束する対象の最大より上、収束しない対象の最小より下の、間の値を選ぶ。収束する対象の最大は cocoon(4,012)、収束しない対象の最小は dart-pub(7,550)。間は 4,012 より大きく 7,550 より小さい。選んだ値は **5,500**(切りの良い値)。

**表**(各対象の、エンジンが解く SCC の、依存の関数の数の最大。`stats.largest_scc_deps` と同じ数え方。測定は 2026-11-24、別の担当):

| 対象 | 依存の関数の数の最大 | 深さ 2 で | 5,500 で |
| --- | --- | --- | --- |
| dart_services | 13,895 | 収束しない | 当たる(2.5 倍) |
| dart-pub | 7,550 | 収束しない | 当たる(1.37 倍) |
| cocoon | 4,012 | 収束する | 当たらない(1.37 倍) |
| Gitea | 1,188 | 収束する | 当たらない |
| gcp | 860 | 収束する | 当たらない |
| dart-gcp | 842 | 収束する | 当たらない |
| memos | 678 | 収束する | 当たらない |
| go-s3 | 661 | 収束する | 当たらない |
| go-curated、zoo-go、zoo-dart ほか | 0 | - | 当たらない |

**余裕**: 下側は cocoon(4,012)に対して 1.37 倍、上側は dart-pub(7,550)に対して 1.37 倍(5,500 × 1.37 ≒ 7,550。4,012 × 1.37 ≒ 5,500)、dart_services(13,895)に対して 2.5 倍。**測った対象**: 上の表の対象。値を選ぶのに使った対象(cocoon、dart-pub)と、確認する対象(dart_services、Gitea、gcp、dart-gcp、memos、go-s3)は、分けている。確認する対象のうち、当たる dart_services は、粗くしたあとに収束することを、別に測る。当たらない対象は、`stats.scc_coarsened` が 0 であることを、合格基準の確認に入れた(下)。

**限界**: 4,012 と 7,550 の間は、測った対象が 2 つで、間に対象がない。1.37 倍の余裕は、依存の更新で cocoon が 5,500 を超える(または dart-pub が超えなくなる)ことに対して、小さい。当たったことを知らずに精度が落ちるのを避けるため、合格基準と依存のベンチの実行で、当たる数を毎回確認し、台帳に記録する。

## 合格基準と記録

- **合格基準の確認**(`bench/deps_bench.py` の `judge`、`bench/deps-targets.json` の `expect_coarsened`): 当てない対象(memos、memos-4gib、Gitea、cocoon)は、`stats.scc_coarsened` が 0。当たる対象(dart-pub、dart_services)は 1。違うと、その行は FAIL(行に `coarsened=<n>/<期待>`)。
- **`--graph-check`**(`bench/graph_check.py`): `scc_coarsened` の行。両方 0 なら same。当たる対象は DIFFERENT で、差は精度の変更として分類する(多めに出る向きだけ)。
- **台帳**(`bench/heavy-ledger.tsv`、`bench/heavy_ledger.py`): 列 `largest_scc_deps`(1 つの SCC が持つ依存の関数の最大)と `scc_coarsened` を、毎回記録する。N に近づいた対象が、台帳で見える。

## 判定を解く前に移した理由

- **順序・マシン・時間切れに依らない**(ADR-118 の (ii))。解いている途中の量(鍵の数)で決めると、`-timeout` や反復の上限(`MaxPasses`)で止まるのが先か、予算に当たるのが先かで、粗くしたかが機械の負荷で変わる。関数の数は、入力だけで決まる。
- **捨てる処理が要らない**。解き直す形は、`global` の置き場、書いた関数、読む関数、記録、統計を、全部、元に戻す必要があり、2 パス目以降は解析全体のやり直しになった。最初から深さ 0 なら、戻すものがない。
- **答えの説明が 1 つで済む**: 「その SCC の依存の関数は、`-dep-k 0`」。

## uncertainty の種類: 新しく足さず、既存の `depth_limit` の detail で言う

`depth_limit` は「解析の上限で、流れの精度を落とした」の種類で、すでに `path_limit`(パスを切った)、`out_limit` と hop の `out_widened`(出力をまとめた)が、同じ形(関数の一覧の記録と、hop の uncertainty)で言う。`scc_coarsened` も同じ意味の延長で、利用者の扱い(その周辺は多めに出る側として読む)が変わらない。`recursion_approximation` は、不動点に届かなかった意味で合わない。新しい kind はスキーマの変更になるので、避けた。

## ADR-118 の 3 条件

- (i) 過大近似の向きだけ: 満たす。深さ 0 は、依存の関数の要素のパスを切るだけで、切った所より下は「まるごと」として扱う(ADR-117、ADR-119)。深さ 0 の答えは、深さ 2 の答えのパスを切ったものを含む(テストで確認: 要素の包含)。
- (ii) 順序・マシンに依らない: 満たす。判定は、コールグラフの SCC の構成と N だけ(`-scc-coarsen` は、同じ入力と同じ値なら、どの計算機でも同じ)。時計も、メモリも、解いている途中の量も見ない。`-workers` 1、2、既定で、要約と記録が同じ(テスト)。
- (iii) 出力が言う: 満たす。上の 3。

### 出力の項目(2026-11-25、ユーザーの了承。項目の追加だけで、既存の項目は変えない)

判定する人とエージェントが、`detail` の文言を読まずに「付いた側」を分けられるように、次を足した。

- `depth_limit` の uncertainty(トップレベルの記録と、その要約を適用したステップ)に `coarsened_scc: {id, packages, packages_count, functions: {group, dependencies}}`。`id` は、集まりの中の最小の関数 ID の文字列の SHA-256 の先頭 12 桁(同じコードなら、どの実行でも同じ)。`packages` は最大 10 件(名前順)、超える分は `packages_count` で分かる。
- finding に `through_coarsened_scc: [<id>, ...]`(経路のステップに、粗く解いた集まりの要約を適用したものがあるときだけ。`id` 順)。経路の途中を省いた finding も、省いたステップを含めて見る。
- **finding の出力の並び**: `through_coarsened_scc` が付かないものが先、付くものが後。それぞれの中は、今までの決定的な順(sink の位置、finding の ID)。有効にした対象で、並びが変わる(`--graph-check` の `findings-order` が DIFFERENT になる)。無効の対象は、付く finding がないので、並びも出力も今と同じ。
- 読み方(`docs/AGENT-GUIDE.md`): 付かない側から読む。付いた側は、粗く解いた依存の中の流れが本物かを確かめてから判定する(無視してよい、ではない)。

## ユーザーの承認

- 「大きい SCC は、依存の関数を最初から深さ 0 で解く」形は、外部の設計者の助言で、相談役とユーザーに伝わっている。
- N = 5,500(依存の関数の数)を既定で有効にすること(2026-11-24。ユーザーの言葉: 「既定で有効にすることを目指す」「おすすめの数値で」)。結果が変わるのは、当たる対象(dart_services と dart-pub)だけで、その差は、精度の変更として分類する(多めに出る向き。`scc_coarsened` の uncertainty が付く)。dart_services の finding がどれだけ変わるかは、マージの前に別に見る。

## まだ届かないもの(未確認と限界)

- N 未満で、深さ 2 で収束しない SCC は、守られない(今の測定では、そういう対象はない。出たら N を下げる)。
- プロジェクトの関数だけの SCC、プロジェクトと依存が混ざる SCC のプロジェクトの関数は、粗くしない。深さ 0 の要素が、プロジェクトの関数の出力の数を増やすかは、測っていない。#187 の残りの項目。
- dart_services と dart-pub が粗くしたあとに収束するかは、測った(2026-11-25、既定のフラグ、N = 5,500、静かな状態、`bench/heavy-ledger.tsv`)。dart_services は 3 回の中央値で 400 秒、tree-RSS 最大 6.05 GB、8 パスで収束、`scc_coarsened` 1、`largest_scc_deps` 13,897(合格基準 D は 600 秒、8 GB)。dart-pub は 119 秒、4.64 GB、9 パスで収束。安全網なしの深さ 2 は、dart_services で収束せず、finding が取れない。finding は、dart_services で 21 件、`-scc-coarsen 1` でも id が同じ。dart-pub の件数と、ほかの対象の差は、測っていない。
- Dart の zoo の再帰のセルでの確認は、していない(そのセルは、プロジェクトの関数だけで、依存の関数がない)。確認は、依存の関数のマークを付けた小さい対象(`testdata/scccoarse`)で行った。
