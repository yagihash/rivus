# ADR-124: 巨大な SCC を、予算で 1 回だけ粗くする安全網の入口(#187)(2026-11-24)

- 状態: 有効(入口の実装。ユーザーの承認が要る点は下。**予算の既定は無効**。値と、既定で有効にするかは、測定のあとにユーザーが決める)
- 関連: ADR-118(規模のための仕組みの 3 条件)、ADR-119(依存のアクセスパスの深さ)、ADR-099(source と sink はプロジェクトの中だけ)、ADR-121(既定の値の選び方の流儀)、課題 #187
- 要旨: 8 関数以上の SCC で、依存の関数の要約の「鍵の数」が予算を超えたら、その SCC の依存の関数の要約を、ラウンドの終わりに 1 回だけ粗い形に移す(深さ 0、global は関数ごとの要素を SCC の全 G に付ける)。戻さない。プロジェクトの関数は粗くしない

**背景:** 依存を読むと、大きい SCC(dart_services: 依存の関数 1.4 万)が、深さ(param の出力の鍵)と global の出力の数で、現実の時間で収束しない。`-dep-k` は深さを一律に変える調整で、収束しないものを止める上限ではない。#187 は、止める上限が流れを落とすことを直す課題で、この ADR はその最初の入口、「予算を超えたら、流れを落とさずに、粗い形に移す」安全網を足す。

## 決めたこと(実装済み。予算は内部。利用者のフラグは付けない)

1. **数える量**(`coarse.go`): SCC の依存の関数の、コミット済みの要約の、(a) 深さ 2 以上(パスの `/` が 2 つ以上)の `param` 出力の鍵の数、(b) `global` 出力の鍵の数。鍵は出力(種類、番号、グローバル、パス)の数で、要素の数ではない。`widen` は要素をまとめるだけで、鍵は減らない。要約は結合(join)で増える向きにしか変わらないので、数は減らない。
2. **いつ数えるか**: 8 関数以上の SCC(ラウンドごとに一斉に公開する分岐)の、ラウンドの終わり。コミットのあとの要約だけを見るので、`-workers` と順序に依らない。8 関数未満の SCC は、関数ごとに順に解くので、ラウンドの区切りがなく、対象にしない。
3. **判定**: (a) か (b) のどちらか 1 つが予算を超えたら、その SCC を粗くする。次元ごとに別々に判定しない。**1 回だけ**。戻さない。以後は、ラウンドの終わりごとに、今の要約に折りたたみ(fold)をかけ直すだけ(SCC が書く G が増えたとき)。
4. **fold(`foldSummary`)**: 依存の関数だけ。(i) 全出力のパスを "" にし、param の要素のパスも "" にする(深さ 0。`-dep-k 0` と同じ向き)。自分自身の param が自分に入る要素は、`summarize` と同じく落とす(流れではない)。(ii) global は、その関数が書く全部の global の要素の和を、SCC の依存の関数が書く全部の G に、関数ごとに付ける(他の関数の param 要素は混ぜない。その関数の引数のことではないため)。(iii) 条件(ガード)は外す(「どの条件でも起こりうる」。理由は下)。(iv) sink の要素のパスも切る。以後、その関数の解析の結果にも fold をかけ、関数の本体は深さ 0 で解く(`state.k()`)。
5. **記録**: SCC ごとに `depth_limit`、detail `scc_coarsened:` の uncertainty を 1 件(`attributable_to: rivus`、`candidates` に依存の関数の一覧。詳細に、関数の数、依存の関数の数、パッケージの数、超えた量と件数、予算、ラウンドとパス)。粗くした要約を適用した経路のステップにも、同じ種類のステップの uncertainty(`out_widened` と同じ作り)。`stats.scc_coarsened` に SCC の数。
6. **値**: `Options.SCCCoarsen`(0 = その量の予算なし。**既定は両方 0 = 粗くしない**。出力は今と同じ)と、テスト用の `SCCCoarsenAtRound`(0: 使わない、n: その SCC の n ラウンド目から、負: 最初の前から、量に関係なく粗くする)。実行から使うには、環境変数 `RIVUS_INTERNAL_SCC_COARSEN_BUDGET=a,b`(a が (a)、b が (b))と `RIVUS_INTERNAL_SCC_COARSEN_AT_ROUND=n`(ビルドタグ `coarseforce` のバイナリだけが読む。配布するバイナリは読まない。ADR-121 と PRINCIPLES の「内部の切り替え」の流儀)。

## uncertainty の種類: 新しく足さず、既存の `depth_limit` の detail で言う

`depth_limit` は「解析の上限で、流れの精度を落とした」の種類で、すでに `path_limit`(パスを切った)、`out_limit` と hop の `out_widened`(出力をまとめた)が、同じ形(関数の一覧の記録と、hop のuncertainty)で言う。`scc_coarsened` も、同じ意味の延長(上限に届いて、粗くした)で、利用者の扱い(その周辺は多めに出る側として読む)が変わらない。`recursion_approximation` は、不動点に届かなかった意味で合わない。`engine.coarsened` は内部の記録で、出力の kind ではない(`path_limit` の元)。新しい kind はスキーマの変更になるので、避けた。`attributable` は `rivus`。

## ADR-118 の 3 条件

- (i) 過大近似の向きだけ: 満たす。fold は元の要素の上に載る(パスは親へ、global は足す、条件は外す、要素は落とさない。落とすのは自分自身の param の、流れでない要素だけ)。上への閉包で、2 回かけても同じ(テスト)。
- (ii) 順序・マシンに依らない: 満たす(テストで確認)。判定はラウンドの終わりの鍵の数だけ。時計もメモリも見ない。`-workers 1`、2、既定で、要約と記録が同じ。**粗くするラウンドを、最初の前、1、2、3、5 に変えても、最終の要約(ステップを除く署名)が同じ**(上への閉包のため)。包含だけでなく、同じであることを確認した。
- (iii) 出力が言う: 満たす。上の 5。

条件(ガード)を外すのは、ラウンドを変えると同じにならなかったため。ガード付きの要素が、粗くする前に別のパスの別のガードと出会うと、合流するときにガードが消える(結合の規則)。最初から粗い実行では出会わず、ガードが残る。どちらも過大近似の向きだが、結果が違った。粗い形ではガードを持たない、と決めて、同じになった。

## ユーザーの承認が要りそうな点

1. **精度を落とす新しい過大近似**であること(予算を超えた SCC の依存の関数で、深さ 0、global の関数ごとの共有、ガードなし)。ただし、**今は既定で無効**で、有効にしない限り出力は今と同一。
2. **予算の既定の値と、既定で有効にするか**: 測定(各対象の各ラウンドの (a)(b))のあとに決める。PRINCIPLES の「既定の値や上限を選ぶとき」に従い、選ぶのに使った対象と、確かめる対象を分け、他の対象で粗くした SCC の数が 0 であることを、合格基準の確認に入れる。dart_services の finding が、粗くしたことでどれだけ増えるかは、そのあと、ユーザーに聞く。

## まだ届かないもの(未確認と限界)

- **global の仮置き**(全 G にまとめる)は、仮置き。収束が遅いだけなら、SCC の中の「f の引数 i → g の引数 j」「f の引数 i → G」のエッジから、G の側から逆向きに一度に計算する表(精度を落とさない)に置き換える道が本命。置き換えるときは、この ADR を覆す別の ADR にする。
- プロジェクトの関数だけの SCC、プロジェクトと依存が混ざる SCC のプロジェクトの関数は、粗くしない。粗い要素が、プロジェクトの関数の出力の数を増やすかは、測っていない(測定のあとの確認)。#187 の残りの項目。
- 数え方は、8 関数以上の SCC だけ。8 関数未満は対象外。
- `dart_services` での収束と、finding の差は、この PR で測っていない(重い実行はしていない)。
- 粗くした SCC を通らない finding は変わらない。通る finding は、ステップの uncertainty が付いて `requires_review` になる。
