# ADR-124: 巨大な SCC が予算を超えたら、依存の関数を深さ 0 にして、その SCC を最初から解き直す安全網の入口(#187)(2026-11-24)

- 状態: 有効(入口の実装。予算の既定は無効。値と、既定で有効にするかは、測定のあとに決める)
- 関連: ADR-118(規模のための仕組みの 3 条件)、ADR-119(依存のアクセスパスの深さ)、ADR-099(source と sink はプロジェクトの中だけ)、ADR-121(既定の値の選び方の流儀)、課題 #187
- 要旨: 8 関数以上の SCC で、依存の関数の要約の「深さ 2 以上の param 出力の鍵の数」が予算を超えたら、その SCC の依存の関数だけを深さ 0(`-dep-k 0` と同じ)にして、SCC を最初から 1 回だけ解き直す。途中までの結果は捨てる。戻さない。プロジェクトの関数は深さを変えない

**背景:** 依存を読むと、大きい SCC(dart_services: 依存の関数 1.4 万)が、深さ 2 の `param` 出力で、現実の時間で収束しない。測定では、依存の関数を深さ 0 にした実行は、`global` の出力を粗くしなくても収束した。`-dep-k` は全体に一律の調整で、収束しないものだけを止める上限ではない。#187 は、止める上限が流れを落とす課題で、この ADR は最初の入口、「予算を超えたら、流れを落とさずに、粗い形で解き直す」安全網を足す。

**経緯:** 最初の案は、予算を超えたとき、途中の要約に「折りたたみ」(fold: パスを切り、global を SCC の全 G にまとめ、ガードを外す)をかけて続ける形だった。ユーザーの返事(2026-11-24)で、「最初から深さ 0 で解き直す」形に変えた。答えが「最初から深さ 0 の解析」と同じになることを、新しい操作の正しさの証明なしに言えるため。fold と、`global` の予算は消した。

## 決めたこと(実装済み。予算は内部。利用者のフラグは付けない)

1. **数える量**(`coarse.go`): SCC の依存の関数の、コミット済みの要約の、深さ 2 以上(パスの `/` が 2 つ以上)の `param` 出力の鍵の数。鍵は出力(種類、番号、パス)の数で、要素の数ではない。`widen` は要素をまとめるだけで、鍵は減らない。`global` の出力は数えない(深さ 0 だけで収束した測定から)。
2. **いつ数えるか**: 8 関数以上の SCC(ラウンドごとに一斉に公開する分岐)の、ラウンドの終わり。コミットのあとの要約だけを見るので、`-workers` と順序に依らない。8 関数未満の SCC は、関数ごとに順に解くので、ラウンドの区切りがなく、対象にしない。
3. **解き直し**: 予算を超えたら、その SCC の依存の関数を深さ 0 にする(`state.k()` が 0 を返す。依存の関数だけ。プロジェクトの関数は元の深さのまま)。**1 回だけ。戻さない**。**どちらの場合も、結果は、その SCC の依存の関数を最初から深さ 0 にした解析と同じ**(テストで確認: 要約、`global` の置き場の中身と書いた関数と読む関数、findings、uncertainties、stats のうち作業量でないもの)。
   - **最初のパスの中で超えたとき**: その SCC は、まだ `global` の置き場に何も書いていない(レベルが書くものは、レベルの終わりまで待つ)。SCC の全関数について、エンジンが解析で書く状態を元に戻し(`discard`: 要約、`states`、`coarsened`、`guardLimit`、`notConverged`、`degraded`、`addsTotal`、`spent`、`heldNothing`、`identityStores`)、待っている `global` の書き込みと読む関数から、その SCC の分を捨て、その場で最初のラウンドからやり直す(ラウンドの数も 8 に戻す)。上のレベルは、まだ解かれていない。
   - **2 パス目以降で超えたとき**: その SCC は、前のパスで `global` の置き場に書いていて、上のレベルの関数は、途中の要約で解かれている。置き場や上のレベルを部分的に戻すのではなく、その SCC にマークを付け、**そのレベルの終わりに、解析全体を最初からやり直す**(`Run` が `runOnce` を繰り返す。`resetForRestart` が、エンジンが解析で書く状態を全部戻す)。マークの付いた SCC は、最初から深さ 0 になる。判定は、予算の数が単調なので、入力だけで決まる(マークは増えるだけ。同じレベルの SCC は全部、そのレベルの終わりまで解かれるので、どれがマークを持つかは、先に終わった順に依らない)。やり直しの回数は、マークが増えるたびに 1 回で、SCC の数が上限。`stats.scc_restarts` に回数を出し、`scc_coarsened` の記録の detail に「後のパスで見つかったので、解析全体を最初からやり直した」と書く。
4. **記録**: SCC ごとに `depth_limit`、detail `scc_coarsened:` の uncertainty を 1 件(`attributable_to: rivus`、`candidates` に依存の関数の一覧。detail に、関数の数、依存の関数の数、パッケージの数、超えた量と件数、予算、ラウンドとパス)。深さ 0 の要約を適用したステップにも、同じ種類のステップの uncertainty(`out_widened` と同じ作り)。`stats.scc_coarsened` に SCC の数。
5. **値**: `Options.SCCCoarsen`(整数。0 = 予算なし。**既定は 0 = 解き直さない**。出力は今と同じ)と、テスト用の `SCCCoarsenAtRound`(0: 使わない、n: その SCC の n ラウンド目から、負: 最初の前から、量に関係なく)。実行から使うには、環境変数 `RIVUS_INTERNAL_SCC_COARSEN_BUDGET=n`(測定のため。`-h` に出さない。ADR-121 と PRINCIPLES の「内部の切り替え」の流儀)。強制のラウンドの環境変数 `RIVUS_INTERNAL_SCC_COARSEN_AT_ROUND=n` は、ビルドタグ `coarseforce` のバイナリだけが読む(配布するバイナリは読まない)。

## uncertainty の種類: 新しく足さず、既存の `depth_limit` の detail で言う

`depth_limit` は「解析の上限で、流れの精度を落とした」の種類で、すでに `path_limit`(パスを切った)、`out_limit` と hop の `out_widened`(出力をまとめた)が、同じ形(関数の一覧の記録と、hop の uncertainty)で言う。`scc_coarsened` も、同じ意味の延長(上限に届いて、粗くした)で、利用者の扱い(その周辺は多めに出る側として読む)が変わらない。`recursion_approximation` は、不動点に届かなかった意味で合わない。`engine.coarsened` は内部の記録で、出力の kind ではない(`path_limit` の元)。新しい kind はスキーマの変更になるので、避けた。

## ADR-118 の 3 条件

- (i) 過大近似の向きだけ: 満たす。深さ 0 は、依存の関数の要素のパスを切るだけで、切った所より下は「まるごと」として扱う(ADR-117、ADR-119)。解き直した答えは、深さ 2 の答えのパスを切ったものを含む(深さ 0 の不動点は、深さ 2 の不動点を切ったものの上に載る)。テストで確認した(要素の包含)。
- (ii) 順序・マシンに依らない: 満たす。判定はラウンドの終わりの鍵の数だけ。時計もメモリも見ない。解き直しは、捨てて最初からなので、答えは「最初から深さ 0 の解析」と同じ。テストで、`-workers` 1、2、既定で要約と記録が同じ、予算に当たるラウンド(1、2、3、5)と、予算の数に当たる場合の要約(要素とガード)が、最初から深さ 0 の解析と同じ、を確認した。
- (iii) 出力が言う: 満たす。上の 4。

## ユーザーの承認

- 「予算に当たったら、最初から深さ 0 で解き直す」形は、ユーザーが了承した(2026-11-24。「良いと思うよ」)。
- 予算の既定の値と、既定で有効にするかは、まだ決めていない(今は無効)。測定のあとに、PRINCIPLES の「既定の値や上限を選ぶとき」に従って決める。他の対象で解き直した SCC の数が 0 であることを、合格基準の確認に入れる。dart_services の finding が、解き直しでどれだけ変わるかは、そのあと、ユーザーに聞く。

## まだ届かないもの(未確認と限界)

- 2 パス目以降で超えたときは、解析全体のやり直しになる(上の 3)。コストは、やり直した回数の分、増える(`stats.reanalyses` は捨てた分も数える)。今わかっている当たりの dart_services は、最初のパスで超える見込みで、やり直しは珍しい形のはず(測定で確かめる)。
- 戻さないもの: 作業量の数(`stats.reanalyses`、`passes`、`adds_max_single_run`。捨てたラウンドの分も数える)、SCC の外で dirty が付いた関数(どのみち解析し直す)、診断(`-pass-stats`、`TraceElement`)の一部。
- **予算に当たる前に**、`-timeout` や反復の上限(`MaxPasses`)で止まると、粗くしたかどうかが、機械の負荷で変わる(ADR-118 の (ii) を満たさない部分)。止まったことは `depth_limit` と `recursion_approximation` が言う。課題 #187 に書いた。
- 解き直しのあとも、パスの上限(`MaxPasses`)とラウンドの上限(8)は変わらない。深さ 0 の解き直しが、残りのパスで収束するかは、dart_services で測る。
- プロジェクトの関数だけの SCC、プロジェクトと依存が混ざる SCC のプロジェクトの関数は、粗くしない。深さ 0 の要素が、プロジェクトの関数の出力の数を増やすかは、測っていない。#187 の残りの項目。
- 数え方は、8 関数以上の SCC だけ。8 関数未満は対象外。
- dart_services での収束と、finding の差は、この PR で測っていない(重い実行はしていない)。
- Dart の zoo の再帰のセルでの確認は、していない(そのセルは、プロジェクトの関数だけで、依存の関数がない)。確認は、依存の関数のマークを付けた小さい対象(`testdata/scccoarse`)で行った。
