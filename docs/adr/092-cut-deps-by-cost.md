# ADR-092: 依存のパッケージを、流れのモデルで「切る」(本体を読まない)のは、収束しないときに加えて、解析に著しくコストがかかるときも。ただし条件を満たしたものだけ(ユーザーの判断、2026-11-22。条件は相談役)

- 状態: 一部覆った(→ADR-098)
- 関連: PRINCIPLES 3 節、GCP-MODELS P12、MODELING
- 状態の詳細: 条件 1(時間かメモリの 9 割)は、パッケージ全体を切るときの条件として残る。実装の多いインターフェースのメソッドを切る別の基準を、ADR-098 が足した
- 要旨: コストの測定の記録、照合の検査、`calls:`、保守的な uncertainty、切ったことの表示。実装は未(ROADMAP)

**背景:** 流れのモデルで依存の本体を読まないのは、これまで「本体がない」「読むと収束しない」「ライブラリが利用者のコードを呼ぶ(`calls:`)」ものに限っていた(3 つの理由)。今回足すのは 4 つ目の「著しくコストがかかる」(PRINCIPLES 3 節、GCP-MODELS の P12「モデルで依存の中を切らない」)。2026-11-22 の測定(`bench/gcp`、Spanner と BigQuery を使う小さい対象): 既定(依存の本体を読む)は 40.7 秒、最大 RSS 4.45 GB。`-no-deps` は 0.4 秒、64 MB。流れ(source → sink の組)は 27 件で、どちらも同じ(消えた finding も、増えた過検出も 0 件)。違いは確信だけで、`no_uncertainty_on_path` が 19 → 15。モデルのない呼び出し先は 29 種(106 回)で、finding の経路に載るのはそのうち 5 種(`models coverage -no-deps`)。時間の 99% 以上が依存の中(P12)。ユーザーの判断: 「収束しない」だけでなく「解析に著しくコストがかかる」ものも、流れのモデルで切る例外にしてよい。大原則(正確な呼び出しのグラフを作る)は変えない。

**決めたこと:** 依存のパッケージを、モデルで切る(本体を読まない)のは、次の 1〜3 を満たしたときだけ。
1. **コストを測って、記録してある。** そのパッケージ(とそれが引き込む依存)を読む時間かメモリが、対象の自分のコードの解析に対して著しく大きい(目安: 依存の側が時間の 9 割以上、または数 GB の桁)。数字は、測った対象と一緒に、モデルのファイルか設計の文書に書く。目安に一致するかは、相談役が判断する。
2. **照合の検査がある。** そのパッケージの API を使うフィクスチャ(zoo かベンチ)で、本体を読んだ結果とモデルで切った結果を比べ、次が同じ: (a) 流れ(source → sink の組)の集合、(b) **境界の呼び出しのエッジ**(自分のコードから依存に入った呼び出しが、自分のコードのどの関数を呼び戻すか: コールバック、依存のインターフェースの自分の実装、依存が返して自分が呼ぶ関数値)。違ってよいのは、モデルの側が多めで uncertainty がある向きだけ。モデルの側で流れやエッジが減る差は、不合格。CI で守る(重い側の実行は定期の層でもよい)。
3. **呼び戻しは、必ずモデルに書く。** 渡した関数、引数やレシーバが持つ関数を呼ぶ API は `calls:`。今の書式で書けない形(レシーバの状態を通る、登録してあとで呼ぶ)は、書式の課題として挙げ、書けるまでは、その API の呼び出し点に uncertainty を出す(何も報告せずに切ることはしない)。

切ったパッケージの扱い:
4. **モデルのない呼び出しは、保守的に、uncertainty つきで。** モデルの行がない関数の呼び出しは、今の `-no-deps` と同じ(引数 → 結果を多めに、渡した関数は呼ばれるものとして扱う、`unmodeled_library_call`)。汚染のない値にしない。
5. **切ったことを示す。** 出力(`summary` と索引の meta)に、モデルで切ったパッケージの一覧。`rivus graph` の「経路なし」の `exhaustive` は、探索がモデルのない境界の関数に達したら false。利用者が本体を読ませるフラグ(全体と、パッケージごと)を残す。

変わらないもの: 自分のコードは必ず読む。依存のインターフェースの自分の実装の本体は読む(ADR-075、ADR-086)。標準ライブラリは今のまま。切るのは 1〜3 を満たしたパッケージだけで、それ以外の依存は、今までどおり既定で読む。組み込みのモデルでも、利用者が外から差し込むルールでも、同じ条件(同じ検査の道具)で切れるようにする。

**確かめたこと:** 上の測定(`bench/gcp`、`bench/go-curated`: 依存がほぼなく、`-no-deps` でも finding・確信・不確実性が同一)。

**限界(まだ届かないもの):** パッケージごとに切る仕組みがない(今は、全部読むか、全部読まないか)。照合の検査がない。第三者の依存が多い対象では測っていない(gcp は、Google Cloud の組み込みモデルが既にあるベンチ。実アプリで、finding に影響する未モデルの呼び出し先が、全体のどれだけかは未測定: gcp では 5 / 29)。切った結果の確信は、gcp で 19 → 15 に下がる(約 30 種のモデルで戻す見込みで、finding に影響するのは 5 種)。実装の順は、段階 4 の第 2 歩のあとに決める(ROADMAP)。
