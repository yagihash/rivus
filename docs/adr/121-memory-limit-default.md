# ADR-121: メモリの上限(`-max-memory`)を足し、指定がないときの既定を物理メモリの 1/4 にする(2026-11-23)

- 状態: 有効
- 関連: ADR-118(規模のための仕組みの 3 条件)、ADR-119(依存の深さ)、`cmd/rivus/main.go` の `tuneGC`(`GOGC` の固定。この ADR では変えない。上限が低いときの見直しは、追記 2026-11-26)
- 要旨: Go のランタイムのやわらかいメモリの上限を、`-max-memory` > `GOMEMLIMIT` > 既定(物理メモリ、cgroup があれば小さいほうの 1/4。下限あり)の順で決め、`summary.memory_limit_*` に出す。結果は変えない

**背景:** 大きい対象(memos: 24 GB のマシンで、既定の RSS が 7.9〜8.3 GB)は、8 GB の監視の線の際で動く。Go の `debug.SetMemoryLimit`(環境変数 `GOMEMLIMIT` と同じ)は、メモリの合計が上限に近づくと GC を強くする。

**決めたこと(ユーザーの決定。相談役の伝言、2026-11-23):**
1. `-max-memory <サイズ>`(`6GiB`、`6GB`、`512MiB`、`512MB`、バイト数、`off`)。`analyze` と、エンジンを動かす他のコマンド(`analyze` のフラグを共有するもの)で使える。不正な値は利用法のエラー(終了コード 2)で、有効な書式を示す。
2. 指定がないときの上限 = `max(基準/4, min(4 GiB, 基準/2))`。基準 = 物理メモリと cgroup の上限(v2 `memory.max`、v1 `memory.limit_in_bytes`)の小さいほう。24 GB → 6 GiB、16 GB → 4 GiB、8 GB → 4 GiB、4 GB → 2 GiB。物理メモリが取れないときは上限なし(今まで通り)で、`summary.memory_limit_note` に理由。
3. 優先順: `-max-memory` > `GOMEMLIMIT` > 既定。`-max-memory off` は、既定の上限も環境の上限も外す。両方あるときは、使った値と、環境の値があったことを `memory_limit_note` に出す。
4. `summary.memory_limit_bytes`(上限なしのときは省略)、`memory_limit_source`(`flag` / `env` / `default` / `none`)、`memory_limit_note`(省略可)。既存の項目は変えない。出力に項目を足すだけで、スキーマのバージョンは上げない。
5. 物理メモリは、macOS は `sysctl hw.memsize`(`golang.org/x/sys/unix`。すでに go.mod にある)、Linux は `/proc/meminfo` の `MemTotal`。他の系は取れず、上限なし。新しい依存は足さない。
6. `GOGC` の固定(`tuneGC`)は、この ADR では変えない。

**理由(memos での測定。macOS、24 GB のマシン。測定は 1 回ずつで、繰り返していない):**

| 上限 | RSS | 結果 |
| --- | --- | --- |
| なし | 7.93 GB(収束) | 別の実行では、8 GB の監視に止められた |
| 7 GiB | 7.06 GB | 収束 |
| 6 GiB | 6.36 GB | 収束、時間 +10% |
| 5 GiB | 5.87 GB(上限 5.37 GB を超える) | CPU 約 2 倍(GC が回り続ける) |
| 4 GiB | 5.8 GB(上限 4.29 GB を超える) | CPU 約 3 倍 |

- finding の ID は、5 本とも完全に一致した。上限は GC を詰めるだけで、結果に影響しない。
- 生きている量は約 5 GB。上限がそれより低いと、守れず、GC が回り続ける。
- macOS では、返したメモリは RSS から引かれない(小さい実験: 4 GB を割り当て、捨て、GC し、`FreeOSMemory` しても、RSS は変わらず、footprint が 3% 減っただけ)。そのため、ピークを「戻す」のではなく、「広げない」ことが効く。
- 段階の境目での強制 GC は、効かなかった。

**時間への影響(マージのあとの測定。2026-11-23、memos、素のバイナリ、既定のフラグ、重い実行のロックの下、交互 2 ラウンド。#354 の前の main e147d896 と、後の fe7740d6):** wall は 44 / 45 秒 → 49 / 49 秒(+4〜5 秒、約 +10%)、CPU は 302 / 317 秒 → 358 / 367 秒(+13〜19%)、本体のピークは 7.73 / 7.80 GB → 6.30 / 6.27 GB(約 −1.5 GB)、RSS 最大は 7.82 / 8.07 GB → 6.36 / 6.33 GB。finding の ID の集合、`functions`、`reanalyses`、`summary_elems` は、4 本とも同一。開始時の負荷は 1.6〜8.9 で、一定ではない(時間は参考)。合否の道具(`make bench-passline`、memos)は、3 回とも PASS(48〜50 秒、メモリ 5.99〜6.15 GB)。

**1/4 を選んだ事情:** 1/3 では効かず、1/4 で効くと分かったうえで選んでいる。測定した対象に線を合わせた面がある。根拠の言葉は「他の作業に 3/4 を残す」。

**まだ届かないもの:**
- 生きている量が上限を超える対象では、上限は守れず、CPU が増える(上の表の 5 GiB、4 GiB)。
- Linux は未確認(測定は macOS)。cgroup の読み方は、コードとテストのみ。**読むのは `/sys/fs/cgroup/memory.max`(v2)と `/sys/fs/cgroup/memory/memory.limit_in_bytes`(v1)の直下だけ**。コンテナの中(自分の cgroup がそこにマウントされる)では読めるが、ホストの上で、入れ子の cgroup(systemd のスライスなど)に上限がある場合は、読まない(物理メモリの 1/4 になる)。
- 実行中に上限を決める案(低めから始め、GC に使う CPU の割合が一定を超えたら、上限を上げる。上げられる上限に達したら、結果を出して、完全でない終了コードで止まる)は、別の PR で扱う。

**出力が計算機で違う件:** `summary.memory_limit_bytes` は、物理メモリで決まるので、同じ入力でも、計算機が違うと、出力の JSON が 1 か所違う(finding と統計は同じ)。確認したところ、出力を丸ごと比べる所は、同じ計算機の中の実行どうし(決定論のテスト: 上限の値は同じ)で、`bench/compare.py` は `findings` と `stats` だけを読み(`summary` は読まない)、文書と `testdata` に `summary` の見本の出力はない(`make test-docs` は出力を比べない)。計算機をまたいで出力を丸ごと比べる道具やテストを足すときは、`summary.memory_limit_*` を比べる対象から外す(上限は、結果ではなく、実行の設定のため)。

**ADR-118 の 3 条件との関係:** 上限は精度を落とす仕組みではなく、結果を変えない(測定で ID が一致)。(i) 過大近似の向きだけ、(iii) 落とした所を出力が言う、は、落とすものがないので、該当しない。(ii) 順序とマシンに依らない: 結果は、上限によらず同一。変わるのは、GC の動きと、時間・メモリだけ。上限は `summary` に出る。

## 追記: 実行の終わりの報告(2026-11-23)

上の本文は書き換えない。上の「まだ届かないもの」の最初(上限が生きている量より低いと守れず、時間だけが増える。何も言われない)を、出力から分かるようにする。止める、上限を上げる、は、別の PR。

1. `summary` に 3 項目を足す。結果(finding、要約、ID)は変えない。スキーマのバージョンは上げない(項目の追加のみ。ADR-008)。
   - `memory_peak_bytes`: 実行の間に、Go のランタイムが使っていたメモリの最大。`runtime/metrics` の `/memory/classes/total:bytes` から `/memory/classes/heap/released:bytes` を引いた量で、`debug.SetMemoryLimit` が見る量と同じ。終わりの 1 回ではなく、最大で見る(超えたかどうかは、ピークで決まる)。
   - `memory_limit_exceeded`: `memory_peak_bytes > memory_limit_bytes × 1.05`(上限を 5% 以上超えた)。上限ちょうどを境目にしない理由: やわらかい上限は、生きている量が上限より低いとき、ピークが上限に張りつく(memos の既定の実行: ピーク 6,408,576,568、上限 6,442,450,944。0.5% 手前、33 MB)。ちょうどを境目にすると、正常な実行が、サンプルの揺れで `true` になりうる。上限が生きている量より低いと、ピークは明確に上限を超える(memos、上限 4 GiB: ピーク 6,300,634,664、1.47 倍)。5% は、この 2 つの実行から選んだ値(選んだ対象)。`true` は、上限が、解析の生きている量より低く、守れず、GC が回り続け、時間が増えた可能性が高いこと。`-max-memory` を上げて、再実行する。やわらかい上限なので、`true` でも結果は完全(`incomplete` とは別)。上限がないとき(`memory_limit_source: none`)は、項目を出さない。
   - `gc_cpu_fraction`: 実行全体の CPU 時間のうち、GC が使った割合(`/cpu/classes/gc/total:cpu-seconds` ÷ `/cpu/classes/total:cpu-seconds`、実行の開始との差分。0〜1、小数 3 桁)。上限がなくても、いつも出る。
2. 計測は、解析の間、軽い goroutine が 250ms ごとと終了時に `runtime/metrics.Read` で読むだけ(stop-the-world の `runtime.ReadMemStats` は使わない)。解析の結果には触れない。解析が終わると止める(`defer` でも止める。残さない)。250ms の間の短い山は見えないことがあるので、ピークは、実際より小さく出ることがある(超えたのに `false` になる向きの誤差。`memory_peak_bytes` で根拠が見える。`memory_peak_bytes` は、上限と比べずに、そのまま出す)。
3. 値は、この実行の、この計算機のもの(ピークと GC の割合は、負荷とスケジューリングで揺れる)。上の「出力が計算機で違う件」と同じ扱いで、出力を丸ごと比べる所では、`summary.memory_limit_*`、`memory_peak_bytes`、`gc_cpu_fraction` を対象から外す。
4. 同じ PR で、`models coverage` の出力の最上位に `incomplete` と `incomplete_reasons` を出す(ADR-120 の追記「問い合わせの出力」と同じ形。完全なら `false` と `[]`)。今の解析から出す場合と、`-index` の場合の両方。`-index` の終了コードは 0 のまま。時間切れの index から作った一覧は、一部だけなので、読む人が分かるようにするため。

上限は memos で選んだので、別の 3 つの対象で、同じ向きに効くかを確かめた(台帳 `bench/heavy-ledger.tsv` の 2026-11-23、`dac8bcb6`、`kind=deps` の 3 行。数字は台帳を見る)。3 つとも既定の上限(6 GiB)で、終了コード 0、収束、`func_timeouts` と `budget_exhausted` は 0。ピークは上限に届かず(余裕は台帳の表示で出る)、`memory_limit_exceeded` は出ていない。つまり、生きている量が上限より低い対象では、上限は何も変えない(結果の同一性は、上限なしと比べていない: 比べたのは memos だけ)。

### 追記: 生きているヒープの最大(2026-11-23)

上の本文と 1〜4 は書き換えない。`memory_peak_bytes` は、やわらかい上限が効いているとき、生きている量が上限より低いと上限に張りつくので、上限との差は余裕を表さない。知りたいのは、生きている量の最大(上限の下限)。

- `summary.live_heap_max_bytes` を足す(整数、バイト)。同じモニターが、`memory_peak_bytes` と同じ 250ms ごとと終了時に、`runtime/metrics` の `/gc/heap/live:bytes`(直近の GC が目印をつけた、生きているヒープ。Go 1.21 以降)も読み、最大を取る。`metrics.Read` だけで、stop-the-world はなく、結果は変えない。スキーマのバージョンは上げない(項目の追加のみ)。
- 意味: GC が確かめた、生きているヒープの最大。上限の下限の目安で、やわらかい上限はこれより低いと守れない(`memory_limit_exceeded`、`gc_cpu_fraction` が上がる)。上限がなくても、いつも出る。GC が 1 回も終わっていない短い実行は 0 で、項目がない。
- `memory_limit_exceeded` の条件(`peak > limit × 1.05`)は変えない。
- 出力を丸ごと比べる所では、`memory_peak_bytes` などと同じく、対象から外す。

### 訂正(2026-11-24): `live_heap_max_bytes` の意味

上の追記(2026-11-23)の「意味」の記述(「生きているヒープの最大」「上限の下限の目安」「これより低いと守れない」)は、誤り。本文と上の追記は、記録としてそのまま残し、ここで訂正する。

- `/gc/heap/live:bytes` は「直近の GC が目印を付けた量」で、GC がマークをしている間に確保された物も「生き」と数える。確保の速い段では、本当の生きている量より大きい。
- 測定(2026-11-24、対象 memos、素のバイナリ、同じ 1 回の実行で、強制 GC を入れたプロファイルと並べた。1 回だけ): 読み込みの段は、`/gc/heap/live` の最大 4.34 GB、強制 GC のあとの本当の生きている量 4.27 GB(一致)。要約の段は、`/gc/heap/live` の最大 4.76 GB、強制 GC のあとの本当の生きている量 2.21 GB(約 2.5 GB の差。マークの間に確保された物と、GC の間隔)。
- 正しい説明: GC が目印を付けた、生きているヒープの実行中の最大。マークの間に確保された物を含むので、確保の速い段(要約の段)では、本当の生きている量より大きくなりうる(上限の目安として見るときは、上側の値)。読み込みの段の山では、本当の生きている量に近い。これが上限より低いことは、上限が守れることの必要条件ではない(守れるかは `memory_limit_exceeded` と `gc_cpu_fraction` を見る)。
- 名前(`live_heap_max_bytes`)と、値の取り方は変えない。説明だけを直す(AGENT-GUIDE、GLOSSARY、コードのコメント、台帳の表示の説明も同じ日に直した)。

## 追記: 合格基準のメモリの測り方を footprint にする(2026-11-26)

`-max-memory` は、木の全体の footprint を約束する(macOS)。Linux は RSS。

**なぜ変えたか(ユーザーの決定、2026-11-26):** macOS は、Go が `MADV_FREE_REUSABLE` で返したページを RSS に数え続ける。そのため、C(Gitea)の RSS のピークは、同じ条件で 6.59〜7.09 GiB と約 0.5 GiB 揺れた。footprint のピークは 6.01 GiB で、毎回同じだった(ソフトな上限が約束するのは footprint のほうで、6.00 と 6.01)。RSS の揺れは、解析の変化ではなく、OS の数え方の揺れなので、合否に使うと、実行ごとの運で結果が変わる。

**変えたのは測り方だけ:** 線(A は 4 GiB、C、D、cocoon は 8 GiB)と、3 状態の判定の余裕(0.15 GiB)は、変えていない。測り方は `bench/deps_bench.py` の `run_watched`: `ps` で木(子孫と同じグループの孤児)を探し、その pid 群に `footprint -j` を 1 回呼ぶ(macOS は 0.5 秒ごと。Linux は `ps` の RSS のまま 0.25 秒ごと)。kill の上限(8 GiB の監視)も、判定と食い違わないよう、同じ footprint で見る。台帳には `peak_footprint_gb` と `mem_basis` を足し、RSS の合計は `peak_tree_gb` に参考として残す。`footprint` が読めない実行は、その実行ごと RSS で測り、`mem_basis=rss` と書く(混ぜない)。2026-11-26 より前の行は RSS のままで、書き換えない(`bench/heavy-ledger.md`)。

## 追記: 上限が低いときは GC を強くする(2026-11-26。承認: ＿＿＿＿＿＿＿＿(日付と言葉は、返事のあとに書く))

本文の 6.(「`GOGC` の固定は変えない」。ユーザーの決定、2026-11-23)の、上限が 4 GiB 付近のときの見直し。本文は、記録としてそのまま残す。

**事実:**
- 6. の根拠(上限 6 GiB の下では、`GOGC=100` と区別できなかった)は、上限が 4 GiB の線(合格基準 A: memos、`-max-memory 4GiB`)の下では当てはまらなかった。A の tree peak(`deps_bench.py` の同時刻の RSS の合計の最大、GiB。以下同じ)は、`GOGC=50` で 3.94(余裕 0.04〜0.08)、`GOGC=40` で 3.55〜3.59。読み込みのフェーズと要約のフェーズの 2 つのピークが同じ高さ(heap 3.33 と 3.34 GiB)で、`GOGC` は両方に効く(片方だけを下げる変更は、tree peak に効かない)。
- 交互 3 往復(memos-4gib、同じ binary で `GOGC` だけを変えた): 50 → 40 で、tree peak 3.95 → 3.59(-0.36)、wall 46 → 50 秒(+9%)、cpu_s 311 → 362(+16%)。結果(finding 182、検出、収束)は同じ。
- 上限が大きいと、同じ効果はない。C(Gitea、既定の上限 6 GiB)と D(dart_services)は、`GOGC=40` でピークが下がらなかった(C は 3 往復で +0.20 上がった)。ソフトの上限がピークを決めていて、`GOGC` ではないため。

**規則(`cmd/rivus/main.go` の `gogcFor`。適用は `applyMemoryLimit`):** 決まった上限(`-max-memory`、`GOMEMLIMIT`、既定のどれでも)に応じて、GC の目標(GOGC)を決める。
- 上限 6 GiB 以上、または上限なし: 50(今まで通り)。
- 上限 4 GiB 以下: 40(定数 `gogcLow`)。
- その間: 線形(5 GiB で 45)。
- 環境変数 `GOGC` があれば、それを優先する(今まで通り)。フラグと環境変数は増やさない。

**利用者への影響:**
- 影響を受けるのは、上限が 6 GiB 未満の実行。既定の上限は物理メモリの 1/4 なので、物理メモリが 24 GiB 未満のマシンの既定(16 GiB なら 4 GiB、8 GiB なら 4 GiB)と、`-max-memory` に 6 GiB 未満を渡した実行。
- GC が強くなる: 速度が約 9% 遅く(cpu は約 16% 増)、メモリが約 10% 減る(memos、4 GiB で 3.94 → 3.55〜3.59。1 つの対象の測定)。結果は変わらない。
- 24 GiB 以上のマシンの既定と、6 GiB 以上の上限は変わらない。C と D も変わらない(既定の上限は 6 GiB)。
- `-max-memory` を使わず、`GOMEMLIMIT` だけを設定している利用者にも、上限が 6 GiB 未満なら効く(`applyMemoryLimit` が、どの経路で決まった上限にも適用するため)。
- 環境変数 `GOGC` で、今まで通り上書きできる。

**まだ分かっていないこと:** 4 GiB の値(`gogcLow`)は、memos 1 対象の測定。同じ条件で、45 は tree peak -0.16、wall +3.7%(40 は -0.33、+7.8%)で、約半分の効きと約半分の費用。4 GiB より低い上限(2 GiB など)では、上限が生きているヒープより低くなりうる(本文の表)ので、40 より強くはしない。
