# ADR-049: グローバルを通る流れの経路に、書いた側の段を入れる（CORE-B / CORE-C）

- 状態: 有効
- 関連: DESIGN-shared-state
- 状態の詳細: 証拠は 069/087

**背景:** W がグローバルに source の値を書き、R がそれを読んで sink へ渡すとき、finding の経路は `R: load > R: sink` だけで、W のステップ（`W: source > W: store`）が無かった。グローバルのストアのセルは、要素だけを持ち（`set[e] = nil`、「ここで作ったものではない」のマーク）、**書いた関数の段を持たなかった**ため。読む側の状態は、グローバルのセルを、ストアから写して始まり、その要素の理由（`why`）は無いので、経路の再構成（`trace`）が、読む側から始まった。結果、finding の `source.func` が経路に出ない finding（`offSourcePath`、BENCH-2）が出た。

**決めたこと:** グローバルのストアに、要素ごとに、**最初に書いた関数の段**（`globalStore.writers`: セル、パス、要素 → `rope`）を持たせる。
1. `compute`: 関数が、ストアにまだ無い要素をグローバルに書くとき、その関数の中の経路（`trace`）を、`globalWrite.steps` に持つ（ストアにすでにある要素は、トレースしない。コストは、新しい要素だけ）。
2. `commitGlobals`: 要素が新しく入ったとき（最初の書き込み側）、その段を `noteWriter` で記録する。レベルの終わりに、（セル、パス、要素、書いた関数の ID）の順に整列してから一度だけ書くので、決定的（整列は後から足した。下の「書き込み側が複数のとき」）。
3. `traceUncached`: 理由が無い要素が、グローバルのルートのセルにあるとき（ストアから読んだ要素）、その段を、経路の先頭に足す。**セルの値（`why`）は変えない**（`set[e] == nil` の意味、「ストアから読んだ」の判定、`addLog` のバージョンは、そのまま。状態の間で共有される `why` を、書き換える危険も避けた）。

**finding の集合は変わらない**（経路の証拠だけが変わる）。前後で確かめた（C-1 の修正 c9aa412 の上）: go-curated、go-synth S / M、paramshare、dogfood、Dart / Rust のサンプルと curated で、finding の追加も削除も 0。経路が変わったのは、paramshare の 4 件（`globalw`、`gwrite`、`gwritehelper`、`gqueue`）、Dart のサンプル 1 件、Rust のサンプル 4 件（`static` を通る流れ）で、**経路に source の関数が無かった finding は、paramshare 4、Dart サンプル 1、Rust サンプル 3 → すべて 0**（`offSourcePath` は全部の場所で 0。`TestParamSourceSharedObject` の `off` の天井も 0 にした）。

**CORE-C（短い経路を残す選び方）:** `collect` は、同じ finding の経路が複数あるとき、短いものを残す（同じ長さなら関数 ID の順）。グローバルを通る経路は、書き込み側のステップが付いて長くなったので、選び方を変えなくても、source の関数が経路に出ない finding は 0 になった。選び方（「source の関数が経路に出るものを優先」）は、足していない。

**限界:** 書き込み側のステップは、**最初に書いた関数**のもの。同じ要素を、別の関数も書くとき（別の経路）は、最初の 1 つだけ。経路の根拠として十分だが、「どの書き込み側も」ではない（書き込み側の全部は、`global_var` の不確実性の候補に残る）。

**書き込み側が複数のとき（advisor の 3 つの質問。コード `internal/taint/engine.go` を読んで確かめた。実行で確かめてはいない）:**
1. どれを見せるか: **最初にストアへ入れた 1 つ**。`commitGlobals` が `merge`（セルに要素が無ければ入れて `true`）が `true` のときだけ `noteWriter` を呼ぶ。同じ要素の 2 つ目以降の書き込みは、`merge` が `false` なので、段は記録されない。
2. 短い経路の書き込み側があとから来たら入れ替わるか: **入れ替わらない**。要素がストアにある間は `merge` が `false` で、`noteWriter` は呼ばれない（`compute` も、ストアに既にある要素はトレースしない）。「短いほう」を選ぶのは、finding の経路の選び方（`collect`）で、書き込み側のステップの選び方ではない。
3. パスをまたいで決定的か: **パスをまたぐ部分は決定的**（最初に入った書き込み側のステップは、後のパスで変わらない。ストアはパスの間で保たれる）。**同じレベルの中は、整列で決定的にした**: `pendingGlobals` への追加は `commit` の中で、レベルの中で並列に実行される SCC（`runLevel`、`workers > 1`）が終わった順に入る。整列がなかったとき（009c0d5）、同じレベルの別の SCC の 2 つの関数が同じ要素を書くと、最初の書き込み側が、ゴルーチンの終わる順で決まり、**書き込み側のステップ（経路の前半）と `fingerprint["path@1"]` が、実行ごとに変わった**（`rivus resolve` が `path_changed` と読む。finding の ID と集合は変わらない）。`gwriters`（書き込み側 8 つ）と `TestDeterministic*`（`GOMAXPROCS` 1 / 4 / 既定、`-workers` 既定 / 2 / 16）で再現した。修正: `commitGlobals` が、`pendingGlobals` を（セル、パス、要素、書いた関数の ID）で整列してから `merge` する（`globalWrite.fn`）。**選び方に意味はない**（関数 ID の順で最初の書き込み側。短い書き込み側を選ぶものではない）。**全部の書き込み側は `global_var` の不確実性の候補に残る**。finding の集合は変わらない。この種の「並列の順が出力に漏れる」不具合は、常設の `TestDeterministic*` が見る。
