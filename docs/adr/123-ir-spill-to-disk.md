# ADR-123: IR は、関数ごとにディスクへ書き、コアが必要なときに読む(2026-11-24)

- 状態: 有効
- 関連: ADR-040(中立 IR の上に解析エンジンを移した)、ADR-118(精度を落とす仕組みの 3 条件)、ADR-120(不完全な解析の終了コード)、ADR-121(メモリの上限の既定)、`docs/PRINCIPLES.md` 8 節(ディスクに書く内容)、#397(`internal/irspill`: 符号化と保存)
- 要旨: IR の全関数を同時にメモリに持たない。extractor の出力は 1 関数ずつ `irspill` に書き、コアは `sg` の構築、要約、`sites`、`valuecalls` で、必要な関数だけを読む。結果は、メモリに持つ今の形と同一。書けないときはメモリに戻し、読めないときは止まる。利用者向けのフラグは足さない。実装は、この PR のあと。

**背景:** 読み込みのフェーズのピークは、memos で約 3.3 GB(GC のマーク時点)で、そのうち IR が約 1.6〜2.0 GB。Dart と Rust は出力の全部を `[]byte` に集めてから `ir.Program` にする。外部の設計者の返事(2026-11-24)で、IR の符号化と保存を、3 言語と、`go/ssa` をやめる作業で共通にする方針になった。#397 で符号化と保存の部品が入った(流れは変えていない)。lifted な SSA を先に済ませて手放す変更(#402)と、構文木の解放(#401)は入っている。IR の 1.6〜2.0 GB を外しても、コールグラフを作る時点の `go/ssa` の分は残る。それは別の作業で下げる。

**決めること:**

1. **extractor とコアの間の約束**
   - プロセスをまたぐ extractor(Dart、Rust)の出力は、今の JSON 行(`ir/stream.go`、`schema_version`。ADR-040)のまま。コアが 1 行ずつ復号して `Put` する。二進の符号化は extractor に実装させない(符号化と往復の検査を 3 つにしない)。
   - プロセスの中の extractor(Go。`go/ssa` をやめたあとの extractor も)は、`*ir.Func` を `Put` に渡す。`Put` の入口の型は、どの言語でも共通。
   - 二進の符号化(#397 の `internal/irspill`)は、コアの内部だけで、同じ実行の中だけ。バージョンの互換は考えない。符号化を変えるときは、`internal/irspill` の 1 か所と、往復の検査だけを変える。
   - 代替案: extractor が二進を書く。却下の理由: 言語ごとに実装が増え、extractor のバージョンとコアのバージョンの組み合わせが問題になる。
2. **記録の形**
   - 長さ(4 バイト)+ CRC32C(4 バイト)+ 本体(#397 のとおり)。関数ごとに閉じた文字列の表を持つ。1 つの記録の本体の上限は `MaxRecord`(256 MB)。
   - 鍵は (関数 ID, 通し番号)。同じ ID の関数が複数あっても、置き換えない(`PruneDeps` は、同じ ID が複数あることを前提にしている)。並びは、頭の表が持つ(Go は ID 順。Dart/Rust は出力の順)。`sg.Funcs` の順は今と同じ。
   - 頭の表(`Dep`、`Symbol`、`Recv`、`Params`、記録の場所など)と、呼び出し先の表、関数の値の呼び出しを持つ関数のマークは、メモリに持つ。
   - `sites.IRRef.Func` は、`*ir.Func` の参照ではなく関数 ID にする(読む側を `ir.Source` 経由にする最初の変更で行う)。
3. **失敗の扱い**
   - 読み出しの失敗(CRC の不一致、読み出しエラー、記録が別の関数)は、コアを止める。ID と原因を標準エラーに出す。何も報告せずに飛ばさない(IR は主な入力)。終了コードは、内部エラーの 1。ADR-120 の不完全な解析(4)ではない。
   - 書き込みの失敗、上限、ファイルなしのときは、その関数をメモリに持つ。結果は同じ。1 回、標準エラーに出す。解析の統計に `MemFuncs` と `Fallback` を出す。
4. **ディスクに書く内容**
   - IR が持つもの: 関数、型、ファイルの名前と位置、**コードの文字列の定数(1 つ最大 64 KB。ソースにある秘密の文字列も入りうる)**。
   - `docs/PRINCIPLES.md` 8 節に合わせる: 実行はしない。読むのは `irspill` の復号だけ。置き場は `$TMPDIR`、モード 0600、作ってすぐ名前を消す。`mmap` は使わない。
   - 書いた内容は、実行をまたいで使わない。`-assume-files-unchanged` と、ファイルの内容のハッシュによる同一性は、この記録に関わらない。実行をまたぐ再利用は、別の ADR で決める。
   - 残る危険: `$TMPDIR` が暗号化されていないディスクのとき、プロセスが死んだあとも、ブロックが読める可能性がある。
5. **上限と、メモリへの退避**
   - 上限の既定は 8 GB と、`$TMPDIR` の空きの半分の小さいほう。切れたら、以降の関数はメモリに持つ。
6. **切り替えと、既定にする条件**
   - **利用者向けのフラグは足さない。** 途中の変更(Go を `Put` 経由にする、Dart/Rust を行ごとの復号にする、valuecalls の重ね書きをディスクの実装で使う)の間は、内部の切り替え(テストの中か、環境変数。`-h` に出さない)で、メモリの実装とディスクの実装を選ぶ。最後の変更で、ディスクを既定にして、切り替えを消す。
   - 既定にする条件: 受け入れ条件のテスト(`internal/frontend/accept`)が通ること。memos で、時間と強制 GC のあとのライブヒープが悪くならないこと。
7. **検証**
   - 往復の検査: 全関数(`testdata`、zoo、curated、gogs、memos、Dart と Rust のサンプル)で `decode(encode(f))` が元と一致(`nil` と空は同じに扱う)。重複 ID のケースを含む。壊れた入力のファズ(パニックも、メモリの使い過ぎもない)。
   - 同一性: `debug extract -all` の JSON が、変更の前後でバイト単位で同じ。解析の JSON の全体のハッシュ(時間とメモリの統計を除く)が同じ。`-workers 1/8`。`rivus index` の DB が同じ。
   - 失敗の注入: 書き込みが失敗しても、上限が小さくても、結果が同じ。読み出しの失敗は、止まる。
   - 各変更は、前の変更の結果を使わず、ゼロから検証できる。

**結果(見込み):** 読み込みのフェーズのピークが下がる。見込みの桁は、Go で 0.4 GB 前後(GC のマーク時点)。IR 以外(変換のところの `go/ssa` など)は残るので、IR の 1.6〜2.0 GB が全部ピークから消えるわけではない。時間は数秒の増加の見込み。どれも推測で、測定で確認する。測定値は台帳(`bench/heavy-ledger.tsv`、`python3 bench/heavy_ledger.py --kind once`)に置き、ここには写さない。比べる基準は、#401 と #402 のあとの値(強制 GC のあとのライブヒープと、GC のマーク時点の最大を分けて見る。測り方は PR の本文と台帳の行を見る)。`sg` は全関数の本体を持つので、要約のフェーズのメモリは変わらない。それを下げる(`sg` の本体を外す)のは、別の ADR。

**検討したほかの案:** IR を細身にする(`ir.Instr` を小さくする): ディスクに出したあとは効きが小さい。JSON をそのまま書く: 復号が遅い。`encoding/gob`: 型を変えると壊れ、遅い。
