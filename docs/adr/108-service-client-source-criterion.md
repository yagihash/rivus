# ADR-108: サービスのクライアントのモデルで、何を source にするかの基準(その値を誰が書いたか。2026-11-23)

- 状態: 有効
- 関連: MODEL-RUNBOOK(2 節)、MODEL-QUEUE
- 状態の詳細: 既存の `dart-gcp` などは変えない(見直しは課題 #158)
- 要旨: `dio` の `Response.data` の判断(#202)

**背景:** 組み込みモデルは、サービスのクライアント(GitHub、Pub/Sub、チャットなど)を広げていく(ADR-096、ADR-097)。応答の値を source にするかは、行ごとに判断が分かれた(Dart の `dio` では、汎用の HTTP クライアントの前例(`dart-http.yaml`)に合わせて、`Response.data` を source にしなかった。一覧の案は source にする形だった)。「リクエストか、レスポンスか」では、決められない。

**決めたこと:**
1. **基準は、「その値を誰が書いたか」。** サービスの利用者(第三者)が書いた内容は source にする。そうでない値は source にしない。
2. **汎用の HTTP クライアント**(`dart-http`、`dio`、Go の `net/http` のクライアントなど)は、相手が分からないので、応答を既定で source にしない(相手のサーバが、利用者の入力を返すとは限らない。決めるのは、使う側のルール)。
3. **サービスのクライアント**は、型から「サービスの利用者が書いた内容」と分かる値がある。それは source にする。例: Issue や PR の題と本文、コメント、ファイルの内容、コミットメッセージ、メッセージの本文、チャットの発言。
4. **サービスが決める値は source にしない**: ID、時刻、SHA、件数、URL のうち、サービスが組み立てるもの。
5. **迷う値は、source にしない。** モデルのファイルのコメントに、「入れなかった理由」を書く(レビューの人が、入れるかを決め直せる)。
6. **既存のサービスのクライアントのモデル(`dart-gcp` など)は、この ADR では変えない。** 同じ基準で見直す課題を 1 件立てた([課題 #158](../issues/158-service-client-sources-review.md))。
7. 手順書(MODEL-RUNBOOK.md の 2 節)の「追加」の段が、この ADR を参照する。一覧(MODEL-QUEUE.md)の案(境界の案)と違う判断をしたときは、PR の本文に理由を書く(手順書 5 節)。

**しないこと(この ADR では)**: 汎用の HTTP クライアントの応答を、使う側のルールで source にする書式の追加、source の確度(信頼度)の段階づけ。
