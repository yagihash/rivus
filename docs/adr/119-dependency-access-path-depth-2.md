# ADR-119: 依存の関数のアクセスパスの深さの既定を 2 にする(2026-11-23)

- 状態: 有効
- 関連: ADR-014(アクセスパスの深さ k)、ADR-117(`access_path_truncated`)、ADR-118(規模のために精度を落とす仕組みの 3 条件。この深さは、過大近似の向きだけ・順序とマシンに依らない・落とした所を出力が言う、を満たす)、docs/issues/189(場所ごとに決める)、PR #302(`-dep-k`、診断)
- 要旨: 依存の関数(`Func.Dep`)は深さ 2、プロジェクトの関数は 3(`-k`)のまま。`-dep-k 3` で前の動作。`-dep-k 0` は `-k` と同じ

**背景:** 依存を読む解析が終わらない対象がある。診断(`-pass-stats` の `summary_sizes.distinct`)で、要約がふくらむ原因が、パスの深さと分かった。ガードは要素を増やさない(同じ要素が別のガードで何度も出ることはない)。依存の関数だけ深さを下げる実験(`-dep-k`)で、既定の集合を保ったまま終わる対象が増えた。

**決めたこと:**
1. 依存の関数の深さの既定は 2(`-dep-k`。`taint.DefaultOptions().DepK`)。プロジェクトの関数は 3(`-k`)のまま。**自分のコードの深さは変えない**。
2. 前の動作(依存も深さ 3)は、`-dep-k 3` で戻る。`-dep-k 0` は「`-k` と同じ」で、`-k` を変えると依存も同じ深さになる。`summary.access_path_depth: {project, dependency}` が、使った深さをいつも言う。
3. 切ったパスを値が通った段には、`access_path_truncated`(ADR-117)が付く。切ったために出た流れは、finding から読める。

**深さと結果の関係(分かっていること):**
- 理論: 切ったパスは、その下すべてを表す。したがって深さを下げると、**流れは減らず、増えるだけ**(別のフィールドへの流れが出る=過検出が増える)。深くすると、要素が増える(深さ 3 → 2 で、AWS SDK のサーバは 100 万以上 → 23.8 万、深さ 1 で 4.6 万)。要素が増えると、セルの要素の上限(96 件で全体にまとめる)、1 つの出力の上限、作業量の上限(`budget`)、時計の上限(関数ごと、全体)に当たり、**終わらない、または、粗くなる**ことがある。時計の上限に当たると、結果がマシンの負荷で変わる(`stats.load_dependent`)。
- 測定(同じコミットで、依存の深さだけを変えた。表の ID は finding の ID の集合):

| 対象 | 深さ 3(前の既定) | 深さ 2(新しい既定) | 深さ 1 |
| --- | --- | --- | --- |
| Go: AWS SDK のサーバ | 終わらない(要素 100 万以上、12 GB) | 終わる(23.8 万、4.0 GB)。finding は同じ 1 件 | 終わる(4.6 万、1.3 GB)。同じ |
| Go: gcp | 終わる。finding 27 | 同じ ID の集合 | 同じ ID の集合(全部の関数で `-k 1` にすると、4 件増える) |
| Dart: gcp | 終わる。19 | 同じ ID の集合 | 同じ ID の集合 |
| Go: 実プロジェクト(AWS SDK に依存) | 8 GB で止められる(終わらない) | 終わる。153 件 | 終わる。153 件(同じ sink 28 個。代表の source が 1 組入れ替わるだけ) |
| Dart: `package:analyzer` に依存する 2 つ | 終わらない | 終わらない | 終わらない |

- 軽い層(`bench/compare.sh --light`。深さ 3 と 2 の比較): go-curated、dart-curated、rust-curated、go-synth-S、go-scale、zoo 3 言語、gogs 2 つ、gin-vue-admin、go-test-bench、dart-pub、gophish、casdoor で、finding の増減は 0。経路が変わった finding(代表の経路の長さのみ): gogs 11(2 つとも)、gin-vue-admin 80、casdoor 1。`other_sources` の変化は gophish の 1。parseable は、Rust の extractor がサンドボックスで失敗し、**取れていない**(自分のコードのベンチ rust-curated、zoo-rust は、ID の集合が同じ)。
- 境界のテスト(`cmd/rivus/depth_boundary_test.go`): 依存の構造体の 3 段目の値 C と、同じ 2 段目の隣 D、同じ 1 段目の隣 X。深さ 3(前の既定)は、C だけ、深さ 2 は、C と D(精度が落ちる所。注記が付く)、深さ 1 は、C と D と X。**流れ(C)は、どの深さでも見つかる**。深さ 2 で D が出るのは、**この既定の変更で精度が落ちる形**(`@fp` 相当。数は課題 #189 で扱う)。
- 深いほど良いとは限らない: 深さ 3 で、AWS SDK 系の対象は終わらず、結果が出ない。深さ 2 で終わり、finding の集合は変わらない。測った範囲で、深さ 3 のほうが良い finding を出した対象は、なかった。ただし、**境界の形を持つ対象は測っていない**(境界のテストが、その形が実際にあることを示す)。
- 深さでは終わらない対象: Dart の `package:analyzer`(巨大な再帰のかたまり、SCC 1 万 2 千関数。深さ 1 でも終わらず、要素はむしろ増える)。Go の gcp は、要素の 79% が source のラベルで、深さの効きが小さい。

**既知の見逃し(Go の実プロジェクト。測定の条件にはしない):** 文字ごとの読み書き(数値は既定で追わない)と、`sinks_lost=6`(`-no-deps` で出た過大近似の sink を、既定では、文字ごとの切れ目で失う)。どちらも、深さによる変化ではない。

**既知の違い:** Dart は、同じ深さの設定で、Go より 1 段粗い(参照の `*` が 1 段に数えられる。課題 #190)。新しい既定 2 は、Dart では Go の深さ 1 と同じ粗さ。Dart で、同じ内側のオブジェクトの隣のフィールドが、どの深さでも区別されないのは、深さと別の問題(課題 #191)。

**しないこと:** 場所ごとの深さ(課題 #189)。プロジェクトの関数の深さを変えること。
