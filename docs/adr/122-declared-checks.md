# ADR-122: 検査の関数は、ルールで宣言する。宣言した検査で、finding を止める(2026-11-24)

- 状態: 有効
- 関連: 課題 #169、ADR-035(値に依存するサニタイズ)、ADR-118(精度を落とす仕組みの 3 条件)、`docs/MODELING.md` 4b-1(`neutralises`)
- 要旨: 検査の関数は、利用者がルールに宣言する(`guards:`)。宣言した検査を通った値は、サニタイザと同じに止める。止めた場所は `suppressions` に、どのルールのファイルの、どの宣言かを出す。解析が構造から見つけるのは、狭い形の事実の uncertainty だけで、finding は消さない。実装は、まだ始めない。

**背景:** Go の実際のプロジェクトでの利用(2026-11-23)で、値を検査してから使う形(検査が通らなければ失敗を返す関数)を、利用者のルールで宣言する書式がないことが分かった。サニタイザは値を変える関数のためで、「通らなければ先に進まない」検査は、同じ形では書けない。課題 #169 は、2026-11-23 に「解析が構造から検査を見つけ、finding に注釈を付ける」方向を決めていた。外部の設計者の見直しと、ユーザーの判断(2026-11-24)で、本体を宣言に変え、構造から見つけるほうは狭める。

**決めたこと:**
1. **本体は、検査の関数の宣言。** 利用者が、ルールのファイルに「この関数は、この引数を検査する」と書く。
2. **宣言した検査で、finding を止める**(サニタイザと同じ)。止めた記録 `suppressions` に、どのルールのファイルの、どの宣言で止めたかを出す。ADR-118 の「省いたものは必ず報告する」に合わせる。
3. **解析が見つけるほうは、狭める。** プロジェクトの関数の本体の中に、引数への条件で失敗(`error` か `false`)を返す分岐があるときだけ、「この関数は、引数の検査に見える分岐を持つ」と事実として注釈を付ける。「検査を通った」とは書かず、finding は消さない。
4. **順序:** 宣言の実装は、文字ごとの汚染(#185)の実装のあと、検査を既定にするかの判断の前。実装は、この PR のあと。始めるときは、否定のセル(止めない形)を先に、肯定のセルは memos の形を 1 つ。
5. **合格基準の条件:** 宣言ができたら、修正のあとのコミットを、宣言のルールつきで、合格基準の条件にする(`bench/passline-baseline.md`)。それまで `quiet_after_fix` は記録だけ。

(宣言の中身の管理は、rivus の外。ルールをリポジトリに置ける人が、見落としの責任を持つ。ユーザーの判断(2026-11-24)。対象の中のルールの数に、検査の宣言を足す条件は、相談役の案だったが、取り下げた。)

## 宣言の書式の案

`sanitizers:` と同じ階層に、`guards:` を置く。

```yaml
guards:
  - symbol: example.com/app/validate.SafeName    # 検査の関数(サニタイザの symbol と同じ書き方)
    checks: [arg0]                               # 検査される引数(arg0、arg1、recv)。必須
    passes_when: no_error                        # 通ったときの結果: no_error | true | false | error
    neutralises: [path_traversal]                # 必須。サニタイザと同じ。この種類の sink だけ止める
```

- 検査の関数が、`passes_when` の結果を返したときだけ、`checks` の引数の値は検査を通ったものとして、`neutralises` の種類の sink に届かない。ほかの種類の sink には、そのまま届く。
- `neutralises` を書かない宣言は、読み込みで断る(サニタイザの「古い意味」は、引き継がない)。空の `neutralises: []` は断る(宣言する意味がない)。
- 検査の関数の戻り値の `error` か `bool` で分岐し、通らない腕が sink の前で抜けるときだけ、止める(下の表)。

## 止めない形の表

次の形は、止めない(finding を出す)。宣言があっても、見落としにしないため。

| 形 | 止めない理由 |
| --- | --- |
| 検査した値と、sink に届く値が違う(検査のあとで、値を作り直す、足す、別の変数から取る) | 検査の対象と、sink の値のつながりが、解析で示せない |
| 結果を捨てる(`validate(x)` の戻り値を見ない) | 通らなくても、先に進む |
| 片方の経路だけ(`if` の片方で検査して、もう片方は検査なしに sink へ) | 検査なしの経路が残る |
| sink より後に検査する | sink に届いたあとの検査は、止めない |
| 結果を変数に入れて、あとで分岐する | 変数と分岐の対応を追わない(最初の実装) |
| `panic`、`os.Exit`、`log.Fatal` などで抜ける | 抜け方を、通らない腕として数えない(最初の実装。広げるかは課題にする) |
| ループの `continue`、`break` で抜ける | 次の周回で、別の値が sink に届きうる |

止めるのは、「通らない腕が、`return` で、sink の前に出る」形だけ。止めるかどうか迷う形は、止めない側に寄せる。

## 構造から見つける決め方を、取り下げた理由

課題 #169 の最初の方向は、「汚染した値を引数に取る呼び出しの結果で分岐し、一方の腕が抜ける形」を、構造から検査として決めて、finding に注釈を付けることだった。取り下げる。Go では `f, err := os.Open(name); if err != nil { return }` の `err != nil` が、全部この形に当てはまる。検査でないものが、検査として注釈される(finding のそばに「検査を通った」と出れば、読む人は安全と読む)。名前を使わない決め方では、検査と、ただの失敗の処理を分けられない。分けるのは、利用者の宣言(人の判断)に任せる。

解析が見つけるほうは、プロジェクトの関数の本体に限り、事実の uncertainty にとどめる(決めたこと 3)。uncertainty は finding を消さず、止めもしない。宣言を書く人が、候補を見つける助けにする。

## ADR-118 の 3 条件との関係

ADR-118 は、規模のために精度を落とす仕組みの基準で、過大近似の側(流れを足す向き)を求める。検査の宣言は、流れを止める(減らす)向きなので、規模の仕組みではない。3 条件との関係は次のとおり。

- (i) 過大近似だけ、の条件は、満たさない。代わりに、利用者の宣言による(人が責任を持つ)。宣言のない検査は、止めない。
- (ii) 順序に依らない: 満たす。宣言と、関数の構造だけで決まる(時間、負荷に依らない)。
- (iii) 止めた場所が報告される: 満たす。`suppressions` に、ルールのファイルと宣言を出す。

## サニタイザとの関係

- 止める仕組みは、サニタイザの `neutralises`(MODELING 4b-1)と同じ。sink の種類を限り、ほかの種類には届く。`neutralises` が必須なのも同じ。
- サニタイザは、値を変えて、ラベルを付ける。検査は、値を変えずに、通らない経路を断つ。そのため、検査は ADR-035 のガード(値に依存するサニタイズ)の、「分岐の腕で値の扱いが変わる」考え方に近い。ADR-035 の自動のガード(引数に由来する条件を記録するだけで、判定しない)は、この ADR で変えない。
- 止めた記録は、`suppressions`(ARCHITECTURE の出力の記録)に、サニタイザの停止と同じ形で出す。サニタイザの `builtin` と人が書いたものは今は残さない(確認済みで膨らむため)が、検査の宣言は、**利用者のルールで、見落としの原因になりうるので、いつも残す**。

## 帰結

- 利用者は、検査の関数を宣言できる。誤った宣言は、見落としになる。それは、ルールをリポジトリに置く側の管理で、rivus は、止めたルールを記録で示す。
- `docs/MODELING.md` に `guards:` の節と、`summary.project_rules` の数え方は、実装のときに足す(この ADR は書式の案)。
- 課題 #169 は、宣言が本体、解析が見つけるほうは狭めた形、に書き換える。
