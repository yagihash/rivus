# ADR-047: パラメータの関数の呼び出しを、要約の記号的な出力にする（コールアウト）

- 状態: 有効
- 関連: DESIGN-callouts
- 状態の詳細: 状態: 棚上げ→精度のため再開。段階 2 は 071 が実装; 訂正・追記あり(書き方を保つ)。状態注記
- 要旨: 状態の注記が本文中に 2 つある

**背景:** `db.WithTx(ctx, func(ctx) error {...})` のように、共有ヘルパーが、呼び出し元の渡した関数を呼ぶ。Go の関数値の呼び出しの候補は、型から作る（VTA）ので、ヘルパーの中の `f(ctx)` は、型の合う全クロージャ（Gitea で 208）を呼ぶ。ADR-045 は、候補に「パラメータ p の関数は、この候補」というガードを付け、呼び出し元が渡した関数で絞った。しかし、(1) ヘルパーの要約は、全候補のクロージャの要約を適用して作るので、呼び出しグラフでは、ヘルパーから全クロージャへエッジが張られ、無関係な関数が 1 つの SCC につながる。(2) ガードは、ヘルパーが渡された関数を別のヘルパーに渡す（中継: `WithTx` → `txWithNoCheck(f)`）と、外側の呼び出し元に伝わらず（ADR-045 の限界）、絞れない。(3) 呼び出し元と別の関数で作ったクロージャがキャプチャした値は、束縛が付かず、`KUndef` で埋まって、何も報告せずに失われる（キャプチャした値が、何も報告せずに失われる問題。`internal/valuecalls` の `Bind` は、クロージャを作った関数の中でだけ付く）。(4) 候補が 8 を超える呼び出し（`valuecalls` の `most`）は、解決されず、不確実性が 1 つ出るだけで、中の sink、throw、書き込みが失われる。

**測定（Gitea、-deps、2026-11-21、未収束の旧バイナリ）:**
- 呼び出しグラフ（エッジを種類で分ける）: 最大の SCC は、静的だけで 86、interface を足して 304、関数値を足して 1,053、両方で 3,370。
- 案の SCC（実装なしで数えた）: V0（今）3,370、V1（パラメータ由来の関数値のエッジを消すだけ）322、V2（呼び出し元が渡す関数へのエッジを足し、中継は上へ送り、その他は全候補）322（interface のエッジを除くと、91、91、171）。呼び出し元の形（508 か所の呼び出し点に対する、呼び出し元の引数）は、直接渡す 1,677、パラメータの中継 250、キャプチャの中継 1、その他 150。この数字は、「呼び出し元が見えない」例外（entry、静的でない呼び出し元）と `go` / `defer` を算入していない。実装後の最大 SCC は、下の検証に書く。
- 漏れの直接測定: ヘルパーの要約を、クロージャを直接渡した呼び出し元に適用した 2,240,695 回のうち、97 %（2,171,496 回）が、渡していない候補の関数を経路に含む。`WithTx` の要約の出力 5,377 要素のうち、関数値のガードが付いているのは 18。落ちた理由は、中継（ADR-045 の限界）で、ガードの上限（4）や join ではない（関数値のガードを上限の外に置く実験で、漏れも、新しい流れの増え方も、変わらなかった）。
- 中継でガードを外へ伝える実験（呼び出しの実引数が今の関数のパラメータそのものなら、`Call` を付けずに書き換える）は、`ctxhelper_relay` の中継の過検出を 65 件から 17 件に減らしたが、キャプチャ経由と、中継が自分でも `f` を呼ぶ形が残る。Gitea では、pass 6 の新しい流れが 30,877 まで下がったが、結果の組み立て（`collect`）でメモリが尽き、収束したかは決まらなかった。収束するかどうかは、**決まらなかった**。
- 要約が変わる原因は、新しい流れの増加（最大 SCC の変化の 97 % 以上）で、ガードの変化だけの変化は 1〜3 %。
- 今の main でも、ヘルパーが `f` を 2 か所で呼ぶだけで、渡していない関数に漏れる（`ctxhelper_relay` の `TwoSites*`）。ガードのキーに呼び出しの位置が入る仮説は、キーから位置を除いても結果が変わらず、確かめられなかった。コールアウトでは、この形は直接渡す形として絞られる。

**決めたこと:**
1. **コールアウト。** パラメータ（またはキャプチャした変数）が持つ関数の呼び出し（Go の関数値、Dart の関数値、Rust の `Fn::call`）は、ヘルパーの解析で、候補の要約を適用しない。ヘルパーの要約に `Callout{Param, Base, Cands, NRes, NArgs, Deref}` を持たせる。呼び出しの結果、throw、ポインタ引数の指す先に、**仮想のパラメータ**（`Base` から連番。0 が throw、1.. が結果、9.. が引数）の `Param` 要素を置く。あとは、普通のパラメータの要素と同じに流れる（パス、サニタイザの演算、`widen`、`SinkReach` がそのまま使える）。呼び出しに渡す引数の中身は、要約の出力（`OutCallArg`、Index は仮想のパラメータ）として持つ。
2. **呼び出し元での具体化。** 呼び出し元が、ヘルパーの要約を適用するとき、(a) コールバックに渡す引数の中身を、合成した値（`synth`）に、普通の出力と同じに展開して置く、(b) コールバックの要約を、その値に適用する、(c) コールバックの結果、throw、書き込みが、仮想のパラメータの値になる（`expandParam` が合成した値を引く）。(a)〜(c) は、値が動かなくなるまで繰り返す（上限 16 回。超えたら `not converged`）。呼び出し元がどの関数を渡したかで、3 通り: **直接渡す**（`sg.ExactClosures`: 関数、その場で作ったクロージャ、それらのコピーと φ）: その関数だけを適用する。**中継**（実引数が呼び出し元自身のパラメータ）: 呼び出し元が、同じコールアウトを自分の要約に載せ直す（呼び出し元の仮想のパラメータで）。呼び出し元の呼び出し元が適用する。**その他**: 候補の全部を適用する（今と同じ。候補が 0 なら `unresolved_callee`）。
3. **束縛（キャプチャした値が失われる問題）。** `ExactClosures` は、クロージャの束縛（`make_closure` の引数 = キャプチャの値）も返す。コールバックの要約に、その束縛を FreeVars として渡す（キャプチャした変数への書き込みは、呼び出し元の値のセルに届く）。メソッドを関数として取った値（Dart の tear-off）は、FreeVars を持たず、束縛が先頭の引数になる。Go でキャプチャした変数を参照で持つ（`load` した FreeVar を呼ぶ）呼び出しは、`Deref` で、呼び出し元の `alloc` に 1 回だけ入れた値を読む（ほかに使われ方がなければ）。
4. **呼び出しグラフ。** `taint` の順序（`order` / `levelsOf` / `callers`）のエッジだけを変える。コールアウトの呼び出し点から候補へのエッジを消し、呼び出し元から、渡した関数へのエッジ（その他の呼び出し元は全候補へのエッジ）を足す。**`sg` の `CandidateFns`、`Program.Reachable`、graphdb のエッジ、`provenance` は変えない**（構造の層は変わらない）。`callers`（要約が変わったとき、再解析する関数）にも、同じエッジを使うので、クロージャの要約が変わると、それを適用した呼び出し元が再解析される。
5. **外す条件（今の扱いに戻す）。** コールアウトにしない: `go` / `defer` の呼び出し、ヘルパーが entry / init、ヘルパーを呼ぶものに静的でない呼び出し元がある（値や interface 越し）、呼び出し元が 1 つもない、パラメータ由来でない（φ で混ざる、フィールドから読む、戻り値）、モデルのある候補、本体のない候補（ルール、モデルは今のまま呼び出し点で適用する）。**キャプチャした関数を呼ぶクロージャは、渡される以外（返す、保存する）に使われるなら、コールアウトにしない**（誰かが呼ぶが、誰も適用しない。go-test-bench の `makeHandler` で、実際に finding が落ちた）。呼び出し元が自分のパラメータを渡すとき、その呼び出し元が上の条件に該当するなら、中継せず、全候補を適用する。exported / library でも、静的な呼び出し元が見えていれば、コールアウトにする（見えない呼び出し元は、もともと、解析に入っていない）。
6. **再帰の上限。** コールバックの要約を適用する連鎖で、同じ関数を、1 つの連鎖に 3 回以上適用するときは、その経路を切る（`path_limit` の注記）。
7. **切り替え。** `Options.CtxCallbacks`（コマンドの `-ctx-callbacks`、環境変数 `RIVUS_CTXCB`）。段階 (a) では、既定は off（off は今と完全に同じ）。

**健全性の論証:**
- 順序と dirty の依存は、不動点の結果を変えない。変えるのは、要約の作り方（ヘルパーが候補を適用する → 呼び出し元が、渡した関数を適用する）。ヘルパーが使っていた全候補の流れは、呼び出し元ごとに、(i) 直接渡す: 渡した関数の流れだけ（渡していない関数の流れは、実際には起きない）、(ii) 中継: 上の呼び出し元が適用する、(iii) その他: 全候補（今と同じ）、で覆う。(ii) の「呼び出し元が適用する」は、条件 5（呼び出し元が静的な呼び出しだけ）で成り立つ。
- 見逃しを作りうる場所は、「誰も適用しない」ことで、条件 5 が、これを塞ぐ。
- 網羅の不変条件（旧の（ヘルパーの呼び出し点, 候補）の組は、新でも、どこかの呼び出し元が適用するか、ヘルパー自身が適用する）は、`planCallouts` の、呼び出し元が適用するエッジと、ヘルパーが適用するエッジ（コールアウトにしない呼び出し点）で、構造的に成り立つ。

**限界:**
- 本体のない候補（ルールが名前で適用する）は、今のまま、呼び出し点で適用するので、中継で絞れない。
- 呼び出し元が、関数を返り値やフィールドから渡す形は、全候補を適用する（今と同じ）。
- Rust は、クロージャの呼び出しが `Fn::call` のメソッド呼び出し（動的なディスパッチ）で、コールアウトに入れたが、`&self` で呼ぶ形（`&f` を渡す）は、実引数が参照で、直接渡す形に入らない。`bench/rust-curated` の `@fp`、`@noisy` は変わらなかった（interface のディスパッチのガード（`makeDispatchGuards`）の課題で、案 1 の範囲）。
- コールバックが、別のコールバックを受け取る形、キャプチャした変数を複数回書く形は、条件 5 と `Deref` の条件（1 つの値）で、全候補に戻ることがある。

**状態: 棚上げ（2026-11-21）。** Gitea の収束には、案 2 は不要だった（ADR-055: 収束させたのは、`reflect` のモデル）。この ADR のコード（ブランチ `worktree-agent-a26babddee62fea72`）は、フラグ（`-ctx-callbacks`、既定 off）つきで、残す。既定 on の議論は、ADR-059（クロージャのキャプチャした値を、作った場所で適用する）のあと、「追加で直る件数」とコストを並べて決める。

**検証（段階 (a) までに分かったこと）:**
- dart-curated（on）: 見つかった `@miss` が 16（32 → 16）、検出されなくなった `@fp` が 2、失ったものは 0。go-curated と rust-curated は変わらない（Rust の `fnself.rs` の 7 か所は、`&self` で呼ぶ形が直接渡す形に入らず、直らない。interface のディスパッチのガードの課題）。
- go-synth S と M: finding の ID も、uncertainty の数も、最大 SCC も、同一（M の時間 30.6 秒と 30.7 秒）。
- gogs（`bench/gogs/rules.yaml`）: 6 パスで収束、43 秒（off は 39 秒）。finding の集合は、sink が同一で、各 sink に届く source が 18 → 20（候補が 9 つ以上で未解決だった呼び出しを、呼び出し元が具体化した結果、コールバックの結果が流れるようになった。`RIVUS_KNOB_NOOVERFLOW` で止めると消える）。
- Gitea（`reflect` のモデルあり）: on は 6 パス、137 秒、finding 43（off は 37、sink は 24 → 26）、最大 SCC 3,134（事前測定は 322）。CVE の再現率は 1/3 のまま。
- **SCC が 3,134 にしか割れなかった理由**（計画だけを実行して測定）: 再帰するヘルパー 48 個と、返す・保存するクロージャ 164 個を、旧方式に戻したため。戻さない計画の最大 SCC は、再帰を戻さないと 459、両方戻さないと 322（事前測定と一致）。

**再開するときの最初の作業:**
1. 「再帰を戻さない」設定（`RIVUS_KNOB_NOREC`）で、gogs と Gitea が収束するかを測る。再帰するヘルパーを旧方式に戻した理由は、gogs の `go-org.parseOne` が、要約を 2,334 要素に膨らませたことだった。`absorbWhole`（ADR-057）と `reflect` のモデル（ADR-055）のあとでは、膨らまないかもしれない。
2. Gitea の finding の入れ替わり（37 → 43、出ていく 5、入る 11）を、1 件ずつ分類する。
3. ADR-059 のあと、dart-curated の `@miss`（16 件が見つかった）が、ADR-059 だけで、どれだけ見つかるかを測り、追加で直る件数を出す。
4. 上限（1 つの関数のコールアウト 6 か所、中継 4 か所）は、`RIVUS_NOCAPS=1` で、gogs の結果が変わらなかった（時間も finding も）。Gitea と ech0 で確かめて、不要なら消す。

**状態: 精度のために再開する（設計: `docs/DESIGN-callouts.md`、2026-11-21）。** 棚上げの理由は、収束に不要だったことだった。再開の動機は、**収束でなく精度**: (1) 別々のクロージャを同じヘルパーに渡す 2 つの呼び出し元が、互いの流れに混ざる（Rust の `two-callers`、3 言語の `relay`、parseable の XTALK）。(2) ライブラリに渡したクロージャの結果が失われる（Rust の `map_err` 285、`Iterator::map` 199、Dart の `Iterable.map` 110）。(3) 作った場所で適用する仕組み（ADR-059）は、結果と throw を適用せず、キャプチャと引数の両方に依る流れを見つけられない。再開の形は、この ADR の最初のバージョンと 3 つ違う: ライブラリのモデル（YAML の `calls`）と同じ表現にする（段階 2 を先に）、`go` / `defer` を外さない、条件のうち「exported なら戻す」を、起点のあるプログラムでは閉じた世界（`closed_world_entry`）にする。このブランチのコード（`-ctx-callbacks`）は、新しい要約の型に合わせて載せ直す。上の「再開するときの最初の作業」は、載せ直しの前に、設計の段階の受け入れとして行う。
