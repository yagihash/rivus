## 4. 「モデルを書く」標準の流れ(4 段)と、型からの生成

報告(Go の実際のプロジェクトでの利用から)された事実: (1) 型の情報から、保守的な規則で粗いモデルを生成できる(戻り値が数値・bool・なしなら `pure`、それ以外は、レシーバとデータを運びうる引数 → `results`、書き込み先の引数には方向のある流れ、`context` は流さない)。直接 import する外部のパッケージの API 全体で、解析なし、約 3 秒。ある対象で、モデルのない呼び出しが 11,466 → 436、finding と sink の集合は不変。別の大きい対象でも 72% 減。(2) 差分テスト(本体とモデル、ライブラリごと、依存込みでも 400〜700 MB)を、約 15,000 の関数とメソッドで実行。体系的な誤り 2 つを直したあと、MISS は意図した 3 件だけ、一致は 90〜99%、残りは妥当な過大な近似。(3) 新しい体系的な誤り: 書き込み先を取る関数(`Decode`、`Read(p)`、`Write(p)`、`SetBytes` など)で、書き込み先の引数が、**戻り値(error に入力の型や値が入る)とレシーバへ流れる経路**を、モデルが落としがち。書き込み先の引数は、読み取り元にもなる。(4) 生成器を直しても、古い生成物が残る(再生成の対象の入れ忘れ)。**これらの数字は、報告された数字で、rivus の側では未確認**(この文書の測定は、rivus の側で測った 3 節と 4.4 だけ)。

### 4.1 標準の流れ

| 段 | 内容 | 道具 | 出力 |
| --- | --- | --- | --- |
| (i) 生成 | 型から粗いモデルを生成する。`origin: generated`。書き込み先の引数は、`results` とレシーバへの流れの読み取り元にも含める | 生成器(言語ごと。4.2) | `internal/model/builtin/<lang>-<package>.yaml`(生成の部分) |
| (ii) 照合 | 差分テストで本体と比べる。MISS は 0。EXTRA は、意図した差として記録(理由つき) | `bench/model-diff`(段階 1) | 差分の一覧。EXTRA の記録 |
| (iii) 追加 | sink / source / sanitizer と、呼び返し(`calls:`)だけを、人か LLM が足す。`origin: human` か `llm` | `rivus models coverage`、肯定と否定のフィクスチャ(zoo) | 手の行 |
| (iv) 宣言 | パッケージに「本体を読まない」を付ける。2 節 5 の条件(i)〜(iii)を満たしたものだけ | 宣言の書式(段階 2) | 宣言 |

この流れで、「pub と Go の人気のパッケージを順にモデル化する」作業の 1 パッケージあたりの時間は、(iii)の人の作業(sink、source、呼び返し)だけに縮められる見込み。流れの速さは、見積もりで、実測ではない。

### 4.2 型の情報の取り方(言語ごと。調査した事実)

| 言語 | 取り方 | 既存の足場 | 注意 |
| --- | --- | --- | --- |
| Go | `go/packages` の `NeedTypes`(`NeedSyntax` なし)で、パッケージの公開の API を `go/types` で列挙する(関数、メソッド、インターフェースのメソッド、フィールド)。報告の方法と同じ | `internal/frontend/gossa/load.go`、`rivus models coverage` のテンプレート(`stub`) | ジェネリクス、埋め込み、エクスポートされた型エイリアスの扱い |
| Dart | analyzer の `LibraryElement`: `exportNamespace` の公開の宣言、`ClassElement` のメソッドとコンストラクタ、型つきのシグネチャ(`FunctionType`)。本体の解決は要らない | `extractor/dart/lib/extract.dart` が `LibraryElement` を既に使っている(`lib.firstFragment.libraryImports` など)。`names.dart` が、IR のシンボル名(`package:...#Class.method`)を作る | シンボル名の綴りは、extractor が出す名前と一致させる(同じ `names.dart` を使う)。`part` と再エクスポート |
| Rust | rustdoc JSON(`cargo +<固定の nightly> rustdoc -- -Zunstable-options --output-format json`)が、公開の項目と、ジェネリクス・トレイト境界つきのシグネチャを出す。代わりに、`extractor/rust/` のドライバ(`rustc_public`)で、`tcx` の公開の項目の `fn_sig` を取る | `rust-toolchain.toml` に固定の nightly がある。ドライバは、`all_local_items` を既に使っている。`cargo metadata` は、パッケージの一覧とバージョンだけで、シグネチャは出ない | rustdoc JSON は不安定(nightly で形式が変わる)。固定の nightly なら、形式は固定できる。`impl Trait`、ジェネリクス、ライフタイムの扱い。シンボル名は、extractor の MIR の名前(`lower.rs`)に合わせる |

3 つとも、型の情報を取る道は既にある。シンボル名の綴りを、extractor の出す IR の名前と一致させる点が、言語ごとの作業の中心。

### 4.3 生成物と手の行の区別、再生成の漏れを防ぐ仕組み

- **`*.gen.yaml` はコミットする**(組み込みは `go:embed` で埋め込むので、ビルドに要る)。先頭に、生成器のバージョンと入力(パッケージとバージョン)を書く。手で書いた行は、別のファイルにする。
- **`origin`**: 規則の行の `origin` は、既に `builtin` / `human` / `llm`(`internal/model/model.go` 45〜47 行)。生成した行には `generated` を足す。生成した行は、再生成で上書きされ、`human` / `llm` の行は残る。生成部分と手の部分は、**別のファイル**にする(`<lang>-<package>.yaml` は手の部分、`<lang>-<package>.gen.yaml` は生成の部分)。同じ symbol に両方の行があるときは、手の行が生成の行を上書きする(行の統合の規則を、`Merge` の中で決める)。
- **漏れを防ぐ**: 生成したファイルの先頭に、`generator: <名前>@<バージョン>` と、`input: <ライブラリ名>@<バージョン>` と、入力(公開の API の一覧)のハッシュを書く。テスト(`go test`)が、全部の `*.gen.yaml` について、生成器をもう一度走らせて、ハッシュと内容が一致することを確認する(依存の取得が要るので、定期の層と、`*.gen.yaml` を触った PR のテスト)。生成器のバージョンを上げたとき、全ファイルの再生成を CI が要求する(1 つでも古ければ失敗)。これで、「生成器を直したが、古い生成物が残る」(報告の 4)を防ぐ。
- **規則の採用**: 報告の生成の規則と差分テストの仕組みは、LLM が書いたもので、人の確認前。**規則は、rivus の側で、zoo と差分テストで確認してから採用する。** 参考の実装(報告元の `apigen`、`diff-test`、`models` のスクリプト)は、この文書を書いた担当は読んでいない(読む許可が、ユーザーの直接の指示で確認できなかった)。生成の規則の詳細は、rivus の側で、zoo の表 S と差分テストの結果から決める。

### 4.3a 生成の規則の決定(段階 3 の生成器。Go の実際のプロジェクトでの利用から)

参考の事実(報告された数字。rivus の側では未確認): 生成器は、Python 約 100 行と、API を列挙する Go 約 170 行。モデルは合計約 18 万行(直接の依存 77 パッケージで約 5.9 万行、推移的な依存で約 8.2 万行、標準ライブラリ約 2.2 万行)で、全部 `origin: llm`。生成の規則は、`go/types` の型の分類(データを運びうる型 / 関数 / error)と、引数の名前と関数名の正規表現の組み合わせ。**丸ごとは取り込まない**。rivus の側で、型の情報から自分で作る。使える所と、変える所を、次のとおり決める。

**使える所(出発点)**:

| 項目 | 内容 | 扱い |
| --- | --- | --- |
| (1) 規則の骨組み | 関数を引数に取る関数はスキップ(手で `calls:` を書く)。戻り値なしで、データを運ぶ引数だけの関数はスキップ(モデルなしのまま = 既定の保守的な扱い)。`context` は流さない。書き込みは方向つき | rivus の生成器の出発点にする |
| (2) 手で書かれた小さいファイル | コールバックの `calls:` の行(errgroup、singleflight の `Do` / `DoChan`、`sync.Map` の `Range`、backoff の `Retry`、goldmark の `ast.Walk`)と、標準ライブラリの追加の行(`io.TeeReader`、`reflect`、`os.Open` など。約 67 行) | 1 行ずつ確認できる量。標準ライブラリの分は、どの Go の利用者にも効くので、課題の「標準ライブラリの 23 行」を約 67 行に広げ、組み込みの基準で 1 行ずつ確認して取り込む(別の作業。取り込む計画として 1 項目) |
| (3) 照合の材料 | あちらの生成物と、rivus の生成物 | rivus の生成器ができたら、重なるパッケージ(cobra、viper、logrus、golang-jwt、`x/oauth2`、connect-go、grpc-gateway、yaml など)で比べて、規則の差を洗い出す |

**規則の決定(rivus の生成器では変える)**:

| | 決定 | 理由 |
| --- | --- | --- |
| a | **書き込み先の引数を、引数の名前(`dst`、`out`、`v`、`dest`、`target`、`ptr` など)で判定しない。型(ポインタ、slice、map、interface、chan)で判定する(広い側に寄せる)** | 名前が違うと(例: `Bind(i any)` のような出力用のポインタ)、レシーバ → 引数の流れが落ちる = サイレントな見逃し。#163 のテンプレートと同じ |
| b | **戻り値が数値や bool だけの関数を `pure` にしない。flows で書き、止めるのはエンジンの `numeric_stop` に任せる**(`pure` は、戻り値が引数にもレシーバにも依らないときだけ) | 既定では数値で止まるので結果は同じだが、`-numeric-taint` のときに流れが消える |
| c | ログの関数(`Info`、`Errorf` など)を `pure` にするのは、流れとしては正しい。ログへの出力を sink にする行と両立することを確認する | sink の行は別に書ける、で足りる見込み。生成のときに、sink の行がある関数は `pure` にしない、で守る |
| d | **レシーバを、既定で `from` に入れる** | 「データを運びうる型」のときだけ入れると、分類が狭いときに、レシーバ → 戻り値が落ちる |
| e | 差分テストのコードは、単純な型の引数の関数しか機械的に作れない(ジェネリクス、複雑な型、コールバックは対象外)。**照合できなかった行は、「未照合」と分かる形で残す**(生成物の行に `unverified: true` のマークを付ける)。宣言を付ける条件の数字に入れる(「照合済みの行の割合」) | 照合できなかった行が、照合済みに見えると、宣言の条件(2 節 5 の(i))が、見かけだけ満たされる |
| f | **`origin: llm` を、生成物用の origin に分ける**(`origin: generated`。生成器のバージョンつき。`verified_versions` と同じ場所(ファイルの先頭)) | バージョンの記録がないと、どの生成器とどの入力で作ったか分からない(4.3、6.7 の 1) |

手順書の 8 節(生成と差分テストの対象外)と整合させる: 機械で作れない行(コールバックを取る関数、ジェネリクス)は、「手で書く」か「未照合」と書く(e)。

### 4.4 組み込みに入れる量の上限

報告では、ある対象で、組み込みの行が約 3 万行になり、読み込みの時間とメモリは変わらないとされている。rivus の側で、合成のモデルで測った(`internal/model/builtin/zz-synth.yaml` を足してビルドしたコピー。1 行の propagator = 2 行の YAML。`rivus analyze` を、Go の小さい 1 ファイルのプログラム(標準ライブラリだけ)で 3 回ずつ。load average 6〜12):

| 組み込みの YAML | 規則(行)の数 | 起動を含む wall(3 回) | 最大 RSS |
| --- | --- | --- | --- |
| 今(4,242 行) | 約 1,700 | 0.54〜1.05 秒 | 381〜386 MB |
| +6,671 行(計 約 1.1 万行) | +2,224 | 0.65〜0.97 秒 | 380〜401 MB |
| +20,003 行(計 約 2.4 万行) | +6,667 | 0.65〜1.08 秒 | 399〜409 MB |
| +66,671 行(計 約 7 万行) | +22,222 | 0.73〜1.17 秒 | 417〜424 MB |

- 約 7 万行(今の 17 倍)で、起動の時間が約 0.1〜0.2 秒、メモリが約 35〜40 MB 増える。数万行なら、時間もメモリも、ほぼ変わらない(報告と一致)。規則の検索は、シンボルをキーにした map(`HasModel` など)で、行数に比例しない。
- 起動のたびに全部を解析している(`go:embed *.yaml` を、全言語分)ので、増加は行数に比例する。10 万行を超えたら、言語ごと、または使うパッケージだけを読み込む(遅延読み込み)案を検討する。それまでは、行数の上限は、起動の時間ではなく、レビューできる量と、`bench/parity/dead-allow.txt`(zoo の行が当たらない行)の管理の量で決める。**上限の目安: 組み込みの手の行が、1 つのファイルで 2,000 行を超えるものは、パッケージごとに分ける。生成の部分(`*.gen.yaml`)は、レビューの対象外で、数万行まで置いてよい**(提案。決めるのは相談役)。
