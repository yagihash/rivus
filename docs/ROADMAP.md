# ROADMAP

優先順位。方向性は [PRINCIPLES.md](PRINCIPLES.md) と、`.claude/prompts/` の開発者・相談役の文書。

- この文書は、各節の目的、終わりの条件、課題の番号、決まった方針だけを持つ。「今の作業」と「済んだもの」は、持たない。今の作業は、リポジトリの文書には持たない。済んだものは `CHANGELOG.md` と git の履歴が正。
- 結果の数字(合格か不合格か、時間、メモリ)は、ここに書かない。重い測定の数字は、台帳(`bench/heavy-ledger.tsv`。読み方は [bench/heavy-ledger.md](../bench/heavy-ledger.md))にだけ置く。
- 状態の文は、決めた PR が、同じ PR で直す。設計メモは、実装が済んだら、冒頭に「実装済み。正はコードと `docs/ARCHITECTURE.md`」と 1 行だけ書き、以後は更新しない。
- 課題は、[ISSUES.md](ISSUES.md) の番号(#N)で指す(GitHub の Issue は使わない)。
- 仕切り直しの前の内部の番号(R-xx、F-x など)は、リポジトリの外の文書の番号なので、ここでは使わない。
- 直していない rivus 自身の弱点の詳細は、ここにも課題の一覧(`docs/issues/`)にも書かない(公開リポジトリ)。直したあとに課題にする。
- 節の順番が、優先順位。0 から 6。どの作業の途中でも、安全の問題と、新しく見つかったサイレントな見逃しは、先に対処する。エンジンとモデルを変える PR は、マージの前に相談役が読む。効果は、既定の解析の数字で示す。

## 0. 安全(いつでも最優先)

- **目的**: 解析の対象(攻撃者が制御しうる)が、rivus を動かすホストに何もさせないこと。
- **方針**:
  - Rust の信頼しないコードは、macOS のサンドボックス(Seatbelt)と、Linux の Landlock + seccomp(試作。[DESIGN-linux-sandbox.md](DESIGN-linux-sandbox.md))の下だけで読む(ADR-093。[rust-isolation.md](rust-isolation.md)、[DESIGN-macos-sandbox.md](DESIGN-macos-sandbox.md))。どちらもないとき(Landlock のない Linux など)は、既定では何も実行せずに止まる(`-unsafe-host-exec` だけ)。
  - 隔離なしでは、取得したクレートのビルドスクリプトとマクロを実行しない。クラウドのモデル作成では、隔離の下(Linux の Landlock + seccomp が、クラウドのセッションで動く)でだけ、Rust を扱う。隔離が作れない環境では、扱わない(#148、ADR-128、MODEL-RUNBOOK.md の 0 節)。
  - 取得元の既定は crates.io だけ。
  - ユーザーの判断(2026-11-22): 取得のフェーズのネットワークの絞り込み([DESIGN-fetch-network.md](DESIGN-fetch-network.md)、#110)と、Go / Dart の隔離は、しばらくやらない。帰結として、Go / Dart の隔離ができるまで、新しい第三者のパッケージをまとめて解析・実行しない(観測との照合は、zoo と自前の curated だけで進める)。Rust の第三者のコードは、サンドボックスの中だけ。
  - あとで隔離を足すときの最初の対象(相談役の判断、2026-11-22): モデル化のタスクの、実行で確かめる手順(`DESIGN-model-authoring.md`)。着手の時期は未定。今は、信頼できるコードにだけ使う、と知らせるに留める。
- **課題**: #110〜#122(後回しのハードニング)、#146(出力の target triple)、#147(ワークスペースの中の crate)、#148(Linux での Rust)。`[env]` で IR が空になる件は、直らない(ADR-093)。
- **終わりの条件**: 3 言語とも、信頼しない入力を隔離の中だけで扱える。#110〜#122、#146〜#148 を閉じる。

## 3. 依存込みの解析が、実用的な時間で終わること

- **目的**: 実際のプロダクトを、`-no-deps` なしで解析して、終わること。
- **合格基準**(ユーザーの決定、2026-11-24、2026-11-25): 4 つの行。A は memos を `-max-memory 4GiB` で(対象名 `memos-4gib`)、C は Gitea、D は `dart_services`、Dart の cocoon `app_dart`。memos のメモリ 8 GB の行(B)は、2026-11-25 に外した。A が同じ対象でメモリの上限が厳しいため。各行の対象、固定したコミット、フラグ、時間とメモリの上限は、`bench/deps-targets.json` と [bench/passline-baseline.md](../bench/passline-baseline.md) が正で、ここには写さない。メモリは 3 状態で判定する(余裕 = 上限 − 最大のメモリ、GiB。0.15 GiB 以上で PASS、0 以上 0.15 未満で `PASS(余裕不足)`、0 未満で FAIL。線は動かさず、余裕不足は合格として通す。定義は [bench/passline-baseline.md](../bench/passline-baseline.md))。
  - 判定は、既定のフラグ(`-no-deps` なし、`-body-replaced` を手で書かない)で行う。条件は、終わること(時間、メモリ、収束)と、検出すること(公開済みで修正済みの脆弱性を、位置で判定して検出する。#387)の 2 つで、別に判定する。
  - A の検出は、memos の CVE-2025-65799。修正後のコミットで検出しないこと(`quiet_after_fix`)は別の指標で、合否には入れない(ガードの仕組み #169、ADR-122 ができるまで)。
  - C の検出は、`bench/gitea-cve-truth.json` の脆弱性ごとに位置で判定し、行に参考として出すだけで、合否には入れない。行と台帳には、検出の件数だけを書く(finding の一覧、経路、場所は書かない)。
  - D は、公開の脆弱性がないので検出は対象外。重いので `make bench-passline` の既定に入れず、`TARGETS=dart_services` で選ぶ。判定は、静かな状態で 3 回の中央値([WORKFLOW.md](WORKFLOW.md)、#480)。
  - Gitea は、2026-11-25 から合格基準の対象として、取得と実行をしてよい。定期の実行や探索に広げるのは、別の判断。
  - 結果は、台帳の `--kind passline` の行(`python3 bench/heavy_ledger.py --kind passline`)を指す。
- **方針**:
  - 本体を読むとコストが大きい依存は、モデルで切る(ADR-098)。依存の中では source と sink を探さない(ADR-099)。パッケージ単位で本体を読まない宣言(`body_replaced_packages`)は、3 言語にある(ADR-100、105、111)。組み込みのモデルでの宣言は、差分テスト(`bench/model-diff`)が PR で動いてから足す。
  - アクセスパスの深さが、コストを決める。依存の関数だけ深さを下げる(ADR-119、`-dep-k`)。全体の `-k` は下げない(精度が変わる)。
  - 巨大な SCC の安全網(ADR-124、#187 の入口、`-scc-coarsen`): 依存の関数の数が一定以上の SCC は、その依存の関数を、最初から深さ 0 で解く(プロジェクトの関数の深さは変えない)。粗くしたことは uncertainty(`scc_coarsened`、`through_coarsened_scc`)で知らせる。値の選び方は ADR にある。
  - IR は関数ごとにディスクへ書く(ADR-123)。メモリの上限は `-max-memory`(ADR-121)。
  - 測定のルール: 時間を比べる実行は、測定の道具の有無を揃える(#478)。判定は 3 回の中央値で、負荷を台帳に残す(#480)。順序の 2 行(#472)。`--graph-check` の Dart への拡張(#473)。言語共通のコードを変える PR は、Go の `--graph-check` を付ける(#476)。
  - Go のフロントエンド(2026-11-24): `go/ssa` をやめる作業は、今は始めない。始めるきっかけは、解析したい実際の対象が入らなくなったとき(測って、extractor の側が全体のピークを決めているとき)。受け入れ条件は「今の `goir` と同じ結果」だけ。知らない構文は、何も報告せずに捨てず、不確実性として知らせる。Go の extractor を別のプロセスに出す作業も、今はやらない。
  - 規模のための仕組みは、[ADR-118](adr/118-scale-mechanisms-three-conditions.md) の 3 条件を満たす。満たさない行の課題: #186、#187、#188、#77、#185。
- **作業**(この順):
  1. 差分テストを PR で動かし、pure / sanitizer / source の行も比べる
  2. 今あるモデルに、宣言を入れる。1 パッケージずつ、既定の解析の前後の数字を付ける
  3. コストの高い依存から、流れのモデルを作る([DESIGN-package-models.md](DESIGN-package-models.md) の 7 節)
  4. アクセスパスの深さを、場所ごとに決める(#189)
  5. `dart_services` の収束(合格基準 D。#126。`docs/issues/126-timeout-inside-large-scc.md`)
- **課題**: #126、#127、#166、#167、#174、#175、#176、#189。
- **終わりの条件**: 合格基準の 4 つの行が、既定のフラグで通る。宣言したパッケージが、全部、差分テストを通っている。

## 5. エージェントが問い合わせるインターフェース

- **目的**: AI のエージェントが、`graph` などを、最小の権限で使えること。スキルと MCP は、導入の手軽さへの投資ではなく、**最小限必要なもの**([DESIGN-agent-interface.md](DESIGN-agent-interface.md)。案。ユーザーの考えは未確定)。
- **順(相談役の判断、2026-11-22)**: 最小のインターフェース(`graph` と、保存した結果への問い合わせを、読むだけの道具として出す MCP + 使い方のスキル 1 つ)→ それを使って、「エージェントだけ」対「エージェント + rivus」の測定を 1 回 → 測定の結果を見て、作り込む所を決める。測定の前に、インターフェースを作り込まない。
- **着手の条件**: 2 節と 3 節の主な作業が進んでから。#91、#95 は、この前に直す。
- **終わりの条件**: 最小のインターフェースで、測定が 1 回できる。

## 6. 汎用のモデルの検出の側

- **目的**: 組み込みモデルで、依存の中の source と sink を検出する(コストの側は 3 節)。Dart の基盤を優先する。
- **範囲**: ADR-096、097。Google Cloud、外部のサービスのクライアント、標準ライブラリ、代わりのないパッケージ、pub の人気の上位。選ぶ基準は公開の指標だけ([DART-MODEL-CANDIDATES.md](DART-MODEL-CANDIDATES.md))。ADR-063 は決まった(組み込みに入れるかは、フレームワークごとに、その都度、相談役が判断する)。
- **方針**:
  - 今あるモデルは `internal/model/builtin/`。作る順番は [MODEL-QUEUE.md](MODEL-QUEUE.md)、手順は [MODEL-RUNBOOK.md](MODEL-RUNBOOK.md)、設計は [DESIGN-model-authoring.md](DESIGN-model-authoring.md)。
  - Rust は、隔離の下(macOS の Seatbelt、Linux の Landlock + seccomp。クラウドのセッションでも動く)でだけ、取得したクレートを読む。隔離が作れない環境では、モデルは書き、extractor を使う確認はしない(#148、ADR-128)。
  - 実行で確かめるステップは、信頼できるコードに対してだけ使う(隔離は作らない。ユーザーの判断、2026-11-22)。
  - sink の行の一括採用(`adopt_rules:`)は、確認の仕組み(3 節の差分テスト)が PR で動いてから使う。新しいパッケージの sink のモデルは、3 節の主な作業のあと。
  - モデルの鮮度(`verified_versions` と、更新の検知。DESIGN-package-models.md の 6.7 節)は、設計案。
- **課題**: #139、#140、#142、#158、#159。Dart の github の課題: `docs/issues/model-dart-github-repositoryslug-miss.md`。
- **終わりの条件**: 順番の一覧の上位が、手順書どおりの PR で入る。
