# #199 Rust: サンドボックスの cargo の置き場(`rivus-cargo-<ハッシュ>`)が、依存が変わるたびに増え、掃除の仕組みがない

- 状態: **open**
- 種類: 資源(利用者のディスク)
- 言語: Rust
- ROADMAP の節: -
- 守るもの: -

## 何が起きるか

本番の経路(`cmd/rivus/isolate_sandbox_darwin.go` の `extractRustSandboxed`)は、`cargoVolume` で、プロジェクトの依存(`Cargo.lock` と `.cargo/config` の内容のハッシュ)ごとに、`rivus-cargo-<ハッシュ>` という置き場を作る。場所は `~/Library/Application Support/rivus/rust/` の下。

依存が変わるたびに別の置き場ができる。**削除も、合計の上限も、掃除の仕組みもない**。使われなくなった古いものが、利用者のディスクに溜まり続ける。1 つが 1 GB 以上になるものもある。

## 設計との関係

再利用のためのキャッシュなので、置き場が増えること自体は設計どおり。足りないのは、古いものの掃除。uncertainty の課題ではなく、資源の課題。

## 修正の案

- 最後に使った日で消す(例: 一定の日数、使われていないもの)
- 合計の大きさに上限を置き、超えたら古いものから消す
- `rivus` の明示のサブコマンドで、一覧と削除ができるようにする

どれを選ぶかは、相談役が決める。

## 順番

今の作業の順(メモリの作業)のあとに修正する。#423 で、テストはこの場所に置き場を作らなくなったので、増えるのは本番の経路だけ。

## 案の比較と推薦(2026-11-24。`cmd/rivus/isolate_sandbox_darwin.go`、`cmd/rivus/isolate.go` の `cargoVolume`、`docs/rust-isolation.md`、ADR-093 を読んで確かめた)

**いまの形**: `rustDataDir()`(`~/Library/Application Support/rivus/rust`。`RIVUS_RUST_DATA_DIR` で変えられる)の直下に、`rivus-cargo-<16 桁の 16 進>`(`Cargo.lock` と `.cargo/config*` の内容のハッシュ)のディレクトリができる。同じ場所の `extractor/`(共有の Rust の extractor。`rivus setup rust` が作る)は、名前が違うだけで、**同じ親ディレクトリにある**。取得の段階だけが書き、抽出は読み取り専用で使う。最後に使った日の記録も、使用中のマークも無い。

**安全の条件**(どの案でも守る。テストで確かめる):

1. 消す対象は、`rustDataDir()` の**直下の、名前が `^rivus-cargo-[0-9a-f]{16}$` に一致する、ディレクトリ**だけ。`extractor/` と、そのほかの名前は、一致しないので消えない。`os.Lstat` で調べ、シンボリックリンクは消さず、たどらない。
2. 今使っているものは消さない。使う側(`extractRustSandboxedTo`)が、置き場の中の `.lock` に `flock`(共有)を、取得と抽出の間、持つ。消す側は、`flock`(排他)を**待たずに**試し、取れなければ飛ばす。プロセスが落ちても、`flock` は OS が外すので、古いロックが残らない。
3. 最後に使った日は、使うたびに置き場の中の `.last-used` を `touch` した日(ディレクトリの `mtime` は、中のファイルが増えたときしか変わらないので、使えない)。マークのない古い置き場は、ディレクトリの `mtime` で代える。
4. 消す前に `-dry-run` で一覧を出せる。消したら、名前と大きさを、1 行ずつ出す。
5. cargo は、読み取り専用のファイルを作る(registry のキャッシュなど)ので、消す前に、権限を直す(`chmod` を、その置き場の下だけに)。

**(a) 最後に使った日から N 日で消す**: 利用者が理解しやすい。単独だと、1 か月に 20 回、別の依存で使う人は、N 日の間に溜まる。

**(b) 合計の上限(大きさ、個数)で、古い順に消す**: 上限の既定値を決める必要がある(1 つが 1 GB 以上になるので、個数のほうが決めやすい。大きさは `du` 相当の数え上げで、遅い)。(a) と組み合わせると、確実。

**(c) 明示のサブコマンド `rivus cache list` / `rivus cache clean`**: `setup` の形(`cmd/rivus/commands.go` の `sub`)に並べて足せる。`list` は、名前、大きさ、最後に使った日、使用中か、を出す。`clean` は、`-older-than 30d`、`-max-size 10GB`(または `-keep N`)、`-all`、`-dry-run`。**利用者の驚きが無い**(自分で動かしたときだけ消える)。Linux では、この置き場を使わないので、「何も無い」と出すだけ。

**(d) 実行の最後に、自動で消す**: 利用者が何もしなくてよい。ただし、(1) 解析のコマンドが、解析と関係のないファイルを消す(1 行出しても、驚きは残る)、(2) 失敗したり、同時に別の `rivus` が動いていたりすると、消す側の誤りが、解析の結果に響く、(3) 安全の条件の 1 と 2 を、ふだんの経路で毎回通すことになる。先に (c) で、安全の条件を固めてからが安全。

**推薦: (c) を作り、その `clean` の条件として (a) と (b) を持たせる。(d) は、いまは入れない**。

- 使う側の変更: `extractRustSandboxedTo` で、`.lock` を取り、`.last-used` を `touch`(約 30 行)。
- 新しいコード: `cmd/rivus/cache.go`(名前の照合、`Lstat`、`flock`、大きさの数え上げ、`list` と `clean`)と、サブコマンドの登録、`docs/rust-isolation.md` の記述、ADR-093 への追記(または、短い新しい ADR)。約 250〜350 行と、テスト(`RIVUS_RUST_DATA_DIR` の一時ディレクトリで: `extractor/` と、名前が似ていて一致しないものが残ること、シンボリックリンクを消さないこと、ロック中のものを飛ばすこと、`-dry-run`)。
- 大きさ: 中。1〜1.5 日。`flagsides_test.go` と補完(`completion`)のテストも、一覧に足す。
- 小さな足し: 実行の最後に、合計がしきい値(例: 5 GB)を超えていたら、「`rivus cache clean` で消せます」と 1 行出すだけにする案(消さない)。これは (d) より驚きが小さい。要るかどうかは、決めてから。

実装は、案を読んでから(状態は `open` のまま)。
