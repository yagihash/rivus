# 144: 汚染された値が、依存の中の sink のルールに一致する呼び出しに届いたことを、finding とは別の一覧で出す(案)

- 状態: **open**
- 種類: 検出の見逃し(サイレント。案)
- 言語: 全
- ROADMAP の節: 0
- 守るもの: -
- 題: 汚染された値が、依存の中の sink のルールに一致する呼び出しに届いたことを、finding とは別の一覧で出す(案)
- 補足(種類): 検出の見逃し(サイレントな見逃し)、案
- 見つけた経緯: Go の実際のプロジェクトでの利用から。

## 問題

source と sink は、プロジェクトの関数の中だけで探す(ADR-099)。依存の本体を読んでも、ライブラリの中で危険な処理に届く形は、プロジェクトがその API を呼ぶ所に sink のモデルがないと検出されない。ADR-099 で、`summary.dependency_sites` が、そのことを毎回言うようになった。しかし、**どの API に sink のモデルが必要か**は、まだ分からない。

## 案

汚染された値が、**依存の関数の中の、sink のルールに一致する呼び出し**に届いたことを数え、finding とは別の一覧で出す(`models coverage` の sink 版)。出すもの: 届いた回数の合計と、入口になったプロジェクト側の API(プロジェクトが呼んだ、依存の関数)の上位。利用者には、どの API を調べるべきか、モデルを書く人には、どの API に sink のモデルが要るかを示す。

- (b) 依存の中の sink を、finding にすることは、やらない: 依存の内部の使い方に由来する誤検出が大きく増える(ADR-099)。この案は、finding を増やさない。

## コストと出力の大きさの見積もり(実装前の見積もり。測っていない)

- 数える場所: `internal/taint/` の、依存の関数の呼び出しの処理。呼び出し先が依存の関数で、その呼び出しが sink のルールに一致し、引数に source の載った値が届いたとき、カウンタを 1 つ増やす。サイトを作らず、経路も作らない。
- 時間: 依存の関数の呼び出しごとに、sink のルールの照合(今、プロジェクトの呼び出しでしている照合と同じ)を 1 回足す。照合は、シンボルのハッシュの引きなので、解析全体の増加は小さいと見込む。測って確かめる(accuracy over performance: 結果は変えない)。
- メモリ: カウンタは、(入口の API、sink のシンボル)をキーにした表だけ。キーの数は、一致した sink のシンボルと入口の API の組の数で、依存の関数の数には比例しない。要約には載せない(要約の要素は増えない)。
- 出力: `summary.dependency_sites` に、`reached` の合計と、`top`(入口の API の上位 10 件。`api`、`sink`、`count`)を足す。大きさは、上位 10 件の固定。`-detail summary` でも出る。
- 難所: 入口の API を、「プロジェクトが呼んだ関数」まで戻って決める所(依存の関数の要約は、呼び出し元ごとに作らないので、どの入口から来たかは、要約の外で持つ必要がある)。ここが、見積もりのいちばん不確かな所。
