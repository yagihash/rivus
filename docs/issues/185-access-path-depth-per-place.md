# #185 全: アクセスパスの深さを、場所ごとに決める

- 状態: open
- 種類: 設計の候補
- 言語: 全
- ROADMAP の節: 3
- 優先度: 中(memos の目標のあとに始める)
- 守るもの: 精度(深さを下げて増える過検出を、必要な所だけにする)と、コスト(要約がふくらむ所だけ浅くする)
- 題: アクセスパスの深さを、場所ごとに決める

## 今

深さは 2 段だけ。プロジェクトの関数は 3(`-k`)、依存の関数は 2(`-dep-k`。ADR-119)。どの依存も、どの関数も、同じ深さ。

## 測ったこと(公開の数字だけ。対象は伏せる)

- AWS SDK を呼ぶ小さい Go のサーバと、Go の実プロジェクト(AWS SDK に依存): 依存の深さで、要約の要素が桁で変わる。深さ 3 では終わらず(要素 100 万、12 GB)、深さ 2 は 23.8 万、深さ 1 は 4.6 万で終わる。要素の 98% がパスを持ち、78% が深さ 3 以上。パスを無視すると、要素は 3.1 分の 1。
- Go の gcp(Spanner と BigQuery): 要素の 79% が source のラベル(`real`)で、パスの影響は 1.12 倍。深さを下げても、時間はあまり変わらない。
- `package:analyzer` に依存する Dart のプロジェクト: 1 つの巨大な再帰のかたまり(SCC)が原因。深さを 1 にしても終わらない。

## 案(候補。順番はない)

1. **エラーを包む・作る関数**(`grpc` の `status.New`、`pkg/errors.Wrap`、`fmt.Errorf` の仲間): ここは深さを保つ価値が高い。ほぼ全部の経路が通るので、ここで切ると、finding の多くに `access_path_truncated` が付く(Go の実プロジェクトで、153 件中 122 件)。
2. **型の形から見積もる**: パッケージや関数ごとに、引数と結果の型の入れ子の深さと、広がり(フィールドの数)から、深さ k でのパスの数を見積もる。ふくらむ所だけを浅くする。型だけで決まるので、安い。
3. **浅く始めて、必要な所だけ深く解き直す**: 浅い深さで解いて、`access_path_truncated` の注記が付いた finding の経路にある関数だけを、深く解き直す。深さを下げると、流れは増えるだけで減らないので、注記のない finding は、そのまま確定してよい。
4. 上の測定(深さが効く対象と、効かない対象)を、見積もりの検証に使う。

## 前提

ADR-117(注記が、どの関数のどの深さのどのパスかを言う)。ADR-119(依存は 2)。
