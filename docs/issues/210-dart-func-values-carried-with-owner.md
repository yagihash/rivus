- 状態: **open**(設計のみ。実装の前に、下の「ユーザーに聞く点」の決定が要る)
- 種類: 道具・ベンチ(グラフのエッジ)。同じ形の `@miss`(`unresolved_callee`)は、見逃しでもある
- 言語: Dart(仕組みは言語に依らない。Rust の `Box<dyn Fn>` と同じ根)
- ROADMAP の節: 1
- 守るもの: zoo `F/clos/stored`、`F/dyn/func-field`、`F/dyn/func-map`、`F/clos/partial-callers`、`F/clos/capture-write-by-ref`、`F/dart/tearoff-instance`、`F/dart/shelf-router-params`、`F/dart/shelf-router-extra-param`、`F/dart/flutter-route-args`
- 題: Dart: フィールドと入れ物に入れた関数値を、持ち主つきの関数値の要素で運ぶ設計

関連: #99(根 D)、#209(根 E。そこの案 B は `valuecalls` に索引を足す形で、この課題はそれと比較する別案)、#203(フィールドのパスに持ち主のクラスを入れる。**持ち主の意味が違う**: #203 は宣言したクラス、ここは `alloc` の場所)、#207(型で補う案。deferred)、#77(`candidate_limit`)、#81、ADR-045(ガード)、ADR-050、ADR-059(`assumed_call`)、ADR-118(精度を落とす仕組みの 3 条件)、`docs/DESIGN-callouts.md` の 3 節(要約に載せた呼び出し)と 5 節(関数値の要素)。

## 1. 結論(先に)

1. **根 D の 20 件と根 E の 6 件のうち、25 件は同じ仕組みで閉じる見込み。1 件(`closure-to-sdk`)は別の仕組み**(モデルで言う形)。
2. 同じ仕組みは、2 つの部品でできる。(a) **関数値の要素(`FUNC`、ラベルつきの `Real` 要素)を、通常のパスの中で、データと同じ道具(コピー、φ、フィールド、要素、グローバル、戻り値、引数、要約)で運ぶ**。(b) **値の呼び出しの呼ばれる値が、そのパラメータの下のパスから来るときは、呼び出しを要約に載せ(`CallOut`)、呼び出し元で、その呼び出し元のセルの要素から候補を決めて適用する**。持ち主は、セルの根(`alloc` の命令、または呼び出しの結果の値)が、そのまま持つ。別の持ち主を足す仕組みは要らない。
3. **推薦する段階**: 段階 0(測定だけ、軽い)→ 段階 1(同じ関数の中と、グローバルを通る形。中)→ 段階 2(要約に載せた呼び出し。大)→ 段階 3(実物の `shelf_router`、Flutter の `routes`)。段階 1 で止めても、使える成果(約 9〜11 件)が出る。
4. **危険は 3 つ**: (i) 入れ物の中の定数キー(`func_map` の decoy)を区別しないと、**同じ持ち主の中**で、別のキーのハンドラに値が届く過検出が出る。(ii) 依存の要約の大きさと SCC の増加への影響は、**推定と過去の測定からは「小さい見込み」だが、`dart_services` では測っていない**。(iii) **グラフのエッジは、`rivus index`(構造だけ)の段階では、まだ決まらない**(7 節)。

## 3. 今の仕組みで足りないこと(読んだこと)

- 値の呼び出しの候補は、**呼び出し点ごとの 1 つの集合**(`ir.Callee.ValueCands`)で、`internal/valuecalls` が、取り込む前に、値の流れ(コピー、φ、パラメータ、呼び出し元の引数)から作る。**メモリ(フィールド、map、List)は、たどらない**(`valuecalls.go` の冒頭のコメント)。だから、候補 0 件になる。
- エンジンは、候補が複数のとき、**全部の候補の要約を、呼ぶ関数の中で適用**し、パラメータ経由の候補には**ガード**を付ける(`valueGuards`、ADR-045)。呼び出し元は、自分が渡した関数だけ残す。ガードが付くのは、**呼ばれる値がパラメータそのもの**のときだけ。フィールドの下(パラメータ + パス)は、`ValueUnresolvedParams` で呼び出し元に「ここに渡したものが呼ばれる」と伝えるだけで、候補は付かない。
- エンジンの場所(`Loc{Root, Path}`)は、**関数ごとに、値(`alloc` の結果、呼び出しの結果、パラメータ)を根にし、その下にパスを持つ**。`Router()` を作る 2 つの `alloc` は、別の根。要約を呼び出し元に適用するとき、**呼び出し元の実引数の場所に**要素が置かれる。つまり、**持ち主は、すでに、セルの根で区別されている**。区別されないのは、(i) 同じ `alloc` の命令(ループの中、同じファクトリを通る 1 つの `alloc`)が作る複数のインスタンス、(ii) アクセスパスの深さ `k` を超えて切った先、(iii) map のキー(`[]` に 1 つにまとまる)。
- `-resolve-func-values`(消す予定。`refactor/remove-resolve-func-values`)は、この仕組みを**別のパス**(エンジンをもう 1 回)で試した。候補を呼び出し点ごとに 1 つに集めたので、`Navigator.pushNamed` の `routes[name]!(...)` に 3 つのセルのクロージャが全部付いた(呼び出し元ごとの候補が分かれない過検出)。この課題の設計は、**候補を、呼び出し元のセルの中身から、呼び出しごとに決める**ので、この形は出ない(zoo の 3 つのセルは、それぞれ別の `Navigator()` を作る)。

## 4. 設計

### 4.1 運ぶもの

- **関数値を作る所**(`make_closure`、関数への参照、メソッドの tear-off)で、**自分のコード(`fn.Dep` でない関数)の中のものだけ**、値の根に `Real` 要素(ラベル `FUNC`、出所 `fn:<関数の ID>`)を 1 つ置く。依存の中で作る関数値は、運ばない(`DESIGN-callouts.md` 5.4 の測定: 依存の分も運ぶと、`gcp` で要素数 1,051,191 → 8,771,021、時間 42 → 677 秒。自分のコードだけだと、要素数 1,051,155、時間 47.9 秒で、試行なしと同じ)。
- 運び方は、**データの要素と同じ**: コピー、φ、`field_store` / `field_load`、`index_store` / `index_load`、レコードの `$1` / `$2`、`List.add` とイテレーション(本体かモデルが書く)、グローバル、戻り値、引数、要約の出力。新しい要素の種類は作らない(`Elem` は変えない。ラベルと出所の文字列だけ)。サニタイザ、数値の停止、`pure` のモデルは、`FUNC` に効かない(合成のラベルなので、finding には出さない。2026-11-22 の試行で、規則の例外は要らなかった)。
- **キャプチャした値**: `make_closure` の引数(キャプチャしたセルへの参照)。呼ぶ関数が、作った関数のときは、今の `applyMade` と同じ束縛で適用できる。**作った関数の外で呼ぶとき**は、`FUNC` 要素の根の下 `/cap/i` に、キャプチャしたセルへの参照を置く(`DESIGN-callouts.md` 5.1)。これは段階 2 の中で、**キャプチャのない関数値(トップレベル関数、メソッドの tear-off、キャプチャのないクロージャ)から先に**行い、キャプチャを運ぶ形は、段階 2b に分ける(下)。

### 4.2 呼び出し点で、候補を決める

呼び出しの呼ばれる値(`Args[0]`)が指す場所の要素を読む。

1. **`FUNC` 要素があれば**、その関数の全部を、この呼び出しの候補にして、要約を適用する(束縛つき)。`?`(下)がなく、数が上限以下のとき、`valuecalls` の候補は使わない。
2. **`Param` 要素(呼び出した関数のパラメータの下のパス)なら**、この呼び出しを、**要約に載せる**(`CallOut`。`DESIGN-callouts.md` 3 節の表現: `Fn` = パラメータ p とパス、`Recv` / `Args[j]` = 呼び出しの引数の場所、ガード、`Mode`)。呼び出し元 K は、`Fn` の p とパスが指す、**K のセルの要素**を読み、`FUNC` 要素の関数ごとに、K の中で `applySummary` を適用する(引数の場所は K の場所に写す)。中継(`wrapper(g)` → `run(g)`)は、K が自分の要約に載せ直す。`CallOut` の仕組みは `DESIGN-callouts.md` 3 節で設計済み(ADR-047 の再開)で、**最初のバージョンは、パスが `""` の呼び出しだけ**と書いてあった。この課題で、**パスつき(`h.a`、`_routes.[].$2`)に広げる**。
3. **`?` の要素**(不明の関数)があるとき、または数が上限を超えたとき: **今の候補(`valuecalls`、抽出器)に戻す**。uncertainty は今と同じ(`unresolved_callee`、`candidate_limit`、`caller_depth_limit`)。`?` が入るのは、入口のパラメータ(呼び出し元が見えない)、依存の中で作った関数値(運ばない)、本体もモデルもない呼び出しの関数型の結果、リフレクション、`dynamic`、セルの上限の畳み込み(下)。

**持ち主**は、この読み方で、次のとおり決まる。

| 形 | 持ち主を決めるもの |
|---|---|
| `final h = Holder(); h.a = f; callA(h)` | `h` の `alloc`(根)の下 `.a` に `FUNC`。`callA` の `CallOut`(`Fn` = パラメータ 0 の `.a`)は、K = `vuln` が、自分の `h` の `.a` から読む。**別のセルの `h` の `.a` は読まない** |
| `Router()` を 2 つのセルが別々に作る | 別の `alloc` の根。`router.get(...)` の要約(`Router.add` → `_routes.add((route, handler))`)は、実引数の `router` の場所に置く。`router(request)` の `CallOut` は、同じ `router` の `_routes.[].$2` を読む |
| 同じファクトリ `Router make()` を、2 つの呼び出し元が呼ぶ | 呼び出しの結果の値は、**呼び出しごとの根**。要約の出力(結果の下のパス)は、呼び出し元の、その呼び出しの結果に置く。**持ち主は混ざらない** |
| 同じ `alloc` の命令(ループの中)が作る複数のインスタンス | **混ざる**(インスタンスを区別しない。`alloc` の場所で決まる)。過大近似の向き |
| シングルトン、グローバルのレジストリ | 1 つのセル。全部の登録が、全部の呼び出しに届く(ほかの汚染と同じ。正しい) |

つまり、**「持ち主つきのフィールド」は、新しい部品ではなく、今のセルの根と、要約の呼び出し元への適用が、すでに持つ性質**。`valuecalls` の索引(#209 の案 B)は、フィールドごとに書き込みを集めるので、持ち主の区別を、`ValueCand` に足す必要がある。こちらは、その必要がない。

### 4.3 候補の数の上限、`candidate_limit`、uncertainty

- **1 つのセルの `FUNC` 要素の数**と、**1 つの呼び出しの候補の数**は、**`ir.ValueCandidateMost`(32)と同じ値**を上限にする(別の数を足さない)。上限を超えたセルは、**全部**を 1 つの `?`(型ごとの不明の関数)にする(**先頭の 32 を残す形にはしない**。残す形は要素が入る順に依るので、ADR-118 の条件 (ii) を満たさない)。畳んだ呼び出しは、今の候補に戻り、`candidate_limit`(`ValueFound` つき)の uncertainty が付く。
- 候補が決まった呼び出しにも、**uncertainty を付ける**場合: (a) 持ち主が区別できない形(同じ `alloc` の命令の複数インスタンス)を通ったとき、(b) キーを区別しない入れ物(4 節の `[]`)を通ったとき、(c) 途中で `?` が混ざったとき(`partial`)。(a) と (b) は、**エンジンの要素が、通ったセルのマーク(`alloc` が 1 つ以上のインスタンスを表す、`[]` を通った)を持たない**ので、**呼び出し点の IR から決まる範囲**で付ける(呼び出しの呼ばれる値が `index_load` から来る、など。`DESIGN` の `unresolved_callee` の文面を、「入れ物の要素のどれでもありうる」に足す)。要素にマークを持たせる案は、段階 1 で、zoo の `@fp` が必要かどうかを見て決める。
- **ADR-118 の 3 条件**(畳み込みの規則について): (i) 畳んだ先は、今の候補(`valuecalls`、抽出器)で、流れを足す側。畳むことで、今ある流れを落とさない(今と同じ)。(ii) 畳むかどうかは、セルの要素の数だけで決まる(時間、負荷、メモリの空きで決めない)。ただし、**反復の途中で、要素が入る順に、畳む時点が変わっても、最終の集合が同じか**は、`absorbWhole` と同じように、テストで確かめる必要がある(**未確認**)。(iii) 畳んだ呼び出しは、`candidate_limit` で言う。`stats` に、畳んだセルの数(`func_cells_folded`)を足す。

### 4.4 `-dep-k` との関係

- `FUNC` の要素は、**自分のコードの関数が作る**ので、依存の要約には**入らない**。依存の要約は、`Param` 要素の流れ(「パラメータ 1 を、パラメータ 0 の `.\_routes.[]` に書く」)で、今も持つ。`FUNC` を運んでも、依存の要約の大きさは変わらない(予測。**段階 0 で確かめる**)。
- 依存の中のアクセスパスの深さは `DepK`(既定 2)。**書き込みと読み出しの両方が、同じ深さで切られる**ので、切った先は、**同じ持ち主のセルの中で**混ざる(別の持ち主には届かない)。例: `Router.add` が `this._routes.[].$2` に書き、`Router.call` が読む。深さ 2 で `_routes.[]` に切られても、`$1`(文字列)と `$2`(ハンドラ)は、`FUNC` が入るのは `$2` だけなので、読み出しで不足しない。**実物の `shelf_router`(登録から `_handler` への書き込みまで、引数の中継が 5 つ。`#209`)**は、`maxDepth`(3)ではなく、**要約の連鎖**(各関数の要約が、パラメータ 1 を、パラメータ 0 のあるパスに書く)で届く。`DepK` を上げる必要は、ない見込み。上げるかは、段階 3 の測定で決める。
- `-dep-k` を上げると、依存の要約が大きくなる(今と同じ)。`FUNC` は、この大きさに足さない。

## 5. 精度の危険

### 5.1 別のセルのハンドラに、値が届く(インスタンスを区別しない候補)

`valuecalls` の索引でフィールドごとに候補を集める案は、この危険がある(#209 に書いた)。**この設計では、持ち主が根で決まる**ので、zoo の `vuln` / `fixed` / `decoy` が、それぞれ別の `Router()` / `Navigator()` / `Holder()` を作る形では、混ざらない。**混ざるのは**、(a) ループの中の 1 つの `alloc`、(b) グローバルのレジストリ(正しい)、(c) 根が決まらない形(要素が `Param` の `?`)。

### 5.2 `partial-callers` の decoy

`applyDecoy(h.cb, 'constant')` と `applyDecoy((x) {...sinkSql(x)}, v)` は、同じ `applyDecoy` を、別のクロージャで呼ぶ。`CallOut` の具体化は呼び出し元ごと(K ごと)なので、**1 つ目の呼び出しは `h.cb` だけ、2 つ目は直接渡したクロージャだけ**を適用する。今のガードの仕組みと同じ向き(`DESIGN-callouts.md` 3.2)。

### 5.3 入れ物の中のキー(`func_map` の decoy)

`m['cmd']` と `m['sql']` は、今は `[]` の 1 つのセルにまとまる。`FUNC` を運ぶと、`m['sql']!(v)` の呼び出しが、`cmd` のクロージャも候補にして、`v` が `sinkCmd` に届く過検出が出る(**同じ持ち主の中**。zoo の `dyn/func-map/decoy`)。直す案は 2 つ(材料: 以前の測定の過検出の形の表)。

- **案 1(推薦): `FUNC` の要素だけに、定数キーのマークを付ける**。`index_store` で、キーが定数のとき、書く要素にマーク(キーの文字列)を付け、`index_load` で、キーが定数のとき、**マークが違う要素を落とす**。キーが定数でない(動的)とき、またはマークのない要素は、落とさない。`transfer.go` の 2 つの命令と、要素の出所の扱い。中。落とす要素は `FUNC` だけなので、データの流れは変わらない(過大近似の向きだけを狭める。要素を落とすのは、キーが**両方とも定数で違う**ときだけ)。
- **案 2: 全部の要素で、キーごとのパス**。大。Go の map にも効く。この課題の範囲を超える。

実物の map から呼ぶ形の数(IR で数えた上限): dart-gcp 1 / 2,249、cocoon 7 / 3,142(定数キー 1、動的 6)、dart_services 2 / 3,785(定数キー 2)。**動的なキーは、案 1 でも区別できない**(`unresolved_callee` で言う)。

### 5.4 ほか

- 変数に後で代入する形(根 I)は、この課題の外。`FUNC` の要素は、セルに入るので、代入の順序を見ない(今の汚染と同じ)。
- `Navigator.pushNamed` の 3 つのセルの混ざり(過検出の 3 つ目)は、**持ち主が別の `Navigator()` の根**なので、段階 2 で出なくなる見込み(段階 2 の受け入れ)。

## 6. メモリと時間のコスト

**測定の材料(既存。この課題では回していない)**:

- 関数値のパス(別のエンジンの実行。`-resolve-func-values`)は、依存の中で作る関数値もシードにし、エンジンをもう 1 回走らせた。合格基準の対象で、memos は CPU 307 s → 1283 s、Gitea は 8 GB で終わらず、cocoon は CPU 114 s → 1697 s だった。
- 同じ仕組みで、**自分のコードで作る関数値だけ**をシードにした試行(`DESIGN-callouts.md` 5.4): `gcp` で要素数、時間とも試行なしと同じ(要素数 +0%、時間 47.9 秒)、集合の最大 558 → 13、小さい対象で要素数 +1〜6%、時間は変わらない。
- 値の呼び出しの数(IR で数えた上限、materials): 候補 0 件の呼び出しは、memos(Go)889、Gitea 428、dart-gcp 83(うち 65 は依存の関数の中)、dart-curated 17。

**推定**(推測。段階 0 で確かめる):

1. **コストの大部分は、(a) エンジンをもう 1 回走らせることと、(b) 依存の中で作る関数値を運ぶことで、通常のパスに入れ、自分のコードの分だけにすると、どちらも消える**。外部の設計者の指摘(2026-11-24。要素が依存の中を流れることは、通常のパスでも同じ)は、**依存の要約の `Param` 要素の流れ**には当たるが、それは今も流れている(`FUNC` を運ぶかどうかに依らない)。足されるのは、自分のコードのセルの `FUNC` の要素と、要約の出力の `FUNC` 要素(自分のコードの関数の要約だけ)。
2. **Go の依存の大きい対象に、`FUNC` を運ぶ理由はない**(Go の抽出器の VTA が、値の呼び出しのほぼ全部を解く)。**シードは、抽出器が値の呼び出しの候補を持たない言語(Dart。将来は Rust)だけにする**。Go の `memos`、Gitea のコストに触れない。
3. **`dart_services` の SCC の増加**(要約の `param` の出力が、ラウンドごとに約 2〜3 倍に増える。増えているのは「どのパスに、どの値が書かれうるか」の組み合わせ)との関係: 増えているのは、依存の関数(`analyzer` の AST のノードのクラス)の `Param` 要素。**`FUNC` は、自分のコードのクロージャ(`dart_services` のサーバのコード)だけが作る**ので、依存の SCC の組み合わせの値の種類には入らない(推定)。ただし、**自分のコードの関数が、その SCC の中にいる**(依存が、自分のコードの関数を、仮想呼び出しの候補にして呼び返す)場合は、その関数のクロージャが、SCC の出力に入る。**これは、段階 0 で、自分のコードのクロージャの数と、SCC の中の自分のコードの関数の数を数えて確かめる**(重い実行は要らない)。
4. メモリ: 要素は `Real` の 1 つ(小さい比較できる構造体)。`FUNC` を運ぶセルが増えるぶんだけ増える。上限は 32 で畳む(4.3)。

**段階ごとの受け入れの測定**(重い実行のロックを使う。この課題は実行しない): `dart_services`(8 GB)、cocoon、dart-gcp、dart-curated で、段階の前後の、時間、木のピーク、要素数、`func_cells_folded`。

## 7. グラフのエッジ(決める点)

`rivus index` の既定(構造だけ。`-taint` なし)は、**エンジンを走らせずに**、`valuecalls` の候補でグラフを書く。`-taint` ありでも、グラフは、**エンジンの前に**書く(`analyze.go` の `afterRead`)。この設計の候補は、**エンジンが、呼び出しごと(呼び出し元ごと)に決める**ので、グラフの呼び出し点に載せるには、**エンジンのあとに、呼び出し点ごとの和集合(全部の呼び出し元での候補)を書く**必要がある。選択肢:

| 案 | 内容 | コスト | 判断 |
|---|---|---|---|
| (i) `index -taint` のとき、グラフを、エンジンのあとに書く(候補の和集合を、`kind: value` の呼び出し点の候補として足し、uncertainty `uncertain`) | `no_edge` の照合(方法 B)は、`index -taint` で出す。構造だけの `index` は、今と同じ(候補 0 件のまま) | `index` の既定は変わらない。照合の道具は、エンジンを走らせる(zoo は小さい) | **推薦** |
| (ii) 構造だけの `index` でも、候補を出す | `valuecalls` に、同じ根拠の、安い索引(#209 の案 B)を足す | 持ち主を区別できない(過大近似)。`valuecalls` の別の索引を持つ(エンジンの仕組みと二重) | 推薦しない(精度の危険 5.1 が戻る。二重の仕組み) |
| (iii) `index` を常にエンジンつきにする | | 重い | 却下 |

(i) のとき、**照合で `no_edge` が減るのは、`index -taint` を使うとき**。`rivus graph path` の「入口 → ハンドラ」(`exhaustive: false` が `true` に近づく)も、`index -taint` のグラフが対象。ユーザーの判断が要る(9 節)。

## 9. ユーザーに聞く点

1. **精度を落とす形を、受け入れるか**。(a) 同じ `alloc` の命令が作る複数のインスタンス(ループの中、1 つのファクトリの中の `alloc`)は、区別しない。(b) 動的なキーの map は、全部のキーが候補(`unresolved_callee` つき)。(c) 定数キーのマーク(5.3 の案 1)を入れるまで、`dyn/func-map/decoy` に `@fp` が出る。**入れずに先へ進むときは、zoo の `@fp` の許可が要る**(zoo-loosened のゲート)。
2. **コスト**: 段階 1 は、Dart のシードだけ(Go と Rust のコストに触れない見込み)。**段階 2 は、`dart_services` の収束と合格基準の D(8 GB)に、影響が出る可能性がある**(測るまで分からない)。段階 2 に入る前に、段階 0 の数字で、進めるか決めたい。止める条件(8 節の最後)でよいか。
3. **依存の要約への影響**: 推定では、依存の要約の大きさは変わらない(`FUNC` は自分のコードだけが作る)。**これを段階 0 と段階 1 の測定で確かめる前提**で、段階 1 に進んでよいか。
4. **グラフのエッジ(7 節)**: 照合の `no_edge` が減るのは `index -taint` のグラフ、でよいか。構造だけの `index` に、候補 0 件が残ることを、受け入れるか。
5. **`valuecalls` の位置づけ**: `FUNC` 要素の候補を使うのは、`?` がなく、数が上限以下のときだけ。ほかは、今の `valuecalls` の候補(2 つの仕組みが並ぶ)。**`valuecalls` の候補を、Dart では、段階 2 のあとで、見直してよいか**(たとえば、`partial` を減らす)。
6. **#209 の案 B**(`valuecalls` に索引を足す)を、この設計に置き換えてよいか。置き換えるとき、#209 の「推薦」の節を、この課題への参照に書き換える。

- 件数のケース別の内訳(2 節の表の stored の 6 件が、フィールド、グローバル、List のどれか)。`capture-write` の 1 件が `vuln3` かどうか。
