# 163: ライブラリそのものを解析の対象にして、sink と source のモデルの候補を、根拠つきで出す(案)

- 状態: **open**
- 種類: 道具(モデル作成の候補の元)、案
- 言語: Go が先。Dart と Rust はあと
- 見つけた経緯: モデル作成の手順のスクリプト化の設計(`docs/DESIGN-package-models.md` 6.11)。段階 1 の候補は、ライブラリ単体の型の規則だけで出す。そこに根拠を足す案。

## 問題

型の規則だけの候補(引数の名前と型、戻り値の型)は、広く出る。go-github のように公開のメソッドが 1,000 以上あるライブラリでは、候補のうち、本当に sink や source にすべきものを、規則だけでは絞りきれない。判断の根拠が要る。

## 案

ライブラリそのものを、解析の対象(プロジェクト)として読む。

- **sink の候補**: 公開の関数の引数が、すでにモデルのある sink(標準ライブラリなど)に届くかを見る。届くなら、その引数は、そのライブラリの sink の候補で、届いた先の sink と流れが根拠になる。例: sqlx の公開のメソッドの SQL の引数が、`database/sql` の sink に届く。
- **source の候補(逆の向き)**: すでにモデルのある source から届いた値が、公開の関数の戻り値に出るなら、その戻り値は source の候補。
- 出力は、候補の一覧で、各候補に根拠(届いた先と、流れの経路)を付ける。モデル作成のコマンド(6.11)の層 1 の候補に、強い根拠として足す。採用か不採用かの判断は、今までどおり人か LLM が行う。

範囲と順序:

- 取得したソースを読むだけで、実行しない。
- Go が先。6.11 の段階 3 のあとに入れる。
- 課題 #144(利用者のプロジェクトで、汚染された値が届いた入口の API の一覧)は、別の課題のまま。こちらは、利用者のプロジェクトを使わず、ライブラリ単体で出す。

## 確認すること

- 公開の関数の引数を、解析の入口(仮の source)にする方法。
- 依存の中を読むコスト(ライブラリの内部と、その依存まで読むと重い)。
- 候補の一覧の、再現率(すでにある手のモデルの行が、候補に入るか)。
