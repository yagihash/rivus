# #194 アクセスパスの深さが、`any` の中身とポインタの先の段を、フィールドと同じに数えるため、別のフィールド(別の型を含む)が区別されない

- 状態: open
- 種類: 注記つきの過大近似(`access_path_truncated` が、区別を失った段に付く)。深さの使い方で減らせる
- 言語: Go
- ROADMAP の節: 2
- 優先度: 中(#290 で、Go の実際のプロジェクトの 1 つで finding が約 7% 増えた)
- 守るもの: 精度(`@sink(none)` のセル。修正と同じ PR で入れる)
- 題: アクセスパスの深さ(既定 k=3)が、`any` の中身とポインタの先の段を、フィールドと同じに数えるため、`any` と型アサーションを通ると、別のフィールドが区別されない

## 何が誤って報告されるか

ジェネリックな型付きハンドラを作る関数(`wrap[T]`)の中で、`typed, ok := r.(*Request[T])` として得たポインタへの書き込みは、#290(5303c941)から、元の値 `r` への書き込みとして追う(別名として正しい: `typed` と `r` は同じオブジェクト)。ところが、同じ値を `wrap[Msg2]` の中の `r.(*Request[Msg2])` で読む経路は、「`r` が `*Request[Msg1]` であり、かつ `*Request[Msg2]` である」ときだけ成り立つので、実在しない。

最小の形(合成の例。実際のプロジェクトでは、ハンドラの連鎖を作る interceptor の `next` の呼び出しに、全ハンドラが候補として載る):

```go
type Request[T any] struct{ Msg *T }
type Func func(r any)

func wrap[T any](f func(*Request[T])) Func {
	return func(r any) {
		typed, ok := r.(*Request[T]) // 別名
		if !ok {
			return
		}
		f(typed)
	}
}

func chain(next Func) Func { return func(r any) { next(r) } } // 候補は、渡した全ハンドラ

func h1(req *Request[Msg1]) { req.Msg.Name = lib.Source() } // source
func h2(req *Request[Msg2]) { lib.Sink(req.Msg.Name) }     // 期待: 出ない(@sink(none))
```

今の main(f67bdab3)で、この形に、h1 から h2 への finding が 1 件出る(測定済み)。#290 の前は、別名を追わないことで、たまたま出なかった。

## 近くの形(測定済み。期待どおり)

今の main で、次の形は期待どおり: comma-ok の型アサーション(同じ値は出る、別の値は出ない)、添字の読み出し(comma-ok の map の参照を含む)、range の値、型 switch の束縛、値(非ポインタ)のコピー(別名にならない。出ない)。つまり、別名づけ自体は正しい。足りないのは、型アサーションの成功の条件。

## 原因

#290 の別名は正しい。原因は、型アサーションが成功する条件(`x` の動的な型)が、流れ(要素)に付いていないこと。要素は、`r` を通ったことだけを持ち、`*Request[Msg1]` として通ったのか、`*Request[Msg2]` として通ったのかを区別しない。

## 修正の方向(案。実装の前に、測定と一緒に相談役へ)

- (a) 型アサーションを、ガードとして流れに付ける: `x.(*T)` を通る要素に「`x` の動的な型が `*T`」という条件を持たせる(dispatch ガードと同じ仕組みに乗せられるか)。finding に条件が載る。
- (b) (a) の上で、同じ値に対する、異なる具体型(ポインタ型、構造体型)の条件が両方付いた経路を、成り立たないものとして落とす(具体型どうしは同時に成り立たないので、健全)。インターフェース型へのアサーションは落とさない(同時に成り立ちうる)。落とした数は `stats` に出す。
- (c) 関数値の呼び出しの候補を、リクエストの型で絞る: 候補を絞る変更で、範囲が広い。今回は選ばない。
- 先に測ること: (a) のガードが、`guard_limit` にどれだけ当たるか。型アサーションを通る要素の数(実在のプロジェクトで)。上限に当たって条件が失われるなら、(b) は効かない。
- #290 は戻さない(戻すと、型アサーションの先への書き込みの見逃しが戻る)。

## 守るもの

修正と同じ PR で、zoo のセルを `@sink(none)` として入れる(形 1 の否定のセル。肯定のセルは、同じ値を同じ型で読む形)。`@fp` のマークでは入れない(正解のマークを足す変更になり、ユーザーの確認が必要なため)。近くの形(添字、range、型 switch、値のコピー)の肯定と否定のセルは、別の PR で、マークなしで通るものとして先に入れる。

## 追記: 深さを何が使うか(測定済み。今の main、合成のコード A、C、D、E、F、2026-11-23)

この課題の見込みは、次のように改める(題と種類を書き直した)。

- パスは文字列 `/段/段…` で、深さは `/` の数(`internal/taint/elem.go` の `pathDepth`)。k で切るのは `pathTrunc`、呼び出しは `state.go` の `targetOf`。k の既定は 3(`engine.go`)。**段は、フィールド名、`[]`、`*` の区別なく、すべて 1 と数える。**
- 変形 A の切られたパスは、4 件とも同じ: 関数 `wrap[Msg1]$1`、根 `r`(`any`)、全体 `/*/Msg/*/Kind` → 残り `/*/Msg/*`。段は、①`/*`(`any` の中身。make_interface が、ポインタの指す先を `/*` の下に置く)、②`/Msg`(フィールド)、③`/*`(ポインタ `Msg` の指す先)、④`/Kind`(フィールド)の 4 段で、k=3 を超え、④が失われる。残る `/*/Msg/*` は「その下すべて」なので、`Name` も `Kind` も含む。C、D、E も同じ形。
- F(`any` なし)は、`/Msg/*/Kind` の 3 段で、k=3 に収まる(切りは 0 件)。つまり、`any` の中身の `/*` が 1 段増やすのが決め手(F の実際のパス文字列は、出していない)。
- **`access_path_truncated` は、A と C の finding の `uncertainties` に付き、A は、実際に区別を失った段(`wrap[Msg1]$1`、desc は `call h1`)の `notes` にも付く**(「`r/*/Msg/*` に、深さ 4 のパスから保存した。以下は汚染とみなす」)。h2 側の段には付かない。つまり、この誤検出は、経路の段の注記から、どこで区別を失ったかが分かる(注記つきの過大近似。memos の 12 件に `access_path_truncated` が付いていたことと合う)。型の条件(案 (a)(b))は、A の一部しか落とせず、C は落とせない。

## 修正の方向(相談役の考え。測定のあとに決める)

- 型アサーションの条件を付ける案 (a)(b) は、保留。
- (i) 深さに数えるのを、名前のあるフィールドだけにする(`any` の中身とポインタの先の `/*` は数えない)。有限性は、数えない段が連続する数に別の上限を置いて守る(超えたら切って、注記)。手計算(推測。実装していない)では、A、C、D、E が 2 段になり、k=3 で切られない。F はもともと出ない。懸念: 同じ値の別の深さの現れ方(`/*` あり・なし)が同じ深さで共存し、要素が増える(コスト)。ポインタの連鎖(リスト、木)は `*` の連続で無限に延びるので、連続の上限が要る。
- (ii) 既定の `-k` を 4 にする: 単純だが、コストが全体に掛かる。
- (iii) 切るときに、フィールド名を残す(切った下を「その名前のフィールドの下の全部」にする): 未検討。
- (iv) インターフェースに入れる段(`make_interface`)が、`/*` を足さないようにする: 今回の決め手は「`any` の中身の `/*` が 1 段増やすこと」なので、原因に最も近い、狭い変更。ポインタをインターフェースに入れたときに、ポインタの先を、インターフェースの値の `/*` の下ではなく、同じ深さに置けるか。置けない理由(値をインターフェースに入れる形と区別が付かなくなる、など)があれば、それも調べて書く。Dart の `dynamic` と Rust の `Box<dyn>` で、同じ 1 段が足されているかも、試作の前に確認する(3 言語で同じ修正になるか)。
- (i) と (iv) は、同じ測定で比べる: 合成の A〜F、zoo の全セル(増減)、`summary_elems` と時間(合成、gogs)、memos は最後に 1 回ずつ。(iv) で A〜E が消え、コストが (i) より小さいなら、(iv) を先に。
- 先に測ること: (i) と (iv) を試作した場合の `summary_elems` と時間(合成、gogs、memos)。#192(段の数の 2 乗)にも影響する(フィールドの区別が残れば、要素は増える)ので、増え方の道具が先に入っていると判断しやすい。アクセスパスの表し方の変更で、ADR-014(深さ k)、ADR-119(依存の深さの既定)に関わる。ADR の文面を変える必要が出たら、ユーザーに聞く。

## 追記: memos での `-k 4` の測定(2026-11-23、memos 00fcd170、GOGC=25、ほかは既定。担当の分類。経路と注記を読んだ見積もりで、確認ではない)

実在のプロジェクト(memos)で、`-k 3`(既定)と `-k 4` を比べた。

| 項目 | `-k 3` | `-k 4` |
|---|---|---|
| finding | 174(xss 95、path_traversal 68、ssrf 11) | 158(xss 95、path_traversal 52、ssrf 11) |
| path_traversal の sink の場所 | 23 か所 | 18 か所(`-k 4` にだけある sink は 0 か所) |
| `summary_elems` | 495428 | 498223(+0.6%) |
| `reanalyses` | 65250 | 65236 |
| 本体のピーク | (別の実行) | 6.36 GB(`GOGC=25`) |

- finding の ID は、代表の source のハッシュで決まり、同じ sink に届く複数の source を 1 件にまとめるので、ID の増減は、代表の選び替えでも出る。**sink の場所と source の数で比べるのが正確**: ほぼすべての sink で、`-k 4` の source の数は `-k 3` 以下。
- `-k 4` にだけある ID 6 件は、全部、構造的な誤検出(sink は `-k 3` にもある)。`-k 3` にだけある ID 22 件にも、本物の経路はない。**深さを上げて、本物の経路が増えた形跡も、消えた形跡もない**(深さ 3 に、見逃しの側の切り捨てがある兆候は、この対象では見えない)。
- `-k 4 -dep-k 4` は、48 秒で、8 GB の監視に止められた(`GOGC=25`)。この深さでは、線の中で終わらない。
- **memos の「#290 で増えた 12 件」**: 経路に、深さの切り捨て、要素を区別しない近似(`container_element_imprecision`)、関数値の候補の広がりの 3 つが重なっている。`-k 4` で消えたのは 2 件(どちらも一時ファイルの作成と削除の sink)。**残る 10 件は、経路の段数も注記も `-k 3` と同じかほぼ同じで、深さだけでは消えない(測定)**。主因が、共有のマップの要素の近似かどうかは、未確認(経路と注記を読んだ見積もり)。最初の分類(型アサーションの別名と `next` の候補の広がりの形)と、今回の分類(共有のマップの要素の混同)は、同じ 12 件について主因の説明が違う。経路に近似が複数あるので、どちらも経路の一部を述べている可能性が高いが、「どの近似を外せば消えるか」は、経路を読むだけでは決まらない。課題を分けるのは、どの近似が主因かが、測定で分かってから。
- 含意: 深さの試作(候補 (i)(iv))は、合成の A〜E には効くが、memos の finding の質への効果は小さい見込み(優先度を下げる)。
