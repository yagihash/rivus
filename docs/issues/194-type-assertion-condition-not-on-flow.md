# #194 型アサーションを通る流れに、型の条件が付かない: 同じ値を、別の具体型へのアサーションで読む経路が出る

- 状態: open
- 種類: 過検出(構造的)
- 言語: Go
- ROADMAP の節: 2
- 優先度: 中(#290 で、Go の実際のプロジェクトの 1 つで finding が約 7% 増えた)
- 守るもの: 精度(`@sink(none)` のセル。修正と同じ PR で入れる)
- 題: 型アサーション `x.(*T)` が成功する条件(`x` の動的な型が `*T`)が流れに付かず、`x` を別の具体型 `*U` にアサーションして読む経路が出る

## 何が誤って報告されるか

ジェネリックな型付きハンドラを作る関数(`wrap[T]`)の中で、`typed, ok := r.(*Request[T])` として得たポインタへの書き込みは、#290(5303c941)から、元の値 `r` への書き込みとして追う(別名として正しい: `typed` と `r` は同じオブジェクト)。ところが、同じ値を `wrap[Msg2]` の中の `r.(*Request[Msg2])` で読む経路は、「`r` が `*Request[Msg1]` であり、かつ `*Request[Msg2]` である」ときだけ成り立つので、実在しない。

最小の形(合成の例。実際のプロジェクトでは、ハンドラの連鎖を作る interceptor の `next` の呼び出しに、全ハンドラが候補として載る):

```go
type Request[T any] struct{ Msg *T }
type Func func(r any)

func wrap[T any](f func(*Request[T])) Func {
	return func(r any) {
		typed, ok := r.(*Request[T]) // 別名
		if !ok {
			return
		}
		f(typed)
	}
}

func chain(next Func) Func { return func(r any) { next(r) } } // 候補は、渡した全ハンドラ

func h1(req *Request[Msg1]) { req.Msg.Name = lib.Source() } // source
func h2(req *Request[Msg2]) { lib.Sink(req.Msg.Name) }     // 期待: 出ない(@sink(none))
```

今の main(f67bdab3)で、この形に、h1 から h2 への finding が 1 件出る(測定済み)。#290 の前は、別名を追わないことで、たまたま出なかった。

## 近くの形(測定済み。期待どおり)

今の main で、次の形は期待どおり: comma-ok の型アサーション(同じ値は出る、別の値は出ない)、添字の読み出し(comma-ok の map の参照を含む)、range の値、型 switch の束縛、値(非ポインタ)のコピー(別名にならない。出ない)。つまり、別名づけ自体は正しい。足りないのは、型アサーションの成功の条件。

## 原因

#290 の別名は正しい。原因は、型アサーションが成功する条件(`x` の動的な型)が、流れ(要素)に付いていないこと。要素は、`r` を通ったことだけを持ち、`*Request[Msg1]` として通ったのか、`*Request[Msg2]` として通ったのかを区別しない。

## 修正の方向(案。実装の前に、測定と一緒に相談役へ)

- (a) 型アサーションを、ガードとして流れに付ける: `x.(*T)` を通る要素に「`x` の動的な型が `*T`」という条件を持たせる(dispatch ガードと同じ仕組みに乗せられるか)。finding に条件が載る。
- (b) (a) の上で、同じ値に対する、異なる具体型(ポインタ型、構造体型)の条件が両方付いた経路を、成り立たないものとして落とす(具体型どうしは同時に成り立たないので、健全)。インターフェース型へのアサーションは落とさない(同時に成り立ちうる)。落とした数は `stats` に出す。
- (c) 関数値の呼び出しの候補を、リクエストの型で絞る: 候補を絞る変更で、範囲が広い。今回は選ばない。
- 先に測ること: (a) のガードが、`guard_limit` にどれだけ当たるか。型アサーションを通る要素の数(実在のプロジェクトで)。上限に当たって条件が失われるなら、(b) は効かない。
- #290 は戻さない(戻すと、型アサーションの先への書き込みの見逃しが戻る)。

## 守るもの

修正と同じ PR で、zoo のセルを `@sink(none)` として入れる(形 1 の否定のセル。肯定のセルは、同じ値を同じ型で読む形)。`@fp` のマークでは入れない(正解のマークを足す変更になり、ユーザーの確認が必要なため)。近くの形(添字、range、型 switch、値のコピー)の肯定と否定のセルは、別の PR で、マークなしで通るものとして先に入れる。

## 追記: 形 1 の変形(測定済み。今の main、5134fe6f、合成のコード)

`wrap[T]`、`chain(next)`、`Run()` は本文の形と同じで、`Run()` は `[]Func{chain(wrap(h1)), chain(wrap(hN))}` に `*Request[Msg1]` を渡す。

| 変形 | 構造 | 期待 | 実際 |
|---|---|---|---|
| A | `Msg1{Kind}`、`Msg2{Name}`。h1 が `Msg1.Kind` に書き、h2 が `Msg2.Name` を読む | 出ない | **出た(1 件)** |
| B | `Msg1{Name}`、`Msg2{Name}`。h1 が `Msg1.Name` に書き、h2 が `Msg2.Name` を読む | 出ない | **出た(1 件)** |

分かること: 書くフィールドと読むフィールドが、名前も型も違っても(A)出る。つまり、誤検出は「同じ名前のフィールド」に限られない。流れが、フィールド名の一致に頼っていないことと、型アサーションが成功する条件が付いていないこととは、矛盾しない。ただし、A で、なぜフィールドを区別しないのか(`Request[T]` の `Msg` から先のアクセスパスが、型を見ていない、または `any` を通った値の全体に広がる、など)は、調べていない。修正の案 (a)(b) の前に、A の原因を調べる(アクセスパスが `r` 全体に切られるのか、`access_path_truncated` が付くのか)。

## 追記: 変形 A の原因は、アクセスパスの深さの切り捨て(測定済み。今の main、合成のコード、2026-11-23)

変形 A(書く側 `Msg1.Kind`、読む側 `Msg2.Name`。名前も型も違う)で、フィールドを区別していない理由を、1 つずつ変えて調べた。

分かったこと(確認済み):
- 原因は、**`-k 3`(既定)でのアクセスパスの切り捨て**。`depth_limit` の `path_limit` の注記に、`wrap[Msg1]$1`(型アサーションを含む中の関数)だけが出る。`-k 3` では、この関数で `Msg` から先(`Kind` の層)のパスが切られ、切られたパスは「その下すべて」を表すので、`Msg1.Kind` が `Name` も含む形になる。
- 切り捨ては `any` を通る経路で起きる(F は `-k 3` でも出ない)。`any`、型アサーション、`typed` のポインタの層が深さを使うため、と考えられる(推測。深さの内訳は見ていない)。
- #290 の別名が前提(戻すと A も C も出ない)。別名自体は正しく、深さ 3 での区別の切れとの組み合わせで出る。
- 出力の widening、関数値の呼び出しの候補の広がりは、主因ではない(D は `next` を使わなくても出る)。#332 のバイナリでも `out_limit` は出ない。
- 変形 C から、**同じ型の別のフィールドでも出る**。つまり、型の条件を付けても C は落とせない(型が同じで、原因は深さ)。
- 出た kind は `depth_limit`(`path_limit`)。memos の 12 件に付いていた `access_path_truncated`(経路の段の注記)との関係は未確認(同じ切り捨ての別の見え方か)。

## 修正の方向への影響

- 案 (a)(b)(型アサーションの条件)は、A の `Request[Msg1]` と `Request[Msg2]` の矛盾で A を落とせる見込みがあるが、C は落とせない。**深さの切り捨てを減らす案が、別に必要**: 例えば、切り捨て時にフィールド名を保持する、`any` やポインタの層を深さに数えない、など(未検討)。
- 既定の `-k` を 4 にする案は、A、C、D、E をすべて消すが、コスト(要約の増え方)と、ほかの形への影響を、測ってから(ADR-119 は、依存の深さの既定を 2 にした。主なコードの深さの既定は 3 のまま)。
- 先に測ること: memos の 12 件が、`-k 4` で消えるか(`-k 4` の実行でのコスト。メモリが 8 GB の線の際にいる、ということも考える)。
