# #203 Dart: フィールドのパスがフィールド名だけで、持ち主のクラスが無い(同名のフィールドが別のクラスでも同じパスになる)

- 状態: **open**
- 種類: 過検出(精度。過大近似の側)
- 言語: Dart(Go と Rust も同じ作りで、差は下の節)
- ROADMAP の節: 0
- 守るもの: -
- 題: Dart の `field_load` と store のパスがフィールド名だけで、持ち主のクラスが無い

## 何か

Dart の extractor は、フィールドの読み書きの `field` に、`target.name`(フィールド名だけ)を入れる(`extractor/dart/lib/exprs.dart` の `_readMember`、`_recordField`。書く側は `_writeMember`)。taint のパスは `/名前` の連なり(`internal/taint/elem.go` の「access paths」)なので、別のクラスの同名のフィールド(`_type`、`_body`、`_target` など)は、同じパスになる。持ち主のクラスの区別は、パスにも要素にも無い。

動きは、過大近似の側に出る: ある実装が `this._type` に書く、という要約は、同じ名前のフィールドを持つ別のクラスにも当てはまるものとして、受け取る側のパスに入る。

## 見つかった場所

dart_services(`bench/deps-targets.json`)の最大の SCC(関数 12,295 個、ほぼ `package:analyzer`)の測定。出力の数が、ラウンドごとに 4〜7 倍に増える(2026-11-24 の測定。ダンプに足したパスの上位は、`param1/_argumentList/*`、`_type/*`、`_typeArguments/*` など、構文木のノードのフィールド名が約 50 個。それぞれが 2,200 から 2,900 の関数に 1 つずつ入る)。抽象型(`Node`、`AstNode`)の引数を受ける関数の要約に、全実装のフィールドの書き込みが、名前だけのパスとして和集合で入る、という見立て(どの実装が書くか、要素の中身は未確認。測定の結果は別に追う)。フィールド名だけのパスが、広がりの 1 つの要因になりうる。

## Go と Rust との差(PARITY)

読んで確かめた(動かしていない)。

- Go(`internal/frontend/goir/ops.go` の `fieldName`): フィールド名だけ(名前が無い、`_` のときは `#<番号>`)。持ち主の型は入れない。構造体の型が静的に決まるので、読み書きの対象は 1 つの型に決まるが、別の構造体の同名のフィールドは、同じパスの名前になる(値の流れが同じ場所を通るときだけ混ざる)。
- Rust(`extractor/rust/src/lower.rs` の `field_name`): 構造体はフィールド名だけ。enum は `バリアント名.フィールド名`、クロージャと `async` は、クロージャ(コルーチン)の名前つき(別のクロージャの `0` と混ざらないため)。つまり、Rust は持ち主を入れる所がある(クロージャ、コルーチン、enum のバリアント)。構造体は入れていない。
- Dart: 持ち主なし。仮想呼び出しの候補が多い(抽象クラスの全実装)ので、同名のフィールドが混ざる機会が、Go より多い。

言語の差としては、Go と Dart は持ち主なし、Rust はクロージャ、コルーチン、enum のバリアントだけ持ち主あり。構造体のフィールドは 3 言語とも名前だけ。

## 直すのは今ではない

持ち主を入れる(`Class.field` の形にする)と、パスの形が変わり、要約、モデル(`fields` の規則)、zoo のセルに影響する。測定(出力の数の広がりの中身)を見てから決める。直すときは、3 言語を一緒に見る(PARITY)。
