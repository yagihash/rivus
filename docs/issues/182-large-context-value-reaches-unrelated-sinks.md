# #182 Go: 大きな文脈の値(`*gin.Context` など)に入れた値が、同じ値から読む別の sink に届く

- 状態: **open**
- 種類: 構造的な過検出
- 言語: Go
- ROADMAP の節: 2
- 守るもの: -

## 何が誤って報告されるか

エラーなどを、リクエストの文脈の値(`*gin.Context`)に書く(`c.Error(err)`、`c.JSON(...)` の中の描画の失敗)と、その値が汚染る。あとで、同じ型の値から読む無関係な処理(別のハンドラ、ミドルウェアの先)の sink にも、その汚染が届いたように報告される。そこでは、sink に届く値は、もともとリクエストの source で汚染ていて、文脈に書いた値は関係ない。

測定(2026-11-23、実プロジェクト 1 つ。場所は書かない): アーカイブの名前を新しく source にしたところ、新しい finding が 87 件増えた。見分けると 12 件が本物の流れ、**75 件がこの形**(エラーを文脈に書く 1 つの流れが、25 の sink に届く。3 つの source で 75)。

## 持っている uncertainty

75 件のすべてに、uncertainty がある(`container_element_imprecision` が全件。`dynamic_dispatch` が 78 件中の多く、`unmodeled_library_call` が 76 件、`global_var` が 6 件)。`confidence` は `requires_review`。つまり、uncertainty のない finding ではない。ただし、`container_element_imprecision` は、文脈の中の `Error` が、エラーの並びに足す所に付いていて、原因を言っていない。

## 場所が分かれない原因の切り分け(今分かっている範囲。新しい調査はしていない)

1. 文脈の型が、型による source(`param_type`)の下で、値全体が 1 つの要素として扱われ、書いた汚染と、リクエストの汚染が同じ要素に入っている可能性。
2. `Context` の中の本体(描画、エラーの並び)で、経路が上限や不動点で切れて、フィールドの区別が失われている可能性。
3. `c.Error` のモデルが「引数 → レシーバの全体」で、並びの中のエラーの要素に限っていない可能性(`(*gin.Context).Error` に行はなく、本体を読んでいる。並びへの追加が「要素を区別しない」近似になる)。

課題 179(埋め込みの昇格でフィールドが分かれない)とは別の原因: 179 は `f.Name` を 1 つ読む所の広がり、これは文脈に書いたあとの広がり。

## 修正の案

3 つの可能性のどれかを、小さな再現(文脈に 1 つ書き、別のフィールドの sink が静かなこと)で切り分ける。再現は、zoo の Go のセルにする(vuln: 同じフィールドの読み出しは届く。decoy: 別のフィールドは静か)。

優先度: 中の上(`*gin.Context` に限らず、リクエストの文脈の値を渡して回る Web フレームワークの全部で起きる。source を増やすたびに、このノイズが増える)。
