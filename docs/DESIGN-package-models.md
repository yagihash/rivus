# パッケージ単位の「本体を読まない」宣言と、モデルを書く標準の流れ(設計案)

状態: 案(2026-11-23。相談役の判断を反映済み)。段階 2(解析側。ADR-100)と段階 4(extractor に宣言を渡す。Go と Dart。ADR-105。7a 節)は実装済み。以下の 1〜6 節は、設計時の調査と試作の記録で、書き換えていない。測定は、Go の実際のプロジェクトでの利用から出た課題と、公開のベンチ(`bench/dart-gcp`、`bench/dart-grpc`)、AWS SDK for Go v2 の `service/s3` を数個呼ぶ小さい合成(リポジトリの外に作った。取得したコードは実行していない)で行った。

目的(ユーザーの方針): モデルの拡充が、解析だけでなく、読み込み(extractor)の時間とメモリにも効くようにする。`-no-deps` なしの実行が実用的に動くことが目標。前に止めてあった `unread_packages` の案([DESIGN-deps-cost.md](DESIGN-deps-cost.md) 7 節)を、この目的に合わせて作り直す。条件の土台は ADR-092(依存を流れのモデルで切る)と ADR-098(実装の多いインターフェースのメソッド)。

## 1. 今の動作(コードの調査)

モデルがあるとき、今、何が省かれていて、何が省かれていないか。

1. **extractor が読む範囲は、モデルの有無で変わらない。**
   - Go: `cmd/rivus/common.go` の `load`(163 行)は `gossa.Options{Deps: !c.noDeps && withGraph}` で `internal/frontend/gossa/load.go` の `Load` を呼ぶ。`Deps` なら `NeedDeps` を足し(169 行)、`ssautil.AllPackages`(239 行)で依存のパッケージも全部、ソースから型検査して SSA にする。`loadGo`(174 行)の `rules.Expand` は、インターフェースのメソッドの規則を、プログラムの中の実装のメソッドに写すだけで、何も読まない・省かない。標準ライブラリだけは、`skip`(486 行の `buildInOrder`)で SSA の本体を作らない(モデルが代わりをする)。
   - Dart: extractor(`extractor/dart/lib/extract.dart`)に渡るのは `--no-deps`、`--include-tests`、`--allow-deps-under` だけ(`cmd/rivus/lang.go` 330〜340 行)。モデルは渡らない。
   - Rust: `--no-deps` だけ(`extractor/rust/src/main.rs` 295 行)。
   - 読む範囲を変えるのは `-no-deps`、`-tests`、`-allow-deps-under` だけ。
2. **依存の具体的な関数に、flows / pure / calls / sanitizer のモデルがあるとき、呼び出しの所では、モデルが使われ、本体の要約は使われない**(`internal/taint/calls.go` 223〜226 行。`rules.HasModel`(`internal/model/model.go` 1254 行)は、sanitizer か propagator の行があること。sink / source だけの行は `HasModel` ではないので、本体が使われる)。インターフェースやトレイトのメソッドにモデルがあるときは、依存の実装の本体は使わず(`dependency_body_unread` の注記。`noteDepBodies`、1143 行)、プロジェクト自身の実装は、読んでモデルと合わせる(ADR-075)。
3. **モデルで置き換えられた関数の本体の要約も、計算される。** `Engine.Run`(`internal/taint/engine.go` 529 行)は、本体のある全関数(`e.prog.Funcs`)を、ボトムアップに計算する。呼び出しグラフはモデルで変わらない。ADR-098 の測定で解析が 65〜90% 減ったのは、「呼び出しの所で、依存の実装の要約を適用して合流する」処理が省かれたから。依存の関数自身の解析は省かれない。
4. **同じパッケージの、モデルのない関数は、本体が読まれる。** パッケージ単位で切る方法がない(今は、全部読むか、全部読まないか)。

## 2. 案

1. **宣言**: モデルのファイルに、パッケージ単位の宣言を書ける。**宣言は、書いたパッケージだけに効く(暗黙の接頭辞一致はしない)。** 配下のパッケージもまとめて指すときは、明示の書き方を 1 つ用意する(Go の `.../...` のような形。例: `github.com/aws/aws-sdk-go-v2/service/s3/...`)。「このパッケージは、このモデルが本体の代わりをする(本体を読まない)」。組み込みにも利用者のルールにも書ける。フラグでも指定できる(一時的に試す用)。フラグで宣言を無効にして、本体を読む実行もできる(照合と確認用)。
2. **extractor の段階から本体を IR にしない。** 言語ごとの、省けるものと省けないもの(3 節の測定つき):

| 言語 | 省ける | 省けない(型の解決に要る) |
| --- | --- | --- |
| Go | SSA の本体を作ること(`go/ssa` の `Build` は関数ごと / パッケージごとに呼べ、`buildInOrder` が既にパッケージごとに `skip` を持つ)、IR にすること(`WithLifted` の 2 つ目の SSA も)。`Load` が `packages.Load` のあと、宣言のあるパッケージの `Syntax` と `TypesInfo` を捨てれば、`ssautil.AllPackages` は本体のない関数だけを作る(下の試作) | `go/packages` は、`NeedDeps` で全部のパッケージを、ソースから型検査する。パッケージごとに `NeedSyntax` を切り替えられない。型検査を省くには、宣言のあるパッケージを、エクスポートデータ(`go list -export`、ビルドが要る)で読む別の読み込みが要る。ただし、この合成での `packages.Load` は、キャッシュがあるとき 0.6〜1.0 秒で、全体の 2.5〜3 秒の一部なので、いまは割に合わない |
| Dart | 宣言のあるパッケージのファイルの `getResolvedUnit`(関数の本体の解決)と、IR への下ろし(`_Lower`)。そのパッケージの `import` をたどらない(推移的な依存を読まない)こと(下の試作) | analyzer が、宣言と型のために、ライブラリの要素モデル(`LibraryElement`)を作ること。プロジェクトのコードが、宣言のあるパッケージの型を使うので、その公開の宣言とシグネチャは要る。本体の解決は要らない |
| Rust | 宣言のあるクレートの `extract`(MIR を IR に下ろして JSON にする。`main.rs` の `driver`。`--crate-name` で、そのクレートと分かる)を飛ばすこと | `cargo check` が、依存のクレートも全部コンパイルする(型の解決のため。`RUSTC_WRAPPER` のドライバは、各クレートで `rustc` の代わりに走る)。これは省けない。今回は測っていない(サンドボックスと固定の nightly が要る) |

3. **宣言のあるパッケージの関数への呼び出し**は、行があればモデル、なければ `unmodeled_library_call`(そのパッケージに限った `-no-deps` と同じ扱い。ADR-092 の 4)。注記が付くので、サイレントにならない。
4. **出力**: `summary` に、本体を読まなかったパッケージの一覧と、その理由(どのモデルのファイルの宣言か)。ADR-092 の 5、と、「依存の中の sink は探していない」の項目(ブランチ `feat/dependency-sites-note` で進行中。`summary` の同じ場所)と、同じ場所に出す。
5. **宣言を付けてよい条件**(ADR-092 / 098 の続き): (i) 差分テスト(`bench/model-diff`。実装済み。手順書 9 節。7 節の段階 1)で、公開の API の flows が、本体と照合済み(MISS 0、EXTRA は意図した差だけ)、(ii) ライブラリが利用者のコードを呼び返す形(コールバック、利用者が実装するインターフェース)が、`calls:` の行で表されている、またはないことを確認済み、(iii) そのパッケージが、ほかの読むパッケージから呼ばれる場合(読む依存 A が、読まない依存 B を呼ぶ)の扱いが決まっている。(iii)は、A の本体の要約は B の呼び出しを「モデル行があればモデル、なければ `unmodeled_library_call`」で扱うので、A の中の B への呼び出しも同じ扱いになる。A が B に渡したコールバックは、`calls:` の行が要る。
6. **推移的な依存**: 読まないパッケージ B だけが使う依存 C は、読み込む必要がなくなる。到達性で自動的に落とせる(Go: B を通らずにプロジェクトから import で届くパッケージだけを残す。Dart: `visit` が B の import をたどらない。Rust は、`cargo check` が全部コンパイルするので、落とせない)。測定(3 節)では、これが読み込みと解析の両方に最も効いた。

## 4. 「モデルを書く」標準の流れ(4 段)と、型からの生成

報告(Go の実際のプロジェクトでの利用から)された事実: (1) 型の情報から、保守的な規則で粗いモデルを生成できる(戻り値が数値・bool・なしなら `pure`、それ以外は、レシーバとデータを運びうる引数 → `results`、書き込み先の引数には方向のある流れ、`context` は流さない)。直接 import する外部のパッケージの API 全体で、解析なし、約 3 秒。ある対象で、モデルのない呼び出しが 11,466 → 436、finding と sink の集合は不変。別の大きい対象でも 72% 減。(2) 差分テスト(本体とモデル、ライブラリごと、依存込みでも 400〜700 MB)を、約 15,000 の関数とメソッドで実行。体系的な誤り 2 つを直したあと、MISS は意図した 3 件だけ、一致は 90〜99%、残りは妥当な過大な近似。(3) 新しい体系的な誤り: 書き込み先を取る関数(`Decode`、`Read(p)`、`Write(p)`、`SetBytes` など)で、書き込み先の引数が、**戻り値(error に入力の型や値が入る)とレシーバへ流れる経路**を、モデルが落としがち。書き込み先の引数は、読み取り元にもなる。(4) 生成器を直しても、古い生成物が残る(再生成の対象の入れ忘れ)。**これらの数字は、報告された数字で、rivus の側では未確認**(この文書の測定は、rivus の側で測った 3 節と 4.4 だけ)。

### 4.1 標準の流れ

| 段 | 内容 | 道具 | 出力 |
| --- | --- | --- | --- |
| (i) 生成 | 型から粗いモデルを生成する。`origin: generated`。書き込み先の引数は、`results` とレシーバへの流れの読み取り元にも含める | 生成器(言語ごと。4.2) | `internal/model/builtin/<lang>-<package>.yaml`(生成の部分) |
| (ii) 照合 | 差分テストで本体と比べる。MISS は 0。EXTRA は、意図した差として記録(理由つき) | `bench/model-diff`(段階 1) | 差分の一覧。EXTRA の記録 |
| (iii) 追加 | sink / source / sanitizer と、呼び返し(`calls:`)だけを、人か LLM が足す。`origin: human` か `llm` | `rivus models coverage`、肯定と否定のフィクスチャ(zoo) | 手の行 |
| (iv) 宣言 | パッケージに「本体を読まない」を付ける。2 節 5 の条件(i)〜(iii)を満たしたものだけ | 宣言の書式(段階 2) | 宣言 |

この流れで、「pub と Go の人気のパッケージを順にモデル化する」作業の 1 パッケージあたりの時間は、(iii)の人の作業(sink、source、呼び返し)だけに縮められる見込み。流れの速さは、見積もりで、実測ではない。

### 4.2 型の情報の取り方(言語ごと。調査した事実)

| 言語 | 取り方 | 既存の足場 | 注意 |
| --- | --- | --- | --- |
| Go | `go/packages` の `NeedTypes`(`NeedSyntax` なし)で、パッケージの公開の API を `go/types` で列挙する(関数、メソッド、インターフェースのメソッド、フィールド)。報告の方法と同じ | `internal/frontend/gossa/load.go`、`rivus models coverage` のテンプレート(`stub`) | ジェネリクス、埋め込み、エクスポートされた型エイリアスの扱い |
| Dart | analyzer の `LibraryElement`: `exportNamespace` の公開の宣言、`ClassElement` のメソッドとコンストラクタ、型つきのシグネチャ(`FunctionType`)。本体の解決は要らない | `extractor/dart/lib/extract.dart` が `LibraryElement` を既に使っている(`lib.firstFragment.libraryImports` など)。`names.dart` が、IR のシンボル名(`package:...#Class.method`)を作る | シンボル名の綴りは、extractor が出す名前と一致させる(同じ `names.dart` を使う)。`part` と再エクスポート |
| Rust | rustdoc JSON(`cargo +<固定の nightly> rustdoc -- -Zunstable-options --output-format json`)が、公開の項目と、ジェネリクス・トレイト境界つきのシグネチャを出す。代わりに、`extractor/rust/` のドライバ(`rustc_public`)で、`tcx` の公開の項目の `fn_sig` を取る | `rust-toolchain.toml` に固定の nightly がある。ドライバは、`all_local_items` を既に使っている。`cargo metadata` は、パッケージの一覧とバージョンだけで、シグネチャは出ない | rustdoc JSON は不安定(nightly で形式が変わる)。固定の nightly なら、形式は固定できる。`impl Trait`、ジェネリクス、ライフタイムの扱い。シンボル名は、extractor の MIR の名前(`lower.rs`)に合わせる |

### 4.3 生成物と手の行の区別、再生成の漏れを防ぐ仕組み

- **`*.gen.yaml` はコミットする**(組み込みは `go:embed` で埋め込むので、ビルドに要る)。先頭に、生成器のバージョンと入力(パッケージとバージョン)を書く。手で書いた行は、別のファイルにする。
- **`origin`**: 規則の行の `origin` は、既に `builtin` / `human` / `llm`(`internal/model/model.go` 45〜47 行)。生成した行には `generated` を足す。生成した行は、再生成で上書きされ、`human` / `llm` の行は残る。生成部分と手の部分は、**別のファイル**にする(`<lang>-<package>.yaml` は手の部分、`<lang>-<package>.gen.yaml` は生成の部分)。同じ symbol に両方の行があるときは、手の行が生成の行を上書きする(行の統合の規則を、`Merge` の中で決める)。
- **漏れを防ぐ**: 生成したファイルの先頭に、`generator: <名前>@<バージョン>` と、`input: <ライブラリ名>@<バージョン>` と、入力(公開の API の一覧)のハッシュを書く。テスト(`go test`)が、全部の `*.gen.yaml` について、生成器をもう一度走らせて、ハッシュと内容が一致することを確認する(依存の取得が要るので、定期の層と、`*.gen.yaml` を触った PR のテスト)。生成器のバージョンを上げたとき、全ファイルの再生成を CI が要求する(1 つでも古ければ失敗)。これで、「生成器を直したが、古い生成物が残る」(報告の 4)を防ぐ。
- **規則の採用**: 報告の生成の規則と差分テストの仕組みは、LLM が書いたもので、人の確認前。**規則は、rivus の側で、zoo と差分テストで確認してから採用する。** 参考の実装(報告元の `apigen`、`diff-test`、`models` のスクリプト)は、この文書を書いた担当は読んでいない(読む許可が、ユーザーの直接の指示で確認できなかった)。生成の規則の詳細は、rivus の側で、zoo の表 S と差分テストの結果から決める。

### 4.3a 生成の規則の決定(段階 3 の生成器。Go の実際のプロジェクトでの利用から)

参考の事実(報告された数字。rivus の側では未確認): 生成器は、Python 約 100 行と、API を列挙する Go 約 170 行。モデルは合計約 18 万行(直接の依存 77 パッケージで約 5.9 万行、推移的な依存で約 8.2 万行、標準ライブラリ約 2.2 万行)で、全部 `origin: llm`。生成の規則は、`go/types` の型の分類(データを運びうる型 / 関数 / error)と、引数の名前と関数名の正規表現の組み合わせ。**丸ごとは取り込まない**。rivus の側で、型の情報から自分で作る。使える所と、変える所を、次のとおり決める。

**使える所(出発点)**:

| 項目 | 内容 | 扱い |
| --- | --- | --- |
| (1) 規則の骨組み | 関数を引数に取る関数はスキップ(手で `calls:` を書く)。戻り値なしで、データを運ぶ引数だけの関数はスキップ(モデルなしのまま = 既定の保守的な扱い)。`context` は流さない。書き込みは方向つき | rivus の生成器の出発点にする |
| (2) 手で書かれた小さいファイル | コールバックの `calls:` の行(errgroup、singleflight の `Do` / `DoChan`、`sync.Map` の `Range`、backoff の `Retry`、goldmark の `ast.Walk`)と、標準ライブラリの追加の行(`io.TeeReader`、`reflect`、`os.Open` など。約 67 行) | 1 行ずつ確認できる量。標準ライブラリの分は、どの Go の利用者にも効くので、課題の「標準ライブラリの 23 行」を約 67 行に広げ、組み込みの基準で 1 行ずつ確認して取り込む(別の作業。取り込む計画として 1 項目) |
| (3) 照合の材料 | あちらの生成物と、rivus の生成物 | rivus の生成器ができたら、重なるパッケージ(cobra、viper、logrus、golang-jwt、`x/oauth2`、connect-go、grpc-gateway、yaml など)で比べて、規則の差を洗い出す |

**規則の決定(rivus の生成器では変える)**:

| | 決定 | 理由 |
| --- | --- | --- |
| a | **書き込み先の引数を、引数の名前(`dst`、`out`、`v`、`dest`、`target`、`ptr` など)で判定しない。型(ポインタ、slice、map、interface、chan)で判定する(広い側に寄せる)** | 名前が違うと(例: `Bind(i any)` のような出力用のポインタ)、レシーバ → 引数の流れが落ちる = サイレントな見逃し。#163 のテンプレートと同じ |
| b | **戻り値が数値や bool だけの関数を `pure` にしない。flows で書き、止めるのはエンジンの `numeric_stop` に任せる**(`pure` は、戻り値が引数にもレシーバにも依らないときだけ) | 既定では数値で止まるので結果は同じだが、`-numeric-taint` のときに流れが消える |
| c | ログの関数(`Info`、`Errorf` など)を `pure` にするのは、流れとしては正しい。ログへの出力を sink にする行と両立することを確認する | sink の行は別に書ける、で足りる見込み。生成のときに、sink の行がある関数は `pure` にしない、で守る |
| d | **レシーバを、既定で `from` に入れる** | 「データを運びうる型」のときだけ入れると、分類が狭いときに、レシーバ → 戻り値が落ちる |
| e | 差分テストのコードは、単純な型の引数の関数しか機械的に作れない(ジェネリクス、複雑な型、コールバックは対象外)。**照合できなかった行は、「未照合」と分かる形で残す**(生成物の行に `unverified: true` のマークを付ける)。宣言を付ける条件の数字に入れる(「照合済みの行の割合」) | 照合できなかった行が、照合済みに見えると、宣言の条件(2 節 5 の(i))が、見かけだけ満たされる |
| f | **`origin: llm` を、生成物用の origin に分ける**(`origin: generated`。生成器のバージョンつき。`verified_versions` と同じ場所(ファイルの先頭)) | バージョンの記録がないと、どの生成器とどの入力で作ったか分からない(4.3、6.7 の 1) |

手順書の 8 節(生成と差分テストの対象外)と整合させる: 機械で作れない行(コールバックを取る関数、ジェネリクス)は、「手で書く」か「未照合」と書く(e)。

### 4.4 組み込みに入れる量の上限

報告では、ある対象で、組み込みの行が約 3 万行になり、読み込みの時間とメモリは変わらないとされている。rivus の側で、合成のモデルで測った(`internal/model/builtin/zz-synth.yaml` を足してビルドしたコピー。1 行の propagator = 2 行の YAML。`rivus analyze` を、Go の小さい 1 ファイルのプログラム(標準ライブラリだけ)で 3 回ずつ。load average 6〜12):

| 組み込みの YAML | 規則(行)の数 | 起動を含む wall(3 回) | 最大 RSS |
| --- | --- | --- | --- |
| 今(4,242 行) | 約 1,700 | 0.54〜1.05 秒 | 381〜386 MB |
| +6,671 行(計 約 1.1 万行) | +2,224 | 0.65〜0.97 秒 | 380〜401 MB |
| +20,003 行(計 約 2.4 万行) | +6,667 | 0.65〜1.08 秒 | 399〜409 MB |
| +66,671 行(計 約 7 万行) | +22,222 | 0.73〜1.17 秒 | 417〜424 MB |

- 約 7 万行(今の 17 倍)で、起動の時間が約 0.1〜0.2 秒、メモリが約 35〜40 MB 増える。数万行なら、時間もメモリも、ほぼ変わらない(報告と一致)。規則の検索は、シンボルをキーにした map(`HasModel` など)で、行数に比例しない。
- 起動のたびに全部を解析している(`go:embed *.yaml` を、全言語分)ので、増加は行数に比例する。10 万行を超えたら、言語ごと、または使うパッケージだけを読み込む(遅延読み込み)案を検討する。それまでは、行数の上限は、起動の時間ではなく、レビューできる量と、`bench/parity/dead-allow.txt`(zoo の行が当たらない行)の管理の量で決める。**上限の目安: 組み込みの手の行が、1 つのファイルで 2,000 行を超えるものは、パッケージごとに分ける。生成の部分(`*.gen.yaml`)は、レビューの対象外で、数万行まで置いてよい**(提案。決めるのは相談役)。

## 5. リスク

**利用者のコードへの呼び返しが落ちる形(2 節 5 の(ii))が、いちばんサイレントになりやすい。** 宣言のあるパッケージが、渡されたコールバックや、利用者が実装したインターフェースのメソッドを呼ぶとき、`calls:` の行がないと、その呼び出しのエッジが消え、そこを通る流れが、注記なしに消える。検出の方法の案:

1. 差分テストに、コールバックを渡す形(関数値、クロージャ、利用者の型の実装)を入れる(段階 3)。
2. extractor(または生成器)が、宣言のあるパッケージの公開の API のうち、**関数や、利用者が実装できるインターフェースを引数に取る**ものを一覧にして、`calls:` の行がないものを警告する(宣言を付ける前の確認。生成器の出力に含められる: 型の情報から分かる)。
3. 宣言のあるパッケージの関数へ渡された関数値は、`calls:` がなければ、呼ばれるものとして扱い、不確実性の注記を出す(ADR-092 の 3。`-no-deps` の既定の動作と同じ)。

**決定: 2 と 3 を両方入れる。** 生成器が、公開の API の一覧と、`calls:` のない行の警告を出す(2)。解析は、宣言のあるパッケージの関数に、関数の値や利用者の実装が渡されたのに `calls:` の行がないとき、「呼ばれるもの」として扱い、注記を付ける(3。**既定を、見逃さない側にする**)。差分テストに、コールバックを渡す形を入れるのは、段階 3。

そのほかのリスク:

- **言語ごとの型の解決**: Go は、宣言のあるパッケージの型情報だけを読んでも、`ssa` が、本体のない関数だけを作る(試作で確認)。Dart は、本体を解決しなくても、宣言とシグネチャは要るので、`part` / 再エクスポートの先のファイルは、宣言のあるパッケージとして扱う。Rust は、`cargo check` が全部コンパイルするので、コンパイルの時間は減らない。
- **IR の互換**: IR の形式は変えない(本体のない関数は、今の `-no-deps` で既にある形)。宣言の有無を、IR のヘッダか `load_error` の `unread: true` に入れるかは、実装のときに決める。
- **`-ir` のファイル**: `-ir` は、IR のファイルを読むので、宣言は IR を作る側(extractor)で効く。宣言を付けた実行で作った IR を、宣言なしの実行で読むと、本体がないまま解析される。IR のヘッダに、宣言したパッケージの一覧を書く。
- **index の鍵**(`cmd/rivus/graphkey.go`): 宣言(と、それを出したモデルのファイルのハッシュ)が、index の鍵に入る(`flags.no-deps` と同じ扱い)。宣言を変えたのに古い index を使うと、本体を読んだ結果と読まなかった結果が混ざる。
- **決定論**: 宣言の一覧はソートする。生成物のハッシュ、`summary` の一覧もソートする。
- **書き込み先の引数の誤り(4 節の(3))**: 現在の `models coverage` のテンプレート(#163: 書き込みの行を、引数ごとに型から)が、この誤りを持っていないかは、**開発者(rivus-developer)が別に確認する**。この文書での決めごと: **生成の規則とテンプレートは、書き込み先の引数を、`results` とレシーバへの流れの読み取り元にも含める。** 差分テストの EXTRA / MISS で、`Decode`、`Read(p)`、`Write(p)`、`SetBytes` の形を、フィクスチャにする。
- **古い生成物**: 4.3 の仕組みで防ぐ。
- **取得したコードを実行しない**: 差分テストと生成器は、依存を取得するが、実行しない(Go: `go mod download`、`go list` と型検査だけ。Dart: `dart pub get` と analyzer。Rust: `cargo fetch` と rustdoc / `cargo check`(ビルドスクリプトと proc macro は動くので、信頼できるコードに限る。サンドボックスの下で))。

## 6. モデル作成のセッションを並べて走らせる準備(設計案)

### 6.5 Rust の環境(調査と案。実装はしない)

状況: `make setup`(`scripts/dev-setup.sh`)は、Go と Dart だけを入れる(「Rust は対象外」)。Rust のモデルを作って確認するには、Rust の extractor が動く必要がある。調べたことと、見積もり(**この環境では入れて測っていない**。数字は、ドキュメントと CI の設定からの見積もり)。

1. **Linux でのビルドの手順と時間**: CI の `rust` ジョブと同じ。`rustup toolchain install`(`extractor/rust/rust-toolchain.toml` の `nightly-2026-11-15`、`minimal` + `rustc-dev`、`llvm-tools`、`rust-src`。取得は約 1 GB: `docs/rust-isolation.md`)、`cargo build --locked`(`rustc_private` にリンクする extractor のビルド)。時間は、回線とマシンしだいで、nightly の取得に 1〜数分、ビルドに数分(CI の `timeout-minutes` は 60)と見込む。実測は、段階の最初に取る。
2. **Linux の隔離**: rivus には、ない(`-lang rust` は、サンドボックスがないと何も実行せずに止まる。`-unsafe-host-exec` だけが通る。ADR-093、`docs/rust-isolation.md`。`docs/DESIGN-macos-sandbox.md` は、「あとで bubblewrap などを足せるよう、起動のインターフェースを 1 つにする」としている)。候補: bubblewrap(`bwrap`。名前空間でファイルとネットワークを絞る。取得の段階はネットワークあり、抽出の段階は `--unshare-net`。macOS のプロファイルと同じ 2 段階にできる)、`unshare`(同じ名前空間。ファイルの絞り込みを自分で組む)、gVisor(ランタイム。コンテナの外から使うもので、クラウドのセッションの中では使えない)。**クラウドのコンテナの中では、非特権のユーザー名前空間が使えないことが多く、`bwrap` が動くかは、環境で確かめるまで分からない(未確認)。** 動かないなら、Linux の隔離は、特権のあるホスト(VM)が要る。コンテナそのものを隔離として使うのは、セッションの資格情報(トークン、署名の鍵)が同じコンテナにあるので、勧めない。
3. **`make setup` に含めるか**: **含めない。別のターゲット(`make setup-rust`)にする。** 取得が大きく、Go と Dart のモデルには要らない。
4. **5 分の制約**: クラウドのセットアップは、5 分以内に終わらないとキャッシュされない。nightly の取得(約 1 GB)と extractor のビルドを足すと、超える見込みが高い(未測定)。超えるものを `make setup` に入れると、Go と Dart のキャッシュまで失う。キャッシュの置き場所は、`~/.rustup`、`~/.cargo`、`extractor/rust/target`。`make setup-rust` は、Rust のモデルを取るセッションの最初に走らせる(毎回のコスト)か、別のキャッシュ(別のセットアップ)に分ける。
5. **動かせない場合: 「作るが、Rust のテストは CI に任せる」は成り立つか**: **部分的に成り立つ。** モデルの YAML の検証は、Go のテスト(`internal/model/builtin` のテスト)で手元でも確認できる。Rust の zoo のセルは、第三者のコードを実行しない形(`bench/zoo-rust` は std だけ。依存のスタブは `path:` の自前のコード)で作れるので、CI の `rust` ジョブ(`-unsafe-host-exec`、自分のリポジトリのコードだけ)で確認できる。ただし、手元で試せないので、PR が赤くなる確率が高く、修正の往復が CI の時間になる。**差分テストの Rust 版は、第三者のクレートの本体を読む(= `cargo check` で、その `build.rs` と proc macro が動く)ので、取得したコードを実行しない規則と衝突する。** rivus の Rust extractor は、読むときに `build.rs` と proc macro を実行する設計で、隔離(2)がないと、この環境では動かせない。CI のランナーで、取得した第三者のクレートを読む差分テストを走らせるのも、同じ理由で勧めない(隔離のあるジョブに限る)。

**推奨: Rust は、いまは CI に任せる。つまり、定期のセッションでは Rust のパッケージを取らない(Go と Dart だけ)。** Rust のモデルは、Linux の隔離(bubblewrap など。段階を 1 つ足す。中規模。環境で `bwrap` が動くことを先に確かめる)と `make setup-rust` が入ってから、差分テストとあわせて始める。それまでに Rust のモデルが要るときは、人(開発者)が、手元(macOS のサンドボックス)で作る。

### 6.7 モデルの鮮度: 確認したバージョン、定期的な照合、利用者の実行のときのずれ(設計案)

問題: 外部のライブラリが更新されると、モデルが古くなる。「本体を読まない」宣言を付けたパッケージは、古いモデルが、**サイレントな見逃し**になる(新しい API はモデルになく `unmodeled_library_call` になるが、変わった動作や、増えたコールバックは、注記なしに落ちる)。

**今ある仕組みで検知できる範囲(事実)**:
- 検知できる: 組み込みの行が、zoo の呼び出しに一致すること(`TestBuiltinRowsAreHitByTheZoo`、`cmd/rivus/dead_rows_test.go`。行のシンボルが、zoo の IR に出ること)。ただし、zoo は、実物でなく骨組みを使うセルがある(`bench/zoo-dart/cells/packages/http` は、「本物のパッケージはない。`Client` API の形」と自分で書いている。Go の `bench/zoo-go/dep` も自前のコード)。**骨組みは、実物の変更を検知できない**(骨組みに行が一致することを見ているだけ)。
- Renovate(`renovate.json`): `bench/**` は `ignorePaths` で、**zoo の依存は更新の対象外**。更新の対象は、rivus 自身の依存(`go.mod`、`extractor/*` の Cargo と pub、GitHub Actions)で、モデルのパッケージの更新を知らせる仕組みではない。
- 検知できない: 新しい API、動作の変更、利用者のプロジェクトのバージョンとのずれ。

#### 1. モデルに、確認したバージョンを書く(最初のモデルの前に、形式を決める)

**書式(推奨)**: モデルのファイルの YAML のトップレベルに、`verified_versions` を置く(`internal/model/model.go` の `RuleSet` のフィールド。`ruleset:` と同じ階層)。**宣言(パッケージ単位の「本体を読まない」。`body_replaced_packages` が実装中)とは別の場所**に置き、宣言は、その同じパッケージが `verified_versions` にあることを検証で要求する。

```yaml
ruleset: rivus/dart/http@1
verified_versions:
  - package: http            # Go: モジュールのパス / Dart: pub のパッケージ名 / Rust: クレート名
    versions: ">=1.2.0 <2.0.0"   # 確認した範囲(Go と Rust は semver の範囲。Dart は pub のバージョンの範囲)
    checked_with: 1.2.2      # 実際に確認したバージョン(1 つ)
    checked: 2026-11-23      # 確認した日
```

宣言と同じ場所に置く案との比較:

| | 別の場所(推奨) | 宣言と同じ場所 |
| --- | --- | --- |
| 宣言のないモデル(手で書いた行だけのファイル、`-no-deps` でも使うモデル)にも書ける | はい(利用者のずれの注記(3)に要る) | いいえ(宣言のあるパッケージだけ) |
| 宣言との整合 | 検証で結ぶ(宣言したパッケージは、`verified_versions` に必須) | 1 つの項目なので、ずれない |
| 生成物の先頭の「入力のバージョン」 | 同じ情報(生成器が書く `input:` から `verified_versions` の `checked_with` を作れる) | 同じ |
| 1 つのファイルに複数のパッケージ(`dart-gcp.yaml`) | 項目を並べる | 宣言と同じ数 |

**検証**(`Rules.Validate` と、`internal/model/builtin` のテスト):
1. 書式: 未知のキーは失敗、必須の 3 つ(`package`、`versions`、`checked`)、`checked` は日付(未来でない)、`checked_with` は `versions` の範囲に入る。
2. バージョンの形: Go はモジュールの semver(`v1.2.3`。`+incompatible` と、疑似バージョンの扱いを決める)、Dart は pub のバージョンの範囲(`^1.2.0` を含む)、Rust は Cargo の semver の範囲。言語は、ファイルの行のシンボルの形(Go の `pkg.Func`、Dart の `package:...#`、Rust の `crate::`)で決める(1 つのファイルは 1 言語)。
3. 存在しないパッケージ: オフラインでは、`package` を持つ行のシンボルが、少なくとも 1 つあること(行のないパッケージを書いていない)。オンラインでは(生成器、定期の照合。ネットワークが要る)、レジストリ(proxy.golang.org、pub.dev、crates.io)にそのパッケージと `checked_with` のバージョンがあること。
4. 第三者のパッケージの行を持つ組み込みのファイルは、`verified_versions` が必須(標準ライブラリは不要)。入れる順: 新しいファイルから必須にし、既存のファイルは、順に足す(足すまでは警告)。

実装は、段階 0 と 2 の PR に続ける(この文書は、形式だけ決める)。

#### 2. 定期的な照合(案。実装は生成器のあと)

最新のバージョン(または、`versions` の範囲の外の新しいバージョン)を取得し、型からモデルを生成し直して、今のモデルと比べる。差分の種類: **増えた API、消えた API、シグネチャが変わった API**。差分テストも実行し直す。差があれば、更新の PR を立てる(題の形: `feat(model): <言語> <パッケージ> のモデルを更新する(<旧バージョン> → <新バージョン>)`。手順書 7 節)。**クラウドの定期実行に載せる想定**(1 回の実行 = 1 パッケージ = 1 つの PR。`verified_versions` の `checked` が古い順に取る)。
- **骨組みのセルも対象にする**: zoo の骨組み(`bench/zoo-dart/cells/packages/http` など)のシグネチャを、実物の公開 API(新しいバージョン)と比べる(生成器の出力と、骨組みの公開宣言の比較。骨組みにあって実物にない API、実物にあって骨組みにない API)。これが、zoo が実物の変更を検知できない穴を塞ぐ。
- 取得したコードは実行しない(Rust は隔離が入るまで対象外。6.5)。

#### 3. 利用者の実行のときのずれ(案)

利用者のプロジェクトが使っているバージョンが、モデルの確認した範囲(`versions`)の外のとき、出力に注記を出す。**既定は、注記を出してモデルを使う**(止めない)。注記の場所: (a) `summary` に、範囲の外のパッケージの一覧(パッケージ、使っているバージョン、確認した範囲)、(b) そのパッケージのモデルが関わった finding の注記(`model_version_outside_verified`。種類は新設)。**フラグで、「範囲の外のパッケージは、宣言を無効にして本体を読む」を選べる**(宣言なしのパッケージは、モデルが使われたまま注記だけ)。

**extractor がバージョンを出せるか(事実)**:

| 言語 | 今、IR にバージョンを出しているか | バージョンの取り方 |
| --- | --- | --- |
| Go | 出していない(IR のヘッダは `schema_version` だけ。`internal/ir/stream.go`、`ir.go`) | `go/packages` は `NeedModule` を既に使っていて(`internal/frontend/gossa/load.go` 164 行)、`pkg.Module.Version` が取れる(`collectInputs` が `pkg.Module` を既に読んでいる)。`go.mod` / `go.sum` のバージョンと同じ。取れる |
| Dart | 出していない | `package_config.json` の `rootUri` はバージョンを直接持たない。取り方は 2 つ: (a) `pubspec.lock` の `version:`(核の側でも、extractor でも読める。hosted のパッケージ。path / git の依存はバージョンがない)、(b) pub のキャッシュのパス `hosted/pub.dev/<名前>-<バージョン>`(extractor の `_packageDir` が、そのディレクトリを持っている。ただし、git の依存は `<名前>-<ハッシュ>`)。(a) を推奨 |
| Rust | 出していない | `Cargo.lock`(`version`)。またはドライバの中で、cargo が `rustc` の呼び出しに付ける環境変数 `CARGO_PKG_NAME` / `CARGO_PKG_VERSION`(cargo の仕様から。この環境では未確認)。`extractor/rust/src/main.rs` は、`cargo metadata --no-deps` を既に使っている |

**最小の拡張案**: コア側で、利用者の対象の `go.mod` / `go.sum`(Go は `go/packages` の `Module.Version`)、`pubspec.lock`、`Cargo.lock` を読む(**IR は変えない**)。`-ir` のファイルだけを渡された場合は、バージョンが分からないので、注記は出さない(「バージョンは不明」と `summary` に 1 行)。次の段階で、IR のヘッダに `packages: [{name, version}]` を足す(extractor が出す)と、`-ir` でも注記が出せる。index の鍵に、バージョンの一覧を入れる(バージョンが変わったら、別の index)。

#### 4. 生成器と差分テストの「対象外として明示する範囲」

別の実装の報告(rivus の側では未確認)から: **ジェネリクスの関数は、差分テストのコードを機械的に作れず、未検証で残った。コールバックを取る関数は、手で書く行になった。** どちらも、生成器と差分テストの、対象外として明示する範囲に入れる(手順書: 「手で書く」「未検証」と、PR の本文に書く)。Dart のジェネリクスのメソッド(`Dio.get<T>` など)も、同じく未検証で残る(型の引数に具体的な型を入れてプローブを作る案が成り立つかは、[課題 #157](issues/157-dart-generic-method-model-diff.md))。**生成したモデルと生成器の一式は、取り込まない**(rivus の側で、型の情報から自分で作る)。

### 6.8 zoo のセルの依存(骨組みか、本物のパッケージか。調査と案)

背景: モデルのセルを作る担当が、骨組み(`bench/zoo-dart/cells/packages/<名前>`)を自分で書くと、手間がかかるだけでなく、**モデルを書いた本人が骨組みも書くので、本物とのずれに気づけない**(確認の意味が弱い)。骨組みが本物と名前でぶつかる、本物と違う引数の渡し方をしてテストが失敗する、という問題が、検証用の 1 本目(Dart の `shelf_router`)で起きた。

**今、骨組みにしている理由(事実。`bench/zoo/README.md`、`docs/DESIGN-zoo.md`、コミット `f70d2b1`、`1f33c8e`)**:
1. **exec が骨組みの記録に依存する。** `bench/zoo-dart/exec` は、セルを実行して、`zoo_mark` の記録(`dependency_overrides` で、宣言だけの `zoo_mark` を、記録する `zoo_mark` に置き換える)で、sink に値が届いたか、届かなかったかを確かめる(実行で裏付ける)。`package:http` の骨組みの記録は、sink でない `recordAny`。本物のパッケージの関数(`Client.get`)は、記録しないので、実行の裏付けができない。
2. **本物のコードが動く。** 本物の `http` のセルを `dart test` で実行すると、本物の `Client.get` が動き、ネットワークに出る(`example.invalid` への接続)。骨組みなら、何も起きない。
3. 「Flutter の本体は入れない(SDK が重く、`pub get` が不安定)」(DESIGN-zoo.md)、Rust の zoo は「依存が一切ない」(`cargo check` が `build.rs` と proc macro を動かすので、zoo は自前のコードだけ)。
4. `pubspec.lock` は、セルを足す PR 同士の conflict を避けるためにコミットしない(`1f33c8e`。CI と `make setup` が `dart pub get`)。本物の依存は、ロックがないと、推移的な依存のバージョンが変わりうる。

**実験(Dart。この機械で。`dart pub get --offline`、実行はしていない)**: `bench/zoo-dart/cells` のコピーで、`packages/http`(骨組み)を、**バージョンを 1 つに固定した本物**(`http: 1.2.2`。キャッシュにあった)に替えて、`rivus analyze -lang dart` を比べた。
| | 骨組み | 本物(`http: 1.2.2`) |
| --- | --- | --- |
| finding | 197 | 197(`http_client_get` のセルは、どちらも 2 件。同じ) |
| コアが読む関数 | 915 | 1,565(依存の 657 関数が増える) |
| load(extractor + IR) | 6.1 秒 | 7.2 秒 |
| 注記 | `unmodeled_library_call` 80 | `unmodeled_library_call` 76、`dependency_body_unread` 16(`Client.send` のモデルがあるので、依存の実装を読まない)、`summary.dependency_sites`(`searched: false`、依存の関数 657) |
- **本物にしたときに変わること**: 依存として読まれる(`Dep`)。`-allow-deps-under` は要らない(pub キャッシュは、常に信頼される。今回のフラグなしの実行で確認)。`summary.dependency_sites` の注記が付く。zoo のテストが、注記の数や種類を比べているなら、期待値が変わる(要確認。`cmd/rivus/zoo_dart_test.go`)。宣言(`body_replaced_packages`)を付けたパッケージは、本体を読まないので、むしろ自然(読み込みが減る)。**行のシンボルが、本物のファイルの構成(`package:http/src/client.dart#Client.send`)と一致するかを、本物で確かめられる**(骨組みは、ファイルのパスまで真似る必要があった)。
- **本物の依存の置き方**: セルのパッケージ(`cells/pubspec.yaml`)に足すと、ロックをコミットしないので、推移的な依存が変わりうる。**本物のパッケージごとに、別のディレクトリ(`bench/zoo-dart/real/<パッケージ>/`)に、自分の `pubspec.yaml` と、コミットした `pubspec.lock`** を置けば、PR 同士で conflict しない(別のファイル)。`bench/dart-gcp` が、同じ形(ロックをコミット)で、公開のベンチになっている。

**exec の安全(事実と判断)**: 本物のパッケージの exec は、取得した第三者のコードの実行になる(`dart test`。依存の本物のコードが呼ばれる)。規則「取得したコードは実行しない」と、衝突する。ただし、CI には前例がある: `gcp-exec`(`bench/gcp`)は、Google Cloud の本物のクライアントを、フェイクに向けて実行している(loopback 以外は拒否するテスト)。**クラウドのセッションでは、この規則のため、本物の exec は走らせられない(CI に任せる)。** 判断: 相談役。

**Go と Rust の同じ点**:
- Go(`bench/zoo-go`): 依存は、自前のモジュール `zoodep`(`go.mod` の `replace zoodep => ./dep`)だけ。「zoo の依存の代わり」で、第三者のパッケージと同じく本体が読まれる(`Dep`)が、第三者のコードではない。本物のモジュールにするなら、`go.mod` の `require` を固定して、`go.sum` をコミットする(Go はロックが `go.sum` で、conflict は、足す行が別なので、起きにくい)。
- Rust(`bench/zoo-rust`): **依存が一切ない**(std だけ。`build.rs` なし、proc macro なし)。Rust の extractor は `cargo check` で `build.rs` と proc macro を動かすので、本物のクレートに依存させると、第三者のコードの実行(隔離の下でだけ許される。6.5)になる。**Rust は、骨組みのままにする**(生成する。下の案 (b))。

**差分テスト(段階 1)との分担**(手順書に書ける形): **zoo のセルは、「sink / source / sanitizer の位置の確認」に絞る**(行が、本物のシンボルに一致して、肯定のセルで届き、否定のセルで届かない)。**流れの確認(引数 → 戻り値、書き込み先、レシーバ)は、差分テストに任せる**(本物の本体と照合する)。zoo のセルは、モデルの流れの正しさを、骨組みで確かめない。骨組みが本物とずれても、位置の確認だけなら、害が小さい。

**案**:
- (a) 本物のパッケージに依存させる(Dart だけ先に)。条件: CI のオフライン(`pub get` は CI で既にオンライン)、ロック(パッケージごとのディレクトリ)、exec の安全。**exec の記録ができない**(骨組みの記録がない)ので、そのセルは、解析だけの確認になり、「実行で裏付ける」を失う。
- (b) 骨組みのまま、ただし、**本物の公開シグネチャから機械的に生成する**(生成器は段階 3 と共有。モデルを書いた本人が手で書かない)。exec の記録(`recordAny`)は、生成した骨組みの中に、機械的に入れる。
- (c) 現状のまま。

**推奨: (b) に、本物での解析の照合を足す。** セルは、生成した骨組みで、解析と exec を行う(実行の裏付けを残す。本物のコードは動かさない)。**同じセルを、本物のパッケージ(バージョン固定。パッケージごとのディレクトリ、ロックをコミット)に対しても、解析だけして、骨組みの解析と、finding の集合が同じことを確認する**(上の実験で、`http` は 197 件が同じだった)。これで、(i) 骨組みの手書きのずれ(名前、ファイルのパス、引数の渡し方)が、照合で見つかる(骨組みが本物とずれると、finding が違う)、(ii) 本物のコードは実行しない(規則と整合)、(iii) 生成器が入る前も、照合は今すぐ入れられる(生成器は後)。理由: (a) は、exec の記録と、本物の実行の安全を失う。(c) は、本物とのずれに気づけない問題が残る。

**外部のパッケージを使うセルの置き方(3 言語で 1 つの方針。事実は、一時の場所で骨組みだけを置いて確かめた。取得はしていない)**:

方針: **セルは、解析では骨組み(本物の公開のシグネチャから作る)に向け、実行では、第三者のコードを新たに動かさない。パッケージごとに、独立したモジュール(Go)、独立したクレート(Rust)に置く**。共有のファイルは、足さない。

| | Go | Rust | Dart |
| --- | --- | --- | --- |
| 置き場所 | `bench/zoo-go-pkg/<パッケージ>/`。自分の `go.mod`(`module zoopkg/<パッケージ>`、`replace zoo => ../../zoo-go`(`zoo/mark` を使う)、`replace <本物のモジュールのパス> => ./skel`)、`skel/`(骨組み。自分の `go.mod` の名前は本物のモジュールのパス)、`cells/`、`rules.yaml` | `bench/zoo-rust-pkg/<パッケージ>/`。自分の `Cargo.toml`(空の `[workspace]` で、zoo の workspace に入れない)、`skel/`(骨組みのクレート。名前は本物)、`zoo-mark`、`src/`(セル)、コミットした `Cargo.lock`、`rules.yaml` | `bench/zoo-dart/cells/packages/<パッケージ>`(path の依存)。`cells/pubspec.yaml` と `exec/pubspec.yaml` は、そのディレクトリから生成する(コミットしない)。`test` の依存と名前がぶつかる骨組みは、自分の `pubspec.yaml` に `zoo_exec_override: <範囲>` を書く(exec の `dependency_overrides` に出る) |

事実(試して分かったこと):
- Go: 独立したモジュール(`zoo-go` の外)は、`zoo-go` の `./...` に入らない。`go build`、`-tags zooexec`、`rivus analyze` が通り、`github.com/gin-gonic/gin` の骨組みの `Context.Query` から `mark.SinkCmd` への finding が出た。
- Rust: **サンドボックスは、対象のディレクトリの外にある path の依存を読めない**(`../../zoo-rust/zoo-mark` は、取得の段で読めずに失敗した)。`zoo-mark` は、テストが対象のディレクトリに写す(今の `zooRustCopy` と同じ)。写せば、サンドボックスの下で動き、finding が出た。取得したクレートは動かしていない(取得そのものがない)。
- **実装済み(`cmd/rivus/zoo_pkg_test.go`)**: テストは、`bench/zoo-go-pkg/*` と `bench/zoo-rust-pkg/*` を、ディレクトリから探す(一覧はない)。`TestZooPkgGo` と `TestZooPkgRust` が、パッケージごとに、3 回の実行(全部のケースが走り、全部の文が走る)、真の注釈の照合、rivus の照合を行う。Go の実行用の `cmd/observe` は、overlay で作る(リポジトリに生成しない)。Rust の実行用の crate は、一時のディレクトリに書く(共有の target で、zoo-mark は 1 度だけビルド)。マークの固定(`zooMarksRows`)と、一致した行の数え上げ(`goZooSymbols`、`rustZooSymbols`)も、同じディレクトリを探す。**zoo 全体の検査(`TestFuncValues*`、パリティ、純粋の行、コールバックの行など)は、`bench/zoo-go`、`bench/zoo-rust` だけを読む**ので、骨組みの `Dep` は入らない。依存の関数を数えるのは、一致した行の数え上げだけ(骨組みを呼ぶことが、その行に当たることなので)。合成の `zoo_synth`(Go と Rust)で確かめた。
- CI: paths-filter の dart と rust に `!bench/zoo-go-pkg/**`(rust と dart)と `!bench/zoo-rust-pkg/**`(dart)を足した。Go のパッケージは `test` のジョブが、Rust のパッケージは `rust` のジョブが、テストの中で拾う(ステップを足さない)。Rust のパッケージは、1 つのジョブの中で順に、共有の target で動く(zoo-mark と標準ライブラリのビルドは 1 度。パッケージごとに足されるのは、骨組みとセルのビルドと、抽出の数秒)。
- **zoo-mark の渡し方(Rust のサンドボックス)**: (a) テストが、パッケージを一時のディレクトリに写し、zoo-mark も写して、`Cargo.toml` の path を書き換える(採用。共有のファイルが増えない。コミットしたパッケージは、リポジトリの中でも `cargo check` が通る)。(b) サンドボックスの読み取りの許可に、zoo-mark の場所を足す(エンジンの隔離の変更になり、対象の外を読ませる許可が増える。採らない)。(c) パッケージごとに zoo-mark をコミットする(写しが増える。採らない)。

| 条件 | Go | Rust | Dart |
| --- | --- | --- | --- |
| (i) 共有のファイルをさわらない | 満たす | 満たす | 満たす(2 つの `pubspec.yaml` は生成物) |
| (ii) zoo 全体を検査するテストに、依存のコードが入らない | 満たす(別のモジュールで、固定のディレクトリに入らない。骨組みの検査は、パッケージごとの処理で行う) | 満たす(同じ) | 満たす(cells に本物の依存がない) |
| (iii) 第三者のコードを動かさない | 満たす(取得なし) | 満たす(取得なし。`build.rs` なし) | 満たす(本物は `test` がすでに動かすものだけ) |
| (iv) 骨組みは機械的に生成する | Go は済み(6.11 の段階 2。`make model ... ARGS="-gen-skeleton"`) | 未(同じ) | 未(同じ) |

**開発用の依存とぶつかる骨組み(Dart。`shelf_router` で起きた。解決済み)**: 骨組みの `shelf_router` が本物の `shelf` に依存すると、`shelf` とその依存(`async`、`collection`、`http_parser` など)が zoo のプログラムに入り、zoo 全体を検査するテスト(`TestFuncValuesDart` など)が、依存の関数に引っかかる。骨組みの `shelf` を置くと、`exec` の `test` が持ってくる本物の `shelf` と名前でぶつかる。解決は、**解析と実行で、依存の解決を分ける**こと。cells(`bench/zoo-dart/cells`)は、`shelf` を骨組み(`packages/shelf`、path の依存)に解決し、rivus は骨組みだけを読む。exec は、`dependency_overrides` で `shelf` を本物(`test` がすでに動かしているもの)に解決し、セルのコードは本物で動く。骨組みは本物の公開のシグネチャから作るので、セルは両方で型が合う。取得したコードを新たに動かさない(上の「exec の安全」の線の内側)。検査のテストは、依存の関数を対象から外さない(zoo に本物の依存を置けないことを守る検査でもあるため)。`test` の依存の名前が、モデルの候補(`shelf`、`shelf_web_socket`、`web_socket_channel`、`async` など)と重なるが、この形で骨組みを置ける。

実装の順(コードは書いていない): 1. 照合の仕組み(`bench/zoo-dart/real/<パッケージ>/` と、比べるテスト。CI で `dart pub get`)。2. 生成器(段階 3)ができたら、骨組みを生成に替える。手順書の 2 節(作る)には、相談役の判断のあとに反映する。

**生成器の要件(骨組み)**: 本物の型の埋め込みと、インターフェースの実装の関係を、本物と同じ形にする(昇格したメソッドが、別のパッケージの行に当たるため。実例: Go の `sqlx.DB` は `*sql.DB` を埋め込む。骨組みが埋め込まないと、昇格したメソッドを呼ぶセルが、本物と違う形で通る)。

### 6.9 module の path に major を持つ Go のパッケージ(`/v*`。ADR-110)

背景: Go の module は、major が 2 以上になると、path に `/vN` を持つ(`github.com/google/go-github/v93`、`github.com/jackc/pgx/v5`)。シンボル(`(*github.com/google/go-github/v93/github.Client).Do`)も、組み込みのモデルの行の鍵も、この path をそのまま含む。そのため、1 つの行は 1 つの major にしか当たらない。major ごとにファイルや行を写すと、行が major の数だけ増え、`.dead-allow` と zoo のセルも同じだけ増える。

**書式**: シンボル(`symbol`)、`kind: field` の `field`、`kind: param_type` の `type`、`verified_versions` の `package` で、module path の major の要素を `/v*` と書く。

```yaml
verified_versions:
  - package: github.com/google/go-github/v*
    versions: ">=93.0.0 <94.0.0"      # 差分テストを通した範囲。いまは v93 だけ
sinks:
  - symbol: (*github.com/google/go-github/v*/github.RepositoriesService).GetContents
```

- **`/v*` が当たるのは、path の 1 要素で、`/v` と数字(2 以上、先頭が 0 でない)だけ**: `/v2`、`/v93` には当たる。`/vendor`、`/v2x`、`/v`、`/v1`、`/v0` と、major のない path には当たらない(`v0`、`v1` は、Go の module の path に現れない)。任意の glob ではない。
- 1 つの文字列に、1 回だけ書ける。module の path のあとに、要素の全体として書く(あとに `/`、`.`、`)` が来る、または文字列の終わり: `x/v*/pkg.F`、`(*x/v*/pkg.T).M`、`x/v*.F`)。それ以外(`v*x`、`v*2`、2 回、path の先頭)は、読み込みで失敗する(検証)。Go のモデルだけ。Dart と Rust には、この書式はない。
- **照合のしくみ**: 索引は、シンボルの文字列そのものが鍵なので、鍵は変えない。解析の読み込みのとき(`loadGo`)、プログラムが持つ package の import path(依存を含む)から、`/v*` の行ごとに、module の path が合う major を集め、major ごとに行の写しを、具体的なシンボルの鍵で足す(`match: implementations` の展開と同じ形。`Rules.ExpandMajors`)。モデルのファイルの行は変わらない。プログラムがその module を使っていなければ、写しはできず、行は何にも当たらない(今までの、当たらない行と同じ)。`rivus models coverage` は、解析の結果から出すので、そのまま動く。
- **道具の側**: `bench/model-diff` は、`-pkg` に `/v*` を書けて、`-version`(`v93.0.0`)の major で具体的な package に直す(`-version` がなければ失敗)。`TestBuiltinRowsAreHitByTheZoo` は、`/v*` の行を、どれかの major のシンボルへの呼び出しが当てれば、当たったとみなす。`.dead-allow` は、行と同じ文字列(`/v*` つき)で書く。`verified_versions` の `package` の `/v*` は、全部の major を指す記録で、`versions` は、実際に差分テストを通した範囲(そのときに確認した major だけ)にする。
- 接尾辞のない v0 / v1 の path には `/v*` は当たらない。v1 と v2 以降の両方を対象にするパッケージは、接尾辞のない行と `/v*` の行の両方が要る(一覧の 14 行で該当するものがあれば、そのパッケージの回で扱う)。
- **確認する major**: 上流が今もサポートしている major が対象(既定は最新。複数をサポートしていれば、それぞれで差分テストを通し、`verified_versions` に並べ、その major にしかない API の行も書く)。「サポートしている」は上流の公開の事実(サポートの方針、README、リリースのブランチ、直近のリリース)で決め、根拠を 1 行で書く。分からないときは最新だけにする。サポートを終えた major は対象にしない(行は当たり、6.10 の注記が出る)。
- **しないこと(この節では)**: 解析した対象の major が `verified_versions` の範囲にないとき、`summary` に注記を出す(6.7 の 3。別の PR)。`body_replaced_packages` の `package` に `/v*` を書くこと。`-ir` で渡された Go の IR への展開(展開は、Go の解析の読み込みの中だけ)。

### 6.10 確認していないバージョンへの適用の注記(`summary.unverified_versions`。Go、Dart、Rust。6.7 の 3 の実装)

解析した対象が使っている module のバージョンが、`verified_versions` の範囲の外のとき、**モデルの行は当てたまま**、`summary.unverified_versions` に 1 件ずつ出す(`[{package, used, verified: [範囲...], source: "go.mod"}]`。`package` は、使っている module の path(`/v*` の記録のときは、対象が持つ major の path)。`body_replaced_packages` と同じく、package でソートされ、決定論)。finding が 0 件でも出る。

- **出す条件**: (1) `verified_versions` の記録があり、その `package`(`/v*` を含む)が、対象が使っている module の path に当たる。(2) 使っているバージョン(完全なバージョン。`go list` の `Module.Version`)が、その module に当たるどの記録の `versions` にも入らない。記録が複数あれば、どれかに入れば出さない。
- **記録のない module には出さない**(組み込みのファイルの大半は、記録がない。全部の解析に注記が付くとうるさく、「確認していない」と言うにも、何を基準にするかがない)。記録を持つモデルが当たっていないとき(対象がその module を使っていない)は、出力は今までと同じ。記録を足すのは、手順書の 2 節の 3 段(新しいファイルは必須)で進む。
- **バージョンが分からない module は出さない**: ディレクトリへの `replace`、別の module への `replace`(`go.mod` のバージョンは、実際に読むコードのバージョンではない)、主 module。バージョンの接尾辞(`-pre`、`+incompatible`)は読まない(疑似バージョンは、前のバージョンの番号とみなされる)。
- **実装**: `gossa.Program.ModuleVersions`(読み込みのとき、`packages.Package.Module` から)、`model.Rules.UnverifiedVersions`、`report.Summary.UnverifiedVersions`。`-ir` で渡された IR と、`-index` の IR からの解析は、モジュール情報がないので出ない。
**Dart(`pubspec.lock`)**: Dart の extractor は、IR にバージョンを出さないので、コアが、対象のディレクトリ(`-C`)の `pubspec.lock` を読む(IR は変えない。6.7 の 3 の最小の拡張案)。Dart の extractor が動いた解析だけが読む(`-ir` と `-index` からの解析は、ディレクトリを読まないので出ない)。`source` は `pubspec.lock`。
- 読むのは `packages:` のうち `source: hosted` の `version`。`path` と `git` の依存は、比べるバージョンがないので出さない。`package` は、pub のパッケージ名そのまま(`dio`、`shelf_router`)。
- `pubspec.lock` がない(`dart pub get` をしていない)ときは、注記も、エラーもない。読めない(YAML が壊れている)ときは、標準エラーに 1 行出して、注記は出さない。
- **未対応**: 複数のパッケージの monorepo や pub のワークスペース(`pubspec.lock` が、`-C` のディレクトリでなく、親のディレクトリにある)。`-C` のディレクトリに `pubspec.lock` がなければ出さない(Dart の extractor も、1 つのパッケージを `-C` に指す前提。解析の警告にもそう書いてある)。
- プレリリース(`6.0.0-beta.1`)は、Go と同じく、接尾辞を読まずに数字だけで比べる(`6.0.0` として、`<6.0.0` の範囲の外)。
- **記録は、言語ごとに照合する**。記録は、どの言語のファイルにあるかを持つ(`model.RuleSetLanguage`。組み込みのファイル名 `dart-*.yaml`、`rust-*.yaml`、`go-*.yaml`、またはルールセット名 `rivus/<言語>/...`)。Go の `go.mod` は Go の記録と、`pubspec.lock` は Dart の記録と、`Cargo.lock` は Rust の記録とだけ照合する。名前が同じで言語が違う記録(Dart の `http` と Rust の `http`)は、別々に扱う。言語が分からないファイル(プロジェクトの `.rivus/rules` や `-rules` で渡したファイル。名前に言語を示すものがない)の記録は、今までどおり、どの言語の依存にも当たる。`rivus models versions` の JSON は変えない。

**Rust(`Cargo.lock`)**: Rust の extractor が動いた解析だけが、`-C` の `Cargo.lock` を読む(IR は変えない。extractor も変えない)。`source` は `Cargo.lock`。
- 読むのは `[[package]]` のうち、`source` が registry(`registry+`、`sparse+`)のもの。path の crate(`source` なし。対象自身を含む)と git の crate は、比べるバージョンがないので出さない。`package` は、lock の綴り(`actix-web`)で出す。照合は `-` と `_` を同じとみなす(`model.SameCrate`。モデルが `google_cloud_storage` と書いても、lock の `google-cloud-storage` に当たる)。
- 1 つの crate が lock に複数のバージョンで入ることがある(`[[package]]` が 2 つ)。全部を見て、**どれかが範囲の外なら** 1 件にする(crate ごとに 1 件)。`used` は、lock の順で最初の外のバージョン、`all_used` が全部(順は lock のまま)。
- `Cargo.lock` がなければ、注記もエラーもない(`--locked` なしで取得した対象)。ワークスペースの子の crate を `-C` に指したとき、`Cargo.lock` がワークスペースの根にあれば読まない(出ない)。未対応。
- プレリリース(`1.0.0-rc.1`)は、Go、Dart と同じ扱い(接尾辞を読まない)。
- 複数のバージョンを持つ lock(Cargo.lock で起きる)のために、`model.UnverifiedVersion` に `all_used` を足した。バージョンが 1 つのときは出ない(Go の JSON は変わらない)。

### 6.11 モデル作成の手順のスクリプト化(設計案)

背景: クラウドで 1 パッケージ分のモデルを作る作業(手順書 [MODEL-RUNBOOK.md](MODEL-RUNBOOK.md))は、Dart(dio、github、shelf、googleapis_auth)、Go(gin、storage、sqlx、go-github、`os` と `database/sql` の行)、Rust(actix-web、axum、google-cloud-storage、octocrab)の 10 本あまりで、ほぼ毎回、手順書への追記が要った。クラウドで確実に回すには、手順を全部スクリプトにして、人や LLM の判断を「sink、source、sanitizer をどれにするか」だけに絞る必要がある。最初の要件(決まった手順はスクリプト、LLM は sink / source / sanitizer の選択だけ)に戻る。この節は設計案で、実装はしない。事実は、手順書の履歴(`git log --follow docs/MODEL-RUNBOOK.md`)と、リポジトリのファイルで確認した。

| 9 | zoo のゲート、`regomark check --no-judge` | なし | `scripts/zoo-loosened-check.sh`(`make zoo-loosened`)、`regomark` |
| 10 | PR の題と本文の材料 | `.claude/work/` などの一時の場所(コミットしない) | 新規(数字の集計) |

**判断の置き場: モデルのファイルそのもの**。入力ファイルを別に作って、そこからモデルを生成する形(`models-src/`)は採らない。手の行は、モデルの書式の全部(`named:`、`categories`、`callback_param`、`calls:`、`checked_by`、コメント)を使う。入力ファイルから生成すると、この書式を入力ファイル側でもう一度定義することになり、既存のモデルの移行も要る。代わりに:

- **採用した候補 = モデルの行そのもの**。今までどおり手で直してよい。
- **採用しなかった候補 = 同じファイルの `rejected:` の節**。1 件は `symbol`、`kind`(sink | source | sanitizer | calls)、`why`、必要なら `position`。今、モデルのファイルの先頭に「採用しなかった候補と理由」をコメントで書いているものを、データにする。ローダーは読んで検証するだけで、解析は使わない。

```yaml
rejected:
  - symbol: github.com/jmoiron/sqlx.LoadFile
    kind: sink
    why: "引数はファイルのパスで、クエリではない"
  - symbol: (*github.com/jmoiron/sqlx.NamedStmt).Exec
    kind: sink
    position: arg0
    why: "クエリは準備のときに決まる。sink は Preparex / PrepareNamed"
```

- **コマンドの動き**: 毎回、候補の一覧を作り直す。各候補を「行がある」か「`rejected:` にある」かに照合る。どちらでもない候補(未決)が 1 つでもあれば、終了コード 70 で止まり、未決の一覧を作業ファイル(コミットしない)に書く。人か LLM は、一覧を見て、行を足すか `rejected:` に足す。`rejected:` にあって候補から消えたもの(API が消えた)は、警告として出力に一覧する(止めない)。
- **状態はモデルのファイルだけにある**。同じ入力(パッケージとバージョン)と同じモデルのファイルなら、同じ結果になる。型から作る `*.gen.yaml` は、別のファイルで、毎回上書きする(手で直さない。直したいときは生成器を直す)。
- **既存のモデルは移行しない**。そのパッケージを次にコマンドに通したときに、未決の一覧を `rejected:` に書いて、足す。

**候補の出し方(決定的。2 層)**: 公開の関数は多い(go-github は公開のメソッドが 1,000 以上あるのに、sink の行は 57)ので、全部に判断を求めるのは無理。そこで、判断を必須にする層と、しない層に分ける。順序は、シンボルの辞書順。**同じ入力なら、同じ候補になる**。

- **層 1(採用か不採用かの判断が必須)**: 規則の表で決める。(a) 引数の名前と型(SQL、コマンド、パス、ファイル名、URL、ホスト、HTML、テンプレート、クエリ)。`resource_name` もここ(サービスのクライアントの名前の引数: bucket、object、owner、repo、project、topic など)。(b) 本文や中身を運ぶ型の戻り値とフィールド(ADR-108 の source の候補)。(c) (string → string)の関数で、名前に `escape` / `quote` / `sanitize` / `clean` を含むもの(sanitizer の候補)。(d) 関数またはインターフェースを引数に取る関数(`calls:` の候補)。規則の表はコードの中にあり、PR で足していく。
- **層 2(判断は要らない)**: ほかの公開の関数で、string / `[]byte` / `any` を取るもの。件数と一覧を、PR の本文の材料に出すだけ。
- 規則の外の行(手の行)は、今までどおり足してよい。

**層 1 の規則の最初の評価(段階 1 の最初の作業)**: 前の晩に採用した 12 個のモデル(dio、github(Dart)、shelf、googleapis_auth、gin、go の storage、sqlx、go-github、actix-web、axum、google-cloud-storage、octocrab)の採用した行のうち、層 1 に入るものがいくつかを数える(再現率)。入らない行は、規則の表に足すか、手の行として残す。この評価は、まだしていない。出発点として、モデルのファイルごとの行の数(`symbol:` の行を節ごとに数えた。2026-11-23)を置く: `dart-dio` sinks 44、`dart-github` sources 1・sinks 15、`dart-googleapis_auth` sinks 4、`go-gin` sinks 7・propagators 51、`go-storage` sinks 7、`go-sqlx` sinks 52、`rust-actix-web` propagators 19、`rust-google-cloud-storage` sinks 23、`rust-octocrab` sinks 21、`rust-web`(axum を含む)sinks 3・propagators 30。shelf、go-github、axum の行は、ファイル名から特定できていない(評価のとき、行の出所を確認する)。

**候補の元**: 段階 1 は、**ライブラリ単体の型の規則だけ**を使う。「ライブラリをプロジェクトとして解析して、公開の関数の引数が、すでにモデルのある sink に届くかを見る」案は、課題 #163([docs/issues/163-library-as-project-candidates.md](issues/163-library-as-project-candidates.md))に分ける。層 1 の強い根拠になる。段階 3 のあとに入れる。課題 #144(利用者のプロジェクトで、汚染された値が届いた入口の API の一覧)は、別の課題のまま。

**コミットするものと、生成するもの**: モデルのファイル(`rejected:` を含む)、`*.gen.yaml`、骨組み、テンプレートのセル、マークの固定、`verified_versions` は、コミットする(ビルドに要る、または CI が読む。4.3 と同じ理由)。PR の本文の材料、未決の一覧、取得したソースは、コミットしない。セルの中身(人か LLM が足したもの)は上書きしない(テンプレートの部分にマークを付け、その外は触らない。**要確認**: マークの形)。

#### 3. 言語ごとの違い

| | Go | Dart | Rust |
| --- | --- | --- | --- |
| 型の取り方(4.2) | `go/packages`(`NeedTypes`) | analyzer の `LibraryElement` | extractor を使う(段階 5) |
| 実行する場所 | クラウドで全段が可能(取得だけ。実行しない) | クラウドで全段が可能 | ローカルのサンドボックスの下。クラウドは Rust を扱わない |
| 骨組みの形 | `skel/`、`zoo/mark` | `cells/packages/<名前>`(`zoo_exec_override`、`--dep-dir`) | `skel/`、`zoo-mark`、`#[track_caller]` |
| 差分テスト | あり | あり | 段階 5 で(extractor を動かす。サンドボックスの下) |

Rust は、extractor を動かす段(型の取得、セルの解析の確認、本物のクレートでの記号の綴りの照合、差分テスト)が、macOS のサンドボックスの下でしか許されていない(手順書 0 節、6.5)。クラウドには隔離がなく、クラウドは Rust を扱わない。**構文だけで署名を読む道具は作らない**(再エクスポートや型の別名を解けず、精度が下がるため)。Rust は、同じコマンドを、サンドボックスの下でローカルに走らせる(段階 5)。

**骨組みの共通の決め**: `--dep-dir` と Rust の `exclude = ["skel"]` は、条件付きにしない。骨組みには常に足す(3 つの言語とも、骨組みを依存として扱うため)。

**セルの置き場所の決め**: 第三者のパッケージは `zoo-<lang>-pkg`。標準ライブラリは、対のセル(parity)の確認を満たせるなら `zoo-<lang>`、満たせないなら `zoo-<lang>-pkg/<標準ライブラリの名前>`(#219、#223 の形)。コマンドが決める(選択は残さない)。

**言語を横断する順**(2026-11-23。言語の間の機能の差を大きくしない。[bench/parity/README.md](../bench/parity/README.md) の機能の差の表で見る): 言語ごとに段 1〜3 を終えるのでなく、段ごとに 3 言語を回す。段 1(枠、候補、検証、差分テスト)は Go → Dart → Rust(Rust はローカルで、サンドボックスの下)。次に段 2(骨組みの生成)を Go → Dart → Rust。段 3(型からの flows の生成)も同じ。Rust を急ぐ必要はないが、段の途中で差が開いたままにしない。Rust の段 1 の前提は、次の 4 つ(見積もりは、あとで足す): (a) Rust の extractor が宣言のある本体を読まない(宣言の段階 4。ADR-105 の続き。7a 節)。(b) Rust の差分テスト。(c) `rust-web.yaml` をパッケージごとのファイルに分ける。(d) `summary.unverified_versions` を Dart と Rust に出す(課題 #162)。

- **セルのテンプレート**: `cells/` に Go のファイルが 1 つもないときだけ、sink の行のカテゴリごとに `cells/<カテゴリ>/<カテゴリ>.go`(vuln / fixed / decoy。`@source`、`@sink`、`@nosink` のマーク付き)を作る。作ったあと、マークの固定(`ZOO_MARKS_UPDATE=1 go test ./cmd/rivus -run '^TestZooMarksLock$'`)が要る。セルがあれば、一切触らない。

**モデルを確認する対象(ユーザーの方針。2026-11-23)**: 上流が今もサポートしている major(公開の事実で決める。根拠をモデルのファイルの冒頭か PR の本文に 1 行)。既定は最新で、並行してサポートされている major は、`make model` を `VERSION` を替えて複数回実行する。Go の `/v*` の行は、実行した major の具体的なシンボルに直して照合し、片方の major にしかない候補は、もう片方の実行で「消えた候補」の警告にならない(`/v*` で書いた `rejected:` の項目は、警告しない)。`verified_versions` は、ローダーが同じ `package` の重複を拒むので、major ごとに具体的な module の path(`x/v2`、`x/v3`)の記録を並べる。Dart と Rust は、パスに major が入らないので行は共通で、並行サポートのバージョンがあれば、それぞれのバージョンで確認する。

## 7a. 段階 4(extractor に宣言を渡す)の状態と測定(ADR-105。2026-11-23)

**実装済み: Go と Dart。Rust は未実装**(ドライバの `extract` を飛ばすだけの見込みで約 20 行。隔離と固定の nightly がないと動作も測定もできないので、CI で確認する)。`-read-declared-bodies` のときは、extractor に宣言を渡さない(本体を読む)。`-drop-after-read`(開発用)は、宣言のあるパッケージを extractor に読ませてから、IR のフィルタ(段階 2)で落とす(比較用)。

| 言語 | 規模 | 内容 |
| --- | --- | --- |
| Go | `gossa/load.go` 約 40 行、`cmd/rivus/common.go` 約 25 行 | `packages.Load` のあと、`go/ssa` の前に、宣言のある依存(標準ライブラリとプロジェクトは除く)の `Syntax` と `TypesInfo` を捨てる(`Options.ReplacedPackage`)。型ごとに作られるラッパーと `init` など、本体のある関数が残るので、`ReplacedFunc`(`taint.UnitOf` が宣言のある単位)で IR に出さない |
| Dart | `extract.dart` 約 85 行、フラグと `body_not_read` | `--body-replaced package:<名前>`。そのパッケージのファイルは、`getResolvedUnit` も、下ろしもしない。**クラスの階層、動的呼び出しの候補、本体のある演算子、コンストラクタは、ライブラリの要素から作る**(`_Index.library`)。ファイルを解決しないと、これらがなくなり、呼び出しの注記(`unmodeled_library_call` と動的呼び出しの候補なし)が、フィルタの IR と変わった(最初の実装で、`dart-gcp` の 注記 196 → 105)。要素から分からないこと(引数のないコンストラクタの本体と初期化子に仕事があるか)は、ないものとして扱う |
| 共通 | IR に `body_not_read`(`unit`、`functions`)、`dropReplacedBodies` のあとの `PruneDeps` | 読まなかった関数の数を、`summary.body_replaced_packages[].functions_declared` に出す(`functions` は、読んで落とした数のままで、extractor が読まなかったパッケージには出ない)。落とした関数だけが届いていたもの(ジェネリクスのインスタンス、ラッパー、そこだけが import するパッケージ)を、フィルタの側でも落とす(これで、`stats.functions` が、extractor の段階と同じになる) |

**finding の同一性**(`-drop-after-read` との比較。`TestBodyReplacedInTheExtractorIsTheSameAsTheFilter`、`TestBodyReplacedGenericsInTheExtractor`、`TestBodyReplacedOfADartPackage`、`TestDartExtractorBodyReplaced`): 合成の Go(ジェネリクスと型のラッパーを含む)と Dart、公開のベンチ(下)で、**finding の ID の集合、`stats.functions`、`summary` の注記と数(`dispatch_candidates`、`program`、`top_symbols` など)が同じ。違うのは、`body_replaced_packages` の項目だけ**: フィルタは `functions`(読んで落とした関数の数)、extractor の段階は `functions_declared`(読まなかったパッケージが宣言している関数の数。`functions` は出さない)(数の意味を、項目の名前で分けた。Go: 宣言のある関数とメソッド。Dart: 最上位の関数、メソッド、コンストラクタ、アクセサ。到達の数ではない)。

## 8. 決めたことと、残る判断

決めたこと(相談役の判断): 宣言は、書いたパッケージだけに効く(暗黙の接頭辞一致はしない。配下は明示の書き方)。`bench/go-s3` を入れる(定期の層だけ)。`*.gen.yaml` はコミットする。呼び返しの検出は 2 と 3 の両方。組み込みの量の上限の目安は 4.4 のとおり。段階の順は 7 節のとおり。zoo のゲートは #167 で直った。手順書は `docs/MODEL-RUNBOOK.md`。

残る判断と未確認:
- 試作の Dart は、`visit` が、宣言のあるパッケージのライブラリで止まるので、別のパッケージ経由でしか届かない依存が落ちる。到達性としては正しい。宣言のあるパッケージの型を、プロジェクトの型の解決に使う場合は、analyzer が、読まなくても解決できる(要素モデルを作る)ことを、finding が同じこと(`dart-gcp` 19、`dart-grpc` 3)で確認した。解決が失敗するケースは、段階 4 のテストで確認した(7a 節。ファイルを解決しないと、クラスの階層と候補が要素から作る必要があった)。
- Rust の測定は、していない(サンドボックスと固定の nightly が要る)。
- 4 節の報告された数字は、rivus の側では未確認(段階 3 の生成器と差分テストで確認する)。
