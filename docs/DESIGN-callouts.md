## 1. 問題

関数値(クロージャ、関数、メソッド値)を通る流れで、解析は、「**どの関数値を、どの呼び出し元が作ったか**」を失う。今ある仕組みは、3 つの部分的なものに分かれている。

| 仕組み | 何をするか | 限界 |
| --- | --- | --- |
| (1) 作った場所で呼ばれると仮定(ADR-059、`assumed_call`) | 呼ばれるところが見えないクロージャを、`make_closure` で適用する(キャプチャした値の sink 到達、書き込み) | 結果と throw は適用しない。1 度も呼ばれないクロージャも一致する(過検出)。引数とキャプチャの**両方**に依る流れ(`write-param`)は見つからない |
| (2) `valuecalls` の追跡(上限 8、深さ 3)と、候補ごとのガード(ADR-045) | 関数値の呼び出しの候補を、コピー・φ・パラメータ(呼び出し元の引数)から求める。パラメータ由来の候補には「p の関数は c」のガードを付け、呼び出し元が直接渡した関数で絞る | **中継**(`wrapper(g)` → `run(g)`)は、ガードが外へ伝わらず絞れない。メモリ(フィールド、マップ、スライス)はたどらない。一部の呼び出し元しか追えなくても、見つかった分を全部として扱う(下の 4 の最後の表)。上限を超えると不確実性になる |
| (3) ライブラリが引数の関数を呼ぶことのモデル | **まだない**。今のモデルは、`flows: [{from: args, to: result}]`(関数値の中身が結果に入る)で近似する(`Future.then`、`Option::map` など) | コールバックの結果が、呼び出し元のキャプチャした値と、ライブラリの渡す値で作られることは、表せない |

3 つに共通の根は、**「関数値を、データと同じ要素として運ぶ」ことと、「呼ぶ側の値と、呼ばれる関数の要約を、呼び出し元ごとに組む」ことが、できていない**こと。結果として、(i) 別々のクロージャを、同じヘルパーに渡す 2 つの呼び出し元が、**互いの流れに混ざる**(XTALK、`two-callers`、`relay`)。(ii) 関数値を、フィールド・グローバル・マップ・スライスに入れると、**呼び出し先が分からない**(`func-field`、`func-map`、`clos/stored`)。(iii) ライブラリが呼ぶクロージャの**結果**が失われる(`to-lib`)。

## 2. 測定

### zoo(3 言語の、同じ形のセル)

「見つかった / 脆弱なケース」。**デコイ**は、相手のクロージャ・別のフィールド・別のキー。FP = デコイが誤って報告される。「流れが失われる」= デコイの本物の側の流れが見つからない(検出されないのは、見つからないから)。セルを足した push は 2a47beb。

| セル | Go | Dart | Rust |
| --- | --- | --- | --- |
| `clos/two-callers`(同じヘルパー、2 つの呼び出し元) | 1/1、検出されない | 1/1、検出されない | 1/1、**FP** |
| `clos/to-own-helper` | 1/1、検出されない | 1/1、検出されない | 1/1、検出されない |
| `clos/relay`(`wrapper(g)` → `run(g)`) | 1/1、**FP** | 1/1、**FP** | 1/1、**FP** |
| `clos/to-lib`(`Once`、`OnceValue`; `forEach`、`map`、`then`; `Once`、`OnceLock`) | 1/2(結果を返す形が `@miss(assumed_call)`)、デコイの流れが失われる | 1/3(`map` の結果、`then`: `@miss(assumed_call)`)、落ちる | 1/2(`Once::call_once`: `@miss(unmodeled_library_call)`)、検出されない |
| `clos/stored`(フィールド、グローバル、スライス) | 3/3、検出されない | 3/3、検出されない | **0/3**(`unmodeled_library_call`)、落ちる |
| `clos/returned` | 1/1、検出されない | 1/1、検出されない | 1/1、検出されない |
| `dyn/func-field` | 1/1、検出されない | **0/1**(`unresolved_callee`)、落ちる | **0/1**、落ちる |
| `dyn/func-map` | 1/1、**FP** | **0/1**(`unresolved_callee`)、落ちる | **0/1**、落ちる |
| `dyn/method-value` | 1/1、検出されない | (Dart の `dart/tearoff-instance` に別の見逃し) | 1/1、検出されない |

読み方: (1) **取り違え(FP)は、中継(`relay`)で 3 言語に残り、Rust は `two-callers` でも残る**(Rust の `Fn::call` の候補が、型の合う全クロージャ)。Go の `func-map` の FP は、マップの値の関数が、型で候補になるため。(2) **関数値をメモリに入れる形(`stored`、`func-field`、`func-map`)は、Dart と Rust で、流れが失われる**。Go は、フロントエンドの候補(VTA)があるので出る。(3) **ライブラリが呼ぶクロージャの結果(`to-lib` の vuln2)は、3 言語とも落ちる**(`assumed_call` を残して)。

## 3. 設計: 要約に、「引数 p の関数を、これらの値で呼ぶ」を持たせる

ADR-047(棚上げ)の `OutCallParam` の再開。違いは 3 つ: **(1) ライブラリのモデル(YAML)と、同じ表現にする**(自前のヘルパーは本体から導き、ライブラリは YAML で書く)。(2) 作った場所で適用する仕組み(ADR-059)がある。(3) 巨大な SCC を割ることは、収束には効果がなかった(ADR-055)ので、**動機は精度**(取り違えと、結果の流れ)。

### 3.1 要約の表現: `CallOut`

`Summary` に、`Calls []CallOut` を足す(ADR-047 の `Callout`。出力の種類 `OutCallParam` の中身):

| フィールド | 意味 |
| --- | --- |
| `Site` | ヘルパーの中の呼び出しの位置(関数 ID、ブロック、命令)。同じ関数値を 2 か所で呼ぶとき区別する |
| `Fn` | 呼ばれる関数値の場所: **(パラメータ p、パス)**。「引数 p の(パス `…` の)関数」。最初のバージョンは、パスが `""`(p そのもの)だけ。フィールド(`h.cb`)は、関数値の要素(5)の範囲 |
| `Recv`、`Args[j]` | 関数に渡す j 番目の実引数の**場所**: ヘルパーの言葉で、`Param(q, パス)`(q の指す先)か、ヘルパーが作った値(`Local` + 要素の集合)。**場所**で持つ(要素でなく): ポインタの引数への書き込みを、呼び出し元の場所に届けるため |
| `Virt` | 仮想のパラメータの基点 `Base`。`Base+0` = 関数が throw するもの、`Base+1+r` = 結果 r、`Base+9+j` = 引数 j の指す先(関数が書いたあと) |
| `Guards` | この呼び出しが起きる条件(ヘルパーの分岐。今のガード) |
| `Mode` | `call`、`go`、`defer`(`go` / `defer` は、結果を読まない: 効果(書き込みと sink)だけを適用する) |

仮想のパラメータは、**普通のパラメータの要素(`Param`)と同じに流れる**(パス、サニタイザの演算、`widen`、`SinkReach`、ガードが、そのまま使える)。ヘルパーの本体は、`x := f(s); sink(x)` を、**呼び出し先の要約を適用せずに**、`x = Param(Base+1)`、sink への到達 = `Param(Base+1)` の要素、として要約する。ヘルパーは、クロージャに依存しない(呼び出しグラフのエッジが、ヘルパーからクロージャへ張られない。SCC が割れる)。

### 3.2 具体化(呼び出し元 K で)

K が、ヘルパー H を呼ぶとき、H の `CallOut` ごとに:

1. **`Fn` の p に、K が渡したものを決める**。`sg.ExactFuncs`(関数、その場で作ったクロージャ、それらのコピーと φ。それ以外が混ざるなら `ok = false`)。ADR-047 のとおり、`ExactClosures` に拡張して、`make_closure` の命令(**束縛** = キャプチャの値)も返す。`ok` で、**集合の大きさが 1〜4**(φ が、決まった数のクロージャを選ぶ)なら具体化する。
2. 引数の場所を、K の場所に写す(`Param(q, パス)` → 実引数の場所。`Local` → K の合成した根に、要素を展開して置く)。
3. 選ばれた各クロージャ(関数)の要約を、**K の中で**、`applySummary` で適用する。実引数 = 2 で作ったもの、束縛 = `make_closure` の引数(**キャプチャした値が、呼ぶところで分かる**。ADR-059 の限界の、引数とキャプチャの両方に依る流れ: `write-param`)。**束縛は、キャプチャした値の中身の写しでなく、キャプチャした場所(セル)への参照**(5.1 と 5.1a)。
4. 適用した結果を、仮想のパラメータの根に置く: 結果 → `Base+1+r`、throw → `Base+0`、ポインタ引数の指す先への書き込み → `Base+9+j`(と、`Param(q, …)` の場所があれば、K のそこへ直接)。
5. H の、仮想のパラメータの要素を含む出力と sink 到達は、**普通の `expandParam`** で、この根から読まれる(引数の列に、仮想の根を足した `argv`)。
6. 2〜5 を、値が動かなくなるまで繰り返す(上限 16。超えたら `not converged` で、今の扱いに戻す)。

呼び出し元ごとに、**自分が渡したクロージャだけ**で組むので、別の呼び出し元のクロージャが混ざらない(XTALK、`two-callers`)。**中継**(`wrapper(g)` → `run(g)`): K = wrapper が、`run` の `CallOut` を、自分の要約に**載せ直す**(`Fn` を、自分のパラメータ g に、`Args` を、自分の言葉に、仮想のパラメータを、自分の `Base` に付け替える)。wrapper の呼び出し元が、具体化する。

### 3.3 適用するもの(ADR-059 が「適用しない」ものを、適用する)

| 出力 | 具体化のとき |
| --- | --- |
| 結果 | **適用する**(行き先は、`Base+1+r`。ADR-059 は、行き先がなく適用しなかった。`WithTx2` の型、`produce(func() T)`、`map` / `then`) |
| throw | **適用する**(`Base+0`。ヘルパーが、呼び出しを囲む `try` を持てば、そこで受ける) |
| sink への到達 | 適用する(クロージャの中の sink。引数の値とキャプチャした値の、**両方**) |
| キャプチャした変数・引数の指す先への書き込み | 適用する |
| グローバルへの書き込み | 適用する(K の `OutGlobal`) |

### 3.4 ライブラリのモデル(YAML)との、同じ表現

ライブラリの関数は、本体がない。**モデルの行が、その関数の要約**: `flows`(今)に、`calls` を足す。`calls` の 1 行 = 1 つの `CallOut`。ヘルパーの「パラメータ q」が、モデルでは「呼び出しの実引数 q(`recv` / `argN`)」。

```yaml
- symbol: dart:core#Iterable.map
  calls:
    - fn: arg0                  # どの実引数の関数か(recv も書ける)
      with: [recv.elem]         # 関数のパラメータ 0 に入るもの(複数なら並べる)
      ret: result0.elem         # 関数の結果 0 の行き先
      throw: result0            # 関数が throw するものの行き先(省略可)
      writes: {1: arg0}         # 関数が、パラメータ 1 の指す先に書いたものの行き先(省略可)
      feed: [{from: ret0, to: with0}]   # 結果を、次の呼び出しのパラメータに戻す(fold の accumulator。省略可)
      mode: call                # call | go | defer
```

**`calls` を書いた行は、`flows`(保守側の近似)も必ず持つ。** ライブラリの関数は本体がないので、**具体化できないとき(`fn` の関数値が、`ExactFuncs` で 1〜4 個に決まらない)の戻り先は、`flows` しかない**。`calls` だけの行は、そのとき、何も運ばない(見逃し)。そこで、
- **`flows` を書かない行は、`calls` から自動で導く**: 各 `calls` の `with` の元 → `ret` の先へ、素通しの流れ(中身がそのまま運ばれる)を作り、使うたびに `assumed_call`(具体化できなかった呼び出し)を付ける。`with` か `ret` がない行(`Once.Do` など)は、導く流れがない(運ぶものがないので、見逃しにならない)。
- **書いた `flows` は、導いたものに足す**(`map_err` の `recv.ok → result0.ok` のような、`calls` で表せない側)。
- **読み込みで検査する**: `ret` を持つ `calls` に対して、導く流れが作れない(`with` が空など)のに `flows` がない行は、エラー。
- 具体化できた呼び出しでは、導いた流れは**使わない**(二重に運ばない)。できないときだけ使う。

**`calls` の行は、実行の検査に向く**(`DESIGN-zoo.md` の表 S): **目印を記録するクロージャ**を渡して、ライブラリが何を渡してきたか(`with`: クロージャの引数の目印)と、クロージャの戻り値がどこに出たか(`ret`: 結果の目印の行き先)を、**実際に呼んで観測**する。YAML の `calls` と、実行の観測が食い違えば、表 S が失敗する(`flows` の `pure` の行と同じ。正解を YAML から作らない)。

`with` と `ret` の**射影**(`.elem`、`.err`、`.ok`、…)は、エンジンがすでに使うアクセスパスの区切り(コンテナの要素 `[]`、構造体のフィールド、Rust の enum の中身)の、言語ごとの固定の表への別名。最初のバージョンは、**射影なし**(全体)で書き、効果を測ってから足す(今の `flows: [{from: args, to: result}]` と同じ精度から始める)。

対応表(要件の API):

| --- | --- |
| Go `sync.Once.Do(f)` | `calls: [{fn: arg0}]` |
| Go `sort.Slice(x, less)` | `calls: [{fn: arg1}]`(今の `pure` は、`pure` のまま、呼ばれることだけを足す) |

具体化できない呼び出し(関数値が 1 つに決まらない)は、**今の扱い**(下の 4)。

## 4. 具体化できる条件と、戻す条件

**ヘルパー H の、パラメータ p の呼び出しを `CallOut` にするのは、H の解析のときに、次のすべてが成り立つとき**(ADR-047 の下書きの「外してよい条件」7 つ、を、今の状態に合わせた)。1 つでも一致すれば、**今の扱い**(H の本体で、候補の全部の要約を適用する。`ValueCands` と、ガード)に戻す。

| # | 外す条件(今の扱いに戻す) | 理由 | 固定するテスト(各 1 つ、今の扱いと同じ結果) |
| --- | --- | --- | --- |
| 1 | パラメータの関数値を、**呼ばずに保存**する(フィールド、グローバル、チャネル、スライス) | 呼び出しは別の関数。`CallOut` にできない(`Fn` は、直接の呼び出しの p のみ)。関数値の要素(5)の範囲 | `clos/stored` |
| 2 | `go f()` / `defer f()` | **外さない**(ADR-047 は最初のバージョンで外した)。`Mode` で、効果だけを適用する | `go` / `defer` の入ったヘルパーの、`@sink` が残る |
| 3 | 別の関数へ渡す(中継) | **外さない**。3.2 の載せ直し。H が、`entry` / 外から呼べる(7)なら、中継もしない | `clos/relay` |
| 4 | 関数値が、**複数のパラメータにまたがる φ**、または、パラメータと別のものの φ(`Param = -1`) | `Fn` が、1 つの p でない | φ のあるヘルパー |
| 5 | 呼び出し元が、クロージャを直接渡さない(`ExactFuncs` が `ok = false`) | **その呼び出し元だけ**、今の扱い(全候補を適用する)。他の呼び出し元は、具体化する | フィールドから渡す呼び出し元と、直接渡す呼び出し元の混在 |
| 6 | H 自身が、関数値・インターフェース越しに呼ばれる(呼び出し元が静的でない) | 呼び出し元が、`CallOut` を具体化しない | `dyn/*` |
| 7 | **起点のないライブラリ**で、H が `exported`。または、呼び出し元が 0。または、**起点のあるプログラム(下の `closed_world_entry`)でも、H が値として参照されている**(`refs` の `arg` / `other`、`Value.FuncValue`。呼び出し元を全部は数えられない)、**呼び出し元の一部が数えられない**(`valuecalls` の `incomplete` と同じ判定) | 具体化する人がいない / 全部の呼び出し元がいない | 公開関数のヘルパー(ライブラリ)。値として渡されるヘルパー(プログラム) |
| 8 | 呼び出し先の候補に、**モデルがある**もの、**本体がない**もの | 要約がない。呼び出しの位置で、今のとおり(モデルが `calls` を持てば、`CallOut` として、同じ流れ) | `to-lib` |
| 9 | キャプチャした関数を呼ぶクロージャが、**返される・保存される**(渡される以外に使われる) | 呼ぶ人はいるが、適用する人がいない(go-test-bench の `makeHandler` で、ADR-047 のときに、実際に finding が落ちた) | `clos/returned` |

**条件 7 の、閉じた世界(前提の名前: `closed_world_entry`)。** Go では、ヘルパーが内部でしか呼ばれなくても、大文字で始まる(`exported`)のがふつうなので、「exported なら戻す」では、**ほぼ全部のヘルパーが対象外**になる。そこで、**起点(`main`)のあるプログラムでは、読んだコードを閉じた世界とする**(`DESIGN-capture.md` の、Rust の `Fn::call` の候補を絞る案 A と**同じ前提**、同じ条件: 起点があり、外から呼ばれるマーク(`#[no_mangle]`、`extern "C"`、`cdylib` など。Go は `//go:linkname`、cgo の export、plugin)がない。読んだ依存と、テスト(`-tests`)の呼び出し元も数える。関数アイテムとして値で使われた所があれば、閉じていない)。このとき、**exported でも、「値として参照されていない」かつ「呼び出し元を全部数えられる」なら、具体化する**。外から呼ぶ人(読んでいないクレートやパッケージ)は、起点のあるプログラムにはいない。**起点のないライブラリだけ**、条件 7 で戻す(exported が起点になり、呼び出し元が外にいる)。
- 具体化した `CallOut` を通った finding には、**前提の名前 `basis: closed_world_entry`** を、案 A と同じフィールド・同じ文字列で付ける(「起点のあるプログラムとして読んだので、外からの呼び出しは数えていない」)。
- **`CallOut` を出すかどうかは、静的に決まる**(性質を保つ): 決めるのは、プログラムに起点があるか、外から呼ばれるマークがあるか、H が値として参照されているか、呼び出し元の集合(呼び出しグラフ)だけで、解析の途中の状態には依らない。

「戻す」場合に、H の本体は、`CallOut` を**出さず**、今のとおり。**戻す判断は、静的**(H と、H の呼び出し元の呼び出しグラフ。解析の途中で変わらない)。1 つの H に、`CallOut` にするパラメータと、戻すパラメータが、混ざってよい(パラメータごとに決める)。

### 作った場所で適用する仕組み(ADR-059、`assumed_call`)、ガード(ADR-045)、案 A、一部の呼び出し元しか追えないとき、との関係

| 仕組み | どうなるか |
| --- | --- |

## 5. 関数値を、汚染の要素と同じ道具で運ぶ

3 の `CallOut` は、「呼ぶ人が、呼ばれる関数を、**直接渡した**呼び出し元」で決まる。保存・返す・中継・マップに入れる形は、**関数値が、データと同じに、状態・アクセスパス・グローバル・要約を運ばれる**ことで解く。

### 5.1 表現

`Elem` に、**第 3 の種類 `Func`**(`Real`、`Param` に並ぶ)を足す。比較できる小さな要素のまま(`label` に関数 ID、`origin` に作った場所): `Elem{Kind: Func, label: 関数 ID, origin: make_closure の位置}`。**不明を表す要素**: `Elem{Kind: Func, label: "?"}`(+ 型)。

| 場所 | 規則 |
| --- | --- |
| 作る | `make_closure`、関数への参照(`KFunc`)、メソッド値の値の根に、`Func` 要素を置く。**キャプチャした値**は、値の根の下 `/cap/i` に、**キャプチャした場所への参照**(束縛の値そのもの。Go の参照でキャプチャした変数なら、その変数のセルへのポインタ。値でキャプチャしたものなら、その値)を置く。**作った時点の中身の写しは取らない**(5.1a)。`Escapes` でないクロージャ(作った関数の中で、直接呼ばれるだけ)は、コピーしない |
| 運ぶ | コピー、φ、`store` / `load`、フィールド、マップ、スライス、グローバル、戻り値、引数、要約の出力(`Output` の `Elem`)、`globalStore`: **データの要素と同じ道具**。サニタイザは、`Func` に効かない |
| 不明 | 入口のパラメータ、本体もモデルもない呼び出しの、関数型の結果、リフレクション、: `?` の要素。**モデルが「結果の関数は、引数 a の関数」と表せるもの**(`OnceValue`、`http.HandlerFunc(f)`)は、`result_funcs: [argN]` で、`?` を足さない |
| 呼ぶ | `CalleeValue`(Rust の `Fn::call`、Dart の関数値の呼び出し)の候補 = 呼ぶ値の場所から `collect` で得た `Func` 要素。**`?` がなく、数が 8 以下**なら、その集合を候補にする(`valuecalls` の候補は使わない。**抽出器の候補(VTA)より絞れる**)。`?` がある、または 8 を超える(`widen`)なら、**今の候補**(`valuecalls`、抽出器)に戻し、`depth_limit` / `candidate_limit` の不確実性を示す |
| 呼んだときの束縛 | `Func` 要素の値の根の `/cap/i`(キャプチャしたセルへの参照)を、`FreeVars` の束縛にして、`applySummary` を適用する。呼ぶときに、セルの**今の**中身を読み、書き込みは、そのセルに届く。**キャプチャした値と引数の両方に依る流れ**(`write-param`)は、この束縛で出る |

**`valuecalls` との関係**: 置き換えでなく、**フォールバックに下げる**。`valuecalls` は、`?` のある呼び出し、上限(8、深さ 3)を超える呼び出し、Go の抽出器の候補、のために残る。**Dart と Rust の、候補 0 件が多い**ところ(Rust の `Box<dyn Fn>` の `Fn::call` 33 か所、Dart の 61 か所)は、フィールドとマップに入れた関数値が、`Func` 要素で呼び出し元まで届けば、0 件でなくなる。

**ADR-059 との関係**: 関数値の要素で、クロージャが**呼ばれるところで、束縛つきで一致する**ので、`make_closure` の位置で適用する `assumed_call` は、**要素が呼ばれる場所に届かない**(`?`、上限、本体もモデルもないライブラリに渡す)クロージャだけに残る。1 度も呼ばれないクロージャ(`cap-never`)は、**呼ばれない**から、検出されないまま(ADR-059 の過検出がなくなる)。

### 5.1a キャプチャした値は、写しか、参照か

**問題**: Go のクロージャは、変数を**参照で**キャプチャする。Dart のキャプチャも、変数のセルを共有する。作ったあとに書く形(`x := ""; f := func(){ sink(x) }; x = src(); f()`)と、**クロージャの中で書いて、外で読む形**(`f := func(){ x = src() }; f(); sink(x)`)は、`make_closure` の時点の中身を `/cap/i` に**コピー**する表現だと、落ちる可能性がある(クロージャの書き込みが、外の変数に届かない。複数のクロージャが、同じ変数を共有するのが、別々の写しになる)。

**今の仕組みは、この形をどう扱っているか(コードを読んで確かめた)**: `internal/taint/calls.go` の `captured` / `applyMade`(ADR-059、`assumed_call`)は、`make_closure` の命令の引数(`in.Args` = キャプチャした値。Go の参照でキャプチャした変数は、`alloc` へのポインタ)を、**そのまま束縛として**、クロージャの要約に適用する(`applySummary(cc, fn, in.Args, …)`)。値のコピーは作らない。束縛は、セルへの参照なので、(1) 作ったあとの書き込みは、同じセルに入るので、読める(解析が流れに依らず、セルは「書かれうるものの和」なので、書く順序の影響を受けない)。(2) クロージャの書き込みは、そのセルへ書かれ、外の読み出し側が読む。(3) 再解析は、`callSigs` が、キャプチャしたセルのバージョン(`rootVer`)を見て、セルが育つたびに、適用し直す。つまり、**今の `assumed_call` は、参照で束縛している**ので、この形を落とさない(はず。zoo では、まだ測っていない)。**Rust は別**: キャプチャのあるクロージャは環境の `alloc` で、可変のキャプチャは変数へのポインタを `field_store` で入れる(`DESIGN-capture.md`)。環境のフィールドのポインタが、指す先と別名にならない問題があり、書く側は、今、落ちる(`@miss`)。

**案の比較**:

| | 写し(作った時点の中身を `/cap/i` に) | **参照(キャプチャしたセルへのポインタを `/cap/i` に)** |
| --- | --- | --- |
| 作ったあとに書く | 元のセルが育つたびに、`make_closure` の転送を再実行すれば、読む側は拾える(再実行が必要) | 同じセルなので、そのまま読める |
| 中で書いて、外で読む | **落ちる**(写しへの書き込みが、元のセルに戻らない) | 書き込みが、元のセルに届く |
| 2 つのクロージャが、同じ変数を共有 | 別々の写しになり、一方の書き込みを他方が読めない | 同じセル |
| ループ変数 | 反復ごとの値の写しが混ざる(言語のバージョンで、反復ごとに別の変数か、1 つの変数か) | 言語の意味どおり(変数のセルが、反復ごとか 1 つか) |
| コスト | 要素のコピー(Gitea は、キャプチャのあるクロージャが 1,496) | ポインタ 1 つ(安い) |
| 経路の説明 | 写された場所のステップが増える | キャプチャした変数のステップになる |

**採る案: 参照(束縛 = キャプチャした値そのもの)**。Go の意味と、今の `assumed_call` の束縛と、同じ。写しは、**採らない**(落ちる形が、設計で分かっているのに、保守側でない)。関数値が、作った関数の外へ運ばれる(返す、保存する)とき、セルへの参照は、返されたポインタと同じに、要約で運ぶ(局所の `alloc` を指すポインタを返す関数と同じ道具)。

**まず、今の出方を、zoo で測る**(段階 3 と 4 の前。段階 2 と同時にできる): セル **`clos/capture-write-by-ref`** を、3 言語に足す(1 セル = 3 ケースの規約に従う)。
- (a) **作ったあとで書く**: `x = ""; f = () => sink(x); x = src(); f()`(クロージャを、ヘルパーに渡して、呼ばせる形も)。
- (b) **中で書いて、外で読む**: `f = () => { x = src() }; run(f); sink(x)`。
- (c) **ループ変数**: ループの中で作ったクロージャが、反復の変数を読む / 書く(Go は、1.22 以降の、反復ごとの変数と、それ以前の、1 つの変数の両方。Dart は、反復ごとの変数。Rust は、`move` と参照)。
- デコイ: 別の変数(キャプチャしていない変数)を読む。

今の出方(`assumed_call` 越しに、3 言語でどう出るか)を、先に記録し、`@miss` / `@fp` を、理由つきで付ける。**段階 3(`CallOut`)と 4(関数値の要素)の受け入れに、このセルの、期待値(3 言語とも、(a)(b)(c) が出て、デコイが検出されない)を入れる**。

### 5.2 上限(widen)に達したとき

- 1 つのセルの `Func` 要素が、**`N`(16)** を超えたら、**型ごとの `Func(*, 型)` の 1 つ**にまとめる(= 「この型の、不明の関数」。`widen` が `Param` を、パラメータごとにまとめるのと同じ)。呼び出しは、今の候補(型の合う全関数)に戻る。**不確実性**: `depth_limit`(`candidate_limit`)。
- 要約の出力の上限(24 要素)は、`Func` 要素にも効く。ディスパッチテーブル(関数 200 個)は、上のまとめで、要素数が増えない。
- 経路は、`Func` 要素の運ばれたステップを持つ(普通の要素と同じ)。finding の経路に、「関数値が、ここで作られ、ここで呼ばれた」が出る。

### 5.3 読めないこと(測る)

**要素の数と、収束への影響は、読めない**: (a)`Func` 要素が増えるぶんの、要約の大きさと、メモリ。(b)キャプチャした値への参照(Gitea は、キャプチャのあるクロージャが 1,496。写しでなく参照なので、要素は増えにくいが、測る)。(c)関数値を運ぶ要素が、SCC のなかの再解析を増やすか。**go-scale に、2 つのプロファイルを足して測る**: `fnvals`(ディスパッチテーブル、マップに入れた関数値、返すクロージャを、200 個の規模で)と、`callouts`(同じヘルパーを 40 の呼び出し元が呼び、各自のクロージャを渡す形)。段階 3 の受け入れには、さらに **`middleware`** を足す(下)。`go-synth` の `-closures` の形(`bench/synthplan`)も使える。**最初のバージョンは、フラグ(`-func-values`、既定は off)**で、結果が同一であることを、先に確かめる。

### 5.4 試行の結果(2026-11-22。使い捨ての試行。コードはローカルのブランチ `exp-funcseed` にだけ置き、main には入れない)

**試行**: `RIVUS_FUNCSEED` のときだけ、(i) 関数値を作る所(`make_closure`、関数への参照、メソッドの tear-off)を、その関数を出所とする合成の source(ラベル `FUNC`)にし、(ii) 値の呼び出しの「呼ばれる値」が持つ要素を読み、(iii) 今の汚染の道具(コピー、φ、フィールド、要素、グローバル、戻り値、引数、要約)にそのまま運ばせる。約 100 行。**どの finding も、パス数も変わらない**(合成ラベルの finding は、出力に出さない)。呼び出し点ごとの候補は、読んだ要素の出所の関数。`Param` 要素(呼び出し元から来る)は、呼び出しの引数が持つ `Func` 要素を、呼び出し元ごとに貯めて束縛した(= 5.1 の「具体化」の近似。試行は文脈なしで貯めるので、集合は大きめ)。

| ベンチ | 候補 0 件の値の呼び出し → 候補が付く | 既存の候補(`valuecalls` / extractor)が、試行の集合に含まれる | 1 つの呼び出し点の集合の最大 |
| --- | --- | --- | --- |
| zoo-dart | **25 / 25** | **42 / 42** | 36 |
| dart-curated | **16 / 21** | **51 / 51** | 33 |
| zoo-go | - | 42 / 47 | 6 |
| go-curated | 0 / 1 | 20 / 21 | 13 |
| zoo-rust | 0 / 3(クロージャが `alloc` で作られ、シードが届かない) | - | 0 |
| rust-curated | 2 / 3 | 4 / 4 | 2 |

- **規則の例外は不要だった**: 数値停止・sanitizer・モデルの `pure` を通っても、ラベル `FUNC` は運ばれ、finding には出ない(合成のラベルなので)。最初の試行で「含まれない」が 3〜5 割あったのは、`Param` 要素を呼び出し元の実引数に束縛して読んでいなかっただけ(試行の道具の不足)。
- **観測との照合**(zoo-dart、`bench/zoo-dart/observed/compare.py` の「グラフにないエッジ」のうち、値の呼び出し 28 件。cells の外の 3 件を除く 25 件): **15 件は呼び出し先が候補に直接入り、10 件はメソッドの tear-off(`X.run$bound` の中継を 1 ステップ挟む。グラフに、ラッパー → 実メソッドのエッジがある)**。**入っていない(誤った集合)は 0 件**。`compare.py` が、`callee_ids` を出す(受け入れの指標。実装のあとも同じ道具で測る)。
- **コスト(gcp。依存の本体を読む)**: 依存の中で作られた関数値もシードにすると、要素数 1,051,191 → 8,771,021(8.3 倍)、時間 42 → 677 秒(16 倍)。**自分のコード(`Dep` でない関数)で作った関数値だけをシードにすると、要素数 1,051,155、時間 47.9 秒**(試行なしと同じ。集合の最大 558 → 13)。小さい対象では、要素数は +1〜6%、時間は変わらない。

**第 1 バージョンの範囲(決定)**:
1. **自分のコード(依存でない関数)で作った関数値だけを運ぶ。** 依存の中で作って依存の中で呼ぶもの(grpc の interceptor 等)は、運ばない。`widen`(5.2)は後回し。
2. **第 1 歩は診断だけ**(`-func-values`。既定 off。off のとき結果は同一。on でも finding は変えず、各値の呼び出しで「`Func` 要素の候補」を出して、`valuecalls` / extractor の候補と比べた表を出す)。束縛は、`applySummary` の中で、**呼び出し点ごとに**(試行の「文脈なしで貯める」でなく、既存のパラメータの具体化と同じ方法で)。集合の大きさが、試行の最大 36 からどこまで下がるかを見る。
3. **第 2 歩は、「今の候補が 0 件の呼び出しにだけ、`Func` 要素の候補を使う」**。候補のある呼び出しは変えない。否定のフィクスチャ(候補に入ってはいけない関数が入らない)を、zoo のセルごとに。第 2 歩に入る前に第 1 歩の数字を相談し、既定を on にするのは、そのあとの判断(ADR とユーザーへの報告)。

**まだ届かないもの(第 1 バージョン)と、その順**:
- **依存が、渡した関数値をキャプチャして返すクロージャ**(ミドルウェアのラップ: `final g = dep.wrapFn(handler); g(req);`。shelf の `Pipeline().addMiddleware(...).addHandler(h)`、dart_frog の形)。依存の中で作られたクロージャは運ばないので、候補 0 件のまま残る。**何も報告していないわけではない**(`unresolved_callee` が、通る finding に付く。zoo のセル `F/clos/wrapped-by-dependency`: vuln は見つかり、fixed とデコイの 1 行が過検出(`@fp`、XTALK)として出る)。依存で作った関数値を全部運ぶバージョンでも、自分のクロージャは、依存のクロージャのキャプチャセルに入っていて、束縛が届かなかった。**届かせるにはキャプチャセルの束縛が必要。第 2 歩の次にやる**(Rust の `alloc` のシード、フィールド / コンテナの区別、`valuecalls` を置き換える話より先)。理由: Dart のサーバの基盤のモデルを書いても、ここが届かないと入口からハンドラへ流れがつながらない。
- Rust のクロージャ(`alloc` で作られる。シードの設定の場所を足す)。フィールド / コンテナに入れた関数値の区別(`stored.go` の `callBoth` など、別の関数が混ざる)。標準ライブラリの中のクロージャ(`sync.Once`)。

### 5.5 第 1 歩(診断 `-func-values`)と第 2 歩(`-resolve-func-values`): 作って、消した(2026-11-24)

5.4 の試行を受けて、関数値を運ぶ別の実行(同じエンジンのコードを、合成の site でもう 1 回実行する)を作り、2 つのフラグの後ろに置いた。**どちらも消した**(コードは `git log` に残る)。

- **第 1 歩 `-func-values <file>`(診断)**: 各値の呼び出しで、運ばれた `Func` 要素の候補と、`valuecalls` / extractor の候補を並べた表を出す。出力と finding は、フラグの有無で同一。
- **第 2 歩 `-resolve-func-values`(実験。既定 off)**: 候補 0 件の値の呼び出しに、その実行が運んだ関数を候補として補ってから、通常の汚染のパスを実行する(最大 4 回の繰り返し。補った呼び出しは `unresolved_callee` の uncertainty を残す。`rivus index` に付ければ、補ったエッジも索引に入る)。

### 5.6 消した理由と、見つけた根

期限は「観測した呼び出しとの照合の作業が終わるとき」で、そこで「既定にするか、消すか」を決める約束だった。測って、**消す**ことにした(ユーザーの決定、2026-11-24。期限は延ばさない)。

**理由(コスト)**: 合格基準の 4 対象(memos、`memos-4gib`、Gitea、cocoon)が、フラグありで全部 FAIL になる(フラグなしは 4 つとも PASS)。関数値のパスは、エンジンを丸 1 回(繰り返しで最大 4 回)余分に実行する。Go の依存の中に候補 0 件の呼び出し(memos 889、Gitea 428)があって、スキップの条件が外れる。cocoon(Dart)も、制限なしで 8 GB に届いて打ち切られた。依存の中の呼び出しを対象から外す案は、Dart での主な効果(依存が利用者のコールバックを呼ぶ形)を失う。既定 on にするなら、コストの修正が先で、その見込みは立たなかった。

**消しても、uncertainty のない見逃しは増えない**: 候補 0 件の値の呼び出しの `unresolved_callee` の uncertainty は、通常のパスが出す(フラグなしで、これまでも出ていた)。関数値のパスだけが出していたのは、補ったあとに残す `func_values_supplemented` と `func_values_rounds` の文言で、これは消した。

**フラグが補っていた、Dart の `no_edge` 37 件**(観測した呼び出しとの照合、方法 B。zoo-dart。根ごとの分類は 40 件で、フラグが消したのは 37 件)は、グラフのエッジの欠落として、そのまま残る(流れの見逃しになるものは、zoo の `@miss` で追っている。マークは変えていない)。根は 5 つ。そのうち F、G、I は、この変更とは別に、`valuecalls` の修正で直った(F #465、G #466、I は b2d5afc8。zoo-dart の `no_edge` がそれぞれ 7 件、4 件、3 件減った見込み)ので、残るのは D、E の 26 件:

| 根 | 内容 | 件数 | 課題 |
|---|---|---|---|
| D | フィールド・map・リスト・グローバル・コンストラクタ引数に入れた関数値を、あとで呼ぶ(候補 0) | 20 | #99、#79 |
| E | 依存・骨組みのフレームワークが、渡されたコールバックを、自分の map / リストから呼ぶ(`Router.call`、`Navigator.pushNamed`) | 6 | #206 |
| F | 返したクロージャを、その場、または変数に入れて呼ぶ(直した) | 7 | #78(#465) |
| G | クロージャが、パラメータで受けた関数を呼ぶ(`g(a)`)(直した) | 4 | #81(#466) |
| I | 先に別の値を入れ、あとで代入した変数の関数値(直した) | 3 | #99(b2d5afc8) |

フラグで補うと、3 つの形の過検出(map のキーを区別しない、変数の代入の順序を見ない、候補が呼び出し点ごとに 1 つの集合で呼び出し元ごとに分かれない)も見つかった。直す所は `internal/taint` の要素の置き場(`OpIndexStore` / `OpIndexLoad`、`locs.go`)で、`valuecalls` の `narrow` ではない。根 D と I を直すときに、同じ形の偽の edge が出ないように、キーや代入を区別する必要がある(各課題に書いた)。

## 6. 段階と、各段階の受け入れ

**精度を変える段階は、消えた finding が本物でないことを示す**: `bench/compare.sh` で、base と head の finding を比べ、**消えたもの**を、経路を読んで分類する(取り違えで消えた = 偽の組だったことを、source から sink までの経路の、どのステップで混ざっていたかで示す)。**本物が 1 件でも消えたら、push しない**。足したものも分類する(本物の流れか、過検出か)。

| 段階 | 内容 | 受け入れ |
| --- | --- | --- |
| **1. `incomplete`** | `valuecalls` が、一部の呼び出し元しか追えないとき(`refOther`、引数の数が足りない、`form` が作れない、`maxDepth`)に、不確実性を足し(finding は減らさない)、`ValueCand` にマークを付ける。`ExactClosures`(束縛つき) | finding の追加・削除 0(`compare.sh`)。不確実性は増える。Dart の再現の入力を `dart-curated` に |

## 7. 順

全体の順(`DESIGN-shared-state.md` と合わせた。測定の数に従う。効果が大きいのは、ライブラリに渡したクロージャ(Rust の `map_err` 285、`Iterator::map` 199、Dart の `Iterable.map` 110)と、Rust の `Box<dyn Fn>` の `call` の 92%):

1. `DESIGN-shared-state.md` の**段階 1(証拠。出力の追加だけ)**。
2. このページの**段階 1(`incomplete`)→ 段階 2(ライブラリの `calls`)**(ヘルパーの要約を変えない。見つかる件数が、すぐ増える)。**`clos/capture-write-by-ref` を測るのも、ここ**。
3. `DESIGN-shared-state.md` の**段階 2(持ち上げ)→ 段階 5(止まらない)**。
4. このページの**段階 3(ヘルパーの `CallOut`)**(要約の型を変える大きな変更。ADR-047 のコードがある)。
5. `DESIGN-shared-state.md` の**段階 6(入口のレシーバ。Dart は入口の整備のあと)→ 段階 3(マップのキー)**。
6. このページの**段階 4(関数値の要素)**(測らないと読めない。go-scale のプロファイルと、`?` の照合の診断が先)と、`DESIGN-shared-state.md` の**段階 4(合流点。測ってから)**。

## 決定

1. **YAML の書式**(`calls:` の `fn` / `with` / `ret` / `throw` / `writes` / `feed` / `mode`。射影は、最初は書かない): **はい**。ただし、`calls` を書いた行は、`flows`(保守側の近似)も必ず持つ(読み込みで検査するか、`calls` から自動で導く。3.4)。
2. **段階 2 を、段階 3 より先に**: **はい**。
3. **`go` / `defer` を、`CallOut` から外さない**: **はい**。
4. **関数値の要素の上限(`N = 16`、`8`)**: **測ってから**。
5. **ADR-047 の位置を埋め直す**: **はい**。`docs/adr/047-param-call-callouts.md` に、「棚上げ → 精度のために再開」の経緯ごと、ADR-047 の本文を戻した。
6. **キャプチャした値は、写しでなく、キャプチャしたセルへの参照**(5.1a)。`clos/capture-write-by-ref` を、段階 3 と 4 の受け入れに入れる。
7. **条件 7 は、起点のあるプログラムでは、閉じた世界**(`closed_world_entry`)。起点のないライブラリだけ戻す(4)。

## 確かめていないこと

- 5.1 の、**`?` の付け方の抜け**(関数型の値が作られる場所を、全部、数えているか)。段階 4 の最初に、Go・Dart・Rust の IR の、関数型の値の作られ方を、網羅して表にする。Go は、フロントエンドの候補との照合(段階 4 の受け入れ)で、機械的に確かめる。
- 5.1a の、今の出方(`clos/capture-write-by-ref` の 3 言語)。上の「落とさない(はず)」は、コードを読んだ結果で、zoo では、まだ測っていない。Dart の `make_closure` の束縛も、Go と同じに、セルの参照かは、セルで確かめる。Rust は、環境の別名の問題で、書く側が落ちると分かっている。
- 3.2 の、**φ が選ぶ、決まった数のクロージャ**(1〜4)を、全部適用するのが、過検出にならないか(その呼び出し元が、実際は 1 つだけを渡す)。
- Rust の `impl Fn` の、`Fn::call`(ジェネリックの呼び出し)が、`CallOut` として、本体から導けるか(今の IR では、`std::ops::Fn::call` の動的な呼び出しで、候補は型の合う全クロージャ)。段階 3 の最初に確かめる。
- parseable の、`async move` のブロックの環境に入れて呼ぶ形(`for_each_live_node`)は、`Fn` が、パラメータの直接の呼び出しでなく、環境のフィールドの呼び出し。段階 4 の対象。

## インターフェース越しの合流の再現(`stagefield`)

memos の AWS SDK(smithy のミドルウェア)の 98 万要素は、関数値でなく、**操作ごとに別のステージ型が、構造体のフィールド(`With`)のインターフェースに入り、`h.With.HandleX(...)` の呼び出しが全操作のステージ型を候補にする**形から来る。この設計の `CallOut`(パラメータ `p`、パス `""`)は、この形に届かない。インターフェース版の要求は、「フィールドに入るインターフェース値の候補を、そのレシーバを組んだ呼び出し元が見える範囲で絞る」ことで、これには「関数値の要素」(段階 4)と、ステージの列を要素として持つことが必要。再現は go-scale の `stagefield` プロファイル(`-shapes stagefield -ops N -stages M -fields F`。`bench/go-scale/README.md`)。操作 N 個 × 操作ごとに別のステージ型 M 種 × 操作ごとの出力型のフィールド F 個で、全ステージが 1 つの SCC になり、全員の要約に全操作のフィールドが載る。`summary_elems` は ops 10 / 20 / 40 / 80(stages 4、fields 8)で 11,843 / 31,393 / 108,893 / 417,493 と、ops の約 2 乗で増え、ops 80 / stages 9 / fields 12 では 1,392,053(memos は 987,412)。finding は本物 2 件、誤り 0 のまま(精度の問題でなく、大きさの問題)。受け入れの基準は、この数字が ops に線形(候補が 1 操作ぶんに絞られた形)になり、finding が同じであること。期待値は `bench/go-scale/expected/stagefield-w1.json`(ops 40、stages 4、fields 8)。
