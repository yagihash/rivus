## 3. 分かったこと

1. **重さは、自分のコードではなく、少数の依存の、生成されたコードに集中する。** go-s3: `service/s3` の 2,866 関数が `summary_elems` の 69%(66.5 万 / 96 万。60 秒の時点)。gcp: `grpc` の `xds` と `grpclb` が時間の上位。
2. **go-s3 のコストは、アクセスパスの深さ(`-k`、既定 3)が決める。** 同じ go-s3 で、`-k` だけを変えた 1 回ずつの実験(今回。コードの変更なし):

   | `-k` | 結果 | wall | 最大 RSS | `summary_elems` | finding の ID |
   | --- | --- | --- | --- | --- | --- |
   | 1 | 収束(3 パス) | 8 秒 | 1.3 GB | 4.6 万 | 同じ 1 件 |
   | 2 | 収束(4 パス) | 43 秒 | 4.3 GB | 23.8 万 | 同じ 1 件 |
   | 3(既定) | 600 秒で打ち切り | 687 秒 | 12.4 GB | 96 万(60 秒の時点。まだ増える) | 同じ 1 件(途中) |

   go-s3 の要約の要素の 98% はパラメータのフィールドの下の経路(`with_path`)を持ち、深さ 3 以上が 78%、条件(ガード)つきが 79%。`real_origins` は 0(依存の中に、source は無い)。つまり、要約は、リクエストの構造体(S3 の入力の型は、フィールドが多い)の「どのフィールドの下の、どの条件つきの流れか」の組合せでふくらんでいる。
3. **`-k` を下げるだけでは足りない。** `bench/gcp` で `-k 1` にすると、finding が 27 → 31 件になり、ID の集合が変わる(精度が変わる。`-k 2` は ID の集合が同じ。ただし wall は短くならず、extractor の読み込みが大半)。したがって、全体の `-k` を下げる案は、精度を犠牲にするので採れない。**依存の関数だけの `-k`** は、まだ試していない(4 節の 1)。
4. **動的な呼び出しの候補の数は、もう 1 つの要因だが、対象で違う。** 候補が 17 以上の動的な呼び出しは、gcp で 1,020(動的な呼び出し 8,012 のうち約 13%)、go-s3 で 35(2,523 のうち約 1%。どちらも `-pass-stats` の `dispatch_candidates`)。最大の候補数は、gcp が 1,685(`go-logr` の `invokeStringer`)、go-s3 が 170(`smithy-go` の `SerializeStep.get`)。go-s3 の最大の SCC(661 関数)の中身は、`service/s3` が 364 関数。**どちらの対象でも、候補を切る案は、まだコアで試していない**(Dart の机上の見積もりだけ)。
5. **宣言(ADR-100、105)は、go-s3 を終わらせる手として確認してある。** しかし、既定の実行には効かない(組み込みモデルに宣言がないため)。宣言を付ける条件(ADR-092、098)は、モデルが本体の代わりをしてよい確認で、エンジンの課題ではなく、モデルの課題。この文書は、**宣言なしでも終わる**エンジン側の手を探す。

## 4. 次に試す価値のあるもの(エンジン側。順に、安く確認られるもの)

1. **依存の関数だけ、アクセスパスの深さを下げる**(要約の表し方)。3 節の 2 が根拠。確認の方法: (a) 診断だけの変更(動作は変えない)で、`summary_sizes` に、「パスとガードを無視したときの、異なる要素の数」を足し、go-s3 と gcp で、ふくらみの元(パスの組合せか、ガードか)を数える。(b) 依存の関数に別の `-k`(例: 2)を使う実験の実行を作り、`bench/go-s3`、`bench/gcp`、`bench/dart-gcp`、zoo と curated で、finding の ID の集合を比べる。ID の集合が変わるなら採らない(精度が優先)。
2. **動的な呼び出しの候補を、依存の関数の中で切る**(候補の絞り込み)。ただし、切ると、本来の呼び出し先を落とす。机上の見積もり(Dart 10.5)を、Go の IR(go-s3 と gcp)でも作ってから決める。精度のために、切るときは `dynamic_dispatch` の注記に、切ったことを書く必要がある。
3. **深さの上限(`-max-passes`、`-func-timeout`、`Budget`)を使った打ち切りの、報告の改善。** 時間切れの結果に、何が重かったかが付いていない(5 節の足りない出力)。コストを減らす手ではないが、利用者が終わらせるための手がかり。
4. **(エンジンの外)組み込みのモデルへの宣言。** go-s3 の既定を終わらせる最短の道だが、ADR-092、098 の条件(本体を読んだ場合との finding の集合の一致)を、公開の対象ごとに満たす必要がある。モデル側の作業。

## 5. 「どの依存が重いか、モデルや宣言があるか」の、利用者に見える出力: あるもの、足りないもの

`bench/gcp` と `bench/go-s3`(60 秒で打ち切り)で、`-pass-stats -pass-stats-top 0 -pass-stats-sort time` の出力を確認した。

**あるもの**

- `stats.packages_top`(`-pass-stats` のとき。`-pass-stats-top N`、`-pass-stats-sort`): パッケージごとの `dep`、`functions`、`reanalyses`、`spent_ms`、`summary_elems`、`largest_summary`。gcp で 545 件、go-s3 で 101 件。時間切れでも出る。
- `stats.dep_spent_ms` / `own_spent_ms`(いつも出る): 依存と自分のコードの時間の割合。
- `stats.largest_scc` と `largest_scc_packages`、`stats.summary_sizes`、`stats.dispatch_candidates`(`-pass-stats`)、`stats.unmodeled_top`(モデルのない呼び出し先と、到達した数)。
- `summary.body_replaced_packages`(宣言があるとき)、`summary.dependency_sites`、`summary.on_findings_top`。
- 手順の案内: AGENT-GUIDE の「終わらないとき」(1〜5 の順)と、README の「自分のプロジェクトで、どの依存が重いかの表を得る」。

**足りないもの(gap)**

1. **`-pass-stats` を付けないと、時間切れの結果に、何が重かったかが出ない。** 既定の出力は、`stats.timed_out`、`load_dependent_note`、`stats.functions` だけ。利用者は、時間切れのあとに、`-pass-stats` で、もう一度、同じコストを払わないと、表を得られない。
2. **`packages_top` の行に、そのパッケージに「モデルの行がある」「宣言がある」が付いていない。** 重いパッケージと、モデルや宣言の有無を、利用者が自分で照合する(`summary.body_replaced_packages` と、組み込みのルールの一覧と)。モデルの行の数も、`unmodeled_top`(シンボルごと)にだけある。
3. **「このパッケージを宣言すると、どれだけ減るか」の見積もりが出ない。** 宣言を勧める判断(ADR-092 の条件 1)の材料(`spent_ms` の割合)は表から計算できるが、割合そのものは出ない。
4. **extractor と読み込みの段階の時間が `stats` に出ない**(課題 #127 の 2。`-v` の標準エラーだけ)。go-s3 は読み込みが 3 秒で小さいが、Dart は 9 割が extractor で、全体の wall と `duration_ms` の差が説明されない。
5. **時間切れの結果が、`-timeout` を超える**(go-s3 で 86 秒。課題 #127 の 1)。上限を信頼できない。
6. **打ち切りの結果が、見逃しの大きさを言わない。** `timed_out` のとき、どの関数が未解析か(どの finding の経路が未確認か)は、`run_timeouts`(件数)と `unstable_count` で分かるが、パッケージ単位ではない。
7. **解析がふくらむ原因(パスの深さ、ガード)が、利用者に出ない。** `summary_sizes` に `by_path_depth` はあるが、「`-k` を下げると軽くなる(が、精度が変わる)」という手がかりは、出力にも AGENT-GUIDE にもない。

この PR は、出力を実装しない。

## 6. 次に勧める、エンジン側の 1 手

**依存の関数だけアクセスパスの深さを下げる実験(4 節の 1)を、診断から始める。**

理由: (1) go-s3 では、`-k` を 3 → 2 にするだけで、終わらない(12 GB 超)ものが 43 秒、4.3 GB で終わり、finding の ID が同じだった(3 節の 2)。他に、1 つの設定で、桁が変わった手は、宣言(モデル側の作業)だけ。(2) 一方、全体の `-k` を下げると、gcp の finding が変わる(3 節の 3)ので、そのままは採れない。違いが依存の関数の中で起きるのか、プロジェクトの関数で起きるのかは、未確認。これを分ける実験が、もっとも小さく、結果が判断を決める。(3) 動的な呼び出しの候補を切る案は、go-s3 は、候補が 17 以上の呼び出しが約 1% しかなく、効きが見えない。(4) 最初の一歩は、診断の追加(動作は変えない)と、実験用のフラグの実行だけで、finding を変える変更ではない。結果が精度を変えるなら、採らない(精度が優先)。

最初の確認は、`bench/go-s3`、`bench/gcp`、`bench/dart-gcp` の 3 つで、`make bench-deps` の行を、前と後で並べる。
