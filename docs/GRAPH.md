# `rivus index` と `rivus graph` の使い方

呼び出しグラフを 1 回作って保存し(`rivus index`)、あとから問い合わせる(`rivus graph`)ための、コマンドと出力の説明です。設計は [DESIGN-graph.md](DESIGN-graph.md) にあります。

`rivus graph` が答えるのは**呼び出しの関係**(誰が誰を呼ぶか)で、**データの流れ**(何が何に届くか)ではありません。出力には必ず `relation: "calls"` と `flows: "not_checked"` が付きます。データの流れは `rivus analyze` と `rivus query` で調べます。

## コマンドの例

```sh
rivus index -C path/to/project ./...       # コールグラフ(構造の層)を SQLite に保存する。速い(taint 解析はしない)。書き先は、ユーザーのキャッシュ(-graph <file> で指定)
rivus graph info -C path/to/project ./...  # 保存したファイルの中身(件数、作成日時、source_hash)と、今のソースと一致するか(fresh: true/false)
rivus graph callers -C . os/exec.Command   # この関数を呼ぶ関数(逆向き)。--depth N(既定 1、最大 6)、--limit K(既定 50 エッジ)
rivus graph callees -C . main.go:42        # その行の呼び出し点が呼ぶ関数(順向き)。複数あれば、候補の一覧を返して選ばせる
rivus graph path -C . --from cmd.run --to os/exec.Command  # 経路を k 本(--limit、既定 5)、最短から。静的 → 動的 → ハブ込みの順に探す(searched に、どこまで探したかを書く)
rivus graph path -C . --from-entry --to os/exec.Command    # main と init(ライブラリなら exported な関数)から届く経路。出力の entry に、何を entry としたかを書く
rivus graph path -C . --from-entry --to routers/web/repo.Activity  # ルータに登録しただけの関数(m.Get("/x", repo.Activity))にも、4 段目(参照)で届く。--refs で 4 段目から、--no-refs で使わない
rivus graph callers -C . repo.Activity --refs   # この関数を、値として持つ関数(登録、保存、受け渡し)も、kind: ref のエッジとして足す。callees --refs は、持っている関数
rivus graph path -C . --from a --to b --avoid log.Error --via db.Query --only-impl bytes.Buffer  # エッジのフィルタ(callers / callees でも使える。繰り返し可。filters に必ず書く)
rivus graph path -C . --from a --to b --avoid-call server/handler.go:42:7  # 呼び出し点を 1 つだけ切る(--avoid は関数を丸ごと切る)
rivus graph impls -C . '(io.Writer).Write'        # インターフェースのメソッドの、実装(関数)の一覧。短い指定(io.Writer.Write、Writer.Write)も可。--limit で切り、総数と by_package(上位 10)を言う
rivus graph dispatchers -C . '(*bytes.Buffer).Write'  # その実装を候補として呼ぶ、動的な呼び出し点(位置、含む関数、kind、candidates、通るインターフェースのメソッド = callee)
rivus index -taint -o idx.json ./...       # taint 解析の結果を JSON で保存(-o だけでも同じ)。構造の層も、同じ実行で、キャッシュに書く
```

## 詳しい説明

- **`rivus index` と `rivus graph info`**（設計: [docs/DESIGN-graph.md](DESIGN-graph.md)）。`index` は、コードを 1 回読んで、関数・呼び出し点・エッジ（静的 / インターフェース / 関数値の別つき）・サイトを、1 つの SQLite ファイルに保存する（純 Go。cgo なし）。使い捨てのキャッシュで、マイグレーションはしない（スキーマバージョンが違えば、エラーで、作り直しを案内する）
  - 書き先は `-graph <file>`。なければ、ユーザーのキャッシュ（`os.UserCacheDir()/rivus/<-C の絶対パスのハッシュ>/graph.db`。`RIVUS_CACHE_DIR` で変えられる）。**解析対象のディレクトリには作らない。読むのも、`-graph` で明示したファイルか、`-C` から導いたキャッシュだけ**（読み取り専用で開く）
  - **構造の層だけ**を作る（taint の層、つまり findings と不確実性は、このファイルにはない。`index` はそれを出力に書く。`-taint` でも、taint の結果は、これまでの JSON の index（`-o`）に入り、`query -index` / `resolve -index` はそれを読む）
  - `graph info` は、スキーマバージョン、rivus のバージョン、作成日時、`source_hash`、層、件数、サイズ、言語を JSON（`rivus.graph/1`）で出す。**`-C <dir>` を付けると、鍵を今のソースから作り直して照合し、`fresh: true/false` と、変わった点（`stale_reasons`）を返す**。`-C` なしのときは、`verified: false`（今のソースとの一致は確認していない）。照合には、`index` に渡したのと同じフラグ（`-tests`、`-no-deps`、`-k`、`-lang`、`-rules`、パッケージなど）を渡す（違えば、`fresh: false`）
  - `source_hash` には、結果に影響しうるものを全部入れる: 実際に読んだファイルの内容（Go は `go/packages` の一覧。依存、標準ライブラリ、ビルドタグで除かれたファイル、`go.mod`、`replace` の中身を含む）、ツリーのファイルの一覧（新しいファイルを見逃さない）、`go.sum` / `go.work` / `pubspec.lock` / `Cargo.lock`、ルール（組み込みの内容、`.rivus/rules`、`-rules`）、フラグ、rivus のバージョン（実行ファイルのハッシュ）、`go env` の全項目、extractor と SDK のバージョン。Dart と Rust は、extractor が読んだファイルを出力しないので、プロジェクトのツリー全体（`.git`、ビルド出力などを除く）の内容を鍵にする。**疑わしいときは、`fresh: false`**
- **`rivus graph callers | callees | path`**（段階 2。DB だけを読む。ソースの再読み込みも taint もしない）。`-graph <file>` か `-C <dir>`（そこから導くキャッシュ）で DB を指す。`-C` を付けると `graph info` と同じ照合をして、出力の `snapshot.verified` / `fresh` に入れ、**古ければ `warnings` に書く**（答えは返す。古いソースの答えである）。`index` に渡したフラグは、`-C` で照合するとき、与えなければ DB に記録されたものを使う
  - **指定（target）は 4 通りを形で判別する**: シンボル（`os/exec.Command`、`(*pkg.T).Method`、Rust は `crate::f`。前を省いた短い指定(`GetUserByID`、`user.User.GetName`、`Widget.build`、`Printer::handle`)も、**識別子の境界で末尾が一致し、グラフ全体で 1 つに決まるときだけ**通る(`ByID` は `GetUserByID` に一致しない)。複数なら、エラーにせず `ambiguous`(自分のコード、本体あり、名前の順に最大 20 件)と `ambiguous_total`、`pkg.Name` のヒントを返す）、`file:行:桁`（その位置から始まる呼び出し点。桁がずれていれば、その行でそれより前に始まる最後の呼び出し点）、`file:行`（その行の呼び出し点。複数あれば、**エラーにせず `ambiguous` に一覧を返す**）、`site:<ID>`（`rivus sites` のサイト。`callers` / `callees` は `--site <ID>` でも）。ファイルは、DB の名前（解析対象からの相対）でも、絶対パスでも、末尾だけでも（1 つに決まるなら）良い。見つからなければ、近い候補を添えたエラー
  - **指定が何を指すか**（関数 F と、呼び出し点 C = 関数の中の、別の関数を呼ぶ場所）: `callers F` は F を呼ぶ関数、`callees F` は F が呼ぶ関数。`callers C` は **C を含む関数**の呼び出し元、`callees C` は **C が呼ぶ関数**（C の呼び出し先の候補）。`path --from C` は C を通って始まり、`path --to C` は C を含む関数で終わる（最後のステップが C）。例: `main.go:42:7` が `exec.Command(...)` の呼び出しなら、`callees main.go:42:7` は `os/exec.Command`、`callers main.go:42:7` は、それを含む関数の呼び出し元
  - **builtin**（`len`、`append` など）の呼び出し点は、既定で結果から外す（呼び出し点の約 4 割）。外した数は `omitted.builtin`。`--include-builtin` で `builtin:len` のノードとして戻す
  - **動的なエッジ**（インターフェース、関数値）は、`kind` と `candidates`（その呼び出し点の候補の数）を必ず持つ。`callers` では「呼び出し元は、候補の 1 つとして、これを呼びうる」と読む。`callees` は静的なエッジをたどり、**候補が 3 以下の動的な呼び出しは展開し、それより多いもの（と候補が 0 のもの）で止めて `frontier` に入れる**（`frontier_total` に総数）。`path` は 3 段で探す: 静的なエッジだけ（`certainty: certain`）、なければ動的なエッジ（候補が 20 以下。`uncertain`）、まだなければ**候補が 20 を超える呼び出し点（ハブ）も含めて**（`certainty: hub`。ハブのステップに `hub: true` と `candidates`。ハブの少ない経路、次に短い経路の順）。`searched` が、どの段まで探したかを示し、`reachable: false` で `exhaustive: true` なら、その範囲では経路がない（3 段目まで探していれば、DB の全部のエッジについて）。2 段目で見つかったときは、ハブを使う経路は探しておらず、出会ったハブの数を `hub_skipped_total` に書く（`--hubs` で、ハブ込みの探索を頼める）
  - 切ったものは必ず報告する: `truncated`（`count` と `limit`、`unit`。`at_least` は、数え切れていないとき。`beyond_depth` は、深さの端のノードに、見せていない先がある数）、`omitted`、`frontier`、`hub_skipped_total`、`warnings`。各出力に `schema: "rivus.graph/1"`、`relation: "calls"`（呼び出しの関係。データの流れではない。参照を含む経路は、経路ごとに `"calls+refs"`）、`flows: "not_checked"`（データの流れは確認していない）、`snapshot`、`query`、`filters`、`hints`（次の一手）
  - **エッジのフィルタ**（`callers` / `callees` / `path` / `impls` / `dispatchers`、繰り返し可）: `--avoid <シンボル>`（その関数を通らない。**その関数の呼び出しも、その関数への呼び出しも、全部**）、`--avoid-call <file:line:col>`（**呼び出し点を 1 つだけ**切る。その呼び出しを含む関数と、その関数のほかの呼び出しは残る。位置は、出力の `at` が示す形で、`file:line` が複数の呼び出しに一致するときはエラーで候補を返す。ハブの経路は「本物らしい順」ではないので、1 本ずつ確かめて、疑わしい呼び出し点を切っていくために使う）、`--via <シンボル>`（その関数を経由するものだけ。`path` は、与えた順。`impls` / `dispatchers` では使えない）、`--only-impl <型>`（インターフェースの呼び出しのうち、**候補に、その型のメソッドが 1 つでもある呼び出し点だけ**を、その型のメソッドに絞る。候補にその型がない呼び出し点（関係のない `Stringer` や `error` の呼び出し）は絞らない。静的な呼び出しと関数値も絞らない。型は、型の名前（`Buffer`）、またはパッケージや経路を付けた形（`bytes.Buffer`）で、**型の名前に一致する**: Rust の `<T as Trait>::m` は `T` だけ（trait の名前では一致しない）、Go はパッケージ名だけでは一致しない、型引数の中（`Vec<Foo>` の `Foo`）では一致しない）。**絞り込んだことは、必ず `filters` に書く**（`--only-impl` は、出会った呼び出し点のうち、絞った数と、絞らなかった数も）。`path` で `reachable: false` のときは、フィルタ（`--via` も）なしで 1 回探し直して、`without_filters` と `hints` で、条件が経路を塞いでいるかを示す。フィルタが 2 つ以上なら、1 つずつ外した探索もして、外すと届くものを `without_filters.culprits` に書く。フィルタつきの探索が上限で切れたときは、「フィルタが原因とは言えない」と報告する
  - **`path` が並べた範囲**: `listed`（`stage`: static / dynamic / hub、`hubs`（hub の段: 並べた経路のハブの数 = 最少）、`shortest_hops`、`max_hops` = 最短 + 2）と、`beyond: "not_searched"`（これより長い経路、ハブの多い経路は、探していない。`truncated.count` は数えない）。`--limit` で切ったものだけが `truncated` に入る
  - **`path --from-entry --to X`**: `--from` の代わりに、プログラムの起点（Go の `main.main` と各パッケージの `init`、Dart の `main`、Rust の `entry_fn`。起点がなければ、読んだコードの exported な関数。起点の決め方は taint の `reachability` と同じ。たどるエッジも、`sg.Program.Reachable` に合わせた（呼び出し、インターフェース・関数値の候補、**値として名前を挙げた関数 = 参照**。参照は `path` の 4 段目でたどる。下の「参照」）。出力の `entry` に、定義(`definition`)、`source`(`entry` / `exported`)、件数、例を書く。経路の最初のステップが、届いた entry。「届かない」は、コードが死んでいるという意味ではない（フレームワークに登録されるハンドラーなど）。**届かないとき**: `exhaustive` は常に `false`(読んでいないコード〔依存、フレームワーク〕が、インターフェース経由で呼ぶ関数は、エッジにない)。探索が呼び出しと参照のエッジを尽くしたことは `edges_exhausted: true` が示す(`exhaustive_of`: 呼び出しと参照のエッジについて。`sg.Program.Reachable` と同じ規則)。`limits`(リフレクション、フレームワークからの呼び出し〔依存の型のメソッドの上書き〕は、エッジにない)と、`target_facts`(終点の呼び出し元の呼び出し点の数〔静的、動的〕、`exported`、`has_receiver`〔メソッドである。メソッドで呼び出し元のエッジがないものは、依存から呼ばれうる〕、`has_body`、`dep`、`value_references`〔参照の数〕、`value_reference_owners`〔参照を持つ関数の上位〕)を付ける。`--no-refs` のときは、従来どおり `exhaustive` は `false`(関数値の保存はエッジにない、と `limits` が示す)。`edges_exhausted` は、エッジについての探索が上限で切れなかったこと。`path` の `exhaustive` は、`exhaustive_of` の範囲についてのもの
  - **`-resolve-func-values` で作った索引**: `rivus index -resolve-func-values` は、候補が 0 件の関数値の呼び出しに、関数値の解析が見つけた関数を候補として補ってから索引を書く。補ったエッジは、普通の動的なエッジ(`kind: value`、`candidates`)で、`callers` / `callees` のエッジ、`dispatchers` の呼び出し点、`path` のステップ(経路には `supplemented_calls`)に `supplemented: true` が付く(索引の `meta` の `func_values_supplemented` に、補った呼び出し点を記録する。表は同じなので、スキーマバージョンは同じ)。補った候補は、その解析が見つけたものであり、呼び出しが届く全部ではない。そのため、補った呼び出しを通る経路があるときも、経路なしのときも、`path` の `exhaustive` は `false` のまま(経路なしでは `not_exhaustive_because.unresolved_calls` に数える)。フラグの有無は索引のキーに入る(on と off は別の索引。`graph info -C` と `graph ... -C` が、食い違いを `stale_reasons` に出す)。`-timeout` は、補う解析の全部の回と、そのあとの解析を合わせた上限で、時間切れの回の候補は使わない(`stats.func_values.timed_out`)。補う解析が使えるのは `-timeout` の半分までで、そのあとの解析には、少なくとも残りの半分が渡る
  - **参照(`refs` 表。スキーマバージョン 2)と、`path` の 4 段目**(設計: DESIGN-graph.md「参照」): `rivus index` は、値として名前を挙げた関数(`m.Get("/x", repo.Activity)` の `repo.Activity`、変数や構造体に入れた関数、関数ポインタ、Dart の tear-off、キャプチャのあるクロージャ)を、`refs` 表に入れる(持っている関数 `owner_func`、書かれた位置、参照される関数 `target_func`、引数に取っている呼び出しの呼び出し先 `via_callee`、`kind` = `arg` / `closure` / `other`)。**スキーマバージョンが 1 から 2 に上がった**ので、前のバージョンのファイルは、エラーで、`rivus index` での作り直しを案内する(マイグレーションはしない)。`path` は、静的 → 動的 → ハブ → **参照** の順に探し、4 段目は、3 段目までで見つからないときだけ(`--refs` で 4 段目から、`--no-refs` で使わない)。参照のステップは `kind: "ref"`(呼び出しではない。**位置 `at` は、参照が書かれた位置 = 登録の行**。`via_callee`、`ref_kind`、`note` つき)。参照を含む経路は `certainty: "reference"`、経路ごとの `relation: "calls+refs"`(呼び出しだけの経路は `"calls"`)で、経路の `note` が「届くかもしれない、の広い近似(登録しただけで、呼ばれるかは分からない)」と報告する。並べる順は、参照が少ない → ハブが少ない → 短い。`searched` に `ref`、`listed.stage` が `ref`(`listed.refs` は参照の数)。`callers` / `callees` は、既定で参照をたどらず、数を `omitted.refs` に書く。`--refs` で、`kind: "ref"` のエッジとして足す(`filters` に書く。関数値の呼び出しの候補 = `kind: "value"` とは別)。`impls` / `dispatchers` は参照を使わない
  - **`rivus graph impls <インターフェースのメソッド>` / `dispatchers <実装のメソッド>`**（段階 3b。具体的な実装から始める使い方の入口。DB のエッジは変えず、`edges` の `kind = interface` を、呼び出し点の静的な型 `callsites.callee` ごとにまとめて読む）。`impls` の指定は、呼び出し点が持つ名前（`(error).Error`、`(io.Writer).Write`、Rust は `pkg::Trait::method`、Dart は `dart:core#List.length`）か、その末尾（`io.Writer.Write`、`Writer.Write`。識別子の境界で、**インターフェースのメソッド全体で 1 つに決まるときだけ**。複数なら `ambiguous` に、呼び出し点の多い順で最大 20 件）。`dispatchers` の指定は、`callers` と同じ規則の関数（シンボル、短い形、`ambiguous`）
    - **`impls` の出力は「DB の中の、その呼び出し点の候補の和」で、「型としての実装の全部」ではない**。Go の候補は VTA が呼び出し点ごとに絞ったもので、どの呼び出し点からも届かない型は載らない。これを `basis` に必ず書く。`call_sites`（そのメソッドの、インターフェース呼び出し点の数）、`zero_candidate_sites`（そのうち候補が 0 のもの。レシーバの型が見つからなかったので、その先の実装は載っていない）、`impls_total`、`impls`（`id`、`at`、`dep`、`call_sites` = その実装を候補に持つ呼び出し点の数。自分のコード、呼び出し点の多い順）。`--limit`（既定 50）で切ったら、`truncated`（総数との差）と `by_package`（全体の、パッケージごとの内訳の上位 10。残りは `by_package_other`）を示す
    - そのメソッドの呼び出し点が DB に 1 つもないとき（関数としては存在する、など）は、エラーにせず、`impls: []`、`call_sites: 0`、`reason`（なぜ何も報告できないか）と `hints` を返す。「空 = 実装なし」ではない
    - **`dispatchers`** は、その関数を候補に持つ**動的な呼び出し点**（`kind` が `interface` または `value`）だけを返す（静的な呼び出し元は `callers`）。各呼び出し点に、位置 `at`、含む関数 `in`、`kind`、`candidates`、**そこから届くインターフェースのメソッド `callee`**（静的な型）、`sites`。候補の少ない順（その実装を名指しに近い順）。`--limit` で切ったら `truncated` と、全体の `by_callee`（インターフェースのメソッドごと、上位 10）。同じ symbol の関数が複数あるとき（型の埋め込みによるラッパー）は、`id` が symbol と同じ本物のメソッドだけを見て、ほかがあることを `hints` で示す
    - `--avoid`、`--avoid-call`、`--only-impl`（`filters` に書く）は使える。`--via` は、意味がないので、エラー。`snapshot`、`-C` の照合、`relation: "calls"`、`flows: "not_checked"` は、ほかと同じ
  - `path` の最後のステップ(呼び出し先)には、宣言の位置 `defined_at`、本体がなければ `no_body: true` が付く（呼び出し点が終点のときは `at`）
  - 出力は、既定で 1 行の JSON（`--pretty` で整形）。`callers` / `callees` は、ノードとエッジに分ける。`path` は、ステップの列（各ステップは関数と、そこから次へ進む呼び出し点の `at`、`kind`、`candidates`、`sites`）

## 答えの読み方(要約)

`rivus graph path` の答えを読むときの要点です(確認: 2026-11-22、9c26a39。正本は `internal/graphq` のコメント)。

- **`reachable: false` は、「届かない」とは限りません。** `exhaustive` を見ます。
  - `exhaustive: false`: 探索が上限で切れました。「経路なし」は証明されていません。
  - `exhaustive: true` で経路なし: **何も省いていません**(2026-11-22 から。それまでは「エッジを探し尽くした」だけを意味していました)。エッジの探索が最後まで終わったことは `edges_exhausted: true` が示し、そのうえで、次のどれかがあれば `exhaustive` は `false` になり、理由が `not_exhaustive_because` と `limits` に出ます。(1) `unresolved_calls`: 起点から届く関数の中に、インターフェースや関数値の呼び出しで候補が 0 件のものがある(どこへ行くか、ファイルは言えない)。(2) `open_functions`: 終点へ届く関数(呼び出し元を逆にたどった集合)の中に、読んでいないコードから呼ばれうるものがある。メソッド(依存や言語が呼ぶ。文字列補間の暗黙の `toString` など)と、値として参照されていて、この探索が届かなかった関数。メソッドかどうかは、今はシンボルの形で決めていて、過剰に `false` になる(向きは安全)。範囲は `exhaustive_of` に書いてあります。グラフのファイルにある呼び出しのエッジ(直接の呼び出しと、インターフェースや関数値の候補)だけです。値として持たれた関数(ルータに登録したハンドラ)、リフレクション、フレームワークからの呼び出しはエッジではありません。`--refs` の段では、参照(関数を値として参照したもの)も範囲に入ります。
  - `--from-entry` で経路なしのとき、`exhaustive` は**常に** `false` です。読んだコードの関数は、読んでいないコードから呼ばれうるからです。`edges_exhausted` が、エッジの探索自体は最後まで終わったかを示し、`limits` が、エッジが持たないものを示し、`target_facts` が、終点についてファイルが知っていること(`has_receiver`: メソッドである、など)を示します。「経路なし」を「使われていないコード」と読まないためのフィールドです。
- **`certainty`** は、最初の経路の確かさです。`certain`(どの呼び出しも、コードに名前がある)、`uncertain`(インターフェースか関数値を通る。候補が 20 以下)、`hub`(候補が 20 を超える呼び出しを通る)、`reference`(関数が値として挙げられた箇所を通る。呼び出しではない)。
- **`searched`** は、探索に使ったエッジの種類(`static`、`dynamic`、`hub`、`ref`)です。前の種類で見つかると、後ろは探しません。載っていない種類は、探していません。
- **`truncated`** は、`--limit` などで切った数です。`listed` と `beyond: "not_searched"` は、並べた経路の範囲と、それより長い経路や、ハブの多い経路を探していないことを示します(`truncated` は、これを数えません)。
- **`relation: "calls"`、`flows: "not_checked"`** は、答えが呼び出しの関係で、データの流れではないことを示します。データの流れは `rivus analyze` と `rivus query` で調べます。

この読み方は、[PRINCIPLES.md](PRINCIPLES.md) の「省いたものは、必ず報告する」の、グラフの検索への適用です。
