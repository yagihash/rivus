# 課題の一覧

課題は、リポジトリの中のファイルで持つ(GitHub の Issue は使わない)。**1 件は 1 ファイル**(`docs/issues/<番号>-<短い名前>.md`)。一覧は `make docs-gen` で作る(コミットしない生成物)。**この文書の表には足さない**(この文書は、表を持たない)。課題を足すとは、課題のファイルを足すこと。書き方は [`issues/README.md`](issues/README.md)。

## 一覧の見方

`make docs-gen` が、全部の課題の表(番号、題、種類、言語、ROADMAP の節、状態、守るもの)を標準出力に出す。ファイルに書くときは `make docs-gen OUT=docs/ISSUES-TABLE.md`(`.gitignore` の対象)。表の中身は、各課題のファイルの先頭のヘッダ(`issues/README.md`)。開いているものを先に、閉じたものを後に出し、それぞれ番号の順。

## 決まり

- **番号**: GitHub の番号を引き継ぐ(#74〜#99)。zoo の `@ref(#N)` と、コミットの `Zoo-Loosened:` の行が指すのは、この番号。**新しい課題の番号は、`docs/issues/` の最大の番号 + 1**(どの文書にも「次の番号」の行は持たない。PR のたびに衝突するため)。番号は相談役が付ける。100〜107 は、直してから記録したもの。#1〜#73 は、日次レビューの指摘(GitHub 側で閉じ済み。ここには写していない)。
- **番号を持たない課題**: モデルを作る PR が見つけた見逃しと誤検出は、`docs/issues/model-<パッケージ>-<名前>.md`(様式は [`issues/README.md`](issues/README.md))に書き、zoo の `@ref(model-<パッケージ>-<名前>)` から指す。相談役が、あとでまとめて番号にしてよい。`TestIssuesFiles` が、番号の一意性、ヘッダの形、生成した表の行、名前の形のファイルの節を確かめる。
- **状態**: `open` / `partial`(一部直った。残りを題に書く)/ `closed`(直した: コミットとテスト)/ `deferred`(後回し。理由と見直す条件)/ `wontfix`(やらない)。
- **誰が何をするか**: 中身と状態は相談役が決め、開発者が書いてコミットする。開発者が作業中に見つけたものは、相談役を待たずに `open` で足してよい(次の報告に番号を書く)。閉じるのは、相談役がレビューで確かめてから(開発者は「閉じられる」と報告する)。`deferred` と `wontfix` は相談役が決める。
- **公開のリポジトリの決まり**: 直していない rivus 自身の弱点(対象が意図して起こせるサイレントな見逃し、隔離の漏れ)の再現の詳細は、ここに書かない。直るまでは、相談役のレビューのファイル(`.claude/reviews/`。追跡されない)にだけ置き、直ってから `closed` で記録する。
- ROADMAP の各項目に、対応する課題の番号を並べ、終わりの条件に「これらを閉じる」を書く。
- **列の意味**: 種類は失敗の重さに合わせて書く(サイレントな見逃しが最も重い)。言語は `Go` / `Dart` / `Rust` / `全` など。ROADMAP の節は、その課題を持つ節の番号。守るものは、再発を止める zoo のセルかテスト(なければ `-`)。開いているものは、重い順に番号を付ける必要はなく、表は番号の順。
