# 設計: Rust の extractor の隔離を、Docker から macOS のサンドボックス(Seatbelt)に移す

> **状態: 案**(2026-11-22。実装はない。advisor のレビュー前)。ユーザーの決定(2026-11-22)の実行計画。ADR-064 を一部覆す ADR を、実装と一緒に書く。

## 0. ユーザーの決定と、前提

- **目的**: `brew install` だけで rivus を使えるようにする。その前段として、Rust の extractor の Docker への依存をなくす(tap と formula は、このあと別に)。
- **決めたこと**: Rust の抽出を、Docker のコンテナの代わりに、**macOS のサンドボックス(Seatbelt、`sandbox-exec`)**の下で動かす。**Docker の経路は、CI を含めて丸ごと消す**。対象の環境は macOS(Apple Silicon)。
- **ユーザーが承知のうえで受け入れたこと**: (1) `sandbox-exec` は、Apple が非推奨にしたまま動いている仕組み。(2) Docker の `--memory` / `--cpus` / `--pids-limit` に当たる**強い**上限がない(時間の上限、プロセスグループごとの kill などで代わりにする)。
- **上のほかに、Docker より弱くなる所が見つかったら、ユーザーに聞く**(セキュリティの制御の変更。PRINCIPLES 8 節、ADR-064)。7 節に、見つかったものを並べる。
- Linux: サンドボックスがないので、信頼できないコードの Rust の解析は、**何も実行せずに止まる**。既知のコードは `-unsafe-host-exec`。

## 1. 手元で確かめたこと(2026-11-22、macOS 26.7.1、arm64。使い捨ての試し。コードは残していない)

`sandbox-exec -f <profile>`(`(version 1)(deny default)(import "/System/Library/Sandbox/Profiles/bsd.sb")` に、要るものだけを足した最小のプロファイル)で:

| 試したこと | 結果 |
| --- | --- |
| 許したディレクトリの読み | できる |
| ホームの秘密の置き場(`~/.ssh`、`~/.rv_secret_test`)の読み | **拒否**(`Operation not permitted`) |
| `/tmp` とホームへの書き込み | **拒否**(許したもの以外) |
| ネットワーク(`curl http://1.1.1.1`) | **拒否** |
| 他のプロセスへの `kill`(自分のユーザーの `sleep`) | **拒否**(相手は生きたまま) |
| `launchctl list`、`pbpaste`(ペーストボード)、`security find-generic-password`(キーチェーン) | **失敗**(中身を得られない) |
| `osascript` で Finder に Apple Event を送り、Desktop にフォルダを作る | **失敗**(`Can’t get application "Finder" (-1728)`。フォルダは作られない)。**注意**: `tell application "Finder" to get name` は、この拒否の下でも `Finder` と答える(名前の解決だけで、Finder への通信ではない)。試験は、**副作用のあるもの**でやる |
| `open -a` | 失敗(`Unable to find application`) |
| `ulimit -v`(アドレス空間の上限)を、サンドボックスの外から設定 | **`setrlimit failed: invalid argument`**(macOS arm64 では使えない)。`ulimit -u` は 4000(ユーザー全体の数。プロセス木ごとではない) |
| `(version 1)(deny default)` だけ(`bsd.sb` なし) | 最小の `cat` も、起動時に落ちる(`rc=134`)。`bsd.sb` を import して、要るものを足す形が現実的 |

(まだ確かめていないこと: `cargo check` とビルドスクリプト、C コンパイラとリンカが、プロファイルの下で動く最小の許可一覧。プロセスの数の増え方。デーモン化して残るプロセスの扱い。ローカルのプロキシだけへの接続の許可 `(allow network-outbound (remote tcp "localhost:PORT"))` が効くこと。これらは実装の段階 3〜4 で測り、表に書く。)

## 3. 設計

### 3.1 構成(言語と OS を知らない部分と、Seatbelt に固有の部分を分ける)

- `internal/sandbox/`(新しい。サンドボックス関連を 1 か所に: CI のパス絞り込みのため)
  - **言語も OS も知らない部分**: 起動(新しいプロセスグループ)、時間と出力の上限、プロセスグループごとの kill、見張り(メモリ、プロセス数)、後始末(目印)、取得の前の検査(対象の cargo の設定を読ませない、`Cargo.lock` / `Cargo.toml` の取得元の検査)。今の `cmd/rivus/isolate.go` の、言語を知らない部分を移す。
  - **Seatbelt に固有の部分**: プロファイルの生成と、`sandbox-exec` での起動。
  - **取得のプロキシ**: 許可リスト、解決したアドレスの検査、検査したアドレスへの接続。
  - Linux の実装は、**「隔離の手段がない」と言って止まる**スタブ。あとで bubblewrap などを足せるよう、起動の口を 1 つにする。
- `cmd/rivus` の Rust 固有の部分(取得の段階の呼び出し、抽出の呼び出し、ツールチェインの固定)は、`internal/sandbox` を呼ぶだけにする。

### 3.2 プロファイル

- `(deny default)` + `bsd.sb` の import(1 節で確かめた)に、要るものだけを足す。許したものには、1 行ずつ理由を書く(Go のテンプレートで生成し、生成した文を試験で読む)。
- 読み取り: 対象、取得した依存、固定のツールチェイン、extractor、作業用の一時ディレクトリ、コンパイルに要るシステムの場所。ホームの残りは許さない。書き込み: 作業用の一時ディレクトリだけ。
- ネットワーク: 抽出は `(deny network*)`。取得は、ローカルのプロキシのポートだけ。
- `mach-lookup`: 既定拒否。要るものだけ(ログなど)を許す。`process-exec`: 許可リスト。`signal`、`process-info*`: 自分のグループだけ。`sysctl-read`: 要るものだけ(他のプロセスの引数や環境を読めないように。要測定)。
- 環境変数: ホストのものを渡さない。決めたものだけ(`CARGO_HOME`、`RUSTUP_HOME`、`RUSTUP_TOOLCHAIN`、`HOME`(作業用の一時ディレクトリ)、`TMPDIR`、`PATH`、取得のときは `CARGO_HTTP_PROXY` など)。

### 3.3 取得の段階のネットワーク

[DESIGN-fetch-network.md](DESIGN-fetch-network.md) の案(取得元だけを許すプロキシ)を、コンテナなしで実装する: プロキシは rivus の Go のプロセスの中(CONNECT)。許す宛先、解決したアドレスの検査(ループバック、プライベート、リンクローカル、ユニークローカル、CGNAT など)、検査したアドレスへの接続(DNS rebinding)、リダイレクトとサブモジュールの要求も毎回検査、は、その文書のとおり。サンドボックスが「ローカルのプロキシのポート以外へは出られない」を保証する(コンテナの専用ネットワークの代わり)。`TestIsolationFetchFollowsWhatTheAllowedRepositorySays`(今は「防げていない」と書いてある)を、「要求が出ない」ことを確かめる試験に反転させる。

### 3.4 ツールチェインと extractor の用意

固定の nightly(`nightly-2026-11-15`、`rustc-dev`、`llvm-tools`、`rust-src`)と extractor のビルドは、**サンドボックスの外で、信頼できるソース(rivus 自身)から**行う。対象のコードを使わない。用意の仕方は、**明示のコマンド `rivus setup rust`** を案とする(初回の Rust の解析で、断ってから行う形にもできる。advisor と決める)。後で formula から呼べる形にする。用意の段階のダウンロード(rustup、crates.io)は、rivus のソースの `Cargo.lock` で固定したもの。置き場所は、利用者のデータのディレクトリ(`~/Library/Application Support/rivus/` など。要決定)。

### 3.5 試験(先に書く。赤を確かめる)

`TestIsolationHostileBuild` が試していることを、すべてサンドボックスでも試す(見えるもの、止まらない `build.rs`、フォークの無限ループ、メモリを使い切る、IR の断片のディレクトリの、リンクと大きなファイル、鍵、隣のファイル、ネットワーク、書き込み、環境変数、…)。加えて、macOS に固有の抜け道(2 節の最後の行): `open`、`osascript`(**副作用のあるもの**で: 1 節の注意)、`launchctl`(サンドボックスの外にプロセスを残す)、ペーストボード、キーチェーン、ホームの秘密の置き場、デーモン化して残るプロセス、シグナルを他のプロセスへ。

- **順**: (1) サンドボックスなし(`-unsafe-host-exec` 相当)で、抜け道がそれぞれ成功することを確かめる(赤)。(2) サンドボックスの下で、すべて失敗する(緑)。
- hostile の crate は、**サンドボックス用の目印**(たとえば、サンドボックスが作業用の一時ディレクトリに置く、決まった名前のファイルと、環境変数)がないと何もしない。ホストで誤って動かないこと(目印がホストに残らない、rivus が `.rivus-hostile` を拒否する)は、今と同じ。
- Docker を前提にした試験(`Mountable`、`CargoVolume`、`NoDocker` など)は、サンドボックスで同じことを確かめる試験に置き換えるか、確かめる必要がなくなったことを ADR に書いて消す。

### 3.6 CI と、開発のマシンでの回し方

- `rust-isolation` ジョブ(Docker)は消す。macOS(Apple Silicon)の runner の、**別のワークフロー(`.github/workflows/isolation.yml`)**を足す。走るきっかけは、`push`(main)と `pull_request` が、隔離に関わるパスの変更のときだけ(`paths`)、`schedule` が週 1 回、`workflow_dispatch`、tag の `push`。試験は、Skip でなく必須(`RIVUS_REQUIRE_*` と同じ形)。パスの一覧は、`internal/sandbox/`、隔離を呼ぶ `cmd/rivus` のファイル、`extractor/rust/test/hostile/`、`extractor/rust/`、`extractor/rust/rust-toolchain.toml`、取得の前の検査、`go.mod` / `go.sum`、このワークフロー自身。`permissions`、`concurrency` は、今の `ci.yml` と同じ。必須のチェックにしない。パスの一覧の漏れを見つける試験を足す。
- 日々の確かめは、開発のマシン(macOS)で回す(`docs/rust-isolation.md` に、1 行のコマンドと環境変数を書く)。
- 既知のコードを読むジョブ(`test`、`dart`、`rust`)は、今のまま Linux のホスト。

### 3.7 OS ごとの動き

| OS | 信頼できないコード(既定) | 既知のコード |
| --- | --- | --- |
| macOS | サンドボックスの下で動かす | `-unsafe-host-exec` で直接 |
| Linux | **何も実行せずに止まる**(隔離の手段がないと言う) | `-unsafe-host-exec` で直接(CI はこれ) |

サンドボックスが使えないとき(`sandbox-exec` がない、プロファイルが読み込めない)も、**何も実行せずに止まる**。黙ってホストでの実行に切り替えない。ベンチの道具が持つ「ホストで読んでよいパスの許可リスト」は残す。

### 3.8 抜け道の一覧(試験の項目。advisor のレビュー SBX-1〜8)

各項目に、1 つ以上の試験を書く(サンドボックスなしで成功 → サンドボックスの下で失敗)。どの規則で止まるかを、1 行書く。

- **SBX-1 DNS**: ネットワークを拒否しても、名前解決のデーモンへの mach の問い合わせを許すと、問い合わせるホスト名にデータを載せて外へ出せる。**抽出も取得も、名前解決のサービスを許さない**。取得は、プロキシに `CONNECT ホスト名` を送る形で、cargo と git が自分で名前を解決しないことを測る。
- **SBX-2 設定の書き込み**: `cfprefsd` 経由の `defaults write`(あとで効く仕掛け)、`crontab`、LaunchAgents、シェルの rc を、名指しで試す。
- **SBX-3 UNIX ドメインソケット**: ssh-agent(`/private/tmp/com.apple.launchd.*/Listeners`)、`docker.sock`、ほかのエージェント。どの規則で止まるかを 1 行。
- **SBX-4 端末**: 子は `Setsid`(制御端末なし)、標準入力は `/dev/null`、`/dev/tty` を拒否。子の標準エラーを端末に流すときは、制御文字を落とす。
- **SBX-5 名前が見える範囲**: 中身の読みだけでなく、`ls ~`、`stat ~/.ssh/…`、`ls /Users`、`/Volumes`、`/Applications`。対象の親と兄弟(隣のリポジトリ)、外を指すシンボリックリンク。`~/.cargo`、`~/.gitconfig`、`~/.netrc`、`~/.config/gh` は名指し。**7 節の 3 は、「何が見えるか」の一覧にしてから、ユーザーに聞く**(「秘密ではない」を、こちらで決めない)。
- **SBX-6 後始末**: 目印の環境変数のほかの見つけ方(実行ファイルのパスと起動時刻、サンドボックスの下かどうかを外から調べる手段、子孫の一覧を取り続ける)を、1 回調べる。完全でないなら、**残ったプロセスがある、または確かめられなかった、を、出力と stderr に言う**(黙らない)。
- **SBX-7 構成**: Linux のコンテナから macOS のホストに移ると、`cfg(target_os)` と `build.rs` の分岐で、**読むコードが変わる**。「解析するのは macOS 向けの構成」と書き、**出力に、対象の構成(target triple)を出す**。Linux 向けにしかない分岐は、範囲の外になる(見逃しの向きの変化)。`--target` を指定して型検査だけする道が取れるかを、調べる。
- **SBX-8 小さい点**: コマンドラインツールがない機械での動き(明示のメッセージで止まる)。`rivus setup rust` は明示のコマンド(解析のコマンドが、断りなくネットワークに出ない)。ツールチェインの置き場所は、サンドボックスから**書き込めない**ことを試験。**プロファイルへの注入**: 対象が決めるパスを、プロファイルの文に連結しない(`-D` のパラメータで渡す)。対象のディレクトリ名に `")(allow default)("` を含める試験。**隔離の下か、ホストで直接かを、`summary` に出す**(PRINCIPLES 8 節の、まだ届いていない所)。

### 3.9 試験の一覧(段階 3。何を、どの無害な印で確かめるか)

**決まり**: (1) 赤(サンドボックスなしで成功する)の試験は、**開発のマシンで、隔離なしで動く**ので、成功の証拠は**無害な印**だけにする: 試験が作った偽の秘密のファイル、試験が立てた受け口、試験用の一意な名前(`rivus-sbx-<ランダム>`)の設定やジョブ。**本物の鍵、キーチェーン、ペーストボードの中身、本物の設定には、触れない**(読むなら、成否と長さだけを報告し、中身は取り込まない)。(2) **ネットワークに出る試験は、手元に立てた受け口(127.0.0.1 と、この機械の LAN のアドレス)だけ**。外へは出さない。(3) 作ったものは、試験の終わりに必ず消す(設定、ジョブ、ファイル、プロセス)。(4) hostile の crate は、今と同じく、**目印がなければ何もしない**(サンドボックス用の目印: サンドボックスが作業用の一時ディレクトリに置く決まった名前のファイルと環境変数。ホストには残らない)。

## 4. 進め方(段階。各段階の終わりで advisor のレビュー)

(**Docker での結果の保存場所**: `~/rivus-docker-baseline/`(`zoo-rust.json`、`rust-curated.json`、`commit.txt`)。**比べ終わるまで、消さない**。)

1. この文書(対応表、方針、試験の一覧)→ advisor のレビュー → 7 節をユーザーに。
2. **Docker での結果を取っておく**(`bench/zoo-rust`、`bench/rust-curated` の finding。Docker の経路を消す前。同一性の確認のため)。
3. 試験を先に書く(3.5。赤)。
4. 抽出の段階のサンドボックス → 取得の段階とプロキシ → ツールチェインと extractor の用意。
5. 既定を切り替え、Docker の経路(`docker/rust-extractor/`、`cmd/rivus/isolate*.go` のコンテナの部分、`-container-*` と `-rust-image`、CI の `rust-isolation`)を消す。CI に macOS のジョブ。
6. 文書と ADR(ADR-064 を一部覆す。**ユーザーの決定であることを書く**)、ADR-INDEX、PRINCIPLES 8 節の「現状」、README、`docs/rust-isolation.md`、`docs/DESIGN-fetch-network.md`。

## 5. 結果の同一性

隔離の方法を変えても IR は変わらないはず。`bench/zoo-rust` と `bench/rust-curated` の finding が、Docker のときと完全に同一であることを確かめる。比べる Docker の結果は、Docker の経路を消す前に取る(4 節の 2)。

## 6. やらないこと

Linux の隔離の新設(余地は残す)、Go と Dart の隔離(後で載せられるよう、言語を知らない部分を分ける)、tap と formula、`-unsafe-host-exec` の意味の変更。

## 7. 1 節の範囲を超えて「弱い」になる行(ユーザーに聞く案。advisor のレビューのあと)

ユーザーが受け入れた「弱い」は、強いメモリ・CPU・プロセス数の上限がないこと(と、非推奨の仕組みであること)。**次は、それ以外で、Docker より弱い所**:

1. **後始末**: `setsid` / 二重フォークで、プロセスグループを抜けたプロセスが、時間切れや終了のあとも残りうる(Docker は、コンテナごと消える)。手当て: 目印の環境変数での掃除(環境を空にして `exec` したものは見つからない)、試験。残る危険: 悪意のあるビルドスクリプトが、サンドボックスの下の(ファイルも、ネットワークも使えない)プロセスを、解析のあとも残せる。**そのプロセスは、サンドボックスの下のまま**で、ホストのファイルとネットワークには触れないが、CPU とメモリは使える。
2. **ユーザー境界がない**: 利用者と同じユーザーで動く(Docker は、非 root のユーザー)。守りは、プロファイルだけ。
3. **ホストのファイルが、システムの範囲で見える**(Docker は、イメージの外が存在しない)。秘密ではない情報(ホスト名、ユーザー名、システムのファイル)が見える。
4. **実行できるプログラムが、ホストに多い**(許可リストで絞る)。
5. **カーネルの攻撃面**(seccomp に当たるものがない)。

6. **解析する構成が、macOS 向けに変わる**(SBX-7): Linux のコンテナから macOS のホストに移ると、`cfg(target_os)` と `build.rs` の分岐で、読むコードが変わる。Linux 向けにしかない分岐は、範囲の外になる(見逃しの向きの変化)。手当て: 出力に target triple を出す。`--target` で Linux 向けに型検査する道を調べる。
7. **Linux では、信頼できないコードの Rust の解析ができなくなる**(Docker を消す帰結。ユーザーの決定に含まれているが、帰結として並べる)。

**advisor の意見**: 2、4、5 は受け入れ可。3 は「何が見えるか」の一覧(SBX-5 の試験で取る)を付けて聞く。1 は SBX-6 の調べのあとに聞く。**5 つ(と、6、7)とも、ユーザーに見せる**(脅威モデルの持ち主はユーザー)。

聞くときに並べるもの: 弱い所、代わりの手当て、残る危険(上のとおり)。
