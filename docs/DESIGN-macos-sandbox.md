# 設計: Rust の extractor の隔離を、Docker から macOS のサンドボックス(Seatbelt)に移す

> **状態: 実装済み(2026-11-23 に書き直した)。** ユーザーの決定(2026-11-22)の実行計画で、ADR-093 が ADR-064 を一部覆した。済んだもの: 抽出と取得の 2 段階のサンドボックス(`internal/sandbox/`、`cmd/rivus/isolate_sandbox_darwin.go`)、既定の切り替え、Docker の経路の削除(`docker/rust-extractor/`、`-container-*` と `-rust-image`、CI の `rust-isolation`)、CI の `sandbox` ジョブ(`ci.yml`)、Homebrew での配布(ツールチェインは keg の外の `$(brew --prefix)/var/rivus/rustup`)。**まだのものは、課題で持つ**: #110〜#122(後回しのハードニング)、#146(出力に target triple)、#147(ワークスペースの中の crate)、#148(Linux での Rust の扱い。8 節)。利用者向けの説明の正本は [rust-isolation.md](rust-isolation.md)、インストールは [DESIGN-install.md](DESIGN-install.md)。この文書は、設計の記録(1 〜 7 節)と、残る論点(8 節)。

## 0. ユーザーの決定と、前提

- **目的**: `brew install` だけで rivus を使えるようにする。その前段として、Rust の extractor の Docker への依存をなくす(tap と formula は、このあと別に)。
- **決めたこと**: Rust の抽出を、Docker のコンテナの代わりに、**macOS のサンドボックス(Seatbelt、`sandbox-exec`)**の下で動かす。**Docker の経路は、CI を含めて丸ごと消す**。対象の環境は macOS(Apple Silicon)。
- **ユーザーが承知のうえで受け入れたこと**: (1) `sandbox-exec` は、Apple が非推奨にしたまま動いている仕組み。(2) Docker の `--memory` / `--cpus` / `--pids-limit` に相当する**強い**上限がない(時間の上限、プロセスグループごとの kill などで代わりにする)。
- **上のほかに、Docker より弱くなる所が見つかったら、ユーザーに聞く**(セキュリティの制御の変更。PRINCIPLES 8 節、ADR-064)。7 節に、見つかったものを並べる。
- Linux: サンドボックスがないので、信頼できないコードの Rust の解析は、**何も実行せずに止まる**。既知のコードは `-unsafe-host-exec`(今もこのとおり。Linux での扱いの論点は 8 節)。

## 1. 手元で確かめたこと(2026-11-22、macOS 26.7.1、arm64。使い捨ての試行。コードは残していない)

`sandbox-exec -f <profile>`(`(version 1)(deny default)(import "/System/Library/Sandbox/Profiles/bsd.sb")` に、必要なものだけを足した最小のプロファイル)で:

| 試したこと | 結果 |
| --- | --- |
| 許したディレクトリの読み取り | できる |
| ホームの秘密の置き場(`~/.ssh`、`~/.rv_secret_test`)の読み取り | **拒否**(`Operation not permitted`) |
| `/tmp` とホームへの書き込み | **拒否**(許したもの以外) |
| ネットワーク(`curl http://1.1.1.1`) | **拒否** |
| 他のプロセスへの `kill`(自分のユーザーの `sleep`) | **拒否**(相手は生きたまま) |
| `launchctl list`、`pbpaste`(ペーストボード)、`security find-generic-password`(キーチェーン) | **失敗**(中身を得られない) |
| `osascript` で Finder に Apple Event を送り、Desktop にフォルダを作る | **失敗**(`Can’t get application "Finder" (-1728)`。フォルダは作られない)。**注意**: `tell application "Finder" to get name` は、この拒否の下でも `Finder` と答える(名前の解決だけで、Finder への通信ではない)。テストは、**副作用のあるもの**でやる |

(まだ確かめていないこと: `cargo check` とビルドスクリプト、C コンパイラとリンカが、プロファイルの下で動く最小の許可一覧。プロセスの数の増え方。デーモン化して残るプロセスの扱い。ローカルのプロキシだけへの接続の許可 `(allow network-outbound (remote tcp "localhost:PORT"))` が効くこと。これらは実装の段階 3〜4 で測り、表に書く。)

## 3. 設計

### 3.1 構成(言語と OS を知らない部分と、Seatbelt に固有の部分を分ける)

- `internal/sandbox/`(実装済み。サンドボックス関連を 1 か所に: CI のパス絞り込みのため)
  - **言語も OS も知らない部分**: 起動(新しいプロセスグループ)、時間と出力の上限、プロセスグループごとの kill、監視(メモリ、プロセス数)、後始末(目印)、取得の前の検査(対象の cargo の設定を読ませない、`Cargo.lock` / `Cargo.toml` の取得元の検査)。今の `cmd/rivus/isolate.go` の、言語を知らない部分を移す。
  - **Seatbelt に固有の部分**: プロファイルの生成と、`sandbox-exec` での起動。
  - **取得のプロキシ**: 許可リスト、解決したアドレスの検査、検査したアドレスへの接続。
  - Linux の実装は、**「隔離の手段がない」と表示して止まる**スタブ(`cmd/rivus/isolate_sandbox_other.go`)。あとで bubblewrap などを足せるよう、起動のインターフェースは 1 つ(8 節)。
- `cmd/rivus` の Rust 固有の部分(取得の段階の呼び出し、抽出の呼び出し、ツールチェインの固定)は、`internal/sandbox` を呼ぶだけにする。

### 3.2 プロファイル

- `(deny default)` + `bsd.sb` の import(1 節で確かめた)に、必要なものだけを足す。許したものには、1 行ずつ理由を書く(Go のテンプレートで生成し、生成した文をテストで読む)。
- 読み取り: 対象、取得した依存、固定のツールチェイン、extractor、作業用の一時ディレクトリ、コンパイルに必要なシステムの場所。ホームの残りは許さない。書き込み: 作業用の一時ディレクトリだけ。
- ネットワーク: 抽出は `(deny network*)`。取得は、ローカルのプロキシのポートだけ。
- `mach-lookup`: 既定拒否。必要なものだけ(ログなど)を許す。`process-exec`: 許可リスト。`signal`、`process-info*`: 自分のグループだけ。`sysctl-read`: 必要なものだけ(他のプロセスの引数や環境を読めないように。要測定)。
- 環境変数: ホストのものを渡さない。決めたものだけ(`CARGO_HOME`、`RUSTUP_HOME`、`RUSTUP_TOOLCHAIN`、`HOME`(作業用の一時ディレクトリ)、`TMPDIR`、`PATH`、取得のときは `CARGO_HTTP_PROXY` など)。

### 3.3 取得の段階のネットワーク

[DESIGN-fetch-network.md](DESIGN-fetch-network.md) の案(取得元だけを許すプロキシ)を、コンテナなしで実装する: プロキシは rivus の Go のプロセスの中(CONNECT)。許す宛先、解決したアドレスの検査(ループバック、プライベート、リンクローカル、ユニークローカル、CGNAT など)、検査したアドレスへの接続(DNS rebinding)、リダイレクトとサブモジュールの要求も毎回検査、は、その文書のとおり。サンドボックスが「ローカルのプロキシのポート以外へは出られない」を保証する(コンテナの専用ネットワークの代わり)。`TestIsolationFetchFollowsWhatTheAllowedRepositorySays`(今は「防げていない」と書いてある)を、「要求が出ない」ことを確かめるテストに反転させる。

### 3.4 ツールチェインと extractor の用意

固定の nightly(`nightly-2026-11-15`、`rustc-dev`、`llvm-tools`、`rust-src`)と extractor のビルドは、**サンドボックスの外で、信頼できるソース(rivus 自身)から**行う。対象のコードを使わない。用意の仕方は、**明示のコマンド `rivus setup rust -source <extractor/rust>`**(実装済み。解析のコマンドは、断りなくネットワークに出ない)。置き場所は、利用者のデータのディレクトリ(`~/Library/Application Support/rivus/rust/`)。Homebrew では、formula がインストールの中で同じものを作る(ツールチェインは keg の外の `$(brew --prefix)/var/rivus/rustup`、`rivus-rust` は keg の `libexec`。理由と手順は DESIGN-install.md の 6 節)。用意の段階のダウンロード(rustup、crates.io)は、rivus のソースの `Cargo.lock` で固定したもの。

### 3.5 テスト(先に書く。赤を確かめる)

`TestIsolationHostileBuild` が試していることを、すべてサンドボックスでも試す(見えるもの、止まらない `build.rs`、フォークの無限ループ、メモリを使い切る、IR の断片のディレクトリの、リンクと大きなファイル、鍵、隣のファイル、ネットワーク、書き込み、環境変数、…)。加えて、macOS に固有の抜け道(2 節の最後の行): `open`、`osascript`(**副作用のあるもの**で: 1 節の注意)、`launchctl`(サンドボックスの外にプロセスを残す)、ペーストボード、キーチェーン、ホームの秘密の置き場、デーモン化して残るプロセス、シグナルを他のプロセスへ。

- **順**: (1) サンドボックスなし(`-unsafe-host-exec` 相当)で、抜け道がそれぞれ成功することを確かめる(赤)。(2) サンドボックスの下で、すべて失敗する(緑)。
- hostile の crate は、**サンドボックス用の目印**(たとえば、サンドボックスが作業用の一時ディレクトリに置く、決まった名前のファイルと、環境変数)がないと何もしない。ホストで誤って動かないこと(目印がホストに残らない、rivus が `.rivus-hostile` を拒否する)は、今と同じ。
- Docker を前提にしたテストは、サンドボックスで同じことを確かめるテストに置き換えた(`internal/sandbox` の `red_darwin_test.go`、`green_darwin_test.go` ほか、`cmd/rivus/isolate_sandbox_darwin_test.go`)。

### 3.6 CI と、開発のマシンでの回し方

### 3.7 OS ごとの動き

| OS | 信頼できないコード(既定) | 既知のコード |
| --- | --- | --- |
| macOS | サンドボックスの下で動かす | `-unsafe-host-exec` で直接 |
| Linux | **何も実行せずに止まる**(隔離の手段がないと表示する) | `-unsafe-host-exec` で直接(CI はこれ) |

サンドボックスが使えないとき(`sandbox-exec` がない、プロファイルが読み込めない)も、**何も実行せずに止まる**。何も報告せずにホストでの実行に切り替えることはしない。ベンチの道具が持つ「ホストで読んでよいパスの許可リスト」は残す。

### 3.7a 決まり(2026-11-22。事故のあと)

- **rivus は、自分が起動したプロセスグループの外のプロセスに、シグナルを送らない。** 探して kill する後始末は、作らない(利用者の機械で、見つけ方の誤りが、そのまま利用者のプロセスの kill になる仕組みは、得るものより危険が大きい)。後始末は、プロセスグループごとの kill(`Setsid` で作った自分のグループだけ)と、**残ったかもしれないことを報告すること**(`Result.MayHaveLeftProcesses`。出力と stderr に)。見つける処理を残すなら、列挙して報告するだけ(PID、名前、起動時刻)で、kill は利用者がする。(事故: 「サンドボックスの下で、実行専用の目印のファイルを読める」ことで残りを見つけて kill する処理が、ほかのサンドボックスのアプリ約 120 個に該当した。)
- **利用者の環境に作用するテスト(シグナル、設定、ジョブ、ほかのアプリへの依頼)は、最初の実行の前に、「どのプロセスに、何をするか」を 1 行で、相談役に送る。** ドライランで、該当したものの名前を目で確かめてから、有効にする。
- **プロファイルの各行に、「拒否が実際に効いている」ことのテストを対応させる**(行を書いただけで安心しない)。測ったこと: **`(deny mach-lookup)`(フィルタなし)は、効かない**(システムの基本のプロファイルの、フィルタつきの許可を、取り消さない)。効く書き方は、`(deny mach-lookup (global-name-regex #"."))` と `(deny mach-lookup (xpc-service-name-prefix ""))`(`security authorizationdb read` が拒否された)。`(deny file-read* (subpath HOME))` は効く(ホームの名前も、中身も)。`/Users`、`/Volumes`、`/Applications` の名前は、`(deny file-read-metadata (literal ...))` で効く。**`kern.procargs2` の拒否は、どの書き方も効かない**(上の表)。

### 3.7b 本番の形の決定(2026-11-22。advisor のレビュー)

- **rivus 専用の `CARGO_HOME`**(固定のツールチェインと同じ、rivus のデータのディレクトリの下)。**取得の段階だけが書き、抽出の段階は読み取り専用**。**`~/.cargo` は、どちらの段階でも、読みも書きもしない**(`~/.cargo/config.toml`、`credentials.toml`、`registry` を含めて、拒否のテスト)。(スパイクは、`~/.cargo/registry` を読ませて、動くことを確かめただけ。)実行ごとに作り直すか、使い回すかは、時間を測ってから(使い回すなら、「抽出の段階から書けない」ことのテストが、キャッシュの汚染を防ぐ根拠になる)。
- **実行の許可は、ディレクトリでなく、名指しのプログラム**(`Spec.ExecFiles`)。スパイクで、`/bin/sh`、`/usr/bin/cc`、`clang`、`ld`、`ar`、`xcrun`、`xcode-select` と、ツールチェインと CommandLineTools のディレクトリだけで、`bench/zoo-rust` と `bench/rust-curated` が抽出できた(`/usr/bin` と `/bin` の全体は、不要だった)。一覧にないものの実行が失敗することをテストする。ビルドスクリプトが作った実行ファイル(作業ディレクトリの中)の実行は、許す必要がある: そこは、対象のコードの実行そのものなので、絞れない。
- **実行時に rustup を使わない**(`RIVUS_RUST_DIRECT=1`: extractor が `+toolchain` なしで呼ぶ)。固定のツールチェインの `bin` を `PATH` に置く。
- **extractor のバージョンの確認**(課題 #109): バージョンが合わなければ止まる。
- **同一性の確認の結果**(2026-11-22): `bench/zoo-rust`(174 件)、`bench/rust-curated`(280 件)で、サンドボックスで抽出した IR の finding の ID が、**Docker(イメージを今のソースから作り直したもの)と一致**。ホストの直接とも一致。最初の基準(298 / 597)は、古いイメージのもので、間違いだった(`~/rivus-docker-baseline/v2/` が正)。**target は、Docker(Linux)とサンドボックス(macOS)で違う**: zoo は OS で分かれるコードを持たないので一致したが、`cfg(target_os)` で分かれるコードでは、読む関数が変わる。SBX-7 のテストで、数字を 1 つ出す。

### 3.7c SBX-7 の数字(2026-11-22)

`extractor/rust/test/cfg_os`(`cfg(target_os)` で分かれる、関数 3 つの crate)を、Docker(Linux)とサンドボックス(macOS)で抽出した: **Docker は `cfg_os::everywhere` と `cfg_os::only_on_linux`、サンドボックスは `everywhere` と `only_on_macos`**。読むコードが変わる(同一性の確認が一致したのは、zoo と rust-curated が、OS で分かれるコードを持たないため)。出力に target triple を出すことは、まだしていない(課題 #146)。**ワークスペースの中の crate**(祖先に `Cargo.toml` があり、cargo がワークスペースを探す)は、サンドボックスでは、祖先のディレクトリを読めないので、`failed searching for potential workspace` で落ちる(Docker は、対象のディレクトリの外が見えないので、同じ制限: 外の path 依存は見えない)。祖先の `Cargo.toml` を名指しで許すだけでは、足りなかった(`.cargo/config.toml` の探索などが、EPERM になるため)。課題 #147(関連: #120)。

### 3.8 抜け道の一覧(テストの項目。advisor のレビュー SBX-1〜8)

各項目に、1 つ以上のテストを書く(サンドボックスなしで成功 → サンドボックスの下で失敗)。どの規則で止まるかを、1 行書く。

- **SBX-1 DNS**: ネットワークを拒否しても、名前解決のデーモンへの mach の問い合わせを許すと、問い合わせるホスト名にデータを載せて外へ出せる。**抽出も取得も、名前解決のサービスを許さない**。取得は、プロキシに `CONNECT ホスト名` を送る形で、cargo と git が自分で名前を解決しないことを測る。
- **SBX-2 設定の書き込み**: `cfprefsd` 経由の `defaults write`(あとで効く仕掛け)、`crontab`、LaunchAgents、シェルの rc を、名指しで試す。
- **SBX-3 UNIX ドメインソケット**: ssh-agent(`/private/tmp/com.apple.launchd.*/Listeners`)、`docker.sock`、ほかのエージェント。どの規則で止まるかを 1 行。
- **SBX-4 端末**: 子は `Setsid`(制御端末なし)、標準入力は `/dev/null`、`/dev/tty` を拒否。子の標準エラーを端末に流すときは、制御文字を除去する。
- **SBX-5 名前が見える範囲**: 中身の読み取りだけでなく、`ls ~`、`stat ~/.ssh/…`、`ls /Users`、`/Volumes`、`/Applications`。対象の親と兄弟(隣のリポジトリ)、外を指すシンボリックリンク。`~/.cargo`、`~/.gitconfig`、`~/.netrc`、`~/.config/gh` は名指し。**7 節の 3 は、「何が見えるか」の一覧にしてから、ユーザーに聞く**(「秘密ではない」を、こちらで決めない)。
- **SBX-6 後始末**: 目印の環境変数のほかの見つけ方(実行ファイルのパスと起動時刻、サンドボックスの下かどうかを外から調べる手段、子孫の一覧を取り続ける)を、1 回調べる。完全でないなら、**残ったプロセスがある、または確かめられなかった、を、出力と stderr に書く**(必ず報告する)。
- **SBX-7 構成**: Linux のコンテナから macOS のホストに移ると、`cfg(target_os)` と `build.rs` の分岐で、**読むコードが変わる**。「解析するのは macOS 向けの構成」と書き、**出力に、対象の構成(target triple)を出す**。Linux 向けにしかない分岐は、範囲の外になる(見逃しの向きの変化)。`--target` を指定して型検査だけする方法が取れるかを、調べる。
- **SBX-8 小さい点**: コマンドラインツールがない機械での動き(明示のメッセージで止まる)。`rivus setup rust` は明示のコマンド(解析のコマンドが、断りなくネットワークに出ない)。ツールチェインの置き場所は、サンドボックスから**書き込めない**ことをテスト。**プロファイルへの注入**: 対象が決めるパスを、プロファイルの文に連結しない(`-D` のパラメータで渡す)。対象のディレクトリ名に `")(allow default)("` を含めるテスト。**隔離の下か、ホストで直接かを、`summary` に出す**(PRINCIPLES 8 節の、まだ届いていない所)。

## 7. 1 節の範囲を超えて「弱い」になる行(ユーザーに聞いた。結果は ADR-093 の「承知している弱さ」。以下は、聞いたときの並べ方)

ユーザーが受け入れた「弱い」は、強いメモリ・CPU・プロセス数の上限がないこと(と、非推奨の仕組みであること)。**次は、それ以外で、Docker より弱い所**:

1. **後始末**: `setsid` / 二重フォークで、プロセスグループを抜けたプロセスが、時間切れや終了のあとも残りうる(Docker は、コンテナごと消える)。対策: 目印の環境変数での掃除(環境を空にして `exec` したものは見つからない)、テスト。残る危険: 悪意のあるビルドスクリプトが、サンドボックスの下の(ファイルも、ネットワークも使えない)プロセスを、解析のあとも残せる。**そのプロセスは、サンドボックスの下のまま**で、ホストのファイルとネットワークには触れないが、CPU とメモリは使える。
2. **ユーザー境界がない**: 利用者と同じユーザーで動く(Docker は、非 root のユーザー)。防御は、プロファイルだけ。
3. **ホストのファイルが、システムの範囲で見える**(Docker は、イメージの外が存在しない)。秘密ではない情報(ホスト名、ユーザー名、システムのファイル)が見える。
4. **実行できるプログラムが、ホストに多い**(許可リストで絞る)。
5. **カーネルの攻撃面**(seccomp に相当するものがない)。

6. **解析する構成が、macOS 向けに変わる**(SBX-7): Linux のコンテナから macOS のホストに移ると、`cfg(target_os)` と `build.rs` の分岐で、読むコードが変わる。Linux 向けにしかない分岐は、範囲の外になる(見逃しの向きの変化)。対策: 出力に target triple を出す。`--target` で Linux 向けに型検査する方法を調べる。
7. **Linux では、信頼できないコードの Rust の解析ができなくなる**(Docker を消す帰結。ユーザーの決定に含まれているが、帰結として並べる)。

**advisor の意見**: 2、4、5 は受け入れ可。3 は「何が見えるか」の一覧(SBX-5 のテストで取る)を付けて聞く。1 は SBX-6 の調査のあとに聞く。**5 つ(と、6、7)とも、ユーザーに見せる**(脅威モデルを決めるのはユーザー)。

聞くときに並べるもの: 弱い所、代わりの対策、残る危険(上のとおり)。

## 8. Linux での Rust の extractor の扱い(論点。課題 #148)

rivus の Rust の extractor は、対象を `cargo check` でビルドするので、対象と依存の `build.rs` と proc macro を実行する。Linux には、隔離の手段がない。

**線(決定。MODEL-RUNBOOK.md の 0 節、MODEL-QUEUE.md): 隔離なしでは、取得したクレートのビルドスクリプトとマクロを実行しない。** 今の動作:
- `-lang rust` は、サンドボックスがないと何も実行せずに止まる。`-unsafe-host-exec` だけが通る(ADR-093、rust-isolation.md)。auto では読まない(`no-sandbox`)。
- CI の `rust` ジョブは、このリポジトリのコード(ベンチ、zoo、`extractor/rust/test`)だけを、`-unsafe-host-exec` で読む。取得した第三者のクレートは読まない。
- クラウドの定期実行のモデル作成(`rivus-model-author`)は、Rust のモデルについて、**モデルは書き、extractor を使う確認は CI に任せる**。取得したクレートを読む差分テストの Rust 版は、隔離のあるジョブに限る。

**Linux の隔離の調査**(DESIGN-package-models.md の 6.5 節。実測はしていない):
- bubblewrap(`bwrap`)が最有力。名前空間でファイルとネットワークを絞れ、取得はネットワークあり、抽出は `--unshare-net` の 2 段階にできる(macOS のプロファイルと同じ形)。
- `unshare` は、同じ名前空間でファイルの絞り込みを自分で組む必要がある。gVisor は、コンテナの外から使うもので、クラウドのセッションの中では使えない。
- **クラウドのコンテナの中では、非特権のユーザー名前空間が使えないことが多く、`bwrap` が動くかは、環境で確かめるまで分からない(未確認)。** 動かないなら、特権のあるホスト(VM)が要る。コンテナそのものを隔離として使うのは、セッションの資格情報が同じコンテナにあるので、勧めない。
- 足すなら、`internal/sandbox` に Linux の実装を足す(起動のインターフェースは 1 つ。3.1)。macOS の 2 節の対応表と同じ形で、弱くなる所を並べ直して、ユーザーに聞く(ユーザー境界、カーネルの攻撃面など)。

**Go と Dart の extractor** は、既知の隔離の外にある(`go list` の cgo、`dart pub get` と `build_runner`)。ここでの線は Rust だけを扱う。
