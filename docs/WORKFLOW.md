# 進め方のルール

設計の判断の基準は [PRINCIPLES.md](PRINCIPLES.md)。ここには、PR、測定、記録、マージのルールだけを書く。
- **PR のタイトルと本文、コミットのメッセージにも、用語チェックのルールを適用する。** PR を立てる前に、タイトルと本文を一時の `.md` に書いて `regomark check` に通す(用語チェックのフックは `.md` を書いたときだけ効くため)。
- **PR の本文の雛形は `.github/pull_request_template.md`(Summary、Background / Motivation、確認の欄)。** 確認の欄の項目に当たる PR は、該当する行を本文に残す。
- **作業の順**は `.claude/work/QUEUE.md`(追跡されない。相談役が書く)。コストか精度を上げる作業は、始める前に、課題の「修正の方向」に「これで動くはずの数字」を 1 行書く。マージのあとに台帳の行と比べ、外れたら課題にそう書く。
- **memos の前後の測定**(`bench/compare.sh --cost-check memos`。交互に 2 回ずつ)が必要なのは、(i) 「結果は同一」と言う PR(速さとメモリ)、(ii) 何度も通る関数に触る PR だけ。関数は `internal/taint` の `add`、`copyLoc`、`copyLocs`、`copyLocsNoted`、`copyLocsGuarded`、`copyLocsAlias`、`applySummary`(呼び出しの数をコードで確かめた)。それ以外の解析の PR は、PR の CI(`TestScaleSynth`、zoo、curated)で足りる。
- **メモリとコストの変更は、グラフの表現(IR、エッジと候補、関数ごとの要約)が前後で同じことを示す。違うなら、それは精度の変更として扱う。** 示すのは `bench/compare.sh --graph-check <対象の名前、カンマ区切り> <base> <head>`(zoo、curated、go-synth-S、memos など。Dart は `dart-curated` と `zoo-dart`。Rust は `zoo-rust` だけで、macOS の隔離の下で動かす(各バージョンの extractor が自分の木のものを隔離の下で head のコードの IR にし、`index -ir` と `analyze -ir` がそれを読む。`-unsafe-host-exec` は使わず、隔離が効いていること(`summary.isolation.mode` が `sandbox`)を毎回確かめ、満たされなければ失敗にする。macOS 以外では NOT RUN)。zoo-dart はパス上限で止まるセルがあるので、`convergence: NOT CONVERGED` の行が出て終了コードは 4(それ以外は同じで、収束だけが欠ける。止まった時点の状態を比べたもの。手元では合格にしない。一部を比べていないときの 3 は、4 より優先する。zoo-go と zoo-rust も同じ(zoo-rust は `state/global-chain`)。定期 CI は対象ごとに別の呼び出しにして、4 を許すのは zoo-go だけ(#217。zoo-rust は手元だけで、定期 CI には入れていない)。go-std10 と go-curated は 0 だけ。1、2、3 はどの対象でも失敗にする)。同じコードを前後のバイナリで解析して、IR、エッジ、要約のハッシュ、finding、uncertainty を比べる。finding と uncertainty は集合としての比較に加えて、出力の順序のままの比較(`findings-order`、`uncertainties-order`)もする。同一なら 1 行ずつ `same`。`scc_coarsened` の行は、`-scc-coarsen`(既定 5500 の依存の関数)で粗くした SCC の数で、当てない対象は両方 0 で `same`、当たる対象(dart_services、dart-pub)は `DIFFERENT` になり、差を精度の変更として分類する。当てない対象が 0 でなくなったら、依存の更新で N に届いた合図)。finding の件数が変わらないことは、これの代わりにならない。PR の本文に、同一だった対象を書く。
- **言語共通のコード(`internal/valuecalls`、`internal/taint`、`internal/sg`、`internal/ir`、`internal/callgraph` など、特定の言語の extractor でないもの)を変える PR は、Dart や Rust 向けの修正でも、Go の `bench/compare.sh --graph-check`(go-std10 と go-curated は必須、memos はロックが空いていれば)の結果を本文に付ける。** 言語共通なので、Dart 向けの `valuecalls` の修正(#465、#466、#471)が Go の memos の edges に 1 本足した(#471 のあとの確認で見つけた)。結果が変わる修正では `--graph-check` が DIFFERENT になるので、差が「見逃しが減った向きだけ」であることを本文で分類する。
- **測定から結論を出すとき**: `bench/compare.sh` は、1 回だけの測定を「single run: no conclusion」と出し、結論にしない。手で測るときは、交互に 2 回以上(A、B、A、B)。ロードアベレージ、方法(主なプロセスか木の合計か)、コミットを付け、「疑い」と「確認した」を分ける。時間を比べる実行は、測定の道具(反復ごとのダンプ `RIVUS_INTERNAL_SUMMARY_DUMP_EACH_ITER`、プロファイル、`RIVUS_TMP_BUDGET_LOG` など、解析の速さに効くもの)の有無を揃え、台帳(`bench/heavy-ledger.tsv`)の `settings` の列に書く(反復ごとのダンプつきの実行は、ダンプなしの実行より、後半のラウンドが数倍遅く、「収束しない」と見えたことがある。`dart_services`、2026-11-24)。
- **重い測定の記録**は台帳(`bench/heavy-ledger.tsv`、`bench/heavy_ledger.py`)だけ。数字は本文に写さず、行を日付とコミットで指す。道具が書いた行は、その日のうちに、1 つの PR で main に入れる(main に無い行は、記録として扱わない)。重い実行は、ロックの下で 1 本ずつ(`bench/heavylock.py`)。台帳には、1 つの SCC が持つ依存の関数の最大の数(`largest_scc_deps`)と、粗くした SCC の数(`scc_coarsened`)を毎回記録する(`-scc-coarsen`、ADR-124)。合格基準の行(`make bench-passline`)は、当てない対象で `coarsened=0/0` を確かめる(`bench/deps-targets.json` の `expect_coarsened`)。
- **時間の判定**: 合格基準 D(と時間の余裕の議論)の判定は、静かな状態で 3 回の中央値(`bench/deps_bench.py -repeat 3`)。開始と終わりの負荷(`uptime` の 1 分、5 分、15 分)と、同時に動いていた重いプロセス(CPU 20% 以上の上位 5 件のコマンド名)は、道具が台帳の `settings` に書く。ロックはロックを取らない実行(ビルド、ほかのセッション)を止めないので、ロックだけでは静かと言えない(`dart_services` で、静かと報告された実行の wall と解析の時間が、同じ設定の別の実行と大きく違ったことがある)。
- **合格基準の確認の頻度(ユーザーの決定、2026-11-25)**: C(Gitea)と cocoon は、`internal/taint`、`internal/sg`、Dart の `extractor/` などを変える PR で、パスで絞った手元の確認に入れる(`make bench-passline TARGETS="cocoon gitea"`)。G12 の警告(下)が出た PR では必ず回す。定期(週 1 回)は A、C、D、cocoon の全部。該当するパスの PR は、本文に 1 行「cocoon と Gitea の確認: 済み / 不要の理由」を書く(強制はしない)。
- **Rust の行(`shlex`。INFO。合格基準ではない)**: `bench/deps-targets.json` の `shlex`(依存 0 の公開 crate)は、Rust の流れ(取得、隔離の下のコンパイル、extractor、解析)が、道具の中で端から端まで通ることを確かめる行。`decided: false`、検出は n/a、`make bench-passline` の既定の対象に入れない(`TARGETS=shlex` と名前で指す)。収束と uncertainty の kind ごとの件数(`unsupported_construct` と `unresolved_callee` は 0 でも書く)を台帳の `settings` に書く。時間とメモリは書くが、意味のある値ではない(小さい crate)。毎回、道具が確かめる: 取得した木に `.cargo/config(.toml)`、`rust-toolchain(.toml)` があれば実行しない、`HOME` は `BENCH_CACHE` の中の空のディレクトリ(共有の場所に書かない)、実行の前に `sandbox-exec` が書き込みを拒否すること、実行後に `summary.isolation.mode` が `sandbox` であること(どちらかが満たされなければ失敗、終了コード 1)。`Cargo.lock` が無い依存 0 の crate だけ、最小の lock(`version = 4` と `[[package]]` 1 つ)を複製に書く(`cargo generate-lockfile` は実行しない)。
- **G12(コストの退行の警告。警告だけで、停止の門ではない)**: `internal/taint`、`internal/sg`、`internal/ir`、`internal/callgraph`、Dart の `extractor/`、`bench/` のどれかを変える PR の CI(ジョブ `cost-warn`)が、小さい対象(go-curated、dart-curated、go-synth-S、dart-synth の S、M、F)を base と head で解析し、`adds_total`、`adds_max_function_total`、`passes`、`largest_scc` のどれかが +10% 以上になると `::warning::` を出す(ログとジョブの summary。ジョブは失敗にしない)。手元は `bench/compare.sh --only go-curated,dart-curated,go-synth-S,dart-synth-S,dart-synth-M,dart-synth-F --cost-rounds 1 <base> <head>`。警告の記録を 2 週間見てから、門にするかを決める。
  - 記録(新しい台帳は作らない): G12 の警告が出た PR は、本文に 1 行「G12 の警告: n 件、手元の重い実行で本物だったか: はい / いいえ / 未確認」を書く(固定の文字列「G12 の警告:」。`gh pr list --search "G12 の警告" --state merged` で読める)。2 週間(2026-12-09 ごろ)後に、advisor が警告が出た PR の件数と本物だった件数を集計し、停止に上げるかをユーザーに聞く。
- **調査の途中の記録**は、追跡されない作業メモ(`.claude/work/`。課題ごとに 1 ファイル)に置き、課題には、結論が出たときに 1 回だけ書く。公開の場所には、外部の設計者の返事のファイル名ではなく、何を、なぜ決めたかを書く。課題と ADR への追記は、作業の PR に含める。作業の PR に入れられない文書の変更は、まとめて 1 日 1 本。
- **道具が守るもの**:
  - 1 日の報告の最後に、`make daily-stats SINCE=<日付>` の 1 行(解析・モデル・extractor の PR の数と、それ以外の数)を付ける。
  - マージ済み(または閉じた)PR のブランチへの push は、`.githooks/pre-push` が止める(有効にするのは `make setup`。意図した push は `RIVUS_ALLOW_PUSH_TO_MERGED=1`)。`daily-stats` の `orphan remote branches: N` が 0 でなければ、取り込むか消す。
  - `make merge PR=<n>`(`scripts/merge-pr.sh`)は、main の最新の `ci.yml`(push)が失敗しているとマージしない。main の CI を直す PR だけ `RIVUS_MERGE_FIXES_MAIN=1`。PR は `-short` なので、重いテストは main でしか実行されない。限界: 失敗するコミットの CI が実行中の間は、その前の成功を見て通る。
  - 定期の CI の失敗で `main-ci`(`.github/workflows/main-ci.yml`、判定は `scripts/main-ci/decide.go`)が失敗になったとき、手動実行(`gh workflow run ci.yml --ref main`、workflow_dispatch)が成功すれば、定期の失敗は解消する(`main-ci` は、定期または手動の、最後に完了した実行が成功なら、失敗の 24 時間のブロックを外す)。定期は毎週月曜 03:17(UTC)だけなので、待つとその日まで続く。
  - `main-ci` が失敗になるのは、(1) main の push の CI のうち、完了した最新のもの(取り消しは飛ばす)が失敗のとき。実行中の CI は待たず、直前の結果で決める(実行中の CI が失敗で終わると、完了の通知で失敗に変わる)、(2) 定期または手動の、最後に完了した実行が失敗で、24 時間以上たったとき。`fixes-main` のラベルが付いた PR は、`main-ci` が(どちらの場合も)成功になり、ブロックから外れる。ラベルを付けるのは、main の CI の失敗を直す PR だけ。ラベルを付けても、PR の `main-ci` は次の `main-ci` の実行まで更新されない(最大 1 時間)ので、`gh workflow run main-ci.yml` で今すぐ更新できる。手元のマージで同じ扱いにするのは `RIVUS_MERGE_FIXES_MAIN=1`(上の `make merge`)。
  - **ユーザーがマージする PR**: ガードレールの部品(workflow、hook、`.claude/settings*`、プロンプト、`.regomark/`、ghmint、ruleset、`scripts/merge-pr.sh` など)を変える PR は、`make merge` が断り、ユーザーがマージする。部品の一覧は [`.github/guardrail-paths`](../.github/guardrail-paths)(1 行 1 パターン。そのファイル自身も含む。一覧が無い・読めないときも断る)。
  - 既定で off の機能の一覧は、コードとテストが持つ。規則は([PRINCIPLES.md](PRINCIPLES.md) 7 節の「既定で off の機能(フラグ)の持ち方」、`cmd/rivus/flagsides.go`)。
- **相談役が読む PR**は、(i) 解析の結果を変える PR、(ii) 出力の項目・uncertainty と不確実性の種類・`summary`・終了コードを変える PR だけ。結果が同一であることを数字で示した PR、道具、文書は読まない。マージは開発者が行う(`ci-ok` のあと、マージコミット)。
