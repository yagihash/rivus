# 設計判断記録（ADR）

rivus の設計判断を、後から経緯を追えるように記録する。
形式は「状況 → 決定 → 理由 → 帰結」。出典は次の 2 種類。

- **ブリーフ**: 初期ブリーフで決まっていたこと
- **レビュー**: ブリーフへの質問（`QUESTIONS.md`）と回答を経て決まった、または訂正されたこと

全 ADR の状態は「採用」。覆すときは新しい ADR を追加して旧 ADR を「置換」にする。

## ADR-001: 事実を出し、判定はしない

- **状況:** プライベートコードのファイル跨ぎ taint 解析を無償で行える選択肢がなく、最終的な正誤判定は LLM や人間が行う前提で使う。
- **決定:** rivus は「到達可能性に関する事実を問い合わせるクエリエンジン」であり、安全か危険かは決めない。
  決定論的に確定できる事実だけを構造化して出し、確定できなかった理由を分類して残す。
  過大近似は維持する。**列挙は網羅的に、判定は保留する。**
- **理由:** 完全な精度（経路感度、エイリアス解析の完全性）を追わずに済む。
  LLM に判定させる前提なら、判定に必要な材料を揃える方が投資対効果が高い。
- **帰結:** 非目標: 判定を下すこと、完全な経路感度、シンボリック実行・SMT 連携、完全なエイリアス解析、
  暗黙的フロー（制御依存）の追跡、Dart / Rust フロントエンドの自作、対象言語のビルド・コード生成の面倒を見ること、IDE 統合 / Web UI / SaaS 化。
  「LLM が後で落としてくれるから見逃してよい」とはしない。

## ADR-002: extractor と解析エンジンの分離

- **状況:** 言語ごとのフロントエンド（型解決・トレイト解決・手続きマクロなど）を Go で再実装するのは非現実的。
- **決定:** CodeQL や Joern と同じ構造にする。言語ごとの extractor（Go / Rust / Dart それぞれの言語の道具で書く）が中立 IR を出し、Go 製のコアエンジンが解析する。
- **理由:** 型解決・名前解決・パッケージ解決は各言語の公式の道具（`go/packages`、`rustc`、`package:analyzer`）に任せるのが最も確実。
- **帰結:** 責務の境界は「言語固有の知識が要るか」。CFG 構築まで（言語固有の脱糖を含む）が extractor、SSA 化から先がコア。

## ADR-003: IR は φ なしの CFG ＋ 書き換え可能ローカル変数

- **状況:** AST レベルで切ると構文差が大きすぎる。SSA レベルで切ると SSA 化を 3 言語ぶん書くことになる。
  さらに `go/ssa` は SSA 化済み（φ 入り）、Rust の MIR は SSA ではなくローカル変数の書き換え形、と形が揃っていない。
- **決定:** IR は**CFG のレベル**で切り、**φ を持たない**。値は書き換え可能なローカル変数で表す。SSA 化（dominator 計算と φ 挿入）はコアに一本化する。
  Go extractor は `ssa.NaiveForm` で `Alloc` / `Store` / `Load` が残る形を取る。
  lifted 版の `go/ssa`（NaiveForm なし）は捨てず、**コアの SSA 化の differential test の oracle** にする。
- **検討した代替:** IR に `phi` を任意で許し、コアの SSA 化を冪等にする案。
  `NaiveForm` により Go 側の追加コストがなくなったため、IR を複雑にするだけの利点がないとして不採用。
- **理由:** 制御構造は CFG まで下げると言語差がほぼ消える。3 言語が同じ抽象度に揃い、IR 設計が単純になる。
  SSA 化は言語非依存のグラフアルゴリズムなので一度だけ書けばよい。
  SSA 化は自作部分で最もバグを埋め込みやすく、症状が分かりにくいため、実績のある実装を正解として持つ価値が大きい。
- **帰結:** 命令セットは当初見積もりの 15 種類程度ではなく 26 種（ARCHITECTURE.md 2.3）。
  `slice` は独立命令にせず `copy` の `view` フラグに畳み（構文として存在するのは主に Go で、汚染の意味は `copy` と同じため）、
  `global_load` / `global_store` は独立させる（関数サマリの境界と `global_var` の書き込み箇所の列挙に必要なため）。
  `async` / `await` と例外は CFG のエッジで表し、`go` / `defer` / `await` は `call` のフラグで表す。
  イテレータなど言語固有の構文は extractor が脱糖する。分岐条件は式言語を作らず、値への参照 ＋ ソース範囲で持つ。

## ADR-004: bottom-up の関数サマリ（functional approach）

- **状況:** 汎用の IFDS を実装すると重い。
- **決定:** コールグラフを SCC に縮約し、トポロジカル順（呼び先から）に関数サマリを算出して、呼び出し側で展開する（SCC 内のみ不動点まで反復）。
  これは Sharir & Pnueli (1981) の **functional approach** であり、IFDS の tabulation の非形式版ではない。
  「IFDS の summary edge に相当するものを functional approach で計算する」と表現を統一する。
- **理由（単なる用語の問題ではなく、方式選択の根拠）:**
  rivus の要件 4.2「ある sink に到達し得る source の列挙」は **seed となる source を与えずに投げるクエリ**である。
  tabulation は entry point と seed fact から前向きに探索する設計なので、この形に素直に乗らない。
  bottom-up の functional approach は全関数の完全なサマリを先に作るので、source 側・sink 側どちらからでも引ける。
  つまり rivus の目玉機能のために bottom-up を選んでいる。
- **帰結:** サマリは関数単位で独立させる（将来の増分解析の土台。ADR-021）。

## ADR-005: 汚染はラベル集合で持つ

- **決定:** ブール値ではなく `map[Value]LabelSet`。sanitizer は特定ラベルだけを落とし、sink は特定ラベルにのみ反応する。
- **理由:** HTML 用にエスケープした値を JS コンテキストの sink に流したら安全ではない、というミスマッチが実務で頻出する。
  設計の初期から入れておかないと後で入れられない。

## ADR-006: 値依存サニタイズの扱いと条件ガード

- **状況:** `func render(s string, escape bool)` のように、引数の値で sanitize するかが変わる関数がある。完全な経路感度は実装しない。
- **決定:** 対応の優先順は次のとおり。
  1. 手書きモデルによる上書き（最優先）
  2. 値依存ノードとして記録し、判定を LLM に委ねる（中核）
  3. 余裕があればサマリの特殊化（引数がリテラルなら定数値ごとに別サマリ）
  述語付きサマリ、シンボリック実行、SMT は実装しない。
  2 を実現するため、サマリの各 Flow に**条件ガード**を付ける。
  - ガードに記録するのは**関数の引数に由来する条件だけ**。ローカルの分岐（ループカウンタの比較など）は含めない
  - 判定は「その条件値が引数からのデータフローで到達可能か」。taint ソルバを流用する（source = 引数、sink = 分岐条件）
  - 1 サマリあたり約 4 個を上限とし、超えたらガードなしの過大近似（全経路の和集合）に畳み、`attributable_to: rivus` の不確実性として記録する
- **理由:** 呼び出し側が制御できるのは引数だけなので、サマリの外から見て意味があるガードは引数由来のものに限られる。
  ローカル分岐まで含めるとガード集合が経路数ぶんに爆発する。
  LLM が後段にいる前提だと、SMT が得意で LLM が苦手な領域（複雑な算術制約）は Web アプリの injection 検出でほとんど出てこない。
- **帰結:** IR の `branch` が条件値とソース範囲を保持する必須要件になる（ADR-003）。ガードは評価せず、対応関係を書き出すだけ。

## ADR-007: soundy を宣言し、扱わなかった箇所は必ず記録する

- **決定:** 原理的には健全（見逃しなし）を目指すが、リフレクション、動的コード生成、並行性の一部は意図的に扱わない。扱わなかった箇所は必ず出力に記録する。
- **理由:** 実在するツールはほぼ soundy であり、最初に立場を宣言する方が誠実。記録することで LLM が調査すべき箇所が分かる。

## ADR-008: 不確実性は閉じた terminal kind で分類し、`attributable_to` を持たせる

- **状況:** 探索を打ち切ったとき、理由を分類して残したい。ブリーフの 10 種に不足がある。
- **決定:**
  - ブリーフの 10 種に 4 種を追加する: `ffi_boundary`、`unresolved_callee`、`missing_source`（サブ理由を文字列で持つ。proc-macro 展開結果や未生成コードを含む）、`recursion_approximation`
  - 集合は**閉じる**。追加はスキーマのバージョンを上げて行う
  - 各 kind に `attributable_to: target | rivus | mixed` を持たせる。
    `mixed` は「言語機能由来だが rivus の精度向上でも減らせる」もの。集計では `rivus` と別々に出す
- **理由:** これらを `depth_limit` に押し込むと「rivus の都合」と「対象の性質」が混ざる。
  `attributable_to: rivus` の比率がそのまま「rivus の未熟さの指標」になり、どこに投資すべきかが数字で出る。既製 SAST では得られないフィードバックループ。
- **帰結:** kind ごとの割り当て初版は ARCHITECTURE.md 4.4。`dynamic_dispatch` / `unresolved_callee` / `concurrency` は `mixed`。
  コールグラフの精度を実装前に見積もれないため、2 値に決め打ちせず 3 値で様子を見る。Phase 1 のステップ 1.12 の実測後に見直す（レビューで決定）。
  `container_element_imprecision` は結論に影響した場合のみ記録する（ノイズで集計が無意味にならないように）。
  ガード上限の超過は専用 kind にせず、サブ理由 `guard_limit` として別の記録に残す。
  `depth_limit` の比率は上限チューニングの指標として監視する。

## ADR-009: 出力は構造化 JSON が本体、SARIF は副次

- **状況:** ブリーフと初版の GLOSSARY は「プライベートリポジトリでも SARIF アップロード自体は GHAS なしで可能」としていた。
- **訂正:** **誤り。** GitHub の code scanning が使えるのは、パブリックリポジトリ、または GitHub Code Security を有効にした組織のリポジトリに限られる。
  プライベートリポジトリで Code Security なしには使えない。SARIF アップロードは code scanning の機能なので同じ制約下にある。
  （出典: GitHub Docs "Uploading a SARIF file to GitHub"）
- **決定:** 構造化 JSON を唯一の一級市民とする。SARIF は副次出力で、用途は次の 3 つ。
  - パブリックリポジトリでの利用
  - VS Code の SARIF Viewer など、ローカルのビューワで見る
  - 将来 Code Security を契約した場合や他の SARIF 対応基盤での互換性
  SARIF 生成は Phase 1 のスコープ外とし、JSON が固まってから実装する。
- **理由:** プライベートリポジトリで無償で使いたい、というのが rivus の出発点であり、Security タブへの出力はその目的に使えない。
- **帰結:** SARIF に載せる場合、LLM 向けの付加情報は `properties` バッグに入れる（ブリーフ 7.1 節の方針は維持）。

## ADR-010: LLM の出力は「モデル」と「判定」に分ける

- **状況:** LLM の判定を還流させたいが、「決定論的な事実だけを出す」原則とぶつかる。
  ブリーフのキャッシュキー（関数のシグネチャ ＋ ボディのハッシュ）では、呼び先が変わっても判定が古いまま残る。
- **決定:**
  - LLM の出力を 2 種類に分ける。**モデル**（関数 1 つの振る舞い。再利用する。YAML に保存）と、
    **判定**（検出結果 1 件の評価。再利用しない。検出結果の注釈にのみ残す）。混ぜない
  - モデルのキャッシュキーは「その関数のボディのハッシュ ＋ 直接呼び出している関数の**モデル ID** の集合」。推移的なボディハッシュにはしない
  - モデルには `origin: builtin | human | llm` を必須とする。`llm` の場合は `decided_at`、`rationale`、`model_version` を付ける
  - 出力に「このモデルで抑制した / 伝播させた」を必ず記録する
  - `--deterministic-only` で `origin: llm` のモデルをすべて無視して走れる
- **理由:** 経路全体についての判定はコードのどこが変わっても意味が変わり得るのでキャッシュに向かない。
  推移的ハッシュは無関係な変更（深い関数のコメント修正など）で全モデルが無効化されすぎる。
  モデル ID を依存関係にすれば、呼び先の振る舞いの記述が変わったときだけ無効化される。
- **帰結:** `--deterministic-only` があるので「rivus 単体は決定論的」と言い切れる。監査や LLM 判定の妥当性検証に使える。
  モデルの依存グラフは、SCC 縮約したコールグラフの部分グラフとして既存の構造から得る。

## ADR-011: フェーズの順序と Dart 実現性スパイク

- **決定:** 順序は Phase 1 (Go のみ、IR なし) → Phase 2 (中立 IR) → Phase 3 (Rust) → Phase 4 (Dart)。入れ替えない。
  ただし、**Phase 1 の合間（Phase 2 の IR 設計の前）に、Dart の実現性スパイクを 2 日のタイムボックスで挟む**。
- **理由（順序）:** 動く実装を 1 つ持ってから IR を設計する方が確実に良いものになる。IR の中立性は軽い言語で検証すべき。
  Dart の CFG ビルダーを書きながら IR も設計する二重の難しさは避ける。
- **理由（スパイク）:** 最優先の言語の最難関（`async`/`await`、`try`/`finally` の CFG）が Phase 4 まで未検証だと、IR 凍結後に手戻りするリスクがある。
  パッケージ解決（モノレポ）と生成コードが見えるかも、駄目なら Phase 4 の前提が崩れるため、同時に潰す。
- **帰結:** スパイクのコードは捨ててよい（`spike/dart-cfg/`）。成果物は「可否の判断」と「IR 設計に反映すべき難所のリスト」。

## ADR-012: Dart / Rust は外部ツールチェイン依存

- **状況:** ブリーフは Dart extractor を `dart compile exe` でネイティブ化して `go:embed` で埋め込む想定だった（+20MB 程度）。
  しかし `dart compile exe` はクロスコンパイルが限定的で、OS/arch ごとのバイナリを埋め込むには各環境でのビルドが必要になる。
- **決定:** **Dart extractor も Rust と同じく外部ツールチェイン依存とする。**
  対象プロジェクトを解析したい人は Dart SDK を持っている、という前提を Rust と同じ理屈で置く。
  Go extractor はコアに同梱。`go:embed` による埋め込みは、すべて動いてから検討する後工程の最適化とする。
- **理由:** Phase 4 の負担に配布の問題を上乗せするのは筋が悪い。
- **帰結:** extractor の在り処を解決する層（`Locator`）を挟み、「PATH から探す / 設定で指定されたパス / 埋め込みバイナリを展開」を差し替え可能にする。初期実装は前 2 つ。
  ブリーフ 5.5 節の配布形態は、この ADR に合わせて読み替える。
  将来 wasm 化できれば外部依存を外せる可能性があるが（dart2wasm は WasmGC 要求、wazero は未対応）、後から置き換えられる設計にはしておく。

## ADR-013: Rust は固定 nightly が前提

- **状況:** `rustc_public`（旧 `stable_mir`）は nightly 専用。`RUSTC_BOOTSTRAP` で nightly 機能を stable に通す手段は正式サポートではなく、依存すると脆い。
- **決定:** 制約を先に宣言する。extractor は特定の nightly に固定される。**解析対象のコードも、その nightly でコンパイルできる必要がある。**
  Phase 3 の成果物は「全 Rust プロジェクトを解析できるツール」ではなく「固定した nightly でビルドが通る Rust プロジェクトを解析できるツール」。
  Phase 3 の最初のタスクは、`stable-mir-json` 等の既存ツールで実在のクレートがどれくらい通るかの確認。
- **理由:** 対象が新しい言語機能を使っていたり、edition や MSRV が噛み合わないと失敗する。リスクを受容した上で前提を明記する方が誠実。
- **帰結:** 想定より通らなければ、Rust の優先度を下げる判断もあり得る。

## ADR-014: ヒープはフィールド感度あり（k=3）、エイリアス解析は作らない

- **決定:**
  - フィールド感度は**フィールド名ベース**。アクセスパスの深さ上限 k の既定は 3、設定で変更可能
  - アロケーションサイトで区別するオブジェクト感度は入れない
  - コンテナ要素は区別せず、`container_element_imprecision` は**結論に影響した場合だけ**記録する
  - 完全なエイリアス解析は作らない（必要箇所の列挙に留める）
- **理由:** フィールド感度がないと構造体を一箇所触った時点で全体が汚染になり実用に耐えない。
  オブジェクト感度はコストが跳ね上がるわりに、injection 検出での見返りが薄い。

## ADR-015: 依存パッケージの境界はモデルで扱う

- **決定:** 解析するのは自モジュールのみ。依存（stdlib・第三者ライブラリ）との境界は手書きモデルで扱い、無ければ `unmodeled_library_call`。
  設定で選んだ依存だけ解析対象に含められる。
  **モデルカバレッジレポート**（`rivus models coverage ./...`）を Phase 1 に含める。
- **理由:** 依存まで全部解析すると遅くなり、ノイズも増える。
  一方、手書きモデル方式は「どこにモデルを書けば検出が改善するか」が分からないと機能しない。
  すでに `unmodeled_library_call` を記録しているので集計するだけで実装が軽く、効果が大きい。
- **帰結:** 組み込みモデルの最低ライン: Go は `database/sql`、`os/exec`、`net/http`、`html/template`、`text/template`、`strings` など。
  Dart は `dart:*` と Flutter SDK の主要部分。Rust は `std` と頻出クレート（`serde`、`tokio`、`reqwest` など）。
  すべてユーザー定義と同じ YAML 形式で書く（ドッグフーディング）。

## ADR-016: ルールは宣言的 YAML、クエリ言語は作らない

- **決定:**
  - 形式は YAML。**v1 では宣言的 YAML のみ**。QL のようなクエリ言語は作らない
  - ルールセットに名前空間とバージョンを持たせる（`rivus/go/stdlib@1`、`myorg/internal@3`）
  - シンボル指定は完全修飾名。**`match: exact` と `match: implementations` を明示的に区別する**
    - `exact`: 具体的な関数だけにマッチ
    - `implementations`: インタフェースのメソッドにマッチし、コールグラフ経由で実装に展開する。展開数の上限と `dynamic_dispatch` の記録を伴う（上限の扱いは ADR-030）
  - ジェネリクスは**型引数を消去して一致**させる
- **理由:** クエリ言語に手を出すと、それ自体が別プロジェクトになる。
  インタフェースの扱いはシンボル指定の最大の難所で、この 2 つは意味がまったく違いどちらも必要。
  型引数ごとに別ルールを書かせるのは使いづらい。

## ADR-017: extractor との通信はサブプロセス ＋ JSON Lines

- **決定:** extractor はサブプロセスとして起動し、**バージョン付き JSON Lines** で IR を受け取る。先頭行は必ず `schema_version`。
  IR ダンプ（`rivus extract --lang=... --output=ir.jsonl`）を一級の成果物にする。
  重くなったら protobuf に移行する。extractor の出力の内容アドレスキャッシュ（キー = extractor のバージョン + 入力ファイル群のハッシュ + 設定）は、Phase 1 では不要だがインタフェースだけ想定しておく。
- **理由:** Phase 4 で Dart の CFG ビルダーをデバッグするとき、IR を人間が読んで検証できることが生命線になる。JSON Lines を選ぶ最大の理由はこれ。

## ADR-018: コールグラフ構築は差し替え可能にする

- **状況:** ブリーフ側で、Go のコールグラフは VTA 既定、CHA は比較用、と提案していた。
- **訂正:** `golang.org/x/tools/go/callgraph/vta.CallGraph(funcs, initial)` は初期コールグラフを引数に取る。
  標準的な使い方は CHA（または RTA）で粗いグラフを作り、VTA で絞り込む 2 段構え。つまり **CHA は「VTA の入力として必須」**。
  実物（`golang.org/x/tools` v0.52.0）で確認した。`initial == nil` なら内部で CHA を使う。
  渡す SSA 関数は `ssa.InstantiateGenerics` 付きで構築する必要がある。結果にはルートノードがない。
- **決定:** `CallGraphBuilder` インタフェースを切り、Go は CHA → VTA の実装を `callgraph/gocg` に置く。
  Dart は `pkg/vm` の type flow analysis、Rust は monomorphize collector など、言語ごとに別実装にする。**Go 固有の手法をコアに漏らさない。**
- **理由:** 言語ごとに使える手法が違う。

## ADR-019: ライセンスは Apache-2.0

- **決定:** Apache-2.0。依存の `golang.org/x/tools` は BSD-3 で互換。

## ADR-020: Go 1.27 と `golang.org/x/tools` 最新

- **決定:** コアは Go 1.27、依存は標準ライブラリ ＋ `golang.org/x/tools`（最新）＋ YAML パーサ。CI は GitHub Actions。rivus 自身を rivus で解析できるようにする。
- **理由:** SSA / 型解決は新しい言語機能への対応がリリースごとに追加されるため、古いと Go 1.27 のコードで失敗することがある。
- **帰結:** Phase 1 では `go/ssa` に触れるコードを `internal/frontend/gossa` に隔離する（Phase 2 の IR 切り出しを楽にするため。必須）。

## ADR-021: 増分解析は当面スコープ外

- **決定:** 増分解析（変更された関数のサマリだけ再計算）は Phase 1〜4 のスコープ外。
  ただしサマリが関数単位で独立しているという性質を壊さない。
  性能目標の叩き台は「20 万行規模のプロジェクトを、ノート PC で 5 分以内」（CI の PR チェックで回せる上限）。現実的でなければレビューで見直す。
- **補足（ADR-025 を受けて）:** エージェントが問い合わせ型で使う場合、**サマリの保存と再利用**は増分解析とは別に必要になる（解析は一度、問い合わせは何度も）。
  これは Phase 1 のステップ 1.8 に含める。コード編集の合間に問い合わせる使い方が現実になった場合は、増分解析のスコープを見直す。

## ADR-022: エントリポイントを明示的に定義する

- **状況:** コールグラフの根の決め方がブリーフに未定義だった。ライブラリには `main` がなく、`exported_api_param` を定義した以上「どこから先が外部か」を決める必要がある。
- **決定:** 言語・用途ごとに既定のエントリポイントを定め（ARCHITECTURE.md 6 節）、ユーザーが追加指定する手段（ルールファイルの `entrypoints:`）も設ける。

## ADR-023: 出力量を制御し、安定 ID を振る

- **状況:** 過大近似を維持し、不確実なものを `requires_review` で残すと、検出件数が経路の組み合わせで膨大になり得て、LLM 判定のコストが破綻する。
- **決定:** 検出結果の単位は (source サイト, sink サイト) の組とし、経路はその中に入れる。1 件あたり経路数に上限（既定 3）を設け、超過分は件数のみ記録する。
  安定した ID と指紋を持たせ、「前回から新規に増えたもの」が分かるようにする（ADR-028）。
- **訂正:** 初版は「(source シンボル, sink シンボル) の組」と書いていたが、シンボルは関数の名前でありプロジェクト全体で 1 つなので、同じ関数の呼び出しがすべて 1 件に混ざってしまう。単位は場所を持つサイトに直した。

## ADR-024: テスト戦略

- **決定:**
  - 言語ごとのマイクロベンチマーク集（`testdata/`）。検出されるべきケースと、意図的に検出できないケース（「検出されないこと」を assert）の両方を置く。期待される terminal kind も assert する
  - コアの SSA 化と lifted `go/ssa` の differential test（ADR-003）
  - Phase が進むごとに、同じ意味のコードを複数言語で書いたクロス言語の等価性テストを足す（IR の中立性の検証）
  - rivus 自身を rivus で解析し、`attributable_to: rivus` の比率を監視する
- **理由:** これがないと、精度を上げたつもりで別のものを壊したことに気づけない。後から足せないので最初に決める。

## ADR-025: エージェントの道具としての使われ方と、3 段階の絞り込み

- **状況:** ブリーフは「LLM が判定するための材料を出す」ことを前提にしていたが、
  利用者として具体的に想定していたのは、判定結果を受け取る後段の LLM までだった。
  レビューで、**脆弱性の有無を判定する LLM エージェントが、コード分析の道具として rivus を呼び出す**使い方が主要なユースケースだと明確になった。
  エージェントは、軽量な（grep より賢い）判定器で疑わしい箇所をまず列挙し、気になる箇所を rivus で詳細に分析する、という 2 段構えで使う。
- **決定:**
  - 絞り込みを rivus の機能として持つ。3 段階とする。
    - **L0**: ルールの source / sink にマッチする**サイト**（箇所）を列挙する（ローダ ＋ シンボル照合のみ。ほぼ即時）
    - **L1**: L0 に加え、sink の引数がリテラル定数だけのものに印を付ける（落とさない。同じ関数内で完結する決定論的な事実）
    - **L2**: 詳細分析（サマリ、ラベル、由来追跡、不確実性の記録）
  - コマンドは `rivus sites`（L0 / L1）と `rivus query --site <ID>`（L2）。サイトには安定した ID を振り、L2 の seed に使う
  - 呼び出し口はまず CLI ＋ JSON 出力。`query` 層は差し替え可能に保ち、必要になれば常駐サーバ（MCP など）を足す
  - 出力の詳細度を選べるようにする（概要のみ / スニペット付き / 関数全文付き）
  - 性能目標を、一括解析と問い合わせ応答の 2 軸にする
- **理由:** L0 / L1 は判定ではなく列挙なので ADR-001 と矛盾しない。
  必要な部品（ローダ、シンボル照合）は Phase 1 で作るもので、追加コストがほぼない。
  grep と違って型解決つきなので、同名の別物を拾わず、別名インポートなども拾える。
  エージェントはコンテキストに制約があるので、出力の量を制御できることが実用上の要件になる。
- **帰結:** Phase 1 にステップ 1.2b（サイト列挙）を追加し、ステップ 1.8 にサマリの保存・再利用を含める。
  サイトの列挙は IR の `call` で行うので言語中立。
  ADR-010 の `origin` と `--deterministic-only` は、エージェントが「どこまで rivus の事実で、どこから推測か」を区別するために、重要度が上がる。

## ADR-026: 自作 SSA 化と differential test は Phase 1 終盤に導入する

- **状況:** コアの SSA 化（`ssabuild`）と、lifted `go/ssa` を oracle にした differential test（ADR-003）を、いつ導入するか。
- **検討した案:**
  - 案 P: Phase 2 で導入。Phase 1 は `go/ssa` だけで済み、設計に集中できる。ただし Phase 2 で SSA 化のバグと IR 切り出しのバグが同時に出て、切り分けが難しい
  - 案 Q: Phase 1 の早い段階で導入。バグを早く潰せるが、Phase 1 の目的（理論と設計を固める）から外れ、ブリーフの順序ともずれる
  - 案 R: Phase 1 の終盤で導入
- **決定:** **案 R。** Phase 1 のステップ 1.11b で導入する。
- **理由:** 解析の設計がほぼ固まり、`testdata` が揃った後なら、SSA 化の問題は「検出結果が変わった」という形で検知できる。
  Phase 2 の前に SSA 化だけを単独で検証できるので、Phase 2 の不確実性は「IR を挟むこと」だけに絞れる。
  ブリーフの順序への抵触も最小限。
- **帰結:** Phase 2 は `gossa` を extractor に置き換えて IR を挟むことに集中できる。

## ADR-027: 性能目標は仮説として置き、実測で確定する

- **状況:** ブリーフに性能目標がなかったため、ADR-021 で叩き台を置いた（20 万行 / ノート PC / 5 分以内）。
  実装前なので、数字の根拠は確かでない。言語によって難しさが大きく違う（Go は型解決と SSA 構築、Dart は `package:analyzer` のコールド解析、Rust は rustc のビルド時間が下限になり得る）。
  エージェントが CLI で何度も問い合わせる使い方では、呼び出しのたびにソースをロードすると応答が遅くなる。
  想定する対象は、プライベートの実プロジェクト（20 万行はありうる）と、著名 OSS。
- **検討した案:** A: 暫定の数字を置き、実測で見直す／B: 数字を置かず測る方針だけ決める／C: 今、厳しい数字を置く。
- **決定:** **案 A。**
  - 一括解析 20 万行 / 5 分と、問い合わせ応答「数秒以内」は仮説とし、ステップ 1.8 の実測で確定する。メモリは 8GB を目安とする
  - 当面の対象は Go のみ。Dart と Rust の数字は、Dart スパイクと Phase 3 の最初の調査の後に置く
  - 規模を小 / 中 / 大 / 超大の階層に分け、20 万行を目標の上限とする。超大は約束せず、段階的に劣化させる（上限に達したら打ち切って記録する）
  - 各階層の実在の Go プロジェクト（著名 OSS を含む）を参照コーパスとして選び、計測値を記録する
  - ロードエラーがあっても全体を失敗させず、解析できた範囲で続行し、`missing_source` として記録する
  - クエリ時にソースのロードをやり直さないよう、サマリ・コールグラフの辺・位置情報を保存する
- **理由:** 根拠のない数字を確定すると、設計を誤った方向に縛る。かといって基準がないと「遅すぎる」の判断ができない。
  著名 OSS で回したい以上、実在のプロジェクトの雑多さ（cgo、ビルドタグ、ロード失敗）に耐えることは、性能と同じくらい重要な要件になる。
- **帰結:** ステップ 1.8 に実測を含める（応答時間の初回計測、ADR-025）。ステップ 1.12 でも `depth_limit` の比率とあわせて計測値を記録する。

## ADR-028: サイトと検出結果の ID は指紋の入れ物で表す

- **状況:** ID は CI の差分（前回から増えた検出）、エージェントによる再参照、注釈の保存に使う。
  行番号に依存する ID は、行のずれで壊れる。一方、「ID が同じなのにコードの中身が変わっている」状態は、古い判断（「安全」という注釈）が変わったコードに残るため、偽の「新規」より危険である。
- **検討した案:**
  - V1（構造キー）: 関数 ID ＋ ルールのシンボル ＋ 同じ関数内での出現順。引数の書き換えには強いが、同じシンボルの呼び出しを前に挿入すると後ろの出現順がずれる
  - V2（内容キー）: V1 の材料のうち出現順を、呼び出し式のハッシュ ＋ 同一テキスト内の出現順に替える。挿入には強いが、引数の書き換えに弱い
  - コールグラフ上の位置を ID の材料に加える案: 無関係な変更・rivus の改善・エントリポイント設定で ID が揺れ、`rivus sites` がコールグラフなしで即時に返せなくなるため不採用
  - simhash を ID に使う案: ID は完全一致で引く鍵であり、「近い」では役目を果たさないため不採用。比較時の補助として使う
- **決定:**
  - サイトと検出結果は、**指紋（fingerprint）の入れ物**に複数の種類を並べて持つ。種類は役割で名付け、版は `@N` で表す
  - 種類: `structural@1`、`content@1`（同一性）、`expr@1`、`body@1`（変化検知）、将来 `sim@1`（類似度）
  - 公開用の `id` は `structural@1` から作る（`s1:` 付き）。検出結果の指紋は、source と sink の同じキー名ごとに合成する
  - 旧新の対応付けは、同一性のキーを優先順位順（内容 → 構造 → 類似度の候補）に当てる。注釈は (ID, 変化検知キー) の組に紐づける
  - Phase 1 では指紋の出力と、ブックマークによる対応付け（ADR-029）まで作る。旧新の結果どうしの比較機能（`rivus diff`）と simhash は、需要が出てから作る
- **理由:** V1 と V2 は失敗する場面が逆なので、両方を持つと片方が外れてもう片方で当たる。
  内容キーを先に当てるのは、構造キーだけだと挿入のときに誤った相手と結び付くため。
  指紋を入れ物にすると、新しい種類のキーを足してもデータ構造とマッチャーを変えずに済む。
  ID は同一性、変化検知は判断の有効性、と役割を分けることで、ID を安定側に倒しても見落としにつながりにくい。
- **帰結:** 版をまたぐ同一性は ID だけで保証するものではなく、比較時の対応付けで成立する。CI の「新規」判定は、もともと前回の結果（ベースライン）との比較が要るので、これで足りる。
  simhash は決定論的でなければならない（トークン化の規則、ハッシュ関数、次元数を固定し、キー名の `@N` で版を表す）。
  リネームや抽出（関数 ID が変わるケース）への耐性は、`sim@1` と比較機能で後から足す。

## ADR-029: エージェントのブックマークと `rivus resolve`

- **状況:** エージェントは、前回の探索で見た箇所を ID で記録しておき、あとで再び見る。コードが変わると、記録した ID が現在のコードで引けなくなる（ID の付け替えが必要になる）。
  また、検出結果（source から sink に届く）を記録していた場合は、サイトが残っていても、途中に sanitizer が追加されるなどして**届かなくなっている**ことがある。
- **決定:**
  - エージェントは ID だけでなく、**指紋全体とスニペットを含むブックマーク**を保存する。保管はエージェント側の責務で、**rivus はステートレスのまま**
  - 新コマンド `rivus resolve` を作る。複数のブックマークをまとめて受け取り（ソースのロードは 1 回）、保存された指紋を現在のコードに当てて、ブックマークごとに状態を返す
  - 状態は `unchanged` / `changed` / `rematched` / `ambiguous` / `unresolved`。`unresolved` の理由は `not_found`（解析できているが該当なし）と `not_analyzed`（読み込めなかった。`missing_source` と同じ）に分ける
  - 付け替えは、内容キー → 構造キー →（将来）類似度の順に当てる。構造キーだけで当たった場合は、一致の根拠（`MatchBasis`）と同じ関数内のサイト数の変化などの事実を添え、確実のように見せない
  - 検出結果のブックマークには `flow`（`present` / `absent_now` / `not_evaluated`）を返す。`absent_now` は「届く経路が見つからない」という事実であり、安全の判定ではない。見つけられなかった理由も一緒に返す
  - 検出結果の指紋に `path@1`（経路の指紋）を足し、同じ組でも経路が変わったことを検知できるようにする
- **理由:** ブックマーク自体が「前回の記録」の役目を果たすので、前回の解析結果（ベースライン）ファイルを要しない。状態を持たない方が rivus は単純に保てる。
  ID だけを覚えていると、コードが変わったときに「見つからない」としか分からないが、指紋を持っていれば「どう変わったか」まで答えられる。
  検出結果で重要なのは「サイトがあるか」だけでなく「今も届くか」であり、届かなくなった理由（sanitizer の追加か、rivus が追えなくなったか）を区別できることが、エージェントの判断材料として最も価値が高い。
- **帰結:** Phase 1 にステップ 1.8b を追加する（指紋の出力は 1.2b、クエリは 1.8 に依存）。
  ADR-001（判定をしない）との線引きとして、`absent_now` や `rematched` は「事実と根拠」を返すだけで、同一かどうか・安全かどうかは判定しない。
  `rivus diff`（旧新の結果どうしの比較）は、`rivus resolve` と同じ対応付けのロジックを共有するので、後から低コストで足せる。

## ADR-030: `match: implementations` の展開上限と sanitizer への展開の禁止

- **状況:** `match: implementations`（ADR-016）は、インタフェースのメソッドに書いたルールを、全実装に広げて適用する。
  実装の数はインタフェースごとに大きく違う（`http.Handler.ServeHTTP` は 100 を超えることが普通で、展開が欲しい結果。`io.Writer.Write` のように、展開するとノイズが洪水になるものもある）。
  初版は「既定上限 20」と書いていたが、根拠はなかった。
- **検討した案（上限を超えたときの振る舞い）:**
  - 切り捨て（先頭 N 個だけ展開）: どれを残すかが恣意的で、見逃しを作る。「列挙は網羅的に」に反する
  - 展開を中止: 何も広がらない代わりに、何を見ていないかが明確に分かる
  - 上限なし: コストが跳ね上がる可能性がある
- **決定:**
  - 上限を超えたら**展開を中止**し、`exact` と同じ扱いに縮退する。総数を `dynamic_dispatch`（`attributable_to: mixed`、サブ理由 `expansion_limit`）として記録する
  - 既定の上限は**暫定 100**。ステップ 1.9 で参照コーパスを使って実測し、確定する。ルールごとに `max_implementations` で上書きできる
  - **sanitizer への `implementations` は既定で禁止**する。許可するときはルール側で明示する（`allow_sanitizer_expansion: true`）
- **理由:** 展開の影響は役割によって向きが逆。source / sink / propagator を広げ過ぎるとノイズが増えるだけだが、
  sanitizer を広げ過ぎると、sanitize していない実装にまで「通れば安全」が及び、汚染が消えて見逃しが生まれる。これは rivus が避けるべき方向。
  部分的に展開すると境界が見えなくなるが、中止なら「このルールは展開していない」と明確に言える。
  インタフェースごとに適切な数が違うため、全体の既定値は暫定とし、ルールごとの上書きを許す。
- **帰結:** 展開を中止した件数は集計でき、既定値の見直しや、ルールごとの `max_implementations` の調整に使える。

## ADR-031: Phase 1 の解析エンジンの実装方式（M2 時点）

Phase 1 のステップ 1.0〜1.8（1.8b は除く）を実装した時点で決めた、実装上の判断を記録する。
ADR-003〜006、014、015 の方針を具体化したもので、方針自体は変えていない。

- **状況:** ADR-004 は bottom-up のサマリ方式を定めたが、サマリの表現と、手続き内の解析との関係は未定だった。
- **決定:**
  - **サマリは記号的な汚染から作る。** 関数の各引数（レシーバ、自由変数を含む）に「呼び出し側が渡すもの」を表す記号的な要素（`Param`）を置いて関数を解く。
    解いた結果（戻り値、引数の指す先、グローバル変数のセルに入った要素）が、そのままサマリになる。
    呼び出し側は、記号的な要素を実引数の汚染で置き換える。手続き内の解析と手続き間の解析が同じ仕組みになり、sink に届く引数の情報（`SinkReach`）も同じ形で持てる
  - **汚染はセル（根 ＋ アクセスパス）のラベル集合で持つ。** 根は SSA 値、複数戻り値の i 番目、または関数の i 番目の戻り値。パスは `/フィールド名`、`/[]`（要素）、`[k]`（map のキー）、`/*`（ポインタの指す先）
  - **ポインタ・スライス・map・channel は「指す先」の位置を値の位置とする。** 同じ SSA 値から派生した参照は同じ位置を指す（値の流れによる別名の追跡だけ。エイリアス解析ではない）。
    ポインタをメモリに保存した場合は、保存先の `/*` に指す先のコピーを置く
  - **ラベル要素は発生元のサイト ID を持つ。** `Real{Label, Origin}`。sink に届いた要素の `Origin` から、検出結果の source が分かる
  - **サニタイザーは `drops` と `adds`。** `adds` は、落としたラベルがあった値にだけ付く（`html_escaped` のように、他の sink にはまだ危険なものを表す）。記号的な要素は操作を `Mods` に覚え、実引数が分かったときに適用する
  - **経路を記録する。** 各要素が各セルに初めて入った理由（命令、元のセルと要素）を残し、sink からたどって経路を復元する。サマリは、関数内の経路をステップとして持ち、呼び出し側で継ぎ足す。検出結果 1 件につき、経路は最短の 1 本のみ（`omitted_paths` は未実装）
  - **関数の内部は、フロー非依存のメモリ ＋ SSA のレジスタ。** メモリのセルは弱い更新（和集合）で、関数内でフロー非依存。レジスタは SSA でフロー依存
  - **グローバル変数は、プログラム全体で 1 つの状態**（フロー非依存）。関数が書いたものを集め、読む関数を再解析する
  - **再解析は、SCC の順（呼び先から）に、サマリが変わった関数の呼び出し元と、グローバルが変わったときの読み手だけを対象に行う。** 不動点まで繰り返す（上限あり）
  - **モデルがある関数は、ボディがあってもモデルを使う**（手書きモデルによる上書き）。sink / source のルールだけの関数は、ボディがなくても「モデルあり」とし、不確実性を出さない
  - **モデルも本体もない関数呼び出しの既定:** 引数（レシーバを含む）の汚染が、bool 以外のすべての戻り値に流れるものとし、`unmodeled_library_call` を経路に記録する（過大近似 ＋ 記録、ADR-007）。呼び先が分からない場合は `unresolved_callee`、インタフェース呼び出しで実装が分からない場合は `dynamic_dispatch` を記録する
  - **インタフェース呼び出しと関数値の呼び出しは、コールグラフ（CHA → VTA）の辺で解決する。** 候補が複数あるか、インタフェース呼び出しなら、`dynamic_dispatch`（候補付き）を経路に記録する。その場で作ったクロージャの呼び出しは、束縛された値を直接使う
  - **ルールのシンボルは `go/types` の `FullName` 形式**（例 `(*net/http.Request).FormValue`、`os/exec.Command`、`(io.Writer).Write`）
  - **ルールの種類:** source は `call_result`（呼び出しの結果）、`param_type`（その型の引数すべて。ハンドラの入口を型で表せる）、`field`（構造体フィールドの読み出し）
  - **無限に広がらないための上限:** アクセスパスの深さ（k=3）、記号的な要素のパスの長さ（k）、サニタイズ操作の記憶（4 個まで。超えたら忘れる。忘れると汚染が多く残る側で、安全側）、経路のステップ数（200）
- **理由:** サマリを別に設計せず、関数を記号的な汚染で解くことで、手続き内と手続き間の解析が分かれず、実装と検証が小さく済む。
  上限は、実在のコード（ghmint）で、上限がないと再帰する構造体のパスやループ中のサニタイズが要素を無限に増やし、メモリが数 GB になって終わらなかったことを受けて入れた。
- **性能のために入れた仕組み（計測は ADR-027 の「初回計測」を参照）:**
  - **呼び出しの入力が変わっていなければ、その呼び出しの処理を飛ばす。** 各セルの根に「追加された要素の数」を持たせ、呼び出しが読む根の値の和が前回と同じなら、サマリを再適用しない
  - **セルの並び順（ソート結果）のキャッシュと、サマリ適用中の読み出し・展開のメモ化。** 集合は増える一方なので、長さが同じならキャッシュは有効
  - **経路をロープ（O(1) で連結できる共有構造）で持つ。** 要素ごとに経路全体をコピーすると、`x/tools` で 5,900 万ステップのコピーになり、メモリと GC が支配的になった
  - **出力の要素が 24 個を超えたら、同じ引数・同じサニタイズ操作の記号的な要素を「引数全体」の 1 つに統合する（widening）。** 「この引数のどこからでも来うる」という、真実より広く、狭くはならない近似。これがないと、ポインタを多用するコードでサマリがフィールド数の組み合わせ（k=3）で増え、`x/tools` で 1 関数 8 万要素になった
  - **サマリは前回との和集合に取る。** 解析は呼び先のサマリに単調なので通常は変わらないが、widening や相互再帰（インタフェース経由の `GenValue`）でサマリが増減を繰り返し、60 パスでも収束しなかったことを受けて、増える一方にして終了を保証する
  - **関数ごとの予算（既定 40 万回の追加）と、全体の時間制限（`-timeout`）。** 超えたら、その関数（または残りの関数）の解析を打ち切り、`depth_limit`（`attributable_to: rivus`）として記録する。打ち切られた関数は再解析しない
- **帰結（既知の限界）:**
  - widening と予算の打ち切りは、サマリを粗くするか、未完成のままにする。前者は過大近似（安全側）、後者は見逃しうるので、必ず `depth_limit` として出力に残る
  - 別名（同じ配列を指す 2 つのスライス、ポインタを介して共有されるオブジェクト）を介した書き込みは、元に反映されない（見逃しうる）。`container_element_imprecision` の記録は今は出していない
  - 関数値として別の場所に保存したクロージャを、後から呼ぶ場合は、束縛された値が分からない
  - 検出結果の経路は 1 本
  - 値依存のサニタイズ（ガード）、由来追跡、`match: implementations`、`rivus resolve` は未実装（ステップ 1.9 以降と 1.8b）
  - 出力の要素数が多い関数の経路は、widening により「どの部分から来たか」が粗くなる
  - Phase 1 の解析エンジンは `go/ssa` に直接依存する（ARCHITECTURE の「`go/ssa` に触れるのは `gossa` と `gocg` のみ」の例外）。Phase 2 で IR に移す

環境: Apple Silicon の Mac（darwin/arm64、Go 1.27.3）。メモリ使用量は計測していない。

### ADR-030 の追記: 実装と実測（ステップ 1.9）

- **実装:** ルール（source の `call_result`、sink、sanitizer、propagator）に `match: implementations` と `max_implementations` を書ける。
  sanitizer は `allow_sanitizer_expansion: true` がないとルールの読み込みでエラーになる。
  展開は `go/types` で行い、**読み込んだパッケージ（自モジュール）の型だけ**を探す（依存は境界で、モデルを別に持つため、ADR-015）。
  `(error).Error` のようにパッケージを持たない型も扱える。展開した結果は `Rules.Expansions` とレポートの `expansions` に残り、上限超過は `dynamic_dispatch`（サブ理由 `expansion_limit`、`mixed`）として出力に出る
- **実測（自モジュールの型の中の実装数）:**

  | インタフェースのメソッド | ghmint | rivus 自身 | x/tools |
  |---|---|---|---|
  | `(fmt.Stringer).String` | 0 | 4 | 165 |
  | `(sort.Interface).Len` | 0 | 0 | 21 |
  | `(io.Reader).Read` | 0 | 0 | 6 |
  | `(io.Writer).Write` | 1 | 0 | 3 |
  | `(net/http.Handler).ServeHTTP` | 1 | （net/http を読み込んでいない） | 1 |

  taint のルールに使いそうなインタフェース（`Reader`、`Writer`、`Handler`）は、実装が 1 桁にとどまった。
  100 を超えたのは `Stringer` だけで、これは汚染のルールの対象になりにくい、どこにでもあるインタフェース。
- **決定（レビューで確定）:** 既定の上限を **300** にする。展開の計算は軽く（x/tools に 6 つのインタフェースを展開しても約 40 ms で、上限 100 と 10 万で差がない）、
  上限の役目は、書き間違いで `Stringer` のようなインタフェースを広く展開してしまう事故を止めること。実装が多いインタフェースに意図して書くルールは、`max_implementations` で個別に上げる。
  展開した結果の解析の重さは別で、広く呼ばれるメソッドを sink にしたときの重さは ADR-032 の「性能の注意」を参照

## ADR-032: 不確実性の記録の範囲と集計（ステップ 1.9）

- **状況:** ADR-007 は「扱わなかった箇所は必ず出力に記録する」とした。ステップ 1.3〜1.8 までは、呼び出し関連（モデルなし、解決できない、インタフェース越し）しか記録していなかった。
  別名を介した書き込み、goroutine と channel、パッケージ変数、reflection は、黙って通り過ぎていた。
- **決定:** 記録の置き場所を 2 つに分け、kind を次のように記録する。
  - **プログラム全体の一覧（`uncertainties`）:** その場所そのものが分かっていないもの。`unmodeled_library_call`（`rivus`）、`dynamic_dispatch`（`mixed`、候補つき）、`unresolved_callee`（`mixed`）、`reflection`（`target`）、`ffi_boundary`（`target`）、`depth_limit`（`rivus`、関数の予算超過、時間切れ、展開の上限超過）、`recursion_approximation`（`rivus`）、`missing_source`（`target`、ロードエラー）
  - **検出結果の経路の区間（`findings[].uncertainties`、各ステップの `notes`）:** その区間を通った検出結果にだけ付く。`container_element_imprecision`（`rivus`。スライス・配列・map・channel の要素の出入り）、`concurrency`（`mixed`。channel、`select`、`go` 文）、`global_var`（`target`。パッケージ変数の読み出し。直接の書き手を候補として列挙する）、ほか `dynamic_dispatch` と `unmodeled_library_call`
    「結論に影響した場合だけ」記録するというルール（ADR-014）を、経路上にあるかどうかで実現した。1 つの区間が複数の不確実性を持てる
  - **集計（`summary`）:** プログラム全体の一覧を kind と `attributable_to` ごとに数え、`rivus` の比率と `depth_limit` の比率、各 kind が付いた検出結果の数を出す。ADR-008 のフィードバックループ
- **未実装・未検証:**
  - `exported_api_param`、`config_read`、`literal` は、由来追跡（ステップ 1.10）の打ち切りの種類で、まだ出ない
  - cgo（`C` パッケージ、`_Cfunc_`）の検出は実装したが、cgo を使ったテストは書いていない。アセンブリやリンクネームで本体のない関数は、`unmodeled_library_call` になる
  - `container_element_imprecision` は、要素への出入りに必ず付くので、スライスを使う経路ではほぼ毎回付く。見た目のノイズになるか、実測と運用で見る
- **実測（プログラム全体の一覧の内訳。`dynamic_dispatch` の帰属を変えた後、完全に収束した実行）:**

  | 対象 | 件数 | `rivus` | `mixed` | `target` | `depth_limit` の比率 |
  |---|---|---|---|---|---|
  | ghmint | 288 | 87% | 13% | 0% | 0% |
  | rivus 自身 | 390 | 93% | 7% | 0% | 0% |
  | x/tools（15.6 万行、96 秒、2 パスで収束） | 12,350 | 78% | 19% | 3% | 0.02% |

  `rivus` の大半は `unmodeled_library_call` と、実装が分からない `dynamic_dispatch` で、どちらもモデルを書けば減る。
  上位は `fmt.Fprintf`（505）、`(*go/types.object).Type`（232）、`strings.HasPrefix`（164）、`(go/types.Type).Underlying`（91）、`(context.Context).Err`（37）など。
  `summary.top_symbols` が、この一覧を出す（ステップ 1.11 のモデルカバレッジレポートの土台）
- **訂正:** この ADR の初版には、x/tools の件数を 5,444（`rivus` 67%、`mixed` 30%）と書いたが、**これは 255 秒の時間制限で打ち切られた、途中までの実行の値だった**（計測用に広い sink ルールを足したため。下の「性能の注意」参照）。上の表が正しい
- **`dynamic_dispatch` の帰属（ステップ 1.9 の相談で決定）:** 呼び先の候補が 0 件のとき（標準ライブラリなど、実装が読み込んだコードの外にある）は `rivus`（モデルを書くと減る）、1 件以上のときは `mixed`（VTA の精度向上で減らせる余地がある）。
  種類は変えず、`attributable_to` を呼び出しごとに決める。x/tools の候補数の分布は 0 件 616 / 1 件 217 / 2〜5 件 623 / 6〜20 件 425 / 21 件以上 213（`summary.dispatch_candidates`）。
  候補 1 件の記録を残す是非と、`mixed` の細かい分け方は、ステップ 1.12 で、より多くのコードの分布を見て決める
- **性能の注意:** `(error).Error`、`(io.Writer).Write`、`(fmt.Stringer).String` のように、**至る所で呼ばれるメソッドに sink ルールを書くと、解析が大幅に遅くなる**。
  x/tools で、こうしたインタフェースメソッドを 6 つ sink にしたところ、96 秒の解析が 255 秒でも終わらなかった（展開なしでも同じ。原因は展開ではなく、呼び出しの数）。
  全ての呼び出しが sink になり、各関数のサマリに「引数が sink に届く」記録が大量に残るため。ルールを書くときは、狭く書く。サマリの `SinkReach` を粗くする対策（出力要素の widening と同様）は未実装
- **帰結:** 経路の区間に付く不確実性は、出力の `notes` を見れば、LLM が「この経路のどこが怪しいか」を種類別に読める。
  `mixed` の割り当て（ADR-008）を見直す材料として、`dynamic_dispatch` の候補数の分布などの追加の計測が要る（レビュー待ち）

## ADR-033: `rivus resolve` の実装（ステップ 1.8b）

ADR-029 の設計を実装した。設計から変えた点と、実装で決めたことを記録する。

- **ブックマークの形式を新しく作らなかった。** rivus が出力した検出結果とサイトの JSON を、そのまま渡せる（配列、`{"bookmarks": [...]}`、単体のどれでもよい）。
  そのために、検出結果の `source` / `sink` にサイトの指紋（`fingerprint`）を入れた。ID だけのブックマークは、指紋がないので受け付けない（エラー）
- **対応付けの順序:** 内容キー（`content@1`）→ 構造キー（`structural@1`）。複数に当たったら `ambiguous`（候補を返し、1 つを選ばない）。
  変化検知（`expr@1`、`body@1`）は、見つかった後に比べる
- **状態の決まり方:**
  - 内容キーで当たり、ID が同じで、変化検知キーが同じ → `unchanged`
  - 内容キーで当たり、ID が同じで、変化検知キーが違う → `changed`（`changed_keys` に違うキー。関数の本体が変わっただけなら `body@1`）
  - 内容キーで当たり、ID が違う（同じシンボルの呼び出しが前に挿入されたなど）→ `rematched`、根拠は `content@1`
  - 構造キーだけで当たった → `rematched`、根拠は `structural@1`。式が書き換えられたか、似た呼び出しが前に増減した可能性があるので、記憶していたスニペット（`previous_snippet`）と現在のスニペットを並べて返し、`evidence` に理由を書く
  - どちらも当たらない → `unresolved`。理由は `not_analyzed`（そのパッケージが解析対象になかった、またはロードに失敗した）か `not_found`（解析したが見当たらない）。この区別のために、レポートに解析したパッケージの一覧（`packages`）を持たせた
- **検出結果のブックマーク:** source と sink の両方を同じ手順で対応付け、状態は両者のうち「大きい方」（`unresolved` > `ambiguous` > `rematched` > `changed` > `unchanged`）。
  さらに `flow` を返す:
  - `present`: 現在の検出結果に、対応付けた source と sink の組がある。`path@1` が記憶と違えば `path_changed: true`
  - `absent_now`: 両端は見つかったが、その組の検出結果がない。**安全の判定ではなく**、見つけられなかった事実として、2 つの関数の中の不確実性と、実行全体に関わる不確実性（`depth_limit`、`missing_source` など。最大 20 件）を添え、source か sink を共有する別の検出結果（`related_findings`）も示す
  - `not_evaluated`: 両端のどちらかが見つからない
- **入力のソース:** 現在のコードを解析する（`rivus resolve -bookmarks b.json ./...`）か、保存した index に対して行う（`-index idx.json`、ソースを読み込まない）
- **検証:** 使い捨てのモジュールを編集して、行のずれ、関数本体の変更、引数の書き換え、同じ呼び出しの前への挿入、sanitizer の追加、関数の削除、パッケージの未解析、コンパイルできないパッケージ、index 経由、指紋のないブックマークの拒否を確かめるテストを書いた
- **未実装:** 類似度（`sim@1`）による対応付けの候補提示。リネームや移動で関数 ID が変わった場合は、`unresolved`（`not_found`）になる（ADR-028 の「後回し」のまま）

## ADR-034: モデルの運用機能（ステップ 1.11）

- **状況:** 不確実性の大半（`rivus` に帰属する 74〜93%）は、モデルを書けば減る（ADR-032）。そのための道具と、LLM が書いたモデルを監査できる仕組みが要る（ADR-010）。
- **決定:**
  - **`rivus models coverage`:** モデルのない呼び出しを、**検出結果の経路に載っている数（`findings`）、呼び出しの数、関数の数**の順に並べる。対象は `unmodeled_library_call`、`reflection`、実装が分からない `dynamic_dispatch`。
    `-yaml` で、埋めるためのルールファイルのひな形を出す（流れ方は仮置きで `TODO` を付ける。人が決める）。`-index` で保存した結果から出せる。出力したひな形は、そのままルールとして読み込める
  - **`pure: true`（propagator）:** その関数を通って汚染は流れない、というモデル。ロック、時計、ログ、述語など。
    「引数が戻り値に流れる」という保守的な既定と、それに伴う不確実性をなくす。組み込みに、よく出る標準ライブラリの関数（`sync`、`time`、`log`、`strings` の述語、`sort` など）を足した
  - **モデルの出所（`origin: builtin | human | llm`）:** どのルールにも付けられ、ルールセットの先頭に書けば既定になる（書かなければ、組み込みは `builtin`、ほかは `human`）。
    `llm` のルールは `decided_at`、`rationale`、`model_version` を必須とし、欠けるとルールの読み込みでエラーになる
  - **`--deterministic-only`:** `origin: llm` のルールをすべて無視して解析する。出力に `deterministic_only` と、無視した数（`ignored_models`）が残る
  - **出力に残す記録:**
    - 検出結果の `models`: 経路で何かを決めたモデル（source と sink のルール、通った sanitizer と propagator）とその出所。`llm_influenced` は、そのうち 1 つでも `llm` なら true
    - `suppressions`: `origin: llm` の sanitizer が、実際に汚染を落とした場所（モデル、位置、落としたラベルと、その発生元のサイト）。検出結果自体がなくなるので、検出結果には書けない
  - **`param` 型の source:** 関数のシンボルと位置（`params`、`recv`）で、フレームワークが汚染を渡す入口を宣言できる。`match: implementations` と組み合わせられる。
    ARCHITECTURE 6 節にある `entrypoints:` セクションの実体はこれで、source の 1 種として実装した（別のセクションは作っていない）
- **効果（組み込みモデルの追加前後。検出結果は変わらない）:**

  | 対象 | 不確実性の件数 | `rivus` の比率 | 検出 |
  |---|---|---|---|
  | ghmint | 288 → **170** | 87% → 80% | 15 件のまま |
  | rivus 自身 | 390 → 337 | 93% → 92% | 0 件のまま |
  | x/tools | 12,350 → 10,638 | 78% → 74% | 4 件のまま |

  `pure` を外すと対応するテストが失敗することを確かめてある（モデルが効いている）
- **見送ったもの:** 検出結果ごとの複数経路と経路数の上限（現状は経路 1 本で足りている）。LLM の判定をモデルのファイルに書き戻す機能（形式は決めたが、書き戻す道具は作っていない）。
  `models coverage` のひな形は `propagator` の仮置きのみで、sanitizer や sink のひな形は出さない
- **帰結:** ルールを書く人（と、書かせる LLM）は、`models coverage` で優先順位を決め、`-yaml` のひな形から始め、`origin` を付け、`--deterministic-only` で影響を確かめられる
