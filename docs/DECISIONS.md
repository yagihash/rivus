# 設計判断記録（ADR）

rivus の設計判断を、後から経緯を追えるように記録する。
形式は「状況 → 決定 → 理由 → 帰結」。出典は次の 2 種類。

- **ブリーフ**: 初期ブリーフで決まっていたこと
- **レビュー**: ブリーフへの質問（`QUESTIONS.md`）と回答を経て決まった、または訂正されたこと

全 ADR の状態は「採用」。覆すときは新しい ADR を追加して旧 ADR を「置換」にする。

## ADR-001: 事実を出し、判定はしない

- **状況:** プライベートコードのファイル跨ぎ taint 解析を無償で行える選択肢がなく、最終的な正誤判定は LLM や人間が行う前提で使う。
- **決定:** rivus は「到達可能性に関する事実を問い合わせるクエリエンジン」であり、安全か危険かは決めない。
  決定論的に確定できる事実だけを構造化して出し、確定できなかった理由を分類して残す。
  過大近似は維持する。**列挙は網羅的に、判定は保留する。**
- **理由:** 完全な精度（経路感度、エイリアス解析の完全性）を追わずに済む。
  LLM に判定させる前提なら、判定に必要な材料を揃える方が投資対効果が高い。
- **帰結:** 非目標: 判定を下すこと、完全な経路感度、シンボリック実行・SMT 連携、完全なエイリアス解析、
  暗黙的フロー（制御依存）の追跡、Dart / Rust フロントエンドの自作、対象言語のビルド・コード生成の面倒を見ること、IDE 統合 / Web UI / SaaS 化。
  「LLM が後で落としてくれるから見逃してよい」とはしない。

## ADR-002: extractor と解析エンジンの分離

- **状況:** 言語ごとのフロントエンド（型解決・トレイト解決・手続きマクロなど）を Go で再実装するのは非現実的。
- **決定:** CodeQL や Joern と同じ構造にする。言語ごとの extractor（Go / Rust / Dart それぞれの言語の道具で書く）が中立 IR を出し、Go 製のコアエンジンが解析する。
- **理由:** 型解決・名前解決・パッケージ解決は各言語の公式の道具（`go/packages`、`rustc`、`package:analyzer`）に任せるのが最も確実。
- **帰結:** 責務の境界は「言語固有の知識が要るか」。CFG 構築まで（言語固有の脱糖を含む）が extractor、SSA 化から先がコア。

## ADR-003: IR は φ なしの CFG ＋ 書き換え可能ローカル変数

- **状況:** AST レベルで切ると構文差が大きすぎる。SSA レベルで切ると SSA 化を 3 言語ぶん書くことになる。
  さらに `go/ssa` は SSA 化済み（φ 入り）、Rust の MIR は SSA ではなくローカル変数の書き換え形、と形が揃っていない。
- **決定:** IR は**CFG のレベル**で切り、**φ を持たない**。値は書き換え可能なローカル変数で表す。SSA 化（dominator 計算と φ 挿入）はコアに一本化する。
  Go extractor は `ssa.NaiveForm` で `Alloc` / `Store` / `Load` が残る形を取る。
  lifted 版の `go/ssa`（NaiveForm なし）は捨てず、**コアの SSA 化の differential test の oracle** にする。
- **検討した代替:** IR に `phi` を任意で許し、コアの SSA 化を冪等にする案。
  `NaiveForm` により Go 側の追加コストがなくなったため、IR を複雑にするだけの利点がないとして不採用。
- **理由:** 制御構造は CFG まで下げると言語差がほぼ消える。3 言語が同じ抽象度に揃い、IR 設計が単純になる。
  SSA 化は言語非依存のグラフアルゴリズムなので一度だけ書けばよい。
  SSA 化は自作部分で最もバグを埋め込みやすく、症状が分かりにくいため、実績のある実装を正解として持つ価値が大きい。
- **帰結:** 命令セットは当初見積もりの 15 種類程度ではなく 26 種（ARCHITECTURE.md 2.3）。
  `slice` は独立命令にせず `copy` の `view` フラグに畳み（構文として存在するのは主に Go で、汚染の意味は `copy` と同じため）、
  `global_load` / `global_store` は独立させる（関数サマリの境界と `global_var` の書き込み箇所の列挙に必要なため）。
  `async` / `await` と例外は CFG のエッジで表し、`go` / `defer` / `await` は `call` のフラグで表す。
  イテレータなど言語固有の構文は extractor が脱糖する。分岐条件は式言語を作らず、値への参照 ＋ ソース範囲で持つ。

## ADR-004: bottom-up の関数サマリ（functional approach）

- **状況:** 汎用の IFDS を実装すると重い。
- **決定:** コールグラフを SCC に縮約し、トポロジカル順（呼び先から）に関数サマリを算出して、呼び出し側で展開する（SCC 内のみ不動点まで反復）。
  これは Sharir & Pnueli (1981) の **functional approach** であり、IFDS の tabulation の非形式版ではない。
  「IFDS の summary edge に相当するものを functional approach で計算する」と表現を統一する。
- **理由（単なる用語の問題ではなく、方式選択の根拠）:**
  rivus の要件 4.2「ある sink に到達し得る source の列挙」は **seed となる source を与えずに投げるクエリ**である。
  tabulation は entry point と seed fact から前向きに探索する設計なので、この形に素直に乗らない。
  bottom-up の functional approach は全関数の完全なサマリを先に作るので、source 側・sink 側どちらからでも引ける。
  つまり rivus の目玉機能のために bottom-up を選んでいる。
- **帰結:** サマリは関数単位で独立させる（将来の増分解析の土台。ADR-021）。

## ADR-005: 汚染はラベル集合で持つ

- **決定:** ブール値ではなく `map[Value]LabelSet`。sanitizer は特定ラベルだけを落とし、sink は特定ラベルにのみ反応する。
- **理由:** HTML 用にエスケープした値を JS コンテキストの sink に流したら安全ではない、というミスマッチが実務で頻出する。
  設計の初期から入れておかないと後で入れられない。

## ADR-006: 値依存サニタイズの扱いと条件ガード

- **状況:** `func render(s string, escape bool)` のように、引数の値で sanitize するかが変わる関数がある。完全な経路感度は実装しない。
- **決定:** 対応の優先順は次のとおり。
  1. 手書きモデルによる上書き（最優先）
  2. 値依存ノードとして記録し、判定を LLM に委ねる（中核）
  3. 余裕があればサマリの特殊化（引数がリテラルなら定数値ごとに別サマリ）
  述語付きサマリ、シンボリック実行、SMT は実装しない。
  2 を実現するため、サマリの各 Flow に**条件ガード**を付ける。
  - ガードに記録するのは**関数の引数に由来する条件だけ**。ローカルの分岐（ループカウンタの比較など）は含めない
  - 判定は「その条件値が引数からのデータフローで到達可能か」。taint ソルバを流用する（source = 引数、sink = 分岐条件）
  - 1 サマリあたり約 4 個を上限とし、超えたらガードなしの過大近似（全経路の和集合）に畳み、`attributable_to: rivus` の不確実性として記録する
- **理由:** 呼び出し側が制御できるのは引数だけなので、サマリの外から見て意味があるガードは引数由来のものに限られる。
  ローカル分岐まで含めるとガード集合が経路数ぶんに爆発する。
  LLM が後段にいる前提だと、SMT が得意で LLM が苦手な領域（複雑な算術制約）は Web アプリの injection 検出でほとんど出てこない。
- **帰結:** IR の `branch` が条件値とソース範囲を保持する必須要件になる（ADR-003）。ガードは評価せず、対応関係を書き出すだけ。

## ADR-007: soundy を宣言し、扱わなかった箇所は必ず記録する

- **決定:** 原理的には健全（見逃しなし）を目指すが、リフレクション、動的コード生成、並行性の一部は意図的に扱わない。扱わなかった箇所は必ず出力に記録する。
- **理由:** 実在するツールはほぼ soundy であり、最初に立場を宣言する方が誠実。記録することで LLM が調査すべき箇所が分かる。

## ADR-008: 不確実性は閉じた terminal kind で分類し、`attributable_to` を持たせる

- **状況:** 探索を打ち切ったとき、理由を分類して残したい。ブリーフの 10 種に不足がある。
- **決定:**
  - ブリーフの 10 種に 4 種を追加する: `ffi_boundary`、`unresolved_callee`、`missing_source`（サブ理由を文字列で持つ。proc-macro 展開結果や未生成コードを含む）、`recursion_approximation`
  - 集合は**閉じる**。追加はスキーマのバージョンを上げて行う
  - 各 kind に `attributable_to: target | rivus | mixed` を持たせる。
    `mixed` は「言語機能由来だが rivus の精度向上でも減らせる」もの。集計では `rivus` と別々に出す
- **理由:** これらを `depth_limit` に押し込むと「rivus の都合」と「対象の性質」が混ざる。
  `attributable_to: rivus` の比率がそのまま「rivus の未熟さの指標」になり、どこに投資すべきかが数字で出る。既製 SAST では得られないフィードバックループ。
- **帰結:** kind ごとの割り当て初版は ARCHITECTURE.md 4.4。`dynamic_dispatch` / `unresolved_callee` / `concurrency` は `mixed`。
  コールグラフの精度を実装前に見積もれないため、2 値に決め打ちせず 3 値で様子を見る。Phase 1 のステップ 1.12 の実測後に見直す（レビューで決定）。
  `container_element_imprecision` は結論に影響した場合のみ記録する（ノイズで集計が無意味にならないように）。
  ガード上限の超過は専用 kind にせず、サブ理由 `guard_limit` として別の記録に残す。
  `depth_limit` の比率は上限チューニングの指標として監視する。

## ADR-009: 出力は構造化 JSON が本体、SARIF は副次

- **状況:** ブリーフと初版の GLOSSARY は「プライベートリポジトリでも SARIF アップロード自体は GHAS なしで可能」としていた。
- **訂正:** **誤り。** GitHub の code scanning が使えるのは、パブリックリポジトリ、または GitHub Code Security を有効にした組織のリポジトリに限られる。
  プライベートリポジトリで Code Security なしには使えない。SARIF アップロードは code scanning の機能なので同じ制約下にある。
  （出典: GitHub Docs "Uploading a SARIF file to GitHub"）
- **決定:** 構造化 JSON を唯一の一級市民とする。SARIF は副次出力で、用途は次の 3 つ。
  - パブリックリポジトリでの利用
  - VS Code の SARIF Viewer など、ローカルのビューワで見る
  - 将来 Code Security を契約した場合や他の SARIF 対応基盤での互換性
  SARIF 生成は Phase 1 のスコープ外とし、JSON が固まってから実装する。
- **理由:** プライベートリポジトリで無償で使いたい、というのが rivus の出発点であり、Security タブへの出力はその目的に使えない。
- **帰結:** SARIF に載せる場合、LLM 向けの付加情報は `properties` バッグに入れる（ブリーフ 7.1 節の方針は維持）。

## ADR-010: LLM の出力は「モデル」と「判定」に分ける

- **状況:** LLM の判定を還流させたいが、「決定論的な事実だけを出す」原則とぶつかる。
  ブリーフのキャッシュキー（関数のシグネチャ ＋ ボディのハッシュ）では、呼び先が変わっても判定が古いまま残る。
- **決定:**
  - LLM の出力を 2 種類に分ける。**モデル**（関数 1 つの振る舞い。再利用する。YAML に保存）と、
    **判定**（検出結果 1 件の評価。再利用しない。検出結果の注釈にのみ残す）。混ぜない
  - モデルのキャッシュキーは「その関数のボディのハッシュ ＋ 直接呼び出している関数の**モデル ID** の集合」。推移的なボディハッシュにはしない
  - モデルには `origin: builtin | human | llm` を必須とする。`llm` の場合は `decided_at`、`rationale`、`model_version` を付ける
  - 出力に「このモデルで抑制した / 伝播させた」を必ず記録する
  - `--deterministic-only` で `origin: llm` のモデルをすべて無視して走れる
- **理由:** 経路全体についての判定はコードのどこが変わっても意味が変わり得るのでキャッシュに向かない。
  推移的ハッシュは無関係な変更（深い関数のコメント修正など）で全モデルが無効化されすぎる。
  モデル ID を依存関係にすれば、呼び先の振る舞いの記述が変わったときだけ無効化される。
- **帰結:** `--deterministic-only` があるので「rivus 単体は決定論的」と言い切れる。監査や LLM 判定の妥当性検証に使える。
  モデルの依存グラフは、SCC 縮約したコールグラフの部分グラフとして既存の構造から得る。

## ADR-011: フェーズの順序と Dart 実現性スパイク

- **決定:** 順序は Phase 1 (Go のみ、IR なし) → Phase 2 (中立 IR) → Phase 3 (Rust) → Phase 4 (Dart)。入れ替えない。
  ただし、**Phase 1 の合間（Phase 2 の IR 設計の前）に、Dart の実現性スパイクを 2 日のタイムボックスで挟む**。
- **理由（順序）:** 動く実装を 1 つ持ってから IR を設計する方が確実に良いものになる。IR の中立性は軽い言語で検証すべき。
  Dart の CFG ビルダーを書きながら IR も設計する二重の難しさは避ける。
- **理由（スパイク）:** 最優先の言語の最難関（`async`/`await`、`try`/`finally` の CFG）が Phase 4 まで未検証だと、IR 凍結後に手戻りするリスクがある。
  パッケージ解決（モノレポ）と生成コードが見えるかも、駄目なら Phase 4 の前提が崩れるため、同時に潰す。
- **帰結:** スパイクのコードは捨ててよい（`spike/dart-cfg/`。#38 で削除した）。成果物は「可否の判断」と「IR 設計に反映すべき難所のリスト」。

## ADR-012: Dart / Rust は外部ツールチェイン依存

- **状況:** ブリーフは Dart extractor を `dart compile exe` でネイティブ化して `go:embed` で埋め込む想定だった（+20MB 程度）。
  しかし `dart compile exe` はクロスコンパイルが限定的で、OS/arch ごとのバイナリを埋め込むには各環境でのビルドが必要になる。
- **決定:** **Dart extractor も Rust と同じく外部ツールチェイン依存とする。**
  対象プロジェクトを解析したい人は Dart SDK を持っている、という前提を Rust と同じ理屈で置く。
  Go extractor はコアに同梱。`go:embed` による埋め込みは、すべて動いてから検討する後工程の最適化とする。
- **理由:** Phase 4 の負担に配布の問題を上乗せするのは筋が悪い。
- **帰結:** extractor の在り処を解決する層（`Locator`）を挟み、「PATH から探す / 設定で指定されたパス / 埋め込みバイナリを展開」を差し替え可能にする。初期実装は前 2 つ。
  ブリーフ 5.5 節の配布形態は、この ADR に合わせて読み替える。
  将来 wasm 化できれば外部依存を外せる可能性があるが（dart2wasm は WasmGC 要求、wazero は未対応）、後から置き換えられる設計にはしておく。

## ADR-013: Rust は固定 nightly が前提

- **状況:** `rustc_public`（旧 `stable_mir`）は nightly 専用。`RUSTC_BOOTSTRAP` で nightly 機能を stable に通す手段は正式サポートではなく、依存すると脆い。
- **決定:** 制約を先に宣言する。extractor は特定の nightly に固定される。**解析対象のコードも、その nightly でコンパイルできる必要がある。**
  Phase 3 の成果物は「全 Rust プロジェクトを解析できるツール」ではなく「固定した nightly でビルドが通る Rust プロジェクトを解析できるツール」。
  Phase 3 の最初のタスクは、`stable-mir-json` 等の既存ツールで実在のクレートがどれくらい通るかの確認。
- **理由:** 対象が新しい言語機能を使っていたり、edition や MSRV が噛み合わないと失敗する。リスクを受容した上で前提を明記する方が誠実。
- **帰結:** 想定より通らなければ、Rust の優先度を下げる判断もあり得る。

## ADR-014: ヒープはフィールド感度あり（k=3）、エイリアス解析は作らない

- **決定:**
  - フィールド感度は**フィールド名ベース**。アクセスパスの深さ上限 k の既定は 3、設定で変更可能
  - アロケーションサイトで区別するオブジェクト感度は入れない
  - コンテナ要素は区別せず、`container_element_imprecision` は**結論に影響した場合だけ**記録する
  - 完全なエイリアス解析は作らない（必要箇所の列挙に留める）
- **理由:** フィールド感度がないと構造体を一箇所触った時点で全体が汚染になり実用に耐えない。
  オブジェクト感度はコストが跳ね上がるわりに、injection 検出での見返りが薄い。

## ADR-015: 依存パッケージの境界はモデルで扱う

- **決定:** 解析するのは自モジュールのみ。依存（stdlib・第三者ライブラリ）との境界は手書きモデルで扱い、無ければ `unmodeled_library_call`。
  設定で選んだ依存だけ解析対象に含められる。
  **モデルカバレッジレポート**（`rivus models coverage ./...`）を Phase 1 に含める。
- **理由:** 依存まで全部解析すると遅くなり、ノイズも増える。
  一方、手書きモデル方式は「どこにモデルを書けば検出が改善するか」が分からないと機能しない。
  すでに `unmodeled_library_call` を記録しているので集計するだけで実装が軽く、効果が大きい。
- **帰結:** 組み込みモデルの最低ライン: Go は `database/sql`、`os/exec`、`net/http`、`html/template`、`text/template`、`strings` など。
  Dart は `dart:*` と Flutter SDK の主要部分。Rust は `std` と頻出クレート（`serde`、`tokio`、`reqwest` など）。
  すべてユーザー定義と同じ YAML 形式で書く（ドッグフーディング）。

## ADR-016: ルールは宣言的 YAML、クエリ言語は作らない

- **決定:**
  - 形式は YAML。**v1 では宣言的 YAML のみ**。QL のようなクエリ言語は作らない
  - ルールセットに名前空間とバージョンを持たせる（`rivus/go/stdlib@1`、`myorg/internal@3`）
  - シンボル指定は完全修飾名。**`match: exact` と `match: implementations` を明示的に区別する**
    - `exact`: 具体的な関数だけにマッチ
    - `implementations`: インタフェースのメソッドにマッチし、コールグラフ経由で実装に展開する。展開数の上限と `dynamic_dispatch` の記録を伴う（上限の扱いは ADR-030）
  - ジェネリクスは**型引数を消去して一致**させる
- **理由:** クエリ言語に手を出すと、それ自体が別プロジェクトになる。
  インタフェースの扱いはシンボル指定の最大の難所で、この 2 つは意味がまったく違いどちらも必要。
  型引数ごとに別ルールを書かせるのは使いづらい。

## ADR-017: extractor との通信はサブプロセス ＋ JSON Lines

- **決定:** extractor はサブプロセスとして起動し、**バージョン付き JSON Lines** で IR を受け取る。先頭行は必ず `schema_version`。
  IR ダンプ（`rivus extract --lang=... --output=ir.jsonl`）を一級の成果物にする。
  重くなったら protobuf に移行する。extractor の出力の内容アドレスキャッシュ（キー = extractor のバージョン + 入力ファイル群のハッシュ + 設定）は、Phase 1 では不要だがインタフェースだけ想定しておく。
- **理由:** Phase 4 で Dart の CFG ビルダーをデバッグするとき、IR を人間が読んで検証できることが生命線になる。JSON Lines を選ぶ最大の理由はこれ。

## ADR-018: コールグラフ構築は差し替え可能にする

- **状況:** ブリーフ側で、Go のコールグラフは VTA 既定、CHA は比較用、と提案していた。
- **訂正:** `golang.org/x/tools/go/callgraph/vta.CallGraph(funcs, initial)` は初期コールグラフを引数に取る。
  標準的な使い方は CHA（または RTA）で粗いグラフを作り、VTA で絞り込む 2 段構え。つまり **CHA は「VTA の入力として必須」**。
  実物（`golang.org/x/tools` v0.52.0）で確認した。`initial == nil` なら内部で CHA を使う。
  渡す SSA 関数は `ssa.InstantiateGenerics` 付きで構築する必要がある。結果にはルートノードがない。
- **決定:** `CallGraphBuilder` インタフェースを切り、Go は CHA → VTA の実装を `callgraph/gocg` に置く。
  Dart は `pkg/vm` の type flow analysis、Rust は monomorphize collector など、言語ごとに別実装にする。**Go 固有の手法をコアに漏らさない。**
- **理由:** 言語ごとに使える手法が違う。

## ADR-019: ライセンスは Apache-2.0

- **決定:** Apache-2.0。依存の `golang.org/x/tools` は BSD-3 で互換。

## ADR-020: Go 1.27 と `golang.org/x/tools` 最新

- **決定:** コアは Go 1.27、依存は標準ライブラリ ＋ `golang.org/x/tools`（最新）＋ YAML パーサ。CI は GitHub Actions。rivus 自身を rivus で解析できるようにする。
- **理由:** SSA / 型解決は新しい言語機能への対応がリリースごとに追加されるため、古いと Go 1.27 のコードで失敗することがある。
- **帰結:** Phase 1 では `go/ssa` に触れるコードを `internal/frontend/gossa` に隔離する（Phase 2 の IR 切り出しを楽にするため。必須）。

## ADR-021: 増分解析は当面スコープ外

- **決定:** 増分解析（変更された関数のサマリだけ再計算）は Phase 1〜4 のスコープ外。
  ただしサマリが関数単位で独立しているという性質を壊さない。
  性能目標の叩き台は「20 万行規模のプロジェクトを、ノート PC で 5 分以内」（CI の PR チェックで回せる上限）。現実的でなければレビューで見直す。
- **補足（ADR-025 を受けて）:** エージェントが問い合わせ型で使う場合、**サマリの保存と再利用**は増分解析とは別に必要になる（解析は一度、問い合わせは何度も）。
  これは Phase 1 のステップ 1.8 に含める。コード編集の合間に問い合わせる使い方が現実になった場合は、増分解析のスコープを見直す。

## ADR-022: エントリポイントを明示的に定義する

- **状況:** コールグラフの根の決め方がブリーフに未定義だった。ライブラリには `main` がなく、`exported_api_param` を定義した以上「どこから先が外部か」を決める必要がある。
- **決定:** 言語・用途ごとに既定のエントリポイントを定め（ARCHITECTURE.md 6 節）、ユーザーが追加指定する手段（ルールファイルの `entrypoints:`）も設ける。

## ADR-023: 出力量を制御し、安定 ID を振る

- **状況:** 過大近似を維持し、不確実なものを `requires_review` で残すと、検出件数が経路の組み合わせで膨大になり得て、LLM 判定のコストが破綻する。
- **決定:** 検出結果の単位は (source サイト, sink サイト) の組とし、経路はその中に入れる。1 件あたり経路数に上限（既定 3）を設け、超過分は件数のみ記録する。
  安定した ID と指紋を持たせ、「前回から新規に増えたもの」が分かるようにする（ADR-028）。
- **訂正:** 初版は「(source シンボル, sink シンボル) の組」と書いていたが、シンボルは関数の名前でありプロジェクト全体で 1 つなので、同じ関数の呼び出しがすべて 1 件に混ざってしまう。単位は場所を持つサイトに直した。

## ADR-024: テスト戦略

- **決定:**
  - 言語ごとのマイクロベンチマーク集（`testdata/`）。検出されるべきケースと、意図的に検出できないケース（「検出されないこと」を assert）の両方を置く。期待される terminal kind も assert する
  - コアの SSA 化と lifted `go/ssa` の differential test（ADR-003）
  - Phase が進むごとに、同じ意味のコードを複数言語で書いたクロス言語の等価性テストを足す（IR の中立性の検証）
  - rivus 自身を rivus で解析し、`attributable_to: rivus` の比率を監視する
- **理由:** これがないと、精度を上げたつもりで別のものを壊したことに気づけない。後から足せないので最初に決める。

## ADR-025: エージェントの道具としての使われ方と、3 段階の絞り込み

- **状況:** ブリーフは「LLM が判定するための材料を出す」ことを前提にしていたが、
  利用者として具体的に想定していたのは、判定結果を受け取る後段の LLM までだった。
  レビューで、**脆弱性の有無を判定する LLM エージェントが、コード分析の道具として rivus を呼び出す**使い方が主要なユースケースだと明確になった。
  エージェントは、軽量な（grep より賢い）判定器で疑わしい箇所をまず列挙し、気になる箇所を rivus で詳細に分析する、という 2 段構えで使う。
- **決定:**
  - 絞り込みを rivus の機能として持つ。3 段階とする。
    - **L0**: ルールの source / sink にマッチする**サイト**（箇所）を列挙する（ローダ ＋ シンボル照合のみ。ほぼ即時）
    - **L1**: L0 に加え、sink の引数がリテラル定数だけのものに印を付ける（落とさない。同じ関数内で完結する決定論的な事実）
    - **L2**: 詳細分析（サマリ、ラベル、由来追跡、不確実性の記録）
  - コマンドは `rivus sites`（L0 / L1）と `rivus query --site <ID>`（L2）。サイトには安定した ID を振り、L2 の seed に使う
  - 呼び出し口はまず CLI ＋ JSON 出力。`query` 層は差し替え可能に保ち、必要になれば常駐サーバ（MCP など）を足す
  - 出力の詳細度を選べるようにする（概要のみ / スニペット付き / 関数全文付き）
  - 性能目標を、一括解析と問い合わせ応答の 2 軸にする
- **理由:** L0 / L1 は判定ではなく列挙なので ADR-001 と矛盾しない。
  必要な部品（ローダ、シンボル照合）は Phase 1 で作るもので、追加コストがほぼない。
  grep と違って型解決つきなので、同名の別物を拾わず、別名インポートなども拾える。
  エージェントはコンテキストに制約があるので、出力の量を制御できることが実用上の要件になる。
- **帰結:** Phase 1 にステップ 1.2b（サイト列挙）を追加し、ステップ 1.8 にサマリの保存・再利用を含める。
  サイトの列挙は IR の `call` で行うので言語中立。
  ADR-010 の `origin` と `--deterministic-only` は、エージェントが「どこまで rivus の事実で、どこから推測か」を区別するために、重要度が上がる。

## ADR-026: 自作 SSA 化と differential test は Phase 1 終盤に導入する

- **状況:** コアの SSA 化（`ssabuild`）と、lifted `go/ssa` を oracle にした differential test（ADR-003）を、いつ導入するか。
- **検討した案:**
  - 案 P: Phase 2 で導入。Phase 1 は `go/ssa` だけで済み、設計に集中できる。ただし Phase 2 で SSA 化のバグと IR 切り出しのバグが同時に出て、切り分けが難しい
  - 案 Q: Phase 1 の早い段階で導入。バグを早く潰せるが、Phase 1 の目的（理論と設計を固める）から外れ、ブリーフの順序ともずれる
  - 案 R: Phase 1 の終盤で導入
- **決定:** **案 R。** Phase 1 のステップ 1.11b で導入する。
- **理由:** 解析の設計がほぼ固まり、`testdata` が揃った後なら、SSA 化の問題は「検出結果が変わった」という形で検知できる。
  Phase 2 の前に SSA 化だけを単独で検証できるので、Phase 2 の不確実性は「IR を挟むこと」だけに絞れる。
  ブリーフの順序への抵触も最小限。
- **帰結:** Phase 2 は `gossa` を extractor に置き換えて IR を挟むことに集中できる。

## ADR-027: 性能目標は仮説として置き、実測で確定する

- **状況:** ブリーフに性能目標がなかったため、ADR-021 で叩き台を置いた（20 万行 / ノート PC / 5 分以内）。
  実装前なので、数字の根拠は確かでない。言語によって難しさが大きく違う（Go は型解決と SSA 構築、Dart は `package:analyzer` のコールド解析、Rust は rustc のビルド時間が下限になり得る）。
  エージェントが CLI で何度も問い合わせる使い方では、呼び出しのたびにソースをロードすると応答が遅くなる。
  想定する対象は、プライベートの実プロジェクト（20 万行はありうる）と、著名 OSS。
- **検討した案:** A: 暫定の数字を置き、実測で見直す／B: 数字を置かず測る方針だけ決める／C: 今、厳しい数字を置く。
- **決定:** **案 A。**
  - 一括解析 20 万行 / 5 分と、問い合わせ応答「数秒以内」は仮説とし、ステップ 1.8 の実測で確定する。メモリは 8GB を目安とする
  - 当面の対象は Go のみ。Dart と Rust の数字は、Dart スパイクと Phase 3 の最初の調査の後に置く
  - 規模を小 / 中 / 大 / 超大の階層に分け、20 万行を目標の上限とする。超大は約束せず、段階的に劣化させる（上限に達したら打ち切って記録する）
  - 各階層の実在の Go プロジェクト（著名 OSS を含む）を参照コーパスとして選び、計測値を記録する
  - ロードエラーがあっても全体を失敗させず、解析できた範囲で続行し、`missing_source` として記録する
  - クエリ時にソースのロードをやり直さないよう、サマリ・コールグラフの辺・位置情報を保存する
- **理由:** 根拠のない数字を確定すると、設計を誤った方向に縛る。かといって基準がないと「遅すぎる」の判断ができない。
  著名 OSS で回したい以上、実在のプロジェクトの雑多さ（cgo、ビルドタグ、ロード失敗）に耐えることは、性能と同じくらい重要な要件になる。
- **帰結:** ステップ 1.8 に実測を含める（応答時間の初回計測、ADR-025）。ステップ 1.12 でも `depth_limit` の比率とあわせて計測値を記録する。

## ADR-028: サイトと検出結果の ID は指紋の入れ物で表す

- **状況:** ID は CI の差分（前回から増えた検出）、エージェントによる再参照、注釈の保存に使う。
  行番号に依存する ID は、行のずれで壊れる。一方、「ID が同じなのにコードの中身が変わっている」状態は、古い判断（「安全」という注釈）が変わったコードに残るため、偽の「新規」より危険である。
- **検討した案:**
  - V1（構造キー）: 関数 ID ＋ ルールのシンボル ＋ 同じ関数内での出現順。引数の書き換えには強いが、同じシンボルの呼び出しを前に挿入すると後ろの出現順がずれる
  - V2（内容キー）: V1 の材料のうち出現順を、呼び出し式のハッシュ ＋ 同一テキスト内の出現順に替える。挿入には強いが、引数の書き換えに弱い
  - コールグラフ上の位置を ID の材料に加える案: 無関係な変更・rivus の改善・エントリポイント設定で ID が揺れ、`rivus sites` がコールグラフなしで即時に返せなくなるため不採用
  - simhash を ID に使う案: ID は完全一致で引く鍵であり、「近い」では役目を果たさないため不採用。比較時の補助として使う
- **決定:**
  - サイトと検出結果は、**指紋（fingerprint）の入れ物**に複数の種類を並べて持つ。種類は役割で名付け、版は `@N` で表す
  - 種類: `structural@1`、`content@1`（同一性）、`expr@1`、`body@1`（変化検知）、将来 `sim@1`（類似度）
  - 公開用の `id` は `structural@1` から作る（`s1:` 付き）。検出結果の指紋は、source と sink の同じキー名ごとに合成する
  - 旧新の対応付けは、同一性のキーを優先順位順（内容 → 構造 → 類似度の候補）に当てる。注釈は (ID, 変化検知キー) の組に紐づける
  - Phase 1 では指紋の出力と、ブックマークによる対応付け（ADR-029）まで作る。旧新の結果どうしの比較機能（`rivus diff`）と simhash は、需要が出てから作る
- **理由:** V1 と V2 は失敗する場面が逆なので、両方を持つと片方が外れてもう片方で当たる。
  内容キーを先に当てるのは、構造キーだけだと挿入のときに誤った相手と結び付くため。
  指紋を入れ物にすると、新しい種類のキーを足してもデータ構造とマッチャーを変えずに済む。
  ID は同一性、変化検知は判断の有効性、と役割を分けることで、ID を安定側に倒しても見落としにつながりにくい。
- **帰結:** 版をまたぐ同一性は ID だけで保証するものではなく、比較時の対応付けで成立する。CI の「新規」判定は、もともと前回の結果（ベースライン）との比較が要るので、これで足りる。
  simhash は決定論的でなければならない（トークン化の規則、ハッシュ関数、次元数を固定し、キー名の `@N` で版を表す）。
  リネームや抽出（関数 ID が変わるケース）への耐性は、`sim@1` と比較機能で後から足す。

## ADR-029: エージェントのブックマークと `rivus resolve`

- **状況:** エージェントは、前回の探索で見た箇所を ID で記録しておき、あとで再び見る。コードが変わると、記録した ID が現在のコードで引けなくなる（ID の付け替えが必要になる）。
  また、検出結果（source から sink に届く）を記録していた場合は、サイトが残っていても、途中に sanitizer が追加されるなどして**届かなくなっている**ことがある。
- **決定:**
  - エージェントは ID だけでなく、**指紋全体とスニペットを含むブックマーク**を保存する。保管はエージェント側の責務で、**rivus はステートレスのまま**
  - 新コマンド `rivus resolve` を作る。複数のブックマークをまとめて受け取り（ソースのロードは 1 回）、保存された指紋を現在のコードに当てて、ブックマークごとに状態を返す
  - 状態は `unchanged` / `changed` / `rematched` / `ambiguous` / `unresolved`。`unresolved` の理由は `not_found`（解析できているが該当なし）と `not_analyzed`（読み込めなかった。`missing_source` と同じ）に分ける
  - 付け替えは、内容キー → 構造キー →（将来）類似度の順に当てる。構造キーだけで当たった場合は、一致の根拠（`MatchBasis`）と同じ関数内のサイト数の変化などの事実を添え、確実のように見せない
  - 検出結果のブックマークには `flow`（`present` / `absent_now` / `not_evaluated`）を返す。`absent_now` は「届く経路が見つからない」という事実であり、安全の判定ではない。見つけられなかった理由も一緒に返す
  - 検出結果の指紋に `path@1`（経路の指紋）を足し、同じ組でも経路が変わったことを検知できるようにする
- **理由:** ブックマーク自体が「前回の記録」の役目を果たすので、前回の解析結果（ベースライン）ファイルを要しない。状態を持たない方が rivus は単純に保てる。
  ID だけを覚えていると、コードが変わったときに「見つからない」としか分からないが、指紋を持っていれば「どう変わったか」まで答えられる。
  検出結果で重要なのは「サイトがあるか」だけでなく「今も届くか」であり、届かなくなった理由（sanitizer の追加か、rivus が追えなくなったか）を区別できることが、エージェントの判断材料として最も価値が高い。
- **帰結:** Phase 1 にステップ 1.8b を追加する（指紋の出力は 1.2b、クエリは 1.8 に依存）。
  ADR-001（判定をしない）との線引きとして、`absent_now` や `rematched` は「事実と根拠」を返すだけで、同一かどうか・安全かどうかは判定しない。
  `rivus diff`（旧新の結果どうしの比較）は、`rivus resolve` と同じ対応付けのロジックを共有するので、後から低コストで足せる。

## ADR-030: `match: implementations` の展開上限と sanitizer への展開の禁止

- **状況:** `match: implementations`（ADR-016）は、インタフェースのメソッドに書いたルールを、全実装に広げて適用する。
  実装の数はインタフェースごとに大きく違う（`http.Handler.ServeHTTP` は 100 を超えることが普通で、展開が欲しい結果。`io.Writer.Write` のように、展開するとノイズが洪水になるものもある）。
  初版は「既定上限 20」と書いていたが、根拠はなかった。
- **検討した案（上限を超えたときの振る舞い）:**
  - 切り捨て（先頭 N 個だけ展開）: どれを残すかが恣意的で、見逃しを作る。「列挙は網羅的に」に反する
  - 展開を中止: 何も広がらない代わりに、何を見ていないかが明確に分かる
  - 上限なし: コストが跳ね上がる可能性がある
- **決定:**
  - 上限を超えたら**展開を中止**し、`exact` と同じ扱いに縮退する。総数を `dynamic_dispatch`（`attributable_to: mixed`、サブ理由 `expansion_limit`）として記録する
  - 既定の上限は**暫定 100**。ステップ 1.9 で参照コーパスを使って実測し、確定する。ルールごとに `max_implementations` で上書きできる
  - **sanitizer への `implementations` は既定で禁止**する。許可するときはルール側で明示する（`allow_sanitizer_expansion: true`）
- **理由:** 展開の影響は役割によって向きが逆。source / sink / propagator を広げ過ぎるとノイズが増えるだけだが、
  sanitizer を広げ過ぎると、sanitize していない実装にまで「通れば安全」が及び、汚染が消えて見逃しが生まれる。これは rivus が避けるべき方向。
  部分的に展開すると境界が見えなくなるが、中止なら「このルールは展開していない」と明確に言える。
  インタフェースごとに適切な数が違うため、全体の既定値は暫定とし、ルールごとの上書きを許す。
- **帰結:** 展開を中止した件数は集計でき、既定値の見直しや、ルールごとの `max_implementations` の調整に使える。

## ADR-031: Phase 1 の解析エンジンの実装方式（M2 時点）

Phase 1 のステップ 1.0〜1.8（1.8b は除く）を実装した時点で決めた、実装上の判断を記録する。
ADR-003〜006、014、015 の方針を具体化したもので、方針自体は変えていない。

- **状況:** ADR-004 は bottom-up のサマリ方式を定めたが、サマリの表現と、手続き内の解析との関係は未定だった。
- **決定:**
  - **サマリは記号的な汚染から作る。** 関数の各引数（レシーバ、自由変数を含む）に「呼び出し側が渡すもの」を表す記号的な要素（`Param`）を置いて関数を解く。
    解いた結果（戻り値、引数の指す先、グローバル変数のセルに入った要素）が、そのままサマリになる。
    呼び出し側は、記号的な要素を実引数の汚染で置き換える。手続き内の解析と手続き間の解析が同じ仕組みになり、sink に届く引数の情報（`SinkReach`）も同じ形で持てる
  - **汚染はセル（根 ＋ アクセスパス）のラベル集合で持つ。** 根は SSA 値、複数戻り値の i 番目、または関数の i 番目の戻り値。パスは `/フィールド名`、`/[]`（要素）、`[k]`（map のキー）、`/*`（ポインタの指す先）
  - **ポインタ・スライス・map・channel は「指す先」の位置を値の位置とする。** 同じ SSA 値から派生した参照は同じ位置を指す（値の流れによる別名の追跡だけ。エイリアス解析ではない）。
    ポインタをメモリに保存した場合は、保存先の `/*` に指す先のコピーを置く
  - **ラベル要素は発生元のサイト ID を持つ。** `Real{Label, Origin}`。sink に届いた要素の `Origin` から、検出結果の source が分かる
  - **サニタイザーは `drops` と `adds`。** `adds` は、落としたラベルがあった値にだけ付く（`html_escaped` のように、他の sink にはまだ危険なものを表す）。記号的な要素は操作を `Mods` に覚え、実引数が分かったときに適用する
  - **経路を記録する。** 各要素が各セルに初めて入った理由（命令、元のセルと要素）を残し、sink からたどって経路を復元する。サマリは、関数内の経路をステップとして持ち、呼び出し側で継ぎ足す。検出結果 1 件につき、経路は最短の 1 本のみ（`omitted_paths` は未実装）
  - **関数の内部は、フロー非依存のメモリ ＋ SSA のレジスタ。** メモリのセルは弱い更新（和集合）で、関数内でフロー非依存。レジスタは SSA でフロー依存
  - **グローバル変数は、プログラム全体で 1 つの状態**（フロー非依存）。関数が書いたものを集め、読む関数を再解析する
  - **再解析は、SCC の順（呼び先から）に、サマリが変わった関数の呼び出し元と、グローバルが変わったときの読み手だけを対象に行う。** 不動点まで繰り返す（上限あり）
  - **モデルがある関数は、ボディがあってもモデルを使う**（手書きモデルによる上書き）。sink / source のルールだけの関数は、ボディがなくても「モデルあり」とし、不確実性を出さない
  - **モデルも本体もない関数呼び出しの既定:** 引数（レシーバを含む）の汚染が、bool 以外のすべての戻り値に流れるものとし、`unmodeled_library_call` を経路に記録する（過大近似 ＋ 記録、ADR-007）。呼び先が分からない場合は `unresolved_callee`、インタフェース呼び出しで実装が分からない場合は `dynamic_dispatch` を記録する
  - **インタフェース呼び出しと関数値の呼び出しは、コールグラフ（CHA → VTA）の辺で解決する。** 候補が複数あるか、インタフェース呼び出しなら、`dynamic_dispatch`（候補付き）を経路に記録する。その場で作ったクロージャの呼び出しは、束縛された値を直接使う
  - **ルールのシンボルは `go/types` の `FullName` 形式**（例 `(*net/http.Request).FormValue`、`os/exec.Command`、`(io.Writer).Write`）
  - **ルールの種類:** source は `call_result`（呼び出しの結果）、`param_type`（その型の引数すべて。ハンドラの入口を型で表せる）、`field`（構造体フィールドの読み出し）
  - **無限に広がらないための上限:** アクセスパスの深さ（k=3）、記号的な要素のパスの長さ（k）、サニタイズ操作の記憶（4 個まで。超えたら忘れる。忘れると汚染が多く残る側で、安全側）、経路のステップ数（200）
- **理由:** サマリを別に設計せず、関数を記号的な汚染で解くことで、手続き内と手続き間の解析が分かれず、実装と検証が小さく済む。
  上限は、実在のコード（ghmint）で、上限がないと再帰する構造体のパスやループ中のサニタイズが要素を無限に増やし、メモリが数 GB になって終わらなかったことを受けて入れた。
- **性能のために入れた仕組み（計測は ADR-027 の「初回計測」を参照）:**
  - **呼び出しの入力が変わっていなければ、その呼び出しの処理を飛ばす。** 各セルの根に「追加された要素の数」を持たせ、呼び出しが読む根の値の和が前回と同じなら、サマリを再適用しない
  - **セルの並び順（ソート結果）のキャッシュと、サマリ適用中の読み出し・展開のメモ化。** 集合は増える一方なので、長さが同じならキャッシュは有効
  - **経路をロープ（O(1) で連結できる共有構造）で持つ。** 要素ごとに経路全体をコピーすると、`x/tools` で 5,900 万ステップのコピーになり、メモリと GC が支配的になった
  - **出力の要素が 24 個を超えたら、同じ引数・同じサニタイズ操作の記号的な要素を「引数全体」の 1 つに統合する（widening）。** 「この引数のどこからでも来うる」という、真実より広く、狭くはならない近似。これがないと、ポインタを多用するコードでサマリがフィールド数の組み合わせ（k=3）で増え、`x/tools` で 1 関数 8 万要素になった
  - **サマリは前回との和集合に取る。** 解析は呼び先のサマリに単調なので通常は変わらないが、widening や相互再帰（インタフェース経由の `GenValue`）でサマリが増減を繰り返し、60 パスでも収束しなかったことを受けて、増える一方にして終了を保証する
  - **関数ごとの予算（既定 40 万回の追加）と、全体の時間制限（`-timeout`）。** 超えたら、その関数（または残りの関数）の解析を打ち切り、`depth_limit`（`attributable_to: rivus`）として記録する。打ち切られた関数は再解析しない
- **帰結（既知の限界）:**
  - widening と予算の打ち切りは、サマリを粗くするか、未完成のままにする。前者は過大近似（安全側）、後者は見逃しうるので、必ず `depth_limit` として出力に残る
  - 別名（同じ配列を指す 2 つのスライス、ポインタを介して共有されるオブジェクト）を介した書き込みは、元に反映されない（見逃しうる）。`container_element_imprecision` の記録は今は出していない
  - 関数値として別の場所に保存したクロージャを、後から呼ぶ場合は、束縛された値が分からない
  - 検出結果の経路は 1 本
  - 値依存のサニタイズ（ガード）、由来追跡、`match: implementations`、`rivus resolve` は未実装（ステップ 1.9 以降と 1.8b）
  - 出力の要素数が多い関数の経路は、widening により「どの部分から来たか」が粗くなる
  - Phase 1 の解析エンジンは `go/ssa` に直接依存する（ARCHITECTURE の「`go/ssa` に触れるのは `gossa` と `gocg` のみ」の例外）。Phase 2 で IR に移す

### ADR-027 の追記: 初回計測（Phase 1 M2 時点、ステップ 1.8）

環境: Apple Silicon の Mac（darwin/arm64、Go 1.27.3）。メモリ使用量は計測していない。

### ADR-030 の追記: 実装と実測（ステップ 1.9）

- **実装:** ルール（source の `call_result`、sink、sanitizer、propagator）に `match: implementations` と `max_implementations` を書ける。
  sanitizer は `allow_sanitizer_expansion: true` がないとルールの読み込みでエラーになる。
  展開は `go/types` で行い、**読み込んだパッケージ（自モジュール）の型だけ**を探す（依存は境界で、モデルを別に持つため、ADR-015）。
  `(error).Error` のようにパッケージを持たない型も扱える。展開した結果は `Rules.Expansions` とレポートの `expansions` に残り、上限超過は `dynamic_dispatch`（サブ理由 `expansion_limit`、`mixed`）として出力に出る
- **実測（自モジュールの型の中の実装数）:**

  | インタフェースのメソッド | ghmint | rivus 自身 | x/tools |
  |---|---|---|---|
  | `(fmt.Stringer).String` | 0 | 4 | 165 |
  | `(sort.Interface).Len` | 0 | 0 | 21 |
  | `(io.Reader).Read` | 0 | 0 | 6 |
  | `(io.Writer).Write` | 1 | 0 | 3 |
  | `(net/http.Handler).ServeHTTP` | 1 | （net/http を読み込んでいない） | 1 |

  taint のルールに使いそうなインタフェース（`Reader`、`Writer`、`Handler`）は、実装が 1 桁にとどまった。
  100 を超えたのは `Stringer` だけで、これは汚染のルールの対象になりにくい、どこにでもあるインタフェース。
- **決定（レビューで確定）:** 既定の上限を **300** にする。展開の計算は軽く（x/tools に 6 つのインタフェースを展開しても約 40 ms で、上限 100 と 10 万で差がない）、
  上限の役目は、書き間違いで `Stringer` のようなインタフェースを広く展開してしまう事故を止めること。実装が多いインタフェースに意図して書くルールは、`max_implementations` で個別に上げる。
  展開した結果の解析の重さは別で、広く呼ばれるメソッドを sink にしたときの重さは ADR-032 の「性能の注意」を参照

## ADR-032: 不確実性の記録の範囲と集計（ステップ 1.9）

- **状況:** ADR-007 は「扱わなかった箇所は必ず出力に記録する」とした。ステップ 1.3〜1.8 までは、呼び出し関連（モデルなし、解決できない、インタフェース越し）しか記録していなかった。
  別名を介した書き込み、goroutine と channel、パッケージ変数、reflection は、黙って通り過ぎていた。
- **決定:** 記録の置き場所を 2 つに分け、kind を次のように記録する。
  - **プログラム全体の一覧（`uncertainties`）:** その場所そのものが分かっていないもの。`unmodeled_library_call`（`rivus`）、`dynamic_dispatch`（`mixed`、候補つき）、`unresolved_callee`（`mixed`）、`reflection`（`target`）、`ffi_boundary`（`target`）、`depth_limit`（`rivus`、関数の予算超過、時間切れ、展開の上限超過）、`recursion_approximation`（`rivus`）、`missing_source`（`target`、ロードエラー）
  - **検出結果の経路の区間（`findings[].uncertainties`、各ステップの `notes`）:** その区間を通った検出結果にだけ付く。`container_element_imprecision`（`rivus`。スライス・配列・map・channel の要素の出入り）、`concurrency`（`mixed`。channel、`select`、`go` 文）、`global_var`（`target`。パッケージ変数の読み出し。直接の書き手を候補として列挙する）、ほか `dynamic_dispatch` と `unmodeled_library_call`
    「結論に影響した場合だけ」記録するというルール（ADR-014）を、経路上にあるかどうかで実現した。1 つの区間が複数の不確実性を持てる
  - **集計（`summary`）:** プログラム全体の一覧を kind と `attributable_to` ごとに数え、`rivus` の比率と `depth_limit` の比率、各 kind が付いた検出結果の数を出す。ADR-008 のフィードバックループ
- **未実装・未検証:**
  - `exported_api_param`、`config_read`、`literal` は、由来追跡（ステップ 1.10）の打ち切りの種類で、まだ出ない
  - cgo（`C` パッケージ、`_Cfunc_`）の検出は実装したが、cgo を使ったテストは書いていない。アセンブリやリンクネームで本体のない関数は、`unmodeled_library_call` になる
  - `container_element_imprecision` は、要素への出入りに必ず付くので、スライスを使う経路ではほぼ毎回付く。見た目のノイズになるか、実測と運用で見る
- **実測（プログラム全体の一覧の内訳。`dynamic_dispatch` の帰属を変えた後、完全に収束した実行）:**

  | 対象 | 件数 | `rivus` | `mixed` | `target` | `depth_limit` の比率 |
  |---|---|---|---|---|---|
  | ghmint | 288 | 87% | 13% | 0% | 0% |
  | rivus 自身 | 390 | 93% | 7% | 0% | 0% |
  | x/tools（15.6 万行、96 秒、2 パスで収束） | 12,350 | 78% | 19% | 3% | 0.02% |

  `rivus` の大半は `unmodeled_library_call` と、実装が分からない `dynamic_dispatch` で、どちらもモデルを書けば減る。
  上位は `fmt.Fprintf`（505）、`(*go/types.object).Type`（232）、`strings.HasPrefix`（164）、`(go/types.Type).Underlying`（91）、`(context.Context).Err`（37）など。
  `summary.top_symbols` が、この一覧を出す（ステップ 1.11 のモデルカバレッジレポートの土台）
- **訂正:** この ADR の初版には、x/tools の件数を 5,444（`rivus` 67%、`mixed` 30%）と書いたが、**これは 255 秒の時間制限で打ち切られた、途中までの実行の値だった**（計測用に広い sink ルールを足したため。下の「性能の注意」参照）。上の表が正しい
- **`dynamic_dispatch` の帰属（ステップ 1.9 の相談で決定）:** 呼び先の候補が 0 件のとき（標準ライブラリなど、実装が読み込んだコードの外にある）は `rivus`（モデルを書くと減る）、1 件以上のときは `mixed`（VTA の精度向上で減らせる余地がある）。
  種類は変えず、`attributable_to` を呼び出しごとに決める。x/tools の候補数の分布は 0 件 616 / 1 件 217 / 2〜5 件 623 / 6〜20 件 425 / 21 件以上 213（`summary.dispatch_candidates`）。
  候補 1 件の記録を残す是非と、`mixed` の細かい分け方は、ステップ 1.12 で、より多くのコードの分布を見て決める
- **性能の注意:** `(error).Error`、`(io.Writer).Write`、`(fmt.Stringer).String` のように、**至る所で呼ばれるメソッドに sink ルールを書くと、解析が大幅に遅くなる**。
  x/tools で、こうしたインタフェースメソッドを 6 つ sink にしたところ、96 秒の解析が 255 秒でも終わらなかった（展開なしでも同じ。原因は展開ではなく、呼び出しの数）。
  全ての呼び出しが sink になり、各関数のサマリに「引数が sink に届く」記録が大量に残るため。ルールを書くときは、狭く書く。サマリの `SinkReach` を粗くする対策（出力要素の widening と同様）は未実装
- **帰結:** 経路の区間に付く不確実性は、出力の `notes` を見れば、LLM が「この経路のどこが怪しいか」を種類別に読める。
  `mixed` の割り当て（ADR-008）を見直す材料として、`dynamic_dispatch` の候補数の分布などの追加の計測が要る（レビュー待ち）

## ADR-033: `rivus resolve` の実装（ステップ 1.8b）

ADR-029 の設計を実装した。設計から変えた点と、実装で決めたことを記録する。

- **ブックマークの形式を新しく作らなかった。** rivus が出力した検出結果とサイトの JSON を、そのまま渡せる（配列、`{"bookmarks": [...]}`、単体のどれでもよい）。
  そのために、検出結果の `source` / `sink` にサイトの指紋（`fingerprint`）を入れた。ID だけのブックマークは、指紋がないので受け付けない（エラー）
- **対応付けの順序:** 内容キー（`content@1`）→ 構造キー（`structural@1`）。複数に当たったら `ambiguous`（候補を返し、1 つを選ばない）。
  変化検知（`expr@1`、`body@1`）は、見つかった後に比べる
- **状態の決まり方:**
  - 内容キーで当たり、ID が同じで、変化検知キーが同じ → `unchanged`
  - 内容キーで当たり、ID が同じで、変化検知キーが違う → `changed`（`changed_keys` に違うキー。関数の本体が変わっただけなら `body@1`）
  - 内容キーで当たり、ID が違う（同じシンボルの呼び出しが前に挿入されたなど）→ `rematched`、根拠は `content@1`
  - 構造キーだけで当たった → `rematched`、根拠は `structural@1`。式が書き換えられたか、似た呼び出しが前に増減した可能性があるので、記憶していたスニペット（`previous_snippet`）と現在のスニペットを並べて返し、`evidence` に理由を書く
  - どちらも当たらない → `unresolved`。理由は `not_analyzed`（そのパッケージが解析対象になかった、またはロードに失敗した）か `not_found`（解析したが見当たらない）。この区別のために、レポートに解析したパッケージの一覧（`packages`）を持たせた
- **検出結果のブックマーク:** source と sink の両方を同じ手順で対応付け、状態は両者のうち「大きい方」（`unresolved` > `ambiguous` > `rematched` > `changed` > `unchanged`）。
  さらに `flow` を返す:
  - `present`: 現在の検出結果に、対応付けた source と sink の組がある。`path@1` が記憶と違えば `path_changed: true`
  - `absent_now`: 両端は見つかったが、その組の検出結果がない。**安全の判定ではなく**、見つけられなかった事実として、2 つの関数の中の不確実性と、実行全体に関わる不確実性（`depth_limit`、`missing_source` など。最大 20 件）を添え、source か sink を共有する別の検出結果（`related_findings`）も示す
  - `not_evaluated`: 両端のどちらかが見つからない
- **入力のソース:** 現在のコードを解析する（`rivus resolve -bookmarks b.json ./...`）か、保存した index に対して行う（`-index idx.json`、ソースを読み込まない）
- **検証:** 使い捨てのモジュールを編集して、行のずれ、関数本体の変更、引数の書き換え、同じ呼び出しの前への挿入、sanitizer の追加、関数の削除、パッケージの未解析、コンパイルできないパッケージ、index 経由、指紋のないブックマークの拒否を確かめるテストを書いた
- **未実装:** 類似度（`sim@1`）による対応付けの候補提示。リネームや移動で関数 ID が変わった場合は、`unresolved`（`not_found`）になる（ADR-028 の「後回し」のまま）

## ADR-034: モデルの運用機能（ステップ 1.11）

- **状況:** 不確実性の大半（`rivus` に帰属する 74〜93%）は、モデルを書けば減る（ADR-032）。そのための道具と、LLM が書いたモデルを監査できる仕組みが要る（ADR-010）。
- **決定:**
  - **`rivus models coverage`:** モデルのない呼び出しを、**検出結果の経路に載っている数（`findings`）、呼び出しの数、関数の数**の順に並べる。対象は `unmodeled_library_call`、`reflection`、実装が分からない `dynamic_dispatch`。
    `-yaml` で、埋めるためのルールファイルのひな形を出す（流れ方は仮置きで `TODO` を付ける。人が決める）。`-index` で保存した結果から出せる。出力したひな形は、そのままルールとして読み込める
  - **`pure: true`（propagator）:** その関数を通って汚染は流れない、というモデル。ロック、時計、ログ、述語など。
    「引数が戻り値に流れる」という保守的な既定と、それに伴う不確実性をなくす。組み込みに、よく出る標準ライブラリの関数（`sync`、`time`、`log`、`strings` の述語、`sort` など）を足した
  - **モデルの出所（`origin: builtin | human | llm`）:** どのルールにも付けられ、ルールセットの先頭に書けば既定になる（書かなければ、組み込みは `builtin`、ほかは `human`）。
    `llm` のルールは `decided_at`、`rationale`、`model_version` を必須とし、欠けるとルールの読み込みでエラーになる
  - **`--deterministic-only`:** `origin: llm` のルールをすべて無視して解析する。出力に `deterministic_only` と、無視した数（`ignored_models`）が残る
  - **出力に残す記録:**
    - 検出結果の `models`: 経路で何かを決めたモデル（source と sink のルール、通った sanitizer と propagator）とその出所。`llm_influenced` は、そのうち 1 つでも `llm` なら true
    - `suppressions`: `origin: llm` の sanitizer が、実際に汚染を落とした場所（モデル、位置、落としたラベルと、その発生元のサイト）。検出結果自体がなくなるので、検出結果には書けない
  - **`param` 型の source:** 関数のシンボルと位置（`params`、`recv`）で、フレームワークが汚染を渡す入口を宣言できる。`match: implementations` と組み合わせられる。
    ARCHITECTURE 6 節にある `entrypoints:` セクションの実体はこれで、source の 1 種として実装した（別のセクションは作っていない）
- **効果（組み込みモデルの追加前後。検出結果は変わらない）:**

  | 対象 | 不確実性の件数 | `rivus` の比率 | 検出 |
  |---|---|---|---|
  | ghmint | 288 → **170** | 87% → 80% | 15 件のまま |
  | rivus 自身 | 390 → 337 | 93% → 92% | 0 件のまま |
  | x/tools | 12,350 → 10,638 | 78% → 74% | 4 件のまま |

  `pure` を外すと対応するテストが失敗することを確かめてある（モデルが効いている）
- **見送ったもの:** 検出結果ごとの複数経路と経路数の上限（現状は経路 1 本で足りている）。LLM の判定をモデルのファイルに書き戻す機能（形式は決めたが、書き戻す道具は作っていない）。
  `models coverage` のひな形は `propagator` の仮置きのみで、sanitizer や sink のひな形は出さない
- **帰結:** ルールを書く人（と、書かせる LLM）は、`models coverage` で優先順位を決め、`-yaml` のひな形から始め、`origin` を付け、`--deterministic-only` で影響を確かめられる

## ADR-035: 値依存のサニタイズと由来追跡（ステップ 1.10）

ADR-006（ガードは引数由来の条件だけ、上限 4 個、判定しない）の方針を実装した。

- **ガード（`Guard`）:** 分岐の条件が引数（レシーバ、自由変数を含む）に由来するとき、その分岐の「どちらの側か」を記録する。
  条件が引数に由来するかは、条件の値を演算の被演算子（オペランド）でたどって、引数に着くかで決める（関数の中だけ。メモリ経由のたどりはしない）。
  条件のソース上の文字列は、分岐の先のブロックにある最初の命令の位置から、`if` / `for` の条件を探して得る（go/ssa の `If` 命令には位置がなく、条件が引数そのものだと、条件を評価する命令がないため）。
  ガードは、ある側にしか入れないブロック（その側の後続が分岐元だけから入られ、そのブロックを支配する）にだけ付く
- **どこに記録するか:** 流れが合流する、または出ていく 3 か所だけ。`Phi`（合流点の辺ごと）、`Return`（その基本ブロック）、sink の呼び出し（その基本ブロックと、そこまでの経路）。
  全ての命令に付けると、ループや早期 return の条件が至る所で付いて、1 つの流れに上限（4 個）を超える数のガードが付くため
- **流れは、ガードを持つ:** サマリの出力要素（`OutElem`）と sink 到達（`SinkReach`）が、そこに至る経路上の記録のガードの和集合を持つ。
  同じ要素が別のガードで（またはガードなしで）着いたら、どの条件も当てはまらないものとしてガードを外す（条件を狭く言うと、流れを見落とすため）。
  4 個を超えたら、ガードを外し（「どんな条件でも起こりうる」という広い側）、`depth_limit`（サブ理由 `guard_limit`、`rivus` に帰属）を関数ごとに記録する
- **呼び出し側での具体化:** 呼び先のガードを呼び出し側から見るとき、その呼び出しと、条件が依存する引数に渡している式を持たせる（`call_site_argument`、`argument`）。
  ガードは、呼び出しごとに 1 回だけ具体化される（最も内側の呼び出し）
- **定数による特殊化（ADR-006 の 3 つ目）:** 条件が依存する引数がすべて定数で、条件が引数・定数・否定・比較だけで書かれているとき、条件を厳密に評価する。
  評価の結果、その流れが起こらない側なら、その呼び出しを通る流れを捨てる。これは判定ではなく、定数の条件の評価（決定論的な事実）である。
  例: `render(s, true)` は、`escape == false` で素通しする流れを持たない。条件が定数だけで決まらないとき（計算が複雑、定数でない引数）は、何も決めない
- **値依存ノード（`conditional_nodes`）:** 検出結果の経路で出会ったガードごとに 1 つ。**関数の両側（条件が真のとき・偽のとき）に、流れがあり、その中身が違うときだけ**出す（早期 return のような片側だけの条件は出さない）。
  内容は、関数名、条件の位置、`kind`（`value_dependent_sanitization`: 一方が sanitize され、他方が素通しなど。それ以外は `value_dependent_flow`）、条件の文字列、依存する引数（`parameter 1 (escape bool)`）、
  `outcomes`（`"<条件> == true"` と `== false` ごとの結果。`sanitized by <モデル>` や `tainted (passthrough)`）、呼び出しの文と引数の式、引数が定数か（`resolved`）、関数のソース、由来追跡。
  結果は関数のサマリから作る。どちらが起こるかは書かない
- **由来追跡（`provenance`）:** 条件が依存する引数の値を、呼び出し側から後ろ向きにたどる。
  `resolved` は定数（`literal`）または、誰も設定しないフィールド（`zero_value`。そのオブジェクトのアドレスが外に渡っていないときだけ）に着いた値、
  `unresolved` は辿れなくなった所で、**terminal kind** で分類する: `exported_api_param`（呼び出しがなく、公開関数の引数）、`config_read`（ルールの `config_reads`: `os.Getenv` など）、`global_var`（書き手を列挙）、
  `dynamic_dispatch`、`unmodeled_library_call`、`reflection`、`container_element_imprecision`、`depth_limit`（深さ 6、300 ノード、呼び出し元 8 件が上限）。
  比較の相手の定数は、値の由来ではないので辿らない
- **検証:** `render(s, escape)` の例（ブリーフと同じ形）を含む `testdata/go/cases/guard` で、ノードの中身、定数の呼び出し、早期 return、ガードの数の超過、由来追跡の各終端（パッケージ変数、環境変数、ラッパー越しの定数、構造体のフィールド、公開関数の引数）を確かめる
- **既知の限界:**
  - ガードは条件の文字列（`a && b` のように複数の条件が 1 つの `if` に入っているときは、各分岐が全体の文字列を持つ）。短絡評価の個々の項は区別しない
  - 条件が引数に由来するかは、関数の中のオペランドだけで決める。引数がメモリ（フィールド、グローバル）に入ってから読み出される条件は、引数由来と見なさない
  - 由来追跡は、引数を渡す呼び出しの 1 つ 1 つを別々にたどる。複数の呼び出し元の値の組み合わせは出さない
  - 値依存ノードは、検出結果の経路にあるガードだけ。経路にない引数依存の分岐は出さない
- **`guard_limit` の記録:** ガードが上限（4 個）を超えたことは、その関数がサニタイズを含む（`Mods` を持つ流れ、または source のラベルを返す流れがある）ときだけ記録する。
  サニタイズを含まない関数では、ガードがあっても流れの結果が変わらないので、落としても何も失わない。この絞り込みで、x/tools の記録が 206 件 → 1 件になった
- **性能（x/tools、15.6 万行、同じマシンで交互に 2 回ずつ）:** ガード導入前 95 秒、導入後 142 秒、対策後 **107 秒**。ガードの計算（ガード関連の関数の合計は CPU の 1% 未満）ではなく、
  サマリを適用するたびの確保が原因だった。次の対策をした:
  - 呼び先のガードを、要素ごとに具体化（コピー）せず、読むとき（出力の組み立て時）に具体化する
  - 呼び出しの引数に定数がなければ、定数による特殊化の評価（マップの確保を含む）を飛ばす
  - 「(セル, 要素) → 理由」の巨大なマップをやめ、要素の集合（`Set`）が理由へのポインタを直接持つ。重複した追加のたびに 2 つのマップを引いていた
  - 合流点と戻りで、ガードがないときは従来と同じ経路を通す。辺ごとのガードはキャッシュする
  - ガードを切った切り分けの計測（環境変数を使った一時的なもの）で、ガード機能そのものが約 40 秒を占めていることを確かめてから、原因を直した

## ADR-036: 自作の SSA 化と go/ssa との differential test（ステップ 1.11b）

ADR-003（IR は φ なしの CFG ＋ 書き換え可能ローカル変数。SSA 化はコアに一本化）と ADR-026（導入は Phase 1 の終盤）の実装。

- **`internal/ssabuild`:** 言語にも go/ssa にも依存しない SSA 化。入力は「基本ブロックと、変数への `Use` / `Def` / `Zero`（宣言＝ゼロ値の定義）」だけの CFG。
  支配木（Cooper, Harvey, Kennedy の方法）、支配辺境、φ の配置（定義のあるブロックの反復支配辺境）、リネーム（支配木の先行順の走査）、デッドな φ の除去（pruned SSA）。
  起点（入口と、recover 後のブロック）は複数あってよく、仮想の根の下の森として扱う。起点に前任者がないことが前提で、`Validate` が確かめる
- **アダプタ（`gossa.NaiveCFGOf`）:** `ssa.NaiveForm` で作った関数から、go/ssa の lifting（`liftAlloc`）と同じ条件で変数（読み書きのみされる `Alloc`）を選び、CFG に写す。
  `gossa.Options.NaiveForm` で NaiveForm の SSA を作れる
- **検証（二重）:**
  1. **go/ssa との比較（`internal/ssacheck`）:** 同じパッケージを、lifted（go/ssa が φ を置く）と NaiveForm の 2 通りに作り、自作の SSA 化が置く φ（ブロック、変数名、宣言の位置）が、go/ssa が置いた φ（NaiveForm にもともとある `&&` / `||` の φ を引いたもの）と、**関数ごとに完全に一致する**ことを確かめる
  2. **独立なアルゴリズムとの比較:** ssabuild を使わない、反復データフローによる到達定義（`ssabuild.ReachingDefinitions`）と、SSA が各使用に対して与える定義（φ をたどって展開したもの）が一致することを確かめる。ランダムなグラフ 5,000 個でも同じ比較をし、φ の引数の数と、定義が使用を支配することも確かめる
- **結果:** すべて一致した。testdata（148 関数、φ 7 個）、rivus 自身（364 関数、φ 590 個、使用 6,387 箇所）、golang.org/x/tools（5,257 関数、φ 4,650 個、使用 67,836 箇所、約 2 秒）。
  ジェネリクスの実体は、2 回のビルドで同名の関数の本体が違うことがある（ビルドの順序による）ので、ブロック数が違うときだけ比較から外す（x/tools では外れたものは 0〜2 件）
- **発見したこと:** (1) 2 つの起点の両方から到達されるブロックの直接支配者は仮想の根になり、その木もたどらないと使用の定義が求まらなかった（ランダムなグラフのテストで発見）。
  (2) 起点に前任者があると φ が必要になる辺が増える。go/ssa の起点にはないので、前提として明記し、`Validate` で確かめる。
  (3) 2 回ロードした `FileSet` は別なので、位置は `token.Pos` ではなくファイルとオフセットで比べる
- **まだ使っていない:** Phase 1 の解析エンジンは、引き続き lifted の go/ssa の上で動く。自作の SSA 化は、Phase 2 で IR を挟んだときに、エンジンの入力を作る

## ADR-037: Dart 実現性スパイクの結果と、ドッグフーディング（ステップ 1.12）

### Dart スパイク（ADR-011）

詳細は `spike/dart-cfg/README.md`(#38 で削除した。git の履歴にある)。捨てコードで、IR を設計する前に 3 つを確かめた。

- **判断: 実現できる。** `package:analyzer`（14.7、Dart 3.13.6）の解決済み AST から、ブリーフが難所とした構文（`async` / `await`、`await for`、`try` / `catch` / `finally`、ラベル付き `break` / `continue`、パターンの `switch`）の CFG を、正しく組める（約 550 行のビルダーと 20 件のテスト）。
  モノレポの複数パッケージにまたがる呼び出しも、生成コード（`part` ファイル）への呼び出しも、宣言に解決できる。アーキテクチャを変える必要は見つからなかった
- **IR の設計に反映する難所（決定したもの）:**
  1. **例外の辺とブロックの切り方。** 例外の辺をブロック単位で持つと、ブロックに呼び出しが 2 つあるときや、ハンドラが覆わないコード（`try` 本体の最後の呼び出しの後ろに続く `finally` の複製）で誤る。
     スパイクは最初にこれを誤った。**保護された範囲（`try`）の中では、投げうる呼び出しをブロックの終端にして、例外の辺と正常な継続の辺を 1 本ずつ持たせる**（MIR の呼び出しと同じ）。ハンドラが関数内にないときは、例外の辺を引かない（関数の外へ出る例外は、関数内の流れではない）。
     ARCHITECTURE.md 2.4/2.5 の「呼び出し点に例外エッジを付けられる」は、この形に読み替える
  2. **`finally` の表現（レビュー項目 4 の決定）:** **extractor が、出口ごとにブロックを複製する**。IR に `finally` の概念は要らない。テスト関数で 1 つの `finally` が 4 つに複製された。
     複製されたコードは同じソース位置を持つので、**サイトの列挙は、複製を 1 つとして数えなければならない**（そうしないと、サイトの ID（出現順）と指紋（ADR-028）が、出口の数で変わる）。IR の命令は必ずソース位置を持ち、複製であることが分かる必要がある（extractor が印を付けるか、コアが位置で重複を除く）
  3. 式の中の `&&`、`||`、`?:`、`??`、switch 式は、extractor がブロックに展開し、合流点の値を持つローカル変数を作る（ADR-003 の書き換え可能ローカル変数に合う）
  4. パターンは、型テスト、フィールドの読み出し、束縛に展開する（`type_assert` と `field_load` で足りる）。網羅性は推論せず、「どの case にも一致しない」辺を残す
  5. `await` は辺（決定済み）。`yield` と `Stream` の要素は、関数内の流れではなく、モデルか、生産者と `await for` を結ぶコールグラフが要る
  6. クロージャとローカル関数は別のグラフ。コンストラクタ呼び出しは `InstanceCreationExpression` で、`MethodInvocation` ではない
- **注意:** `package:analyzer` は版ごとに API が変わる（14.7 では `ClassDeclaration.name` がなく、引数は封印された `Argument`、`ForPartsWithPattern` がある、要素モデルは v2）。extractor は analyzer の版と SDK の版を固定する
- **調べていないこと:** コールグラフ（`pkg/vm` の type flow analysis）、`dynamic` の受け手の多さ、大きなプロジェクトの解決の時間とメモリ。Phase 4 の次のリスクはここ

## ADR-038: 出力にリビジョンを記録する（`target`）

**背景:** ID（`s1:`＋structural）にはリビジョンが入っていない。リビジョンが変わっても ID が安定することが目的なので、これは正しい。ただし `rivus resolve` はリビジョンが変わった後を前提にするのに、出力が「どのコードの結果か」も、ブックマークが「どのコードから取ったか」も記録していなかった。

**決定:**
1. **ID は変えない。** リビジョンは ID に入れない
2. **出力に `target` を入れる:** `analyze` / `sites` / `query` / `resolve` と、保存したインデックスに `target: {revision, dirty}` を付ける。`revision` は git の HEAD、`dirty` は追跡ファイルに変更があること。git の作業ツリーの外では省略する（エラーにしない）
3. **ブックマークに `revision` を持たせる:** ブックマーク単体の `revision`、または `{"target": ..., "bookmarks": [...]}` の形でまとめて渡す（個別の `revision` が優先）。出力の `target` をそのまま写せばよい
4. **`resolve` の出力:** 各結果に `from_revision` と `revision_change` を付ける。`revision_change` は `same`（同じコミットで、どちらの作業ツリーも変更なし）、`different`、`unknown`（どちらかが不明、または作業ツリーに変更あり）
5. スキーマ版数を上げる: `rivus.result/1`、`rivus.query/1`、`rivus.sites/1`、`rivus.resolve/1`（フィールドの追加のみで、既存のフィールドは変えていない）

**限界:** `dirty` は変更の中身を区別しない（追跡されていないファイルは見ない）。dirty な作業ツリー同士は、同じコミットでも `unknown` になる。古いリビジョンを自分で展開して解く `resolve --from <rev>` は、まだ作らない（ブックマークのスニペットとフィンガープリントで足りるうちは不要）。

### 追記: `dirty` をやめ、git を実行しない（yagihash/rivus #6）

- **決定:** `target` は `{revision}` だけにする。リビジョンは `.git/HEAD`、refs、`packed-refs`（リンクされたワークツリーは `commondir`）を直接読んで求め、git は実行しない。`dirty` は出さない。
- **理由:** 解析対象の `.git/config` は信頼できないコードの一部で、`git status` は `core.fsmonitor`、`filter.*.clean`、`include.path`、サブモジュール、promisor など、設定が指すコマンドを実行する。設定を列挙して打ち消す方式は、経路が増えるたびに抜けた（#6 が再オープンされた）。
- **影響:** `revision_change` の `same` は「同じコミット」の意味になり、作業ツリーに未コミットの変更があるかどうかは見ない。`unknown` は、どちらかの target がないとき。reftable など、読めない形式のリポジトリは `target` なし。

### 追記: `when_arg_type` の数え方を `args` に揃え、`recv: true` を足した（yagihash/rivus #56）

- **決定:** `when_arg_type.arg` は、`args` / `params` / `out` と同じく、**レシーバを除いて**数える。レシーバの型を条件にするときは `when_arg_type: {recv: true, types: [...]}`（`arg` は読まない。`recv: true` と 0 以外の `arg` はエラー）。レシーバのない呼び出しは、レシーバへの条件を満たさない。
- **理由:** 同じ sink の中で数え方が 2 通りあると、メソッドの sink に書いた条件が、1 つずれた引数を見て、黙って効かなくなる（見逃しになる）。組み込みの `when_arg_type` は関数にしか使っていないので、既存のルールは変わらない。
- **限界（既存）:** 型は、引数の局所変数の型と、そこに直接入る `convert` の元の型（最大 4 段）だけを見る。変数に一度入れてから渡した値（`var o Out = Web{}; o.Put(x)`）は、元の型をたどれず、条件が成り立たない。

## ADR-039: Phase 2 の IR を、Phase 1 の実測から具体化する（案）

**状況:** 2.3 の命令セット（26 種）は Phase 1 の前に書いた。Phase 1 で、エンジンが `go/ssa` から使っているものが分かった（ARCHITECTURE 2.7.1）。

**案:**
1. 命令数は 26 のまま。`call` の戻り値をリストにし、`addr_of` に経路を持たせ、クロージャの捕捉値を `param` で受け、引数ごとのソース範囲を持たせる（フィールドの追加だけ）
2. 型は `TypeID` に加えて `TypeClass`（`pointer` / `interface` / `func` / `container` / `struct` / `scalar` / `other`）だけを持つ。構造は持たない
3. テキスト（スニペット、式、本体）は IR に運ばない。IR は `Pos` を持ち、テキストは言語ごとの `ir.Texts`（extractor と同じプロセス、同じ構文木）が位置から切り出す。**当初は「コアが切り出す」としたが、ステップ 2.3 で修正した:** 文の範囲や式の正規化は言語の構文の問題で、`expr@1` / `body@1` のハッシュの元になるため、コアが言語を知らずに切り出すことはできない
4. コールグラフと実装列挙は extractor の責務。結果は `call` の `dynamic(candidates)` と `implementations` レコードで IR に入る
5. Go は同じプロセスの中で IR の型を直接渡す。JSON Lines は `rivus extract` と、他言語の extractor のためだけに使う。両経路の一致をテストする
6. `const` は文字列の中身を省略せず持ち（上限を超えるときは `truncated` を明示）、文字列補間は extractor が `binop` か補間専用の `call` に展開する。テキストの切り出しは表示と指紋のためだけで、判定には使わない（ARCHITECTURE 2.7.2b）
7. 移行中は旧経路（`go/ssa` 直）と新経路を並走させ、`Report` を突き合わせる。一致するまで旧経路を消さない

**未確定（レビューで決めたい）:**
- `TypeClass` の分類が足りるか（たとえば Rust の `Box` / `Rc` / 参照、Dart の `Future` / `Stream` をどの分類にするか）。Phase 3 の入口で Rust を見てから変えうる
- 「テキストは IR に運ばない」ことで、extractor を別プロセスにしたとき、コアが同じソースを読める前提が要る。コンテナ越しなどでは崩れる
- `Select` / `Send` / `Recv` を、命令にせずシンボル付きの `call` にしてよいか（`concurrency` の不確実性の出し方が、シンボルの名前に依存する）

## ADR-040: Phase 2 の結果: 解析エンジンを中立 IR の上に移した（ステップ 2.0〜2.6）

**結果:** Go のコードは、`go/ssa`（NaiveForm）→ extractor（`goir`）→ 中立 IR → SSA グラフ（`irssa`、`sg`）→ エンジン（`taint`）の順に流れる。コアは `go/ssa` を知らない（`go list -deps` で確認）。旧経路は除いた。

**突き合わせ（移行中に両経路を動かして JSON を比べた）:**
- サイト: ID、指紋 4 種、位置、スニペット、ラベル、`literal_only`、並び順が、testdata（212 サイト）、rivus 自身、ghmint、x/tools（243 サイト）で完全に一致
- 解析結果: testdata の全ケース、rivus 自身（36 検出 / 614 不確実性）、ghmint（15 / 176）で完全に一致。x/tools（4 / 10,628）は、不確実性が 1 件だけ違う（generic な関数の中の range-over-func で、位置のない合成された呼び出しの扱い）。許容した

**決めたこと（ADR-039 への追加・修正）:**
1. **テキストは言語ごとの `ir.Texts` が切り出す**（ADR-039 の 3 を修正）。文の範囲と式の正規化は言語の構文の問題で、指紋の元になるため
2. **TypeClass は 9 つ**（`pointer` / `interface` / `func` / `container` / `struct` / `bool` / `string` / `number` / `other`）。`container` は「別の場所の要素を指す値」（スライス・map・チャネル）に絞り、配列は `struct`。`bool` はモデルのない呼び出しの結果を捨てるのに、`string` / `number` は定数のゼロ値の綴りに要る
3. **言語の操作は、シンボル付きの `call` にする**（チャネル、範囲、`select` の送受信）。専用の命令は増やさない（命令は 26 のまま）。これらのシンボルの意味は、エンジンが知っている（将来、モデルに出せるかもしれない）
4. **コールグラフは extractor が作り、`call` の `candidates` に入れる。** Go では、VTA が NaiveForm の上だと粗いので、lifted 版から取って対応づける
5. **`rules.Expand`（実装列挙）は、まだ Go のパッケージを直接引く**（`gossa.Program` が `model.Resolver` を実装）。IR の `implementations` レコードを使う形への移行は、2 つ目の言語を足すときに行う

**性能:** x/tools（15.6 万行）で、107 秒・最大 4.9 GB → 97 秒・最大 2.4 GB。IR に移した直後は最大 6.2 GB に増えたが、`-v` の各段階の生きているヒープ（読み込み後 306 MB、IR 後 453 MB、`sg` 後 761 MB、解析後 461 MB）から、増えた分は解析中の状態だと分かった。関数ごとの解析の状態（セルとキャッシュ）を、結果に要る分（検出・抑制・不確実性）だけ残して手放したら、解析結果は変わらずに 2.4 GB になった。

**残る課題:**
- `taint` の `go/token` と `go/constant`（ガードの定数評価）。言語に依らないので、後回し
- 別プロセスの extractor（Rust、Dart）は、`Texts` と `rules.Expand` の相当を、extractor が提供する形が要る

## ADR-041: Dart の extractor の最初の版（Phase 4）

**結果:** `extractor/dart`（Dart 製）が、`package:analyzer` の解決済み AST から、中立 IR を JSON Lines で出す。コアは `rivus analyze -ir` と `rivus sites -ir` で読む。`testdata` の Go のケースと同じ形の、Dart のサンプル（`extractor/dart/test/sample`）で、注釈に書いた 10 本の流れがすべて見つかり、静かなはずの sink（サニタイズ後、定数、`catch` の中の `toString()`）には届かない（`cmd/rivus/dart_test.go`。`RIVUS_DART` を設定すると走る）。実在の `args` パッケージ（663 関数）では、収束し、10 ミリ秒で終わる。

**決めたこと:**
1. **シンボルは `<ライブラリの URI>#<型>.<メンバー>`**（コンストラクタは `Type.new` / `Type.name`、クロージャは `<外側>$N`）。ルールのフィールドも同じ形
2. **変数は書き換え可能なローカル。** クロージャが捕捉し、かつ宣言の後に代入される変数だけ、セル（`alloc` / `load` / `store`）に置く。それ以外の捕捉は値の捕捉
3. **名前つきの引数は、位置の引数の後ろに、名前の順で並べる。** メソッドとそのオーバーライドで、宣言の順が違っても揃う。呼び出しが渡さなかった引数は nil。エンジンは、渡された引数が呼び先の引数より少ないとき、足りない分を何も運ばない値として扱う（オーバーライドが任意の引数を足す Dart の形に合わせた。Go では起きない）
4. **オブジェクトは `pointer`、コレクションは `container`、`Future` と `Stream` は `other`**（`await` が中の値を取り出す）。`await` は、呼び出しの `await` フラグと、ブロックの切れ目
5. **コールグラフは extractor が作る。** 読んだコードの中のクラス階層（CHA）で、`dynamic` な呼び出しの `candidates` を決める。関数値の呼び出しは、候補なし
6. **`go/chan.*` と `go/range.*` を `chan.*`、`iter.*` に改名した。** 言語に依らない操作の名前にするため。同じ理由で、`binop` の `is` / `is!` を比較として扱う
7. **クロージャを、コピーされた変数の経由でも静的に解く**（`sg`）。ローカルの関数宣言が変数に入るため

**残る課題:** `extractor/dart/README.md` の「Not done」。パターン、switch 式、関数値のコールグラフ、`Stream` と `yield` のモデル、依存パッケージのモデル（`dart:*`、`package:flutter`）。

**追記（Dart のモデル）:** 組み込みのモデルに、`dart-core`（文字列・`Uri`・コレクション・`dart:convert` の伝播と、`Uri.encodeComponent` / `HtmlEscape` のサニタイザ）、`dart-io`（`HttpRequest` を source、`Process.run`・`File.new`・`HttpClient.*Url`・`dart:html` の `innerHtml` を sink、ファイルの読み取りを source）、`dart-packages`（`package:shelf` の `Request` を source、`package:http` と `sqflite` を sink）、`dart-config`、`dart-pure` を足した。分かったこと:
- **SDK の内部ライブラリは、公開されているライブラリの名前にする**（`dart:_http` → `dart:io`）。`HttpRequest` が `dart:_http` に宣言されているため、そのままでは型もシンボルも一致しなかった
- **サニタイザが `adds` で付けるラベルを、sink が拾う。** `accepts` のない sink は、どのラベルでも検出するため、Dart の sink には `accepts: [user_input, file_content]` を付けた（Go では、`adds` は HTML の文脈だけだった）
- サンプルの `server.dart`（shelf と http）を含め、`cmd/rivus/dart_test.go` が 15 本の流れを確かめる

**追記（モデルを育てる道具、プロジェクトのルール）:**
- `rivus models coverage` は、`-ir` でも動く。shelf、http、collection、async、path、args の 6 パッケージ（延べ約 3 万行）で回したところ、SDK（`dart:*`）のモデルのない呼び出しは 3,014 回（323 シンボル）あった。上位を `dart-async`（新設）、`dart-core`、`dart-pure`、`dart-config` に足して、534 回（215 シンボル）に減った。残りは長い裾（`Stream.empty`、`Map.forEach` など）
- **解析するディレクトリの `.rivus/rules/*.yaml` を、フラグなしで読む**（`-no-project-rules` で外せる）。プロジェクトの固有の source・sink と、組み込みにないライブラリのモデルを、コードと一緒に置ける
- setter の関数 ID に `=` を付けた（getter と同じ名前が衝突していた。シンボルは変えない）

**追記（パターンと関数値）:**
- **Dart 3 のパターンを下ろした**（`switch` と `if-case`、分割代入、`switch` 式、レコード）: 値への型テストと定数の比較、部分の読み出し、束縛する変数。`||` のパターンは両方が同じ変数に束縛する。リストの長さやマップのキーの有無の検査は、していない（マッチする側は常にありうる）
- **関数値の呼び出しの呼び先を、コアで解く**（`sg`）。Go の VTA のような呼び出しグラフがない extractor（Dart）のため、関数がコピー・φ・呼び出し側の引数を通って値に届く経路をたどる。メモリ（フィールドやリスト）は通らない。見つけた無名関数は、捕捉した値を受け取らない（何も運ばない値として扱う）。文脈を区別しない（呼び出しグラフの精度）のは、Go の VTA と同じ

**追記（性能。Dart の `archive` パッケージで見つけた遅い関数の対策）:** 実在の Dart パッケージ `archive`（圧縮の復号器。状態機械の大きな関数が多い）で、解析が 10 分たっても終わらなかった。CPU とアロケーションのプロファイルで見つけた無駄を直した。x/tools（Go）も、**95 秒 → 29 秒**になった（検出は同じ 4 件、最大メモリは同じ）。
- `trace` と `guardsOfChain` の結果を、関数の解析の間、覚える（要素が入った理由は変わらないので、経路は変わらない。ガードは、落とされたときだけ無効にする）
- 要約を適用するとき、**既知のものより短くならない流れは、ガードを計算する前に捨てる**（ラベルだけは足す）。ガードの統合（並べ替えと map）が、アロケーションの 3 分の 1 だった
- 展開した要素の重複を、同じ要素ごとに 1 つにする（セルは最初の理由を残すので、結果は変わらない）。セルの読み出し（`collect`）は、並べたパスの範囲を二分探索で引く
- **関数ごとの時間の上限**（`-func-timeout`、既定 30 秒）。超えた関数は `depth_limit` で記録し、以後は解析し直さない。全体の `-timeout` も、関数の途中で効くようにした
- それでも `archive` は 4 分半かかる（10 秒の上限で収束）。要約の要素数と、引数のセルにある要素数の積が大きい形で、**未解決の課題**。`-func-timeout` を縮めると早く終わる代わりに、`depth_limit` が増える

**追記（決定性）:** 同じコードを 2 回解析して、結果が違うことがあった。原因は 3 つあり、直した。
- **go/ssa の構築が並行で、順序が一定でなかった**（`Program.Build` はパッケージを同時に作る）。ジェネリック関数のインスタンスやメソッドのラッパーは、先に着いたパッケージの都合で作られ、IR が毎回変わった。パッケージを、パスの順に 1 つずつ構築する（`buildInOrder`）
- 同じ名前の関数が複数あるとき（ラッパー、ジェネリックとそのインスタンス）の並びを、本体の大きさ、位置、シグネチャで決める
- 並び替えの同点が、マップの順に任された（パッケージ変数、他の関数の値のセル）。固定の順（関数 ID、種類、名前、定義の位置）で決める
- **残る揺れ:** x/tools では、ジェネリックな関数 `fwdBuilder.propagate` の合成された呼び出し 1 件の候補が、実行ごとに違うことがある（検出と、不確実性の件数は同じ）
- 時間の上限（`-func-timeout`、`-timeout`）が効いた関数は、時間に依存するので、結果は実行ごとに違いうる。上限に達した関数は、`depth_limit` で記録される

**追記（セルの要素の上限）:** セルが、1 つの引数についての記号的な要素を、部分ごとに 96 個より多く持つとき、部分を引数全体（パス `""`）にまとめる（真より多く、少なくはない）。引数の部分と、要約が尋ねる部分の積が、作業量を決めていた。x/tools は 28 秒 → **12 秒**（検出は同じ 4 件）、Dart の `archive`（4 分半だった）は **97 秒**で、`depth_limit` なしに収束する。上限の数は、実測で決めた（`maxCellElems`）。

## ADR-042: Rust の extractor の最初の版（Phase 3）

**結果:** `extractor/rust`（Rust 製）が、`rustc_public` で MIR を読み、中立 IR を JSON Lines で出す。ワークスペースを `cargo check` で、`RUSTC_WORKSPACE_WRAPPER` に自分を指して走らせ、rustc は普通にコンパイルし、ドライバが各クレートの IR を書く。`rivus analyze -ir` で読む。サンプル（`extractor/rust/test/sample`）の注釈つきの 12 本の流れ（直接、フィールド、クロージャ、分岐、関数、`&mut` を渡す、`Vec`、`enum`、`format!`、`String::push_str`、`std::env::args` から `Command::new`、`fs::read_to_string`）がすべて見つかり、静かなはずの sink（定数、`len()` を通したもの）には届かない（`cmd/rivus/rust_test.go`）。

**決めたこと:**
1. **nightly を 1 つに固定する**（`nightly-2026-11-15`）。`rustc_public` は不安定で、コンパイラと一緒に動く。更新は意図して行う
2. **MIR は IR にほぼそのまま下りる**（ブロックの CFG、書き換え可能なローカル）。アドレスを取ったローカル（`&x`）だけセル（`alloc` / `load` / `store`）に置く。射影のある場所は `field_load` など。`(*p).f` は 1 回のアクセス
3. **シンボルは関数のパス**（`std::fs::read_to_string`）。トレイトのメソッドは、実装でなくトレイトの名前（`std::ops::Deref::deref`）で、どの実装にも効く。実装のジェネリクスは落とす。**レシーバは最初の引数**（`arg0`）
4. **呼び出しは `Instance::resolve` で解く:** 本体のあるもの → 静的。ないもの → 外部の静的（モデルが決める）。解けないもの（型パラメータ、トレイトオブジェクト）→ `dynamic`（ワークスペースの impl を候補に）。クロージャは `Fn::call` を型で解き、引数のタプルをほどく
5. **巻き戻し（`drop`、`assert`、クリーンアップ）は描かない。** パニックは関数の中の流れではない
6. **位置は行と列**（`rustc_public` はバイトのオフセットをくれない）。ストリームのオフセットは `行 * 100000 + 列`
7. **コアの修正（Rust で見つかった）:** ポインタの `copy` は同じポインタ（別名）として扱う。以前は、コピーを通した書き込みが元に届かなかった（Dart のオブジェクトの別名にも効く）
8. **Mac の SDK:** 最新の SDK（27.0）をリンカが読めず、`tapi error` で、stable の hello world も通らなかった。`SDKROOT` を古い SDK にすると通る（環境の問題。README に書いた）

**残る課題:** `extractor/rust/README.md` の「Not done」。`async`、ジェネリクスの単相化、フレームワーク（actix-web、axum）の入口、引数のテキスト。

**追記（Rust の仕上げ）:**
- **`core::` と `alloc::` は `std::` に正規化する**（`std` が再公開しているので、ルールは `std::` だけでよい）
- **トレイトオブジェクトの呼び出し**（`Instance` の種類が `Virtual`）は `dynamic` にして、ワークスペースの impl を候補にする。型パラメータ越しの呼び出しも同じ
- **`Box`・`Unique`・`NonNull`・`Rc`・`Arc` のフィールドは、ポインタそのもの**として読む（`vec![a, b]` は `Box::new_uninit` に生ポインタ越しに書き込む形に展開され、フィールドを本物のフィールドにすると流れが切れた）
- ジェネリック関数の呼び出しは、型引数つきのインスタンス名ではなく、定義の名前で本体を探す
- サンプルは、トレイトオブジェクト、ループ、イテレータとクロージャ、`?`、`HashMap`、メソッド、`while`、`match` を含み、`cmd/rivus/rust_test.go` が 20 本以上の流れを確かめる。ジェネリックな関数は多相のまま解析するので、その `T::method` の呼び出しは、すべての impl が候補になる（文脈を区別しない）

**追記（crates.io の `rivus`）:** `extractor/rust` を、クレート名 `rivus`（0.1.0）として公開できる形にした。`cargo package` で、パッケージにしたものがそのままビルドできることを確かめた（`rust-toolchain.toml`、`build.rs`、README、LICENSE を含む）。実行ファイルの名前は `rivus-rust` のまま（`rivus` は Go 本体のコマンドなので、衝突させない）。`cargo +nightly-2026-11-15 install rivus` で入る。**公開はしていない。** 名前を押さえるための `rust/`（0.0.0）は、同じ名前なので、公開の前に、どちらかにまとめる必要がある。

**追記（Rust の実コードでの検証）:**
- **`vercel/workflow`**（SWC プラグイン、1.1 万行、クレート 4 つ）: 抽出 39 秒、1,692 関数、解析 78 ミリ秒、`unsupported` 0。source と sink がないので、検出は 0 件で正しい
- **`vercel-labs/agent-browser/cli`**（ブラウザを操る CLI、14.8 万行）: 抽出 2 分 29 秒（release ビルドのドライバ）、IR 702 MB、34,097 関数。解析は 8〜10 秒、最大 6.7 GB（読み込みが大半）。**`std::io::stdin` から `Command::args` へ**、MCP サーバーが受け取った JSON の `restore` が、起動する子プロセスの引数に届く流れを含め、`std::env::args` / `stdin` から `fs` と `reqwest` の sink への流れ 28 件が出た。経路は 8 関数・約 55 歩で、読める
- **見つけたこと:** (1) 抽出器が、ファイルの行を、位置ごとに複製していて、2 乗の時間だった（`Rc` で共有して直した）。(2) **`file_content`（ファイルの中身）を、sink が受け付けると、「ファイルを読んで、その中身をパスにする」流れが 800 件近く出て、使い物にならなかった。** Rust と Dart の sink は `accepts: [user_input]` だけにした（読んだファイルの中身を信頼しない設定は、ルールで足せる）。(3) 実コードで多かったモデルのない呼び出し（`fmt::Formatter` の `debug_*`、serde、tokio、futures）を `rust-misc.yaml` に足して、モデルなしの呼び出しは 18,681 → 6,191 に減った
- **残る課題:** 動的ディスパッチの不確実性が 1.6 万件（`dyn` の多い非同期コード）。IR が大きい（702 MB）ので、JSON の詳細（位置の重複など）を絞る余地がある

**追記（IR を絞る: 位置のファイル名、1 回目）:**
- agent-browser の IR の中身を測ると、関数のレコードが 99.8%、そのうち命令が 73%、命令の位置（`pos`）だけで 44.8% だった。位置の `file`（パス）が、命令ごとに繰り返されていた
- **`Func.file`** を足した。関数が、その位置が入っているファイルを 1 回だけ書き、そのファイルにある位置は `file` を省く。読み込みが戻す（`ir.Func.expand`）ので、コアは変わらない。書く側は `Program` の書き出し（Go）と Rust の extractor が使う。Dart は、まだ省かない（読む側は両方を受け付ける）
- 読み込みは、型・関数・シンボルの文字列を共有する（`internal/ir/compact.go` の `interner`）
- 結果: agent-browser の IR が 702 MB → **523 MB（−25%）**。解析の結果は、件数が同じ（findings 28、uncertainties 22,529）。最大メモリは 7.1 GB → 7.0 GB で、ほとんど減らなかった。メモリの大半は、IR の文字列ではなく、SSA とグラフにある。**メモリを減らすには、IR の形ではなく、読んだあとの表現を絞る必要がある**
- 残る候補: `line`/`col`/`offset` の重複（Rust は `offset` が `line`,`col` から決まる）、直前の命令と同じ位置の省略、`locals` と基本ブロックの終端

**追記（メモリを減らす: 2 回目）:** agent-browser の最大 RSS が **7.0 GB → 2.9 GB**（x/tools は 2.4 GB → 1.2 GB）。時間は同じ（9 秒、13 秒）で、findings と uncertainties の件数も同じ（28 / 22,529、4 / 9,883）。
- **測ったこと:** 生きているデータは、IR が 1.3 GB、グラフが 1.6 GB で、IR とグラフが同時に残っていた。グラフは、IR の命令（`sg.Instr.IR`）と、SSA 形式（`sg.Func.Form`）を持ち続けていたので、IR は解放できなかった
- **やったこと:** (1) `sg.Func.Form` を持たない（誰も読んでいなかった）。(2) `sg.Instr.IR` を、読む 9 個のフィールドだけの `InstrInfo` にして、`sg.Func.IR` は、ブロックと変数を落とした写しにした。(3) `sg.BuildConsuming` が、関数を 1 つ作るごとに、IR の関数を手放す（`Build` は、テストのために、IR を残す）。そのため、サイトの列挙を、グラフの構築の前に動かした。(4) GC の `GOGC` を 50 にした（環境変数があれば、それが優先）。時間はほとんど変わらず、最大 RSS が約 1.7 GB 減った
- **残り:** 読み込み（`ir.Read`）は、全部を読んでからグラフにするので、そのときに IR 全体（1.3 GB、`reflect.growslice` が大半）を持つ。読みながらグラフにすれば、さらに約 1 GB 減らせる。解析中の一時割り当て（`applySummary`、`collectUncached`）は、まだ手を付けていない

**追記（Rust の extractor は、テストを既定で読まない）:** `cargo check` から `--all-targets` を外した。ライブラリと実行ファイルだけがコンパイルされるので、`#[cfg(test)]`、`tests/`、`examples/`、`benches/` は、**ビルドの対象にならない**（名前や場所で見分けるのではなく、確実に入らない）。`rivus-rust --include-tests [dir]` で、`--all-targets` に戻せる。agent-browser では、関数の約 16%（34,097 のうち約 5,600）がテストのモジュールだった。含めたときも、含めないときも、利用者が前提を取り違えないように、README に書いた。Dart（`lib/` だけを読む）と Go（パッケージの読み込みの設定）は、別の話で、今回は変えていない。

## ADR-043: 精度のベンチマーク（go-test-bench）

**状況:** 実コードでの速度・メモリは測っていたが、**検出の精度（見つけた割合、誤検出）は測っていなかった**。
**決定:** `bench/` に、正解のラベル（`truth.json`）と採点（`score.py`）を置く。対象は取り込まない（取ってきて回す）。最初の対象は Contrast Security の `go-test-bench`（OWASP Top 10 の脆弱性を、わざと入れた Go アプリ。標準ライブラリ、gin、chi、httprouter、go-swagger の 5 種）。ラベルは、コードを読んで付けた（元の対象に答えの一覧はない）。判断が分かれたものは `note` に書く。採点は、sink の位置（ファイル、行、カテゴリ）で突き合わせる。
**最初の結果（コミット前の基準）:** 見つけるべき 18 件のうち 11 件（**再現率 0.61**）、報告した 13 件のうち誤検出 2 件（**適合率 0.85**）。不確実性は 585 件。
- **見つけたもの:** コマンド注入 2、SQL インジェクション 1（パラメータ化した安全な枝は報告しなかった）、パス・トラバーサル 4、SSRF 1、オープンリダイレクト 3（net/http の 3 つのフレームワーク）
- **誤検出（2 件）:** `exec.Command("echo", in)`（定数のコマンドに、入力を引数で渡す）。ベンチマークは安全とするが、rivus は「コマンドの引数」を sink としているので、報告する。**方針の問題で、バグではない**。引数注入を報告したくなければ、ルールで外せる
- **見逃し（7 件、すべてモデルの不足）:** (1) gin の `c.Redirect`、`c.File`、`c.String` のモデルがない。(2) `fmt.Fprint(w, data)` で、`ResponseWriter` に書く XSS が見えない（モデルは `ResponseWriter.Write` だけ）

**追記（ベンチマークで見つけたモデルの不足を直した）:**
- **sink の条件 `when_arg_type`** を足した。引数の静的な型が、指定した型のときだけ、sink になる。`fmt.Fprint(w, data)` は、`w` が `net/http.ResponseWriter` のときだけ XSS の sink（`os.Stderr` や `bytes.Buffer` への出力は対象外）。`io.Writer` に変換されてから渡される（`ResponseWriter` → `io.Writer`）ので、変換の元の型までたどる（最大 4 段）。`fmt.Fprint`/`Fprintln`/`Fprintf`、`io.WriteString` に使った
- **gin のモデル** `go-gin.yaml` を足した（source: `Query`、`Param`、`PostForm`、`GetHeader`、`Cookie` など。sink: `Redirect`、`File`、`FileAttachment`、`SaveUploadedFile`、`String`、`Data`）
- **結果:** 再現率 0.61 → **1.00**（18 件中 18 件）、適合率 0.85 → **0.90**（誤検出は、`exec.Command("echo", in)` の 2 件のまま）。不確実性は 585 → 573
- **この数字の読み方（重要）:** モデルを、**同じベンチマークの見逃しを見て足した**ので、再現率 1.00 は、「このベンチマークに合わせた」結果で、一般の精度ではない。ベンチマークが教えてくれたのは、**「どのモデルが足りないか」**であって、「未知のコードでの精度」ではない。後者を測るには、モデルを足すときに見ていない、別の対象（Go の CVE の修正前のコミットなど）が要る。また、ラベルのない sink（`servechi.go:87`、`servestd.go:119`）の報告は、採点していない

**追記（go-test-bench の外で測る: CVE の修正前のコミット）:** モデルを足したときに見ていない対象として、Go の脆弱性データベースの 2 件を、修正の 1 つ前のコミットで解析した（`bench/gin-vue-admin/`、`bench/ech0/`）。
- **gin-vue-admin（GHSA-gv3w-m57p-3wc4、CVE-2024-31457）: 見つかった。** プラグインの `plugName`（`AutoPlug`）が、`CreatePlug` の `os.MkdirAll` と `os.OpenFile` に届く（再現率 2/2）。**ただし、最初は見つからなかった。** 原因は 2 つで、どちらもエンジン側の欠陥だった: (1) gin のモデルが、`c.Query` の結果だけを source にして、`c.ShouldBindJSON(&a)` が構造体を埋めることを表せなかった。`*gin.Context` を source（`*http.Request` と同じ）にして、getter と `Bind*` を propagator にした。(2) **`json.Unmarshal(b, &x)` のように、ポインタを `any` に変換して渡すと、モデルの「引数に書く」流れが、ポインタの指す先に届かなかった**（`make_interface` が別のルートを作るため）。`applyFlows` が、変換の元のポインタの指す先にも書くようにした。`json.Unmarshal`、`Decoder.Decode` を含め、**Go のどのプロジェクトにも効く修正**で、回帰テストを `testdata/go/cases/heap` に足した
- **ech0（GHSA-8mc6-xjpr-h98x、SSRF）: 採点しない。** 管理者が追加した対端の URL をデータベースに保存し、あとで `fetchPeerConnectInfo` が取りに行く、**2 次の流れ**で、rivus はデータベースの中身を持たないので、見えない。`SendRequest` は、プロジェクトの関数なので、プロジェクトのルールで sink にする必要もある。見逃しではなく、見える範囲の限界として記録した
- **新しく分かった問題（未解決）:** ech0 で、**1,273 件**の findings が出た（sink は 12 か所）。`response.Execute(fn)` のような、ハンドラを包む共通の関数が、`fn` を呼ぶ。この関数の中の呼び出しが、`Execute` を呼ぶ**すべての箇所のクロージャ**を候補にするので（文脈を区別しない）、あるハンドラの `c` が、別のハンドラ（OAuth のリダイレクトなど）に届く。**同じ sink に、127 個のハンドラの `c` が届く**形で、件数が 100 倍になる。実在の流れ（`OAuthLogin` が `c.Query` で受けた値を `c.Redirect` に渡す）は 1 つで、残りは経路の誤り。**次の候補: クロージャを返す関数（ファクトリ）の呼び出しごとに、候補を分ける（呼び出しの文脈を 1 段区別する）**
- **gin-vue-admin の他の findings（99 件、25 か所）は、見ていない。** ZIP、アップロード、ブレークポイント再開のコードで、本物らしいが、確かめていない。適合率は、ラベルのある範囲でしか言えない

**追記（有名なプロジェクトで測る: Gogs の CVE 2 件、修正の 1 つ前のコミット）:** `bench/gogs/`。モデルを足す前に測った。
- **CVE-2024-55947（ファイル更新 API のパス・トラバーサル）:** ルールなしの rivus は、**0/4**（見つけるべきハンドラ 4 つのどれも見つからず、検出は無関係な 2 件だけ）。**原因は、Gogs が macaron を自分の `Context` 型で包んでいて、rivus は、ハンドラの引数が何かを知らないこと。**
- **macaron の組み込みモデル**（`go-macaron.yaml`: `*macaron.Context` を source にして、`Query`/`Params`/`GetCookie` などを propagator に）と、**Gogs のプロジェクトのルール**（`bench/gogs/rules.yaml`: 自分の `Context`、`APIContext`、フォームの構造体 37 個を source に）で、**4/4**。ルールは `-rules` で渡す
- **CVE-2026-23633（Git フックの編集のパス・トラバーサル）:** ルールと組み込みモデルで、最初は **0/2**。原因: **フックのファイルを読み書きするのは、依存の `git-module` の中で、依存の中の sink は探さない**（既定の設計）。プロジェクトのルールで `(*git.Repository).Hook` を sink にして **2/2**。あわせて `io/ioutil.ReadFile`/`WriteFile`/`ReadDir`、`os.ReadDir`/`Chmod`/`Truncate`/`Symlink`/`Link` のモデルを足した（`io/ioutil` は、古いコードに多いのに、モデルがなかった）
- **読み方:** どちらも、「rivus 単独では見つからず、フレームワークの組み込みモデルとプロジェクトのルールを足すと見つかる」という結果で、**精度ではなく、ルールの量の問題**だった。有名なプロジェクトほど、独自のラッパー（Context 型）を持つので、**手でルールを書く手間が、実際の導入のコスト**になる。この手間を減らす案: **「型 T を埋め込んでいる型も source にする」条件**（`*macaron.Context` を埋め込む型を、自動で source にする）。Gogs のルールのうち `Context`/`APIContext` の 2 つが不要になる。フォーム構造体の列挙は、別の工夫が要る
- 同じく、**重複の問題**（ech0 と同じ）: Gogs で 818〜834 件のうち、`Context` のメソッド（`HTML`、`Title`、`Redirect` など）が、それぞれ source になって、同じ sink に何度も届く。上の採点は、ハンドラ単位なので影響しない

**追記（同じ流れの重複をまとめる）:** ech0 で 1,273 件、Gogs で 818 件の findings が出ていた原因は、**リクエストの型の引数（`param_type` の source）が、それを受け取るすべての関数で source になる**ことだった。ハンドラも、ハンドラが呼ぶ補助の関数（`Context` のメソッド）も、関数値をすべての候補に解決した先の別のハンドラも、同じ sink に届く同じ流れを、それぞれ 1 件ずつ出していた。
- **決定:** 同じ sink、同じカテゴリ、同じラベル、同じ source のシンボル（同じ型の引数）で、**関数だけが違う findings を、1 件にまとめる**（`mergeParamSources`）。残すのは、**経路がいちばん短い 1 件**（同じ長さなら、関数名の順）で、残りは `other_sources`（最大 5 件、スニペットなし）と `other_sources_count`（全部の数）に書く。呼び出しの結果（`call_result`）の source は、場所が違えば別の流れなので、まとめない
- **ただし、まとめるのは見せ方で、情報は落とさない:** 短い経路を残すので、実在の流れ（ハンドラが自分の引数から sink へ）が残り、別のハンドラから共通の関数を通ってくる経路（誤りの経路）は、`other_sources` に回る
- **結果:** ech0 **1,273 → 22 件**（`OAuthLogin` が代表で、他の 124 件の source は `other_sources_count`）。Gogs **818 → 131 件**。gin-vue-admin **99 → 26 件**。go-test-bench、Gogs、gin-vue-admin の採点は変わらない（18/18、4/4、2/2）。Go、Dart、Rust のテストも通る
- **残る問題:** 根本の原因（クロージャを返す共通の関数が、すべての呼び出し元の候補を混ぜる、文脈の区別のなさ）は、そのまま。誤りの経路は、まとめて隠れただけで、`other_sources` の中にある。**代表の経路が誤りで、他の source のどれかが正しい**場合もありうるので（経路の長さで決めている）、`other_sources_count` が大きいときは、見直す価値がある

**追記（方針: 組み込みは「言語と標準ライブラリ」まで、フレームワークはユーザーのルール）:** ベンチマークで足した gin と macaron のモデルを、組み込み（`internal/model/builtin/`）から外して、`examples/rules/` に移した（コピーして直す見本で、rivus の一部ではない）。理由: 個別の製品に合わせていくと、モデルが際限なく増え、組み込みに入っていないものが「安全」に見えてしまう。プロジェクトに合わせたルール（フレームワーク、独自のラッパー、独自のファイル操作）は、**ユーザー側が `.rivus/rules/*.yaml` か `-rules` で書く**ことを前提にして、**エンジンとしての精度と性能**を磨く。標準ライブラリの穴（`io/ioutil` など）は、組み込みに残す。ベンチマークは、必要なルールを `-rules` で渡す形にした（結果は変わらない: 18/18、2/2、4/4）。
- **まだ決めていない:** 既存の Dart と Rust の組み込み（`dart-packages.yaml`、`rust-web.yaml` など、サードパーティのパッケージ）を、同じ方針で外すか。サンプルのテストが使っているので、外すなら、サンプルのルールに移す必要がある

**追記（依存のソースを読む `-deps`: 不確実性の 7 割は、依存の関数に本体がなかったこと）:** Gogs と ech0 の不確実性（5,500 件、2,500 件）の 7〜8 割は `unmodeled_library_call`（本体もモデルもない呼び出し）で、その大半は標準ライブラリではなく、**サードパーティの依存**（xorm、gorm、macaron、zap、clog など）だった。原因: パッケージの読み込みが、依存を型の情報だけで読んでいて、**依存の関数には本体がなく、解析は、プロジェクト自身のコードだけを見ていた**（呼び出しは、「入ったものは出るかもしれない」という保守的な既定で扱う）。
- **`-deps`（既定はオフ）:** 標準ライブラリ以外の依存を、ソースから読む（`packages.NeedDeps`、`ssautil.AllPackages`）。標準ライブラリは、本体が大きく（`unsafe`、アセンブリ）、よく使う呼び出しはモデルがあるので、読まない。**プロジェクトから届かない依存の関数は、IR から落とす**（`ir.Program.PruneDeps`: 呼び出し、候補、関数の値、実装の一覧をたどる）
- **結果（Gogs / gin-vue-admin / go-test-bench）:** 不確実性 5,593 → 1,494（−73%）、1,989 → 640（−68%）、573 → 296（−48%）。採点は変わらない（4/4、2/2、18/18）。Gogs の findings は 131 → 141（依存を通る流れが増えた。確かめていない）
- **コスト:** Gogs 5.8 秒 / 0.5 GB → 14 秒 / 4.8 GB、gin-vue-admin 7 秒 / 0.5 GB → 46 秒 / 6.3 GB、go-test-bench 5 秒 / 1.5 GB。**メモリの山は、読み込みと IR の作成**（依存の go/ssa をすべて作る）で、解析ではない。なので既定はオフのままにして、コストを下げる作業（**必要な依存の関数だけ作る**、読み込みの後に go/ssa を早く手放す）を、次にやる
- 実際、PruneDeps で、Gogs の解析の時間が 15 秒 → 6 秒、`depth_limit`（時間切れ）の不確実性が 139 → 97 件に減った
- **追記（`-deps` のコスト、1 回目）:** IR への変換を、プロジェクトの関数から**届く関数だけ**にした（`goir.Extract` が呼び出し・候補・関数の値・実装の一覧をたどりながら変換する）。依存の関数をすべて IR にしてから落とすのをやめた。Gogs で 4.67 GB → 3.87 GB、結果は同じ（108 件、不確実性 1,478 件）。残りは、go/ssa の 2 回のビルド（lifted は約 0.6 GB）と、依存の全構文・型情報。次は、これらを早く手放す、または、届く依存のパッケージだけビルドする
- **追記（`-deps` のコスト、2 回目）:** (1) 依存パッケージの構文と型情報を、そのパッケージのビルドが終わったらすぐ手放す（naive と lifted を 1 パッケージずつ交互にビルドする）。(2) IR を作った後に、読み込んだパッケージ全体（`Initial`）を手放す（解析の間、依存の構文・型が残っていた。常駐は 2.9 → 1.8 GB）。結果: gin-vue-admin のピークは 6.4 → 5.5 GB、Gogs は 3.3 GB（4.7 GB から）。結果（findings、不確実性、採点）は同じ。**残りのピークは、go/ssa の 2 つのビルド（naive と lifted）と、依存の読み込みで、これ以上は、設計を変えないと下がらない**（例: 呼び出しグラフだけのために lifted をビルドするのをやめる）。既定オンにするには、まだ重いので、オプトインのまま
- **追記（`-deps` で変わった findings の中身、Gogs、同じルール）:** 105 → 108 件（新しい 6 件、なくなった 3 件）。
  - **なくなった 3 件**（`download.go:36` の xss 2 件、`web.go:319` の path_traversal 1 件）: 以前は、本体のない `git-module` の `Blob.Bytes` などを「入ったものは出るかもしれない」という既定で通っていた。本体を読むと、リポジトリの中身は、リクエストの値からは流れてこない（外部コマンドの出力）。**推測による findings が、正しく消えた**
  - **新しい 6 件**（`repo.go:708/711` の `os.MkdirAll`/`WriteFile`、source は 3 種類）: 経路が 112〜113 歩で、xorm の `Insert`（DB への書き込み）を通り、`PatchPath` が `repo.Owner.Name`（DB から読んだ値）を使うところに着く。**DB を通る 2 次の流れ**で、リクエストの値が、直接パスに入るのではない（Gogs は名前を検証している）。エンジンは、DB の往復を、フィールドの共有で近似している。本物かどうかは確かめられない（推測だが、危険度の低い、長い経路の findings）
  - 次にやること候補: 経路が極端に長い findings の信頼度を下げて示す、整数型を通った値の扱い（`com.ToStr(index)` は整数から文字列を作る）
- **追記（経路の段数と、数値型での停止）:**
  - finding に `path_steps`（表示する最短経路の段数）を足した。`confidence` は、経路に未解決（不確実性）がなければ `no_uncertainty_on_path`、あれば `requires_review`（判定ではなく、分類）。Gogs では 105 件中 2 件だけが前者。実際の順位付けには `path_steps` が使える
  - **数値型（number、bool）の値には、タイントを入れない**（`state.add`）。組み込みのシンクはすべて文字列を受ける（path、sql、command、xss、ssrf、redirect）ので、数値は注入を運べない。`com.ToStr(repo.ID)` のように、構造体全体のタイントが、整数のフィールドを通ってパスに入る誤検出が消える。数量をシンクにするルールのために、`-numeric-taint` で戻せる
  - 結果: Gogs（`-deps`）108 → 76 件。**消えたのは path_traversal だけ**（`repo.ID`、`user.ID` などの整数を通る流れ。さきほどの DB 経由の 6 件も）。採点は変わらない（Gogs 4/4 と 2/2、go-test-bench 18/18、gin-vue-admin 2/2）。消えたものを読んだ範囲（wiki.go など）は、すべて整数の ID を通る経路だった（全 32 件は読んでいない）
- **追記（標準ライブラリのモデルを足す、Gogs `-deps`）:** 不確実性の内訳を数えて、よく出る標準の関数と、標準の interface のメソッド（`fs.FileInfo`、`hash.Hash`、`io.Writer`、`os.File`、`time`、`context`、`database/sql`、`os/exec` など）にモデルを足した。`unmodeled_library_call` 627 → 310、`dynamic_dispatch` 743 → 698、findings は同じ 76 件、採点も同じ。**教訓:** `(*os.File).WriteString` に「引数 → 受け手」の流れを書くと、ファイルの内容のタイントが、ファイルのハンドル全体に付き、`File.Name()` を通ってパスに流れる誤検出が 2 件出た（セルがフィールドを区別しない）ので、書き込みは `pure` にした
- **追記（IR のストリーム読み込みは、やらない）:** 測った。Go は、IR をファイルを通さず、メモリの中で作るので、読み込みの節約は効かない（`-deps` のピークは go/ssa のビルド）。ファイルから読む Dart と Rust の IR は、手元の実在のパッケージで数 MB、Go の Gogs（依存を含まない）でも 25 MB で、`analyze -ir` のピークは 0.24 GB。**節約できるのは、数十 MB の IR で、数十 MB なので、複雑さに見合わない**。IR が桁違いに大きくなる対象（Rust の大きなワークスペース）が現れたら、測り直す
- **追記（`-deps` を既定でオンにする）:** メモリの多いマシンで動かす前提なので、既定をオンにした。軽くしたいときは `-deps=false`（メモリは約 6 分の 1、依存への呼び出しはすべて推測になる）。呼び出しグラフのいらない経路（サイトの列挙だけ）では、依存を読まない

## ADR-044: 組み込みモデルの範囲 — 言語、標準ライブラリ、めちゃくちゃ有名なサードパーティ

- **決定（上の「組み込みは言語と標準ライブラリまで」を、こう改める）:** 全言語（Go、Dart、Rust）で、**めちゃくちゃ有名なサードパーティのライブラリ**も、組み込みでカバーする。範囲は、徐々に広げる。基準を厳密に決めるのは、いまは難しいので、下の目安で、1 つずつ、足すかどうかを決める。プロジェクト固有のもの（自前のラッパー、小さなフレームワーク）は、これまでどおり、ユーザーのルール
- **目安（暫定）:** (1) その言語で、広く使われている（公開されている利用数、ダウンロード数、いいね数で、上位であること）、(2) セキュリティに関わる面（リクエストの入り口、DB、HTTP クライアント、テンプレート、コマンド、ファイル）を持つ、(3) モデルが小さく、実在のプロジェクトか、テストで確かめられる、(4) ルールセットは、ライブラリごとに 1 ファイル（`rivus/<lang>/<name>@N`）で、外しやすくする
- **現状:** Go は gin（`examples/rules` から組み込みに戻した。ベンチは、組み込みのままで、同じ採点）。macaron は、Gogs のように、1 つのプロジェクトで使われる範囲なので、例のまま。Dart は `dart-packages.yaml`、Rust は `rust-web.yaml`（reqwest、sqlx、actix-web、axum のシンクのみ）が、すでにある。前に決めると言っていた、Dart と Rust のサードパーティのモデルを外すかどうかは、**外さない**ことで決まった
- **候補（順不同、あとで測りながら足す）:** Go: echo、chi、gorm、sqlx、pgx、go-redis。Rust: actix-web と axum の、リクエストの入り口、serde。Dart: shelf、dio、http
- **注意:** 組み込みのモデルが増えるほど、誤検出と取りこぼしの責任が、rivus にある。足すときは、ベンチか、テストで、効果を示す。モデルは、`-rules` と同じ書式で、ユーザーが上書きできる
- **追記（ADR-044、gin は外した）:** gin を組み込みに戻したが、「めちゃくちゃ有名」かどうかを調べると、Go の Web フレームワークでは最大（JetBrains 2025 の調査で 48%）だが、半数に満たず、`net/http` のように、ほぼ全員が使うものではない。しかも、入れた理由は、ベンチの採点に必要だったという都合が大きく、基準としては弱いので、`examples/rules` に戻した。**Go の組み込みは、いまは標準ライブラリだけ**。Go に足すなら、「分野ごとの第 1 位」のような、はっきりした基準を決めてから。Dart と Rust の既存のモデルは、そのまま
- **追記（Dart と Rust も、依存を読む）:** Go の `-deps` と同じ考えで、Dart と Rust の extractor も、依存の関数を IR に出し、`dep` の印を付けるようにした。コア（`analyze -ir`）は、`PruneDeps` で、プロジェクトから届くものだけを残す。
  - **Dart:** 読んだライブラリが import している `package:` のライブラリ（SDK は除く）を、再帰的に解決して変換する。`--no-deps` で無効。依存のテキスト（スニペットなど）は出さない
  - **Rust:** `RUSTC_WORKSPACE_WRAPPER` を `RUSTC_WRAPPER` に変えて、すべてのクレートに extractor を通す。ワークスペースのメンバーかどうかは、cargo が付ける `CARGO_PRIMARY_PACKAGE` で見分ける。proc-macro は読まない。`--no-deps` で、メンバーだけ
  - **確かめたこと:** Rust のサンプルに、ワークスペースの外の依存クレートを足した。依存を通る流れ（`wrap`）は追われ、中で値を捨てる関数（`constant`）の後ろは、`--no-deps` では誤検出になるが、読むと正しく消える。呼ばれない関数（`never_called`）は IR から落ちる。Dart は、サンプルの findings が同じ 28 件のまま
  - **注意:** Dart で不確実性の合計が増える（shelf 単体で 154 → 382）のは、読むコードが増えて、依存の中の `dynamic_dispatch` が数えられるため（`unmodeled_library_call` は 36 → 14 に減る）。Go と違い、合計は良い指標ではない。Rust の `dyn Trait` の候補は、そのクレートの実装だけ（依存の実装は入らない）。実在の大きなプロジェクトでの測定は、まだ
- **追記（オプション名）:** Go の `-deps`（既定オン）を、`-no-deps`（無効にする）に改めた。3 言語（Go の `-no-deps`、Dart と Rust extractor の `--no-deps`）で、読むのが既定で、外すオプションの名前が揃った
- **追記（`rivus` コマンドから全言語を呼ぶ）:** `rivus analyze`（`query`、`index`、`resolve` も）が、ディレクトリの言語を、マーカーのファイルで自動で判別する（`go.mod`/`go.work`、`pubspec.yaml`、`Cargo.toml`）。`-lang auto|go,dart,rust` で指定できる。Go はこのプロセスの中で読み、Dart と Rust は extractor（`rivus-dart`、`rivus-rust`）をサブプロセスで呼んで、IR のストリームを読む。**複数の言語があれば、IR を 1 つにつなげて、1 回で解析する**（関数の名前は言語ごとに重ならないので、IR のレベルでつなぐだけでよい。結果のレポートを混ぜる必要がない）。混ぜるときは、Go のテキストもストリームの形（`goir.AddTexts`）にする
  - extractor の場所: `-dart-extractor`/`-rust-extractor`、なければ `RIVUS_DART_EXTRACTOR`/`RIVUS_RUST_EXTRACTOR`、なければ PATH の `rivus-dart`/`rivus-rust`。Dart は `pubspec.yaml` に `executables` を足したので、`dart pub global activate --source path extractor/dart` で `rivus-dart` が入る

  - **限界:** 絞れるのは、引数が呼び出しのすぐ前で作られているときだけ。パラメータを、さらに別の関数に渡して呼ぶと（`get2(b)` → `get(b)`）、内側のガードは、外側の呼び出し元では評価されない（絞らない）。構造体のフィールドに入れた値も、絞らない。これは、点の解析（points-to）で解く問題
  - 再現: `testdata/go/cases/dispatch`（絞れる例が出ない、別の型は出る、型が分からないと出る、埋め込みは出る）。gin-vue-admin で 1 件が消えた（`c.JSON` が `render.JSON` を渡しているのに、`IndentedJSON.Render` 経由で届いていた経路）。go-test-bench、Gogs は同じ
- **追記（gRPC サーバのカバレッジ。生成コードは、解析の前に済ませておく）:** gRPC のハンドラーへの入力は、生成コード（protoc-gen-go-grpc、protoc_plugin、tonic-build）と、サービスの登録（`any` と構造体のフィールドを通る）を経由する。呼び出しグラフは、そこを繋げない（unary の `dec(in)` は関数値の呼び出しで、候補がない）。そのため、**ハンドラーは、生成コードの規約から見つけて、入口として宣言する**。
  - **前提（決定）:** 生成コードは、**解析を実行する前に、生成済みであること**。コードの生成は、rivus の仕事ではなく、利用者（CI）の手順にする。生成コードがないと、ハンドラーは見つからない（findings は出ない。出ないことを、見逃しと区別するため、将来、生成コードがありそうなのに見つからないときは、警告を出す）
  - **ライブラリのモデル（組み込み）:** Go `go-grpc.yaml`（`metadata.FromIncomingContext`、`ValueFromIncomingContext`、`ServerStream.RecvMsg` の out、`grpc.NewClient`/`Dial`/`DialContext` の SSRF）、Rust `rust-grpc.yaml`（tonic の `Request`、`Streaming`、メタデータの経路、`tokio::fs` のシンク）、Dart `dart-grpc.yaml`（`ServiceCall.clientMetadata`、`ClientChannel` の SSRF）。有名な第三者ライブラリを、組み込みにしてよい方針（ADR-044）のとおり
  - **unary と streaming のハンドラー（Go）:** ルールに `marker:` を足した（`kind: param`、`match: implementations`、シンボルなし）。そのメソッド名（glob）を持つインターフェース（`mustEmbedUnimplemented*`）の、ほかのメソッドを、実装に展開して、**メッセージ型（構造体へのポインタ）の引数だけ**を source にする。`context.Context` とストリームは、インターフェースなので外れる。マーカーのないインターフェースは、サービスではない。`require_unimplemented_servers=false` で生成したものは、マーカーがないので、プロジェクトのルールに書く。検索は、ソースから読んだパッケージだけ（生成コードがプロジェクトにあれば動く）
  - **Rust、Dart:** メッセージ型が生成型（Dart）、または `tonic::Request`（Rust）。Rust は `tonic::Request` などの `param_type` で、ハンドラーの引数が source になる（型の ID は、再エクスポートの `tonic::Request`）。Dart は、生成されたリクエストの型を、プロジェクトのルール（`kind: param_type`）に書く。マーカー方式は、まだ Go だけ（Dart の `ServiceBase` のサブクラス、Rust のトレイト実装は、別のリゾルバーが要る）
  - **直した不具合:** Dart の extractor が、単項と二項の `-`（`fixnum` の `Int32`）に同じ ID を付けて、`function ... is defined twice` で依存込みの抽出が失敗していた（protobuf を使う Dart プロジェクト全部が対象）。単項は `unary-` にした
  - テスト: `testdata/go/cases/grpcsrv`（メタデータ、`RecvMsg`、接続先）、`grpcunary`（生成コードの規約からのハンドラー）。テスト用に、同じ import パスのスタブ（`testdata/go/stubs/grpc`）を使う。**テストでは、ハンドラーの型が、インターフェースに変換されていないと、go/ssa がメソッドを作らない**（実際のプロジェクトは、`Register…Server(s, &impl{})` で変換される）

### 追記: 言語の文法の取りこぼしを埋めた（Dart と Rust）

- Dart extractor: extension のメンバーは、レシーバーを最初の引数に取る関数にした（今まではレシーバーが渡らず、`this` が nil で、extension を通る流れが全部切れていた）。`Ext(x).m()`（extension override）、コンストラクタの tear-off（`C.new`）、型引数付きの関数参照、dot shorthand（`.red`、`.make(x)`、`.new(x)`）、型リテラル、コレクションの `for`（古典的な形、識別子、パターン）を落とさず lower する。
- Rust extractor: `ptr::copy_nonoverlapping` の MIR 文（最適化したビルドで出る）を、`load` と `store` にする。インラインアセンブリは、入力を引数、出力を結果にした `std::arch::asm` の呼び出しにする（今までは、ブロックを `unreachable` で終えて、それ以降のコードを落としていた）。モデルは `rust-std.yaml` に足した。
- どれも、取りこぼしていたものを拾うだけの変更で、`unsupported` を出していた箇所は 0 になった。

### 追記: 生成コードが見つからないときの警告（gRPC、Go）

- `marker:` のルールに `marker_call:`（サービスを動かすときに呼ぶ関数。go-grpc は `google.golang.org/grpc.NewServer`）を足した。その関数をプログラム自身のコードが呼んでいて、マーカーを持つインターフェースが 1 つも見つからなければ、`missing_source`（`attributable_to: target`）の不確実性 `generated_code_missing` を出す。クライアントだけのプログラムは、`NewServer` を呼ばないので、警告しない。
- Rust（tonic）は、ハンドラーが `tonic::Request` を引数に取るので、`param_type` ですでに全部見つかる。Dart は、リクエストが生成クラスなので、型の継承関係が IR にないと自動では見つけられない。IR に型の階層を足すのは契約の変更なので、まだやっていない（プロジェクトのルールで `param_type` を書く）。

### 追記: IR に型の階層（`type` レコード）を足した、`extends:` のルール（Dart の gRPC ハンドラー）

- **決定:** IR のストリームに、`{"kind":"type","type":{"id":...,"supers":[...]}}` のレコードを足した。クラスが、直接に、継承・実装・mixin している型の ID を持つ。足すだけの変更で、`schema_version` は変えない（古いストリームは、階層なしとして読める。このレコードを知らない古い読み手は、未知のレコードとして拒む。extractor と本体は同じ版で配る前提）。
- **ルール:** `kind: param` に、`extends: <型 ID>` と `with_param_type: <型 ID>` を足した。「`extends` のサブタイプ（推移的）の、解析対象のコードのメソッドのうち、`with_param_type` の型の引数を取るもの」が入口になり、その型の引数と受け手を除いた引数が入力になる。`exclude_methods`（glob）で、生成コードのラッパーを外す。`marker_call` は、Go の `marker:` と同じ使い方で、その関数を呼んでいるのに 1 つも見つからなければ、`generated_code_missing` を出す。
- **Dart の gRPC:** `Service` のサブクラスで `ServiceCall` を取るメソッドが、ハンドラーになる（`dart-grpc.yaml`）。リクエストの型を、プロジェクトのルールに 1 つずつ書く必要はなくなった。生成コード（`.pb.dart`、`.pbgrpc.dart`）は、解析の前に済んでいる前提（コミット済み、または `protoc` の実行後）。
- **しなかったこと:** Rust の tonic は、ハンドラーが `tonic::Request` を取るので、`param_type` で足りる。Go は、`gossa` が型の情報を持っているので、`marker:` のまま。

### 追記: Dart のベンチマーク（dart-lang/pub）

- `bench/dart-pub`: pub の `extractTarGz` の zip slip（GHSA-q739-79rh-vmvp / CVE-2026-27704）。修正の 1 つ前のコミット（`5e24336e`）で、正解にした 9 サイトを全部見つけた（recall 1.00）。ほかに 8 サイトを報告するが、正解には入れていない（同じ流れが届くヘルパー 5、Windows のシンボリックリンク作成 1、プロジェクトのテスト 2）。修正のコミットでも同じ結果になる（`p.normalize` と `p.isWithin` はサニタイザーとして知られていない）ので、精度ではなく、大きな実コードでの recall の動作確認である。pub のエコシステムには、このほかに、taint の流れとして測れる勧告がなかった（調査: GitHub の勧告 14 件）。

### 追記: Rust の static（グローバル）と、別名を返すモデル（**提案。未決定**）

- **直したこと（extractor）:** Rust の `&STATIC`（static への参照の定数）は、今まで、ただの定数（`const`、nil）として出ていた。それを `addr_of`（`global` に static の名前）にした。どの関数も、同じ static を、同じ 1 つの変数として見る。parseable の finding は、80 件のまま変わらなかった。
- **まだ届かない流れ:** parseable の `src/alerts/target.rs:494`（アラートの宛先の SSRF。リクエストで作った対象が、グローバルの `TARGETS`（`LazyLock<…RwLock<HashMap>>`）に保存され、あとで別の場所が読む）。再現は、`Mutex<String>` を持つ `static` に、一方の関数が `*S.m.lock().unwrap() = source()` と書き、他方が `S.m.lock().unwrap().clone()` を sink に渡す形で、同じ形で切れる。
- **原因:** モデルの `flows: [{from: args, to: result}]` は、「引数の中身の taint を、結果にコピーする」意味で、`Deref::deref`、`Mutex::lock`、`RwLock::write`、`Result::unwrap`、`DerefMut::deref_mut` のように「同じ場所への参照を返す」関数の別名関係を持てない。だから、ガードを通した書き込み（`*guard = x`、`guard.push(x)`）が、元のグローバルの場所に届かない。
- **案:** フローの属性に `alias: true`（結果は、引数が指す場所を指す）を足して、`locs(結果)` を `locs(引数)` と同じにする。Rust の標準ライブラリのモデルのうち、参照を返すものにだけ付ける。ほかのモデルと既存の結果には影響しない（付けたものだけ）。コスト: エンジンの別名の扱いに触れるので、`collect` のキャッシュ（root ごとのバージョン）との整合を確かめる必要がある。
- **要判断:** エンジンの設計に触れるので、まだ入れていない。`std::sync::RwLock::read/write` のモデルが、標準のものにないことも見つかった（tokio のものだけある）。

### 追記: モデルの `alias: true` を入れた（上の提案を実装）

- **決定:** フロー `{from: args, to: result, alias: true}` は、「結果は、その引数と同じ場所を指す」を表す。`locs(結果)` に、引数の `locs` を足す（結果自身の root も残す）。引数が、ローカルのセルのアドレス（ガードを変数に入れて `&mut guard` で渡す形）なら、そのセルに `store` された値の `locs` も足す。taint のコピーは、`alias` が無いフローと同じに行う。
- **付けたもの:** Rust の std の `Deref::deref`、`DerefMut::deref_mut`、`Mutex::lock`、`RwLock::read/write` と `try_*`、`Result::unwrap/expect`、`RefCell::borrow/borrow_mut`、tokio の `Mutex::lock`、`RwLock::read/write`。
- **もう 1 つ直した:** `sg.Program.Global`（パッケージ変数のアドレスの値）に、クラス `pointer` を付けた。付いていなかったので、`p := &G` の `copy` が、ポインタのコピーとして扱われず、グローバルの場所がたどれなかった。
- **確認:** Mutex / RwLock<HashMap> / RwLock<Vec> を持つ `static` に、一方の関数が書き、他方が読む 3 つの流れが通る（`extractor/rust/test/sample/src/global_flows.rs`）。go-test-bench（37 件）、gogs（78 件）、gin-vue-admin（28 件）、Gitea（246 件）、parseable（80 件）は、変更の前後で、finding が完全に同一。
- **検証:** 関数には、結果が同じ場所を指す引数が 1 つしかない。1 つのモデルに alias のフローが 2 つ、1 つのルールセットの中に、同じシンボルで alias を持つモデルが 2 つあると、パースで弾く。複数のルールセットにまたがる重複（組み込みとプロジェクトのルール）は、合成後の `Rules.Validate()`（`AliasArgs()` のエラー）が弾く。読み込み側（`cmd/rivus` とテスト用の `testutil.Rules`）が、これを呼ぶ。弾かないと、後のものが、黙って前のものに取って代わる。
- **まだ届かない:** parseable の `src/alerts/target.rs:494`。tokio の `RwLock` と `.await`（async の状態機械）、`entry().or_default().insert()`、`Option::ok_or`、`call` の動的ディスパッチと、鎖がまだ長い。

### 追記: `unsupported` 命令の記録（CORE-1）と、例外のデータフロー（CORE-2）

- **CORE-1:** コアが `ir.OpUnsupported` を無視していた。`unsupported_construct`（`attributable_to: rivus`）の不確実性を、その場所に出すようにした。`missing_source`（`target`）にしなかったのは、対象のコードが足りないのではなく、rivus が読めなかったものだから。結果のスキーマの版は、kind の追加なので上げていない（読み手は、知らない kind を、そのまま持てばよい）。ARCHITECTURE 2.3 の「`unsupported` は理由の文字列を持ち、記録の起点になる」を、実装が満たした。
- **CORE-2:** `throw` の値が、`catch` のハンドラーに届かなかった（`transfer()` に `OpThrow` と `OpExceptionValue` の case がなく、サマリにも「投げる」出力がなかった）。関数ごとに、投げた値を 1 つの場所（結果の番号 -2）に集めて、`exception_value` がそこから読む。サマリに出力の種類 `throw` を足して、呼び元は、呼び先が投げた値を、自分の同じ場所に受ける。どの `throw` を、どのハンドラーが受けるかは、区別しない（本当より多く、少なくはならない）。投げる値は、interface に入れたときと同じく、オブジェクトなら `/*` の下に置く。

- **まだ手を付けていないもの:** CORE-5（数値・真偽値で汚染を止めたことの記録。検討事項）、クロージャの環境のフィールドごとの区別（RUST-2 の精度）、parseable の SSRF（`src/alerts/target.rs:494`）。

### 追記: 数値・真偽値で追うのを止めたことの記録（CORE-5）

- **決定:** 数値型と bool 型の値には、既定で、taint を載せない（インジェクションの対象にならないため。ルールの sink が、サイズや件数のときは、`-numeric-taint`）。これは、意図して再現率を捨てている箇所なので、**実際の source のラベル**が、数値や bool になって止まった場所を、`numeric_stop`（`attributable_to: rivus`）として、source の種類（シンボルとラベル）ごとに 1 件、記録する（リクエスト型の引数は、受け取る関数ごとに別のサイトなので、サイトごとだと、同じことが関数の数だけ出る。Gogs で 271 件になった）。最初の場所、ラベル、サイトの数、起きた関数の一覧（10 件まで）を持つ。入力が数値に変えられる場所（`strconv.Atoi` のような `pure` のモデルの呼び出し、数値型の値への追加）が、これに当たる。
- **「どの場所でも出る記録」にしなかった理由:** 「数値型で止めた」とだけ出すと、ほぼ全部のプログラムで出て、レビューする人の役に立たない。止まったのが「実際の入力」のときだけにして、数を絞った。
- **限界（出力の説明にも書いた）:** 関数のサマリを通って止まる分（呼び先の中で、引数の記号的なデータが数値になる）は、記録されない。呼び先が、実際のデータを渡されたときにだけ見える。完全な形は、数値を追う版の解析も走らせて、差分の flow を別に出すこと（約 2 倍の時間）で、必要になったら足す。

## ADR-045: 関数値の呼び出しの候補に、sink / source / モデルを当てる（yagihash/rivus #54）

**背景:** サイトも、モデルを当てる呼び出しも、呼び出しの静的なシンボルだけで決まっていた。`hd := http.Head; hd(u)` や `var run = exec.Command` は、関数値の呼び出し（`CalleeValue`）で、シンボルがなく、sink にならなかった（不確実性は `unmodeled_library_call`、「no body and no model」）。

**決めたこと:**
1. **候補は IR の上で、1 か所で決める**（`internal/valuecalls`）。サイトの列挙（`rivus sites` / `analyze`）と、解析のグラフ（`sg`）が、同じ候補を見る。結果は `ir.Callee.ValueCands`（ストリームには出さない）。`sg` の中にあった関数値の解決（`resolveValueCalls`）は、これに置き換えた
   - 値がそのまま関数（またはその場で作ったクロージャ。コピーと、関数型から関数型への `convert`（Rust の関数アイテム → 関数ポインタ）を通る）なら、その 1 つ
   - extractor が候補を持つ（Go の VTA）なら、それ
   - それ以外は、コピー・φ・パラメータ（呼び出し側が渡す引数、3 段まで）を通って届く関数。8 個を超えたら解決しない。メモリ（フィールドやリスト）は通らない
   - 本体のない関数も候補に入れる（ルールが名前で当てる）。シンボルは、IR に関数があればそのシンボル、なければ ID
2. **コピー・φ 由来の候補（その関数の中で分岐して届く関数）には、全部の候補にルールとモデルを当てる。** 候補ごとに別のサイトを作る（シンボルが違うので、ID も別）。候補が複数のときは、不確実性 `dynamic_dispatch` を候補つきで残す。候補が 1 つなら、静的な呼び出しと同じ扱い（シンボルで sink / source / モデル。`hd := http.Head; hd(u)`、`var run = exec.Command`）
3. **パラメータ由来の候補は、呼び出し側ごとに解決する。** `func run(f func(string), x string) { f(x) }` の候補は、すべての呼び出し側が渡す関数の和集合（`run(a, x)` と `run(b, y)` なら a と b）で、呼び出し側を区別しない。そこで、ADR-031 の追記（インターフェース呼び出しの候補を、呼び出し元が渡した型で絞る）の `Guard`（`disp`）と同じ仕組みを、関数値に広げた
   - 候補が、その関数のパラメータ p だけを通って届くとき（`ValueCand.Param = p`）、その候補（本体の要約から出る流れ、本体のない候補の sink に届く流れ）に、「p の関数は、この候補」というガードを付ける
   - 呼び出し側は、p に渡す引数が、**その場で決まる関数**（関数、その場で作ったクロージャ、それらのコピーや φ。`sg.ExactFuncs`）で、その中に候補がないなら、この流れを落とす（`feasible`）。a の sink は、`run(a, x)` から入った流れにだけ付き、`run(b, y)` から入った流れには付かない
   - 安全側: 渡す値が分からない（別の関数の戻り値、フィールド、自分のパラメータ）ときは落とさない。見逃しは増えない
   - ガードは、コードの条件ではないので `conditional_nodes` には出さない（`dispatch` ガードと同じ）
   - 関数の中で選んでいる候補（コピー・φ）は、パラメータ由来と混ざっていても、ガードを付けない（常に届く）。複数のパラメータを通る候補も同じ
4. **不確実性の説明:** 候補が分かっている呼び出しでは、シンボルにその候補を載せる。ルールだけで決まる候補（sink / source）は、不確実性を出さない（静的な呼び出しと同じ）。複数の候補のとき、本体のない候補だけが `unmodeled_library_call` で、候補の ID は `dynamic_dispatch` の `candidates` に載る

**限界:**
- 絞れるのは、パラメータに渡す値が、呼び出しのすぐ前で決まっているときだけ。パラメータをさらに別の関数に渡す（`wrapper(g)` → `run(g, x)`）と、内側のガードは、外側の呼び出し元では評価されない（絞らない）。フィールドに入れた関数も同じ（点の解析の問題）
- パラメータ由来で複数の候補があるとき、ルールの **source とモデル**（結果の汚染、サニタイザ、プロパゲータ）には、ガードを付けない（汚染のラベルは要素の流れではなく、セルに直接入る）。候補のどれかに当たるなら、全部の呼び出し側に当てる（過大側）。sink は、ガードで絞る
- 関数値を、フィールドやリストに入れて後から呼ぶ場合は、解決しない（メモリは通らない）。Go は、VTA が持つ候補を使う
- メソッドを関数として取った値（`(*T).M`）は、最初の引数がレシーバとして扱われる（`ValueCand.Recv`）。メソッド値（`x.M`）は、extractor が作る束縛の関数（本体がある）を通る

**検証:** `testdata/go/cases/funcsink`（コピー、グローバル変数、φ、パラメータの a / b、本体のない sink、呼び出し側が分からないとき）、`extractor/dart` と `extractor/rust` のサンプル（変数に入れた sink、パラメータで渡した sink、sink でない関数を渡す経路で出ない）。結果が変わるのは、関数値の呼び出しが sink / source / モデルのある関数に届くとき、と、パラメータ由来の過検出（b の経路から a の sink）が消えるとき。Gogs（2 件）、Gitea の `./modules/...`（5 件）、Dart / Rust のサンプル（足したケースの 2 件ずつだけが増える）、Dart の serverpod / pub、Rust の parseable の IR は、前後の findings が同じ。Gitea の `modules` では、`unmodeled_library_call` が 8 件減った（関数値の呼び出しが、シンボルを持ち、モデルのある関数に当たった）。Gitea 全体（`./...`）は、このマシンのメモリ（27 GB のピーク）で終わらず、前後の比較ができていない。

## ADR-046: 独自のベンチ（bench/go-curated と bench/go-synth）の位置づけ

**背景:** エンジンの変更のたびに Gitea（約 35 万行）で確かめると、10〜16 分、5〜15 GB かかる。しかも Gitea や gogs には正解がない（ラベルは人が読んで付けたもの）。速さと精度を、別々の小さなベンチで、毎回確かめられるようにする。

**決めたこと:** `bench/` に、言語ごとの 2 種類のベンチを置く（今は Go。Dart と Rust は、同じ形で並べる）。
1. **`bench/go-curated`（精度の回帰。正解つき）。** Gitea、gogs、gin-vue-admin、ech0 の書き方（ハンドラの登録、ミドルウェアの連鎖、ORM、DI、インターフェース越しの呼び出し、クロージャ、関数値、alias 付きのモデル、設定、functional options など）を縮めた、約 20 ファイルのモジュール。「検出すべき流れ」と「検出してはいけない流れ」を、サンプルと同じ注釈（`@source` / `@sink` / `@sink(none)`）で書く。それに、いまのエンジンができないことを、`@miss`（流れがあるのに見つからない）と `@fp`（ないのに出る）で書く。**両側から検査する**（直ったのに印が残っていたら、テストが落ちる）ので、これは棘（ラチェット）になる。検査は `cmd/rivus/bench_curated_test.go`（`checkCurated`。ディレクトリを受け取るので、Dart・Rust のプロジェクトも同じ検査を使う）で、毎回の `go test ./...` に載る（1〜2 秒）。注釈の数: 検出すべき流れ 22 件（うち `@miss` 1 件: functional options で、クロージャの列を回して構造体のフィールドに書く形が見つからない）、出してはいけない 19 件（うち `@fp` 5 件: コンテキストの `Set` / `Get` のキーの違い 3 件、キャッシュのマップのキーの違い 1 件、switch の許可リスト 1 件）。
2. **`bench/go-synth`（速さ・資源のスケール。生成）。** パラメータ（関数数、呼び出しの深さ、SCC の大きさ、インターフェースと実装の数、実装からの呼び戻し、フィールド数、関数値の表、共有ヘルパーに渡すクロージャ、4 段のパスなど）から、Go のコードを作るジェネレータ（`gen`。同じパラメータなら同じバイト列。テストで確かめる）。サイズ S（1.2 秒、126 MB、171 関数）、M（28.5 秒、810 MB、459 関数）、L（約 127 秒、3.2 GB、911 関数）。測定は `measure.py`（時間、最大メモリ、findings と uncertainties の数、finding の ID の集合のハッシュ。`compare` で前後を比べ、`snapshot` / `check` で `expected/` と比べる）。
3. **運用:** エンジンの中核（`internal/sg`、`internal/sites`、`internal/taint`）に触れたら、`go test ./...`（`go-curated` を含む）と、S と M の前後比較（同じ条件で 2〜3 回。結果は同一でなければならない。速度の変更は特に）。Gitea などの実プロジェクトは、節目だけ。絶対時間は、同時に動くほかの処理で揺れる（M は、マシンが空いているときは 28.4〜28.5 秒、ほかの解析が動いていると 45〜60 秒。メモリは、混んでいても、ほぼ同じ）ので、同じ条件で相対で比べる。
4. **精度を下げて速くしない:** ベンチは、速さの指標を、結果が同一であることとセットで出す（`ids_sha256` と `uncertainties_sha256`）。

**Gitea の形（これをパラメータにした）。** 作業ツリーのバイナリ（2026-11-21、他の変更を含む）で、`-timeout 300s`、12 コア、24 GB のマシンで、1 回測った。
- 段ごとの時間とヒープ（`-v`）: ロードと IR 37.5 秒（ヒープ 5.4 GB）、サイト 1.1 秒、グラフ 8.4 秒（3.7 GB）、taint は 300 秒で打ち切り（`converged: false`、5 パス目）。全体 384 秒、**最大 RSS 15.7 GB**。
- グラフの形: 関数 61,655、段 94、一番広い段に 16,828 個の SCC、**最大の SCC は 3,370 関数**（ADR-044 の追記の時点では 907。この作業ツリーには `internal/valuecalls` などの未コミットの変更があり、関数値の呼び出しの候補が増えた影響の可能性がある。**確かめていない**）。要約: 要素 636 万、ステップ 3.4 億（1 関数あたり約 100 要素）、最大の要約は 14,960 要素。再解析 135,490 回。
- 時間の使い方（CPU プロファイル、335 秒、1,649 CPU 秒）: **GC の走査が約 75 %**（`tryDeferToSpanScan` 34 %、`moveInlineMarks` 24 %、`memclrNoHeapPointers` 8 %、`spanInlineMarkBits.init` 6 %。小さなポインタ付きオブジェクトを 3.7 GB 抱えたヒープ）。解析そのものでは、`applySummary` が累積 24 %。ADR-044 の追記（GC の設定では速くならない、`Elem` の整数化が次の一手）と同じ結論で、今のところ変わっていない。
- 割り当て（`alloc_space`、300 秒で 371 GB）: `newWhyFrom` 11 %、`expandParam` 9 %（累積 17 %）、`unionGuards` 6 %、`collectUncached` 6 %、`state.add` 5 %（累積 12 %）、`goir.conv.emit` 4 %（ロード時）。
- `depth_limit` 1,777 件の出どころ: `guard_limit`（条件が 5 つを超える）1,548、関数の予算切れ（`-func-timeout`）227、`path_limit`（アクセスパスを深さ 3 で切る。13,332 関数をまとめた 1 件）1、全体のタイムアウト 1。
- 遅い関数（`-v` の `slow function`）: 通知（Notifier）の実装（インターフェースの多数の実装が、呼び先の要約を引数ごとに展開する）、`db` のトランザクションのクロージャ（`$1`）、出力 10〜30、ルート 10〜300。
- 大きな SCC の作られ方: 共有ヘルパー（`db.WithTx(ctx, func...)` の形）がクロージャを呼ぶ → 使う側の全体が 1 つの SCC、インターフェースの実装が呼び戻す、リング状の相互再帰。ジェネレータは、この 3 つを別々のパラメータ（`-with`、`-back`、`-sccs`）にした。**SCC の大きさの分布（全体）は、出力にない**ので取っていない（最大だけ）。

**ジェネレータの限界:** サイズは、エンジンが終わらせられる範囲に収めた（L でも Gitea の関数数の 1/60）。1 関数あたりの費用が高い形（フィールドの多い構造体、SCC）なので、小さなコードでも、実コードの 10 倍の大きさに相当する時間がかかる。時間の絶対値は Gitea と比べない。見るのは、前後の比。

**追記（Dart と Rust）:** `bench/dart-curated` / `bench/rust-curated`（巨大 SCC の案 2、つまりヘルパーの要約にコールバックの出力を持たせる変更の前の基準）と、`bench/dart-synth` / `bench/rust-synth`（ジェネレータの計画は共通の `bench/synthplan`、測定は `bench/go-synth/measure.py -lang dart|rust`。extractor の実行は 1 回で、測るのは `rivus analyze -ir` だけ）を足した。検査は `TestCuratedDart` / `TestCuratedRust`（`RIVUS_DART` / `RIVUS_RUST` が無ければ skip。`checkCurated` の流用）。注釈に、Rust でクロージャの呼び先が「型が合う全クロージャ」になる過検出を数えるための `@noisy(N)`（その sink に他の source の N 件が届く。数が変わると落ちる）を足した。基準（2026-11-21）: dart-curated は検出 74、`@miss` 32、静か 39、`@fp` 4（捕獲した変数を読み書きするクロージャをヘルパーが呼ぶ形、返されたクロージャ、オブジェクトに持たれたコールバック、エラーと Future が `@miss`）。rust-curated は検出 112、`@miss` 11、静か 42、`@fp` 14、`@noisy` 183 件（17 か所。1 つのヘルパーの 2 つの呼び元が互いの sink に届く）。synth の S は、Dart が 0.13 秒・21 MB・最大 SCC 4、Rust が 0.35 秒・81 MB・最大 SCC 153（M は 1.3 秒・418 MB・SCC 508、L は 13 秒・1.3 GB・SCC 1030）。Dart は、捕獲を持つクロージャの流れが落ちるので、SCC も findings も小さい（案 2 の後に増えるはずで、それが比べる点）。

## ADR-048: `kind: param` の source の汚染を、呼び元へ書き戻さない（C-1）

**背景:** `kind: param`（`param_type`、`marker`、`extends` も同じ）の source は、そのパラメータが指すオブジェクトを汚染する。この汚染は、要約の `OutParam`（そのパラメータ）と `OutGlobal`（グローバルへの書き込み。グローバルのストアにも公開される）として、呼び元へ書き戻っていた。呼び元が同じオブジェクト（`main` が `os.Args[2:]` を、複数の `run*` に渡す形、ルータが同じリクエストを複数のハンドラに渡す形）を別の関数に渡すと、「source = runB のパラメータ、sink = runA の中」という finding が出た。runB が sink に届かなくても、である（`testdata/go/cases/paramshare`、`cmd/rivus/paramshare_test.go` の CORE-A）。

**決めたこと:** **`kind: param` の source は、その関数が受け取った値についての宣言**として読む。**書き戻さないのは、「種」だけ**: `seedParam` が、パラメータのセルに置いた要素（理由が `source: parameter ...` で、`from` を持たないもの）を、要約の `OutParam`（そのパラメータ自身）に出さない（`summarize`、`why.isParamSeed`）。関数が命令で行った書き込み（store、チャネルへの送信、呼び先の要約が書いたもの）で着いた要素は、命令の理由と `from` を持つので、**外さない**。つまり、
- `shared = r.Path`、`save(r.Path)`（ヘルパーがグローバルに書く）、`queue <- r.Path`（グローバルのチャネル）、`c.App.Last = c.Query`（同じパラメータの先の共有の状態）は、`OutGlobal` / `OutParam` として出て、グローバルのストアにも公開される。別の関数がそれを読めば、finding になる（`testdata/go/cases/paramshare/gwrite`、`gwritehelper`、`gqueue`、`ctxstate`）。
- 種そのものは、呼び元に書き戻らない。`runB(r)` の `r` が、呼び元で、`runB` の source として汚染されることはない。

最初の実装（a540f30）は、`OutGlobal` を、種かどうかを見ずに外し、`compute` のグローバルへの公開も止めていた。そのため、関数自身がグローバルに書いた値まで消え（上の 4 つの形が、変更前は 1 件、a540f30 では 0 件）、gogs の `InstallPost` からの流れ 11 件と、gin-vue-admin の 3 件が消えた。この規則に直した。`os.Args` の再現（`global`）は、`OutGlobal` を外さなくても直る（`runB` の `OutParam` の種を呼び元に書き戻さないだけで、呼び元の実引数（グローバル）に当たらない）。

**この退行(a540f30)は、実コードのベンチ(gogs、gin-vue-admin)の finding の差分で見つかった。コアの精度の変更は、その手順(前後のバイナリ、`measure.py compare`、実コードの finding の差分を 1 件ずつ分類、見逃しが 1 件でもあれば push しない、走らせられなければ push しない)を `bench/README.md` の「Changing the accuracy of the core: the procedure」に置いた。**

止めるのは**これだけ**: 種以外の要素（ほかのパラメータへの書き込み、同じパラメータの別の場所への書き込み、戻り値、例外、通常の source の書き戻し、グローバルへの書き込み）は、そのまま。パラメータ自身から、その関数の中で sink に届く流れ（`direct`）は残る。複数の source が同じオブジェクトを受け取って、それぞれが sink に届く形（`repro`）は、finding の数が変わらない。

**理由（実測）:**
- rivus 自身（dogfood のルール）: finding 88 → 39（`OutGlobal` を外さない規則でも同じ 39 件。書き戻しの偽の組み合わせは、`OutParam` の種で起きていた）（8 つの入口 × 11 の sink の組み合わせのうち、source の関数に呼び出しで届かない、偽の組み合わせ 43 件（キーで数えて）が消えた。残りの 39 件は、すべて経路に source の関数を含む）。経路に source の関数が出ない finding は 77 → 0。`runExtract` は、規則の sink のどれにも届かない（11 件がすべて偽だった）。再解析は、種だけを外す規則では 10,151 回（変更前 10,155。`OutGlobal` まで外した a540f30 の 8,168 は、グローバルへの書き込みを止めた効果で、書き込みの消失を含んでいた）。
- `other_sources` の誤った痕跡: `param_type` で、同じリクエスト型を受け取るハンドラ 2 つ + 共通の補助関数に sink（`ptype`）で、届かないハンドラが、届くハンドラの finding の `other_sources` に入っていた。finding ごとに判定する LLM は `other_sources_count` を見て「ほかの入口からも届く」と読むので、誤った痕跡だった。直った（`other_sources_count` が 0）。
- go-synth S / M、Dart・Rust のサンプル、Dart の pub と serverpod、3 つの curated（`@miss` / `@fp` / `@noisy` の数）は、finding が同一。Rust の parseable は 94 件のまま、1 件の source が入れ替わった（書き戻しの偽の経由先だった `get_user_from_request` から、実際に tenant を読む `get_tenant_id_from_request` へ）。
- Gitea（`./...`、実験のとき。再実行していない）: 収束（7 パス）、**最大の SCC は 3370 のまま**（書き戻しは SCC を作っていない。案 2 の領分）。finding は 37 → 41（off にだけある 8 件はすべて、経路が source の関数から始まらない。on にだけある 12 件のうち 5 件は、経路が source の関数から始まる）。書き戻しは、収束の問題としては部分的で、精度の問題が主。

**失うもの:** `func runB(r *Req){ _ = r }` が source で、呼び元が `runB(r); os.Create(r.Path)` と書くとき、「runB が受け取った値が、呼び元の sink に届く」流れは、**出なくなる**（`testdata/go/cases/paramshare/lost`、`TestParamSourceNotWrittenBackIsLost`。既知の見逃し。痕跡もない）。source が受け取った値は、その関数の中で使われたときだけ追う。呼び元の側でも追いたいなら、呼び元を入口にする（`main` や、リクエストを作る関数に、`kind: param` や `call_result` の source を宣言する）。

**限界:**
- 別のオブジェクト経由の書き戻し（source のパラメータが指す値が、ほかのパラメータやグローバルが指すオブジェクトに入れられて、それが書き戻る）は、止めていない。止めるのは、param source のサイトが起点の要素が、そのパラメータ自身（`OutParam`）と `OutGlobal` に出る場合だけ。
- Gitea の on / off の差は、実験の保存された出力の読みで、呼び出しの到達の確認ではない。
- 巨大 SCC（Gitea の 3370）は、この変更では小さくならない。

## ADR-049: グローバルを通る流れの経路に、書いた側の段を入れる（CORE-B / CORE-C）

**背景:** W がグローバルに source の値を書き、R がそれを読んで sink へ渡すとき、finding の経路は `R: load > R: sink` だけで、W のステップ（`W: source > W: store`）が無かった。グローバルのストアのセルは、要素だけを持ち（`set[e] = nil`、「ここで作ったものではない」の印）、**書いた関数の段を持たなかった**ため。読む側の状態は、グローバルのセルを、ストアから写して始まり、その要素の理由（`why`）は無いので、経路の再構成（`trace`）が、読む側から始まった。結果、finding の `source.func` が経路に出ない finding（`offSourcePath`、BENCH-2）が出た。

**決めたこと:** グローバルのストアに、要素ごとに、**最初に書いた関数の段**（`globalStore.writers`: セル、パス、要素 → `rope`）を持たせる。
1. `compute`: 関数が、ストアにまだ無い要素をグローバルに書くとき、その関数の中の経路（`trace`）を、`globalWrite.steps` に持つ（ストアにすでにある要素は、トレースしない。費用は、新しい要素だけ）。
2. `commitGlobals`: 要素が新しく入ったとき（最初の書き手）、その段を `noteWriter` で記録する。レベルの終わりに、決まった順で一度だけ書くので、決定的。
3. `traceUncached`: 理由が無い要素が、グローバルのルートのセルにあるとき（ストアから読んだ要素）、その段を、経路の先頭に足す。**セルの値（`why`）は変えない**（`set[e] == nil` の意味、「ストアから読んだ」の判定、`addLog` の版は、そのまま。状態の間で共有される `why` を、書き換える危険も避けた）。

**finding の集合は変わらない**（経路の証拠だけが変わる）。前後で確かめた（C-1 の修正 c44bfdd の上）: go-curated、go-synth S / M、paramshare、dogfood、Dart / Rust のサンプルと curated で、finding の追加も削除も 0。経路が変わったのは、paramshare の 4 件（`globalw`、`gwrite`、`gwritehelper`、`gqueue`）、Dart のサンプル 1 件、Rust のサンプル 4 件（`static` を通る流れ）で、**経路に source の関数が無かった finding は、paramshare 4、Dart サンプル 1、Rust サンプル 3 → すべて 0**（`offSourcePath` は全部の場所で 0。`TestParamSourceSharedObject` の `off` の天井も 0 にした）。

**CORE-C（短い経路を残す選び方）:** `collect` は、同じ finding の経路が複数あるとき、短いものを残す（同じ長さなら関数 ID の順）。グローバルを通る経路は、書き手の段が付いて長くなったので、選び方を変えなくても、source の関数が経路に出ない finding は 0 になった。選び方（「source の関数が経路に出るものを優先」）は、足していない。

**限界:** 書き手の段は、**最初に書いた関数**のもの。同じ要素を、別の関数も書くとき（別の経路）は、最初の 1 つだけ。経路の根拠として十分だが、「どの書き手も」ではない（書き手の全部は、`global_var` の不確実性の候補に残る）。

## ADR-050: 関数値の呼び出しを、rivus の上限で解決しなかったときは、「知らない」と言わない（CORE-D）

**背景:** `internal/valuecalls` の `resolve` は、関数値の呼び出しの候補を、コピー・φ・パラメータ（呼び元が渡す引数、`maxDepth` = 3 段まで）を通って求める。見つかった関数が 8 個（`most`）を超えると、候補を 1 つも付けずに戻る。何も見つからなかったときと同じ形だったので、解析は不確実性 `unresolved_callee`（「the called function is not known」、`attributable_to: mixed`）を出した。**関数は分かっているのに、rivus が自分の上限で捨てた**ので、これは誤った痕跡だった（読む人は、コードの側の問題（動的で分からない）と読む）。呼び元を 3 段より上に辿らないで 0 件のときも同じ。

**決めたこと:**
1. `ir.Callee` に、IR のストリームに出ない `ValueLimit` と `ValueFound` を足した（`ValueCands` と同じ扱い）。`resolve` が、候補を付けないときに理由を残す。
   - `candidate_limit`: 見つかった関数が 8 個を超えた（`ValueFound` = 見つけた数）。
   - `caller_depth_limit`: 何も見つからず、呼び元を辿る歩みが `maxDepth` で切られた（`resolver.cut`）。切られていなければ（本当に分からない）、従来どおり `unresolved_callee`。
2. 解析（`calls.go` の呼び出しの処理、`provenance.go` の来歴）は、`ValueLimit` があるとき、`unresolved_callee` ではなく、**`depth_limit`**（`attributable_to: rivus`）を出す。文面は理由で始まる（`candidate_limit: the function value may be any of N functions, more than the 8 that rivus keeps; ...`、`caller_depth_limit: ...`）。場所は、呼び出しの位置と関数。kind を `depth_limit` にした理由: 「上限を超えたので、解析が切った」という意味に合うのは `depth_limit`（`guard_limit`、`path_limit` と同じ系列）で、`unresolved_callee` は「関数がどれか分からない」ことだから。
3. **上限そのもの（8、3 段）は変えない**。候補を持たない呼び出しの扱い（候補なしで、モデルもなし）は同じ。finding の集合は変わらない（不確実性の kind と文面と attributable_to だけが変わる）。

**限界:** 3 段で切れたが、途中で 1〜8 個が見つかったとき（候補が足りないかもしれない）は、まだ、何も言わない。呼び元の 3 段より先にある関数は、候補に入らない（`resolver.cut` は、この場合も立つが、痕跡は 0 件のときだけに付けた）。8 と 3 を外すのは、案 2（巨大 SCC の整理）の ADR で。

**検証:** `bench/dart-curated/lib/limits.dart`（9 個の関数を渡すヘルパー、5 段のヘルパーに渡すクロージャ。`TestCuratedDart` が、`depth_limit` の `candidate_limit` と `caller_depth_limit` を要求する）。Go は、VTA が候補を持つので、この経路を通らない。curated の `@miss(silent)` の数え方（source と sink の関数にある不確実性だけを痕跡とする）では、ヘルパーの中の痕跡は数えない。そのため、足した 2 つの見逃しは `@miss(silent)` のまま（Dart 27/34 → 29/36）。数えているのは、足したケースの 2 件だけで、既存の見逃しの痕跡は変わらない。

## ADR-051: `Reachable` が、捕まえる値のあるクロージャの関数も辿る（CORE-E）

**背景:** `sg.Program.Reachable`（finding の `reachability` と、graph の `path --from-entry` の元）は、呼び出し、候補、関数値（`KFunc`）を辿る。`make_closure` のうち、**捕まえる値のないもの**（`Args` が空）は `KFunc`（関数値）になり、呼び出しの引数に出るので辿られる。**捕まえる値のあるものは `KFunc` にならず、辿られなかった**（graph の `refs` は、捕まえる値のある `make_closure` を、`closure` 種別の参照にしていた。x/tools で 454 関数、約 8 %）。実際には届く関数が、finding の `reachability` で `not_from_entry` になりうる、誤った痕跡だった。

**決めたこと:** `Reachable` は、届いた関数の中の `make_closure` 命令の、クロージャの関数（`IR.Func`）も辿る。捕まえる値の有無に依らない（graph の `refs` の `closure` 種別と、`KFunc` の参照を合わせると、同じ集合になる）。`TestReferencesCoverReachable` の例外（`Lit`: 「graph は届くが、`Reachable` は届かない」）をなくした。**graph の辿る集合と `Reachable` は、呼び出し + 参照で一致する**ことを、そのテストが固定する（graph が届く関数は、すべて `Reachable` にある。逆も同じ）。

**finding の集合は変わらない**（`Reachable` は finding を消さない）。変わるのは、`reachability` の値（`not_from_entry` → `from_entry`）と、代表の経路の選び方（「到達可能」が、選び方の最初の基準）。

**検証:** go-curated、go-synth S / M、paramshare、dogfood、Dart / Rust のサンプルと curated で、finding の追加・削除 0、`reachability` の変化 0、経路の変化 0（これらのプログラムでは、`Reachable` が足りなかったことで `not_from_entry` になった finding がない）。x/tools などの実プロジェクトのベンチは、このマシンのスワップが逼迫していた（94 %）ので、**走らせていない**。454 関数が対象の x/tools での件数（`not_from_entry` → `from_entry`、代表の経路が変わる件数）は、未確認。

## ADR-052: `not_from_entry` に、起点に入っていないものの説明を添える（つなぎ）

**背景:** finding の `reachability: not_from_entry` は、「経路のどれかの関数が、起点（`main`、`init`、Dart の `main`、Rust の `entry_fn`。なければ exported）から届かない」と言う。**フレームワークが呼ぶメソッド（依存の型のメソッドの上書き）や、フレームワークに登録するハンドラは、起点に入っていない**（依存を読まない Dart と、依存を読まないときの Go / Rust では、フレームワークの側が読まれず、そこから呼ぶ辺もない）。読む人が「死んだコード」と読むと、誤り。C-4（`overrides` の辺）が入るまでのつなぎ。

**決めたこと:** `not_from_entry` の finding に、説明の文字列 `reachability_note`（`taint.NotFromEntryNote`）を付ける（新しいフィールド。`from_entry` と、起点が分からないとき〔`reachability` が無いとき〕には付けない）。内容: 「`not_from_entry` はコードが死んでいるという意味ではない。フレームワークが呼ぶ関数（依存の型のメソッドの上書き、フレームワークに登録したハンドラ）は、ここでは起点に入っておらず、読まなかった依存のコードは、それを呼ばない」。全言語で同じ文字列（言語ごとに分けると、依存を読んだかどうかの情報が、解析の側に要る。C-4 で、辺として入れるときに、説明ごとなくす）。finding の集合も、`reachability` の値も変わらない。出力の形は、フィールドの追加だけ。
