# 設計: 取得のコンテナのネットワークを絞る

> **状態: 案**(ADR-093 で、隔離はコンテナからサンドボックスになった。この案のコンテナ(専用ネットワークとプロキシのコンテナ)の部分は、サンドボックスに読み替える: 取得のサンドボックスから、ローカルのプロキシのポートだけに出られる形で、プロキシは rivus の Go のプロセスの中。後回しの課題として残っている)(確認: 2026-11-22、9c26a39)
> - 未実装: `docker/fetch-proxy` も、専用ネットワークの作成(`network create`)も、コードに無い。記述は今のコードと合っている。
> - 隔離の今の姿の正本は [rust-isolation.md](rust-isolation.md)。この文書は、残る抜けの計画。

設計時の状態の記述(今の状態は上の枠が正本): **設計のみ(実装は別の機会)**。背景は ADR-064(の訂正)と `docs/rust-isolation.md`。

## 問題

取得の段階(`cargo fetch --locked`)のコンテナは、Docker の既定の bridge に付くので、**どこへでも出られる**: インターネット、利用者の LAN、`host.docker.internal`(Docker Desktop)、クラウドのメタデータのアドレス、同じホストの別のコンテナ。取得で動くのは cargo だけで、対象の設定は読ませない(済み)。`Cargo.lock` の取得元は、既定では crates.io だけ(済み。git の依存は、ホストを問わず、`-allow-fetch-host` で許したものだけ)。残るのは次の 2 つで、どちらも**多層の防御**で塞ぐ。

1. 取得元の検査をすり抜けるもの: 公開の名前が、内側のアドレスに解決される(DNS)。**リダイレクト**: 許したホストが、30x で内側のアドレスや別のホストへ飛ばす(git の smart HTTP の最初の要求、sparse レジストリ。確かめた: `TestIsolationFetchFollowsWhatTheAllowedRepositorySays`)。**サブモジュール**: cargo は git の依存を取るとき、サブモジュールも再帰的に取る。その URL は依存のリポジトリの `.gitmodules` にあり、`Cargo.lock` には出ないので、取得元の検査では見えない(同じテストで、要求が出ることを確かめた)。
2. cargo や、cargo が使うライブラリ(libgit2、libcurl)の、未知の脆弱性。コードが動いたときの被害を、コンテナの外の内側へ広げない。

## 案: 専用ネットワーク + 取得元だけを許すプロキシ

```
取得のコンテナ ──(internal な専用ネットワーク。出口なし)── プロキシのコンテナ ──(外へ)── 許した取得元だけ
```

- **取得のコンテナ**: `docker network create --internal` で作った、使い捨てのネットワークにだけ付ける(外への経路がない。ホスト、LAN、メタデータ、`host.docker.internal` に届かない。Docker の内蔵 DNS は、外の名前を引かない)。環境変数(`CARGO_HTTP_PROXY`、`HTTPS_PROXY`。rivus が渡す。対象の設定は読ませない)で、プロキシを指す。
- **プロキシのコンテナ**: 同じ internal のネットワークと、外へ出られるネットワークの両方に付く。小さな Go の CONNECT プロキシ(このリポジトリの、信頼できるソース。イメージは取得のイメージと別に、`docker/fetch-proxy`)。
  - 許す宛先: `Cargo.lock` の取得元のホスト(検査を通ったもの。`-allow-fetch-host` を含む)と crates.io(`index.crates.io`、`static.crates.io`、`crates.io`)だけ。ポートは 443(と、`-allow-fetch-host` で許した http なら、そのポート)。
  - **名前の解決は、プロキシがする**。解決したアドレスが、ループバック、プライベート、リンクローカル(169.254.0.0/16 と fe80::/10)、ユニークローカル(fc00::/7)、CGNAT(100.64.0.0/10)、マルチキャスト、未指定なら**拒否**。接続は、検査したアドレスに対して張る(検査と接続の間で、解決し直さない: DNS rebinding を避ける)。IPv6 も同じ。
  - リダイレクトの先と、サブモジュールの URL への要求も、すべてプロキシを通るので、同じ検査(許可リストと、解決したアドレス)を通る(CONNECT のたびに)。許したホストのリポジトリが `.gitmodules` で別のホストを指しても、許可リストになければ拒否される。
  - (http の redirect を、プロキシの側で追わせる作りにはしない: 追うのは cargo/libgit2 で、要求ごとに、プロキシを通る。)
  - 接続の数、時間、転送量に上限。ログ(拒否した宛先)は、取得の段階の報告に出す。
- **後始末**: 段階が終わったら、取得のコンテナ、プロキシ、ネットワークを消す(`--rm`、`network rm`。時間切れや中断でも、`rivus=rust-extractor` のラベルで消す)。

## 防御の層

| 層 | 何を止めるか |
|---|---|
| 設定を読ませない(済み) | 対象の設定による、コードの実行と、要求の宛先の変更 |
| `Cargo.lock` の取得元の検査(済み) | crates.io 以外の取得元(許したホストだけ通る) |
| internal なネットワーク | 取得のコンテナから、プロキシ以外の、すべて |
| プロキシの宛先の許可リスト | 許していない外の宛先 |
| プロキシの、解決したアドレスの検査 | 公開の名前が内側へ解決される、rebinding、redirect |
| 既存の制限(非 root、権限なし、読み取り専用、上限) | コードが動いたときの、コンテナの中の被害 |

## テスト(実装のときに書く)

コンテナの中(取得のコンテナ)から、次が**すべて失敗**する: メタデータのアドレス、`host.docker.internal`、ホストの LAN のアドレス、同じホストの別のコンテナ(bridge 上のもの)、許可リストにない公開の名前、内側のアドレスに解決される名前(ローカルの偽の DNS)、許可した名前でも、内側のアドレスへの redirect。**成功する**: 許可した取得元(テストでは、ブリッジ上の偽のレジストリ)。偽のレジストリへの要求が、プロキシを通ったことを、プロキシのログで確かめる。

## 決めること(実装の前に)

- Docker Desktop(macOS、Windows)、Linux の Docker Engine、rootless、Podman で、internal なネットワークとプロキシの経路が同じに動くか(まず Docker Desktop と Engine)。
- プロキシを Go で書く(CONNECT だけで足りるか。libgit2 が、https の git の smart HTTP をプロキシ越しに使えるか。cargo の `http.proxy` の効き方)。
- コスト: コンテナ 2 つとネットワーク 1 つの起動(1 秒前後の見込み。測る)。取得の大きさでの、プロキシの通す速さ。
- `-allow-fetch-host` で、http の取得元を許したときの扱い(許したホストだけの、プロキシの許可リストに入れる)。
- Go と Dart(`go mod download`、`pub get`)を同じ作りに載せるときの、プロキシの共有(許可リストの作り方だけが、言語ごと)。
