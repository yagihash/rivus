# Rust: `async` の中の `Fn::call` の候補を絞る(調べたこと)

> **状態: 実装済み**(確認: 2026-11-22、9c26a39)
> - 実装済み: `async` の状態機械のレシーバをたどって `Fn::call` の候補を絞る(ADR-085)。
> - 未実装: 呼び出し元ごとのガードの案。
> - 関連: 同じ `Fn::call` の絞り込みが [DESIGN-generics-dispatch.md](DESIGN-generics-dispatch.md)、[DESIGN-capture.md](DESIGN-capture.md) の XTALK の節、ADR-079、081、085 に分かれている。統合して歴史的な文書にまとめる案がある。

ADR-079(案 A)は、zoo と rust-curated で `@fp` / `@noisy` を減らしたが、parseable では、複数の候補を持つ `Fn::call` 3 か所のうち 1 か所しか絞れなかった。主因の呼び出し(15 候補)のレシーバは、**`async` の状態機械(coroutine)のフィールド**で、出所をたどれず、全候補のままだった。ここは、その原因を、独立した小さい例(`bench/rust-curated/src/narrow_async.rs`)で再現して調べた記録。

## IR での `async` の形(確かめた)

(`rivus-rust` の出力。`async` ブロックは `{async block@file:l:c}` という型、`async fn` は、本体の `{closure#0}` という名前の関数 + coroutine。)

* **`async move { g(&s) }`**: 呼び出し元の関数で、coroutine を `alloc`(型 `{async block@…}`)し、キャプチャした値を `field_store`(フィールド名は `"0"`、`"1"`…: **番号だけ**)で入れる。`Poll` する側(executor)はコードにないので、抽出器は、coroutine を作った所で、本体を呼ぶ(`Pin { pointer: &mut coroutine }` を作って、`call 本体(pin, 0)`。lower.rs の `AggregateKind::Coroutine`)。
* **本体**(`関数名::{closure#N}`): パラメータは `pin`(と resume の引数)。coroutine は `pin.pointer`(`field_load`)から取り、キャプチャした値は、その `addr_of`(path = フィールド `"0"`)で読む。中の `g(&s)` は `Fn::call`(レシーバ = そのアドレス)。
* **`async fn`** は、同じ形: 関数自身は、パラメータを coroutine の `"0"`、`"1"` に入れて、本体を呼ぶ。`.await` と `Future` は、本体の `Poll` の分岐(`Ready.0` の `field_store`)になり、呼び出しの先ではない(`spawn` の中の `tokio::spawn` は、本体のない関数。引数の future は、すでに本体が実行されている)。

## たどれなかった原因(根拠つき。2 つ)

1. **coroutine のフィールドの名前**: `narrow.go` は、環境のフィールドを、**クロージャの名前を持つフィールド**(`{closure#…}.0`)で数える(同じ名前への store を全部集める。ADR-079)。クロージャの環境のフィールドは、抽出器が `{closure@…}.0` のように、そのクロージャの名前を付けるが、**coroutine のフィールドは `"0"` だけ**。`isClosureField` が偽で、`unknown_origin`。付け方を揃えると、(同じ番号の)別の coroutine のフィールドと混ざらない利点もある。
2. **ジェネリックなヘルパーの中の `f.clone()`**: `async` ブロックに入れる前に、ヘルパーの中で `let g = f.clone()` と複製する形(`for_each_live_node` の `api_fn.clone()`)。`F: Fn + Clone` の型パラメータに対する `clone` は、抽出器が実装を決められず、**dynamic な `Clone::clone`**(候補は意味のない 1 個)。`narrow.go` がたどる `clone` は、**クロージャの型の静的な `clone` だけ**で、dynamic のものはたどらず(`unknown_origin`)。さらに、`f` がパラメータなので、`&f` のセル(`alloc` + `store`)があり、その別名が `clone` に渡ると、「セルの別名が、レシーバ以外に渡った(= 外に出た)」として、セルもたどれなかった。これは `async` に限らない(同期のジェネリックなヘルパーでも、同じ)。

(`async` の本体が別の関数に出る点は、原因ではない。本体は、coroutine を作った関数から呼ばれ、フィールドの store(作った関数の中)も、IR にある。)

## 再現(`narrow_async.rs`)

型は形ごとに別(`Qa`〜`Qd`)。(1) `async move` ブロックがクロージャの clone をキャプチャ、(2) `async fn` がクロージャを引数に取る、(3) `for_each_live_node` の形(`async fn`、ループの中で clone して `async move`)、(4) 出所が 2 つで片方がたどれない(キャプチャのあるクロージャを返す関数)。各形に、呼び出し元が 2 つ(本物と別)と、渡されないが型の合うクロージャ(`*_extra`)がある。**直す前**: `*_extra`(渡されていないクロージャ)の sink に、本物の source が届く(候補が 3 個のまま)。

## 直したこと(ADR-085)

1. **抽出器(足すだけ。フィールドの名前だけが変わる)**: coroutine のキャプチャした値(upvar)のフィールドを、`本体の名前.番号`(`curated::narrow_async::run_block::{closure#0}.0`。クロージャの環境と同じ作り)にする(`lower.rs` の `coroutine_field`。`Aggregate` の store と、本体の読み出しの両方)。**await をまたいで保存する局所変数**(状態 = `Downcast` の先のフィールド)も、状態つきの名前(`本体の名前.s状態.番号`)にする: `async fn` の本体は、パラメータを、最初の await の前に、状態のフィールドへ移し、そこから呼ぶ(`for_each_live_node` の形)。rustc は、保存する局所変数ごとに (状態, 番号) を 1 つだけ決めるので、その局所変数への読み書きは、全部同じ名前になる。確かめた: parseable の IR で、読まれるフィールド名 7,595 のすべてに store がある(名前の食い違いが無い)。
2. **`narrow.go`**: dynamic な `std::clone::Clone::clone`(引数 1 つ)を、`copy` と同じく、引数の出所をたどる。`&f` のセルの別名が、この `clone` のレシーバになるのは、読むだけなので許す(外に出たとはしない)。静的な `{closure} as Clone>::clone` も同じ。「全部たどれたときだけ絞る」は変えない: たどれない部分が 1 つでもあれば、全候補のまま(`narrow_async.rs` の (4))。

3. **`narrow.go`(深さ)**: 環境のフィールドの 1 段は、呼び出し元を 1 つ上る段ではないので、深さ(`maxDepth`)に数えない(async の入れ子は、フィールドを 3〜4 段通る)。
4. **`narrow.go`(共有参照)**: 環境のフィールドのアドレスが、**共有参照 `&F` の型の局所変数**にだけコピーされるとき(`&mut` や、型のない複製が 1 つも無いとき)、そのアドレスが環境や呼び出しに渡っても、フィールドへの書き込みの経路とは数えない(関数値の中身が、共有参照越しに別の関数になることは無い)。`async fn` の本体が、状態のフィールドの `&api_fn` を、`map` のクロージャの環境に入れる形(`for_each_live_node`)で必要。

**効果(`narrow_async.rs`)**: どの呼び出し元も渡さないクロージャ(`*_extra`)の sink は、検出されなくなる(候補 3 → 2)。(4)(片方が、関数の結果でたどれない)は、全候補のまま、`@sink(async-unknown)` が見つかる。await を挟む形(5)も同じ。

**parseable(隔離のモード: コンテナで抽出した IR)**: 複数の候補を持つ `Fn::call` 3 か所の、絞れた数は 1 → 3(候補の合計 375 → 13: 10 → 1、15 → 8、350 → 4)。主因の `for_each_live_node`(15 候補。8 呼び出し元)は、15 → 8。findings は 164 → 137。(source, sink) の組は、`other_sources` の上限(5)を外して数えると 723 → 544 で、**新しい組 0、消えた組 179**(上限のある表示で見た「追加 17、削除 32」は、同じ sink の source の並びが変わった見かけ)。消えた 179 組の分類(件数と種類): (a) 98 組は、**ほかの呼び出し元のクロージャの中の sink**(転送先の HTTP 呼び出し)に届く流れ。呼ばれ得ない候補(7 個)を通る: 候補の削除の結果。(b) 81 組は、そのヘルパーが呼ぶ関数の先のストレージの読み書きに届く流れ。呼び出し元のクロージャがキャプチャしたリクエストは、その関数の引数に関係しないが、coroutine の状態のフィールドが全 coroutine で同じ名前(`"3"`、`"4"`)だったため、混ざっていた(名前を分けた結果)。手で経路を 4 種確かめた(ヘルパーのコードは、その値を使わない)。リクエスト由来の値が、別の引数として届く流れは、前後とも残る(件数と種類だけ。第三者の未公表の件の場所は書かない)。`bench/parseable` の真値の採点は前後で同じ(TP 2、FN 1)。

## 直していないこと: 呼び出し元ごとの絞り込み(ガード)が、coroutine を通らない

候補を絞っても、**呼び出し元が 2 つあれば、候補は 2 つ残る**(どちらの呼び出し元のクロージャも、レシーバになりうる)。同期のヘルパーでは、ADR-045 のガード(「パラメータ p に渡された関数が、この候補」)で、呼び出し元が渡したほうの候補を通る流れだけが残る。ガードは、**呼び出しのある関数のパラメータ**に付くが、`async` では、呼び出しのある関数は本体で、そのパラメータは `Pin<&mut coroutine>` の 1 つだけ。クロージャは、ヘルパー(`run_block` / `for_each_item`)のパラメータ → coroutine のフィールド(`clone` を通る)→ 本体のレシーバ、と流れる。そのため `CandParam`(= `t.cur`)が付かず、`block_other` の sink に `block_real` の source が届く(`narrow_async.rs` の `@fp` 3 つ)。ADR-045 の限界「中継のガードが外の呼び出し元に伝わらない」と同じ型。

**案(まだ入れない。大きい)**: 本体の呼び出し(`call 本体(pin, 0)`、ヘルパーの中)で、本体の要約から出る流れに付いたガードを、ヘルパーのパラメータのガードに**言い換える**。条件: 本体の呼び出しの引数 `pin` の `pointer` → coroutine の `"N"` のフィールドが、ヘルパーのパラメータ(`copy` / `clone` だけを通る)とわかるとき。言い換えたガード(「ヘルパーのパラメータ f は、この候補」)は、ヘルパーの呼び出し元で評価される(今のガードと同じ)。必要なもの: (1) ガードに、パラメータからの経路(フィールド、間接参照)を持たせる(`Guard.Params` + `Path`)、(2) `instantiate` が、引数の出所(`sg.Value` の `Copy` / `Clone` / `field_store`)を、呼び出し元の関数の中でパラメータまでたどる(今の `ExactClosures` の逆向き)、(3) ガードの鍵(`computeKey`)と上限(`maxGuards`)の見直し、(4) 同期の中継(`outer(g)` → `inner(g)`、`narrow.rs` の (3))も同じ仕組みで直る。**Go の関数値のガードにも効く仕組み**なので、結果が変わる範囲は Go 全体(Gitea を含む)に及ぶ。アーキテクチャの助言者の判断を待つ。
